## 0. 结论

1. 拆页的本质不是"把一屏切成两屏"，而是把**阶段 9（人工审核）**和**阶段 10–11（组装 / 预览 / 导出）**
   分开。两者的**完成判据不同**：前者是"队列归零"这个数字，后者是"预检通过 + 你通读过"。
   放在一屏，就只能互相让步（v3 为兼顾一屏把页图压到 340–422px，而 PDF 正是判字的依据）。
2. **审校页的唯一目的**：把机器标出的每一处可疑判完，并让"还剩多少"成为一个能对齐的数字。
3. **预览导出页的唯一目的**：以读者的方式通读组装后的成品，改掉机器没标出来的错，
   并确认这就是要交的东西。
4. 分界线不是"按钮"，是"**谁负责发现**"：机器指得出的疑点归审校页，机器指不出的错误归预览导出页。
   能力可以重叠（改一行文本两页都能），**责任不能重叠**。
5. **成品不落库。** `Segment` 是导出时推导的（`export/segments.py:135`），`segment_id` 就是首块
   `block_id`（`:138`），随合并 / 拆分而变。所以不给预览导出页建"成品版本表"；预览导出页的每一处修改
   都必须落回 `block.text` / `block_line.text`，否则就是"预览 ≠ 导出"。
6. 拆页顺带消掉一笔老账：审校页不再渲染全书正文，就不再需要"行必须在流内"这个筛子。
   现在 `next-lines` 只认流内，实测 `567 条未审汉字 = 流内 562 + 流外 5`
   （`api/routes_review.py:390` 注），而顶栏分母是同一个队列口径。拆页后两者都回到
   `queue_items()` 的同一来源（汉字级分母 899），那 5 条不再被静默漏掉。
7. **预览并入导出（2026-11-05 用户定）。** 第 6 步「预览导出」是唯一面对成品的地方：组装、通读、改、
   提交、预检、导出都在它上面；审校页只判差异，`renderReading` 整块退役。两页的编辑都改为
   「草稿 → 确认提交」，**有未提交时导出置灰**，保证"导出的版本 = 预览的版本"。
8. **手改算判完，记 `edited`。** 新增第三个 ack 值（`kept` / `adopted` / `edited`）：
   不留 `null`（否则下一轮又回队列）、不冒充 `adopted`（否则"采纳候选"的质量数字虚高）。
   `diff_ack` 列没有 CHECK，**不需要迁移**；要改的是 `DIFF_ACKS`、事件 action、统计卡、界面标签。

## 1. 两页的唯一目的与边界

### 1.1 一句话

| 页 | 一句话目的 | 完成判据（可数 / 不可数） |
|---|---|---|
| 审校页 | 只判差异：判完机器标出的每一处可疑 | `queue_items().totals.unacked == 0`（可数） |
| 预览导出页 | 只面对成品：组装、通读、改、导出 | 预检通过 + 导出成功（**不设"预览完成"**，D-090；见 §8） |

### 1.2 边界原则

**审校页负责"机器指得出的疑点"，预览导出页负责"机器指不出、人读出来的问题"与成品本身。**

这条原则的好处是它直接可检：任何一条机器信号（marks / 乱码 / 页码 / 版面建议），
在审校页必须有入口、在预览导出页不得成为"唯一的家"；反之，任何"两路一致但都错"的行，
预览导出页是唯一的家（队列在结构上不可能覆盖它，实测"一致但都错"约 2.5%，
见 `docs/ocr-evaluation.md` §8–9）。

### 1.3 错误类别 → 归属（这一张表就是边界）

| 错误 / 事项 | 机器有信号吗 | 归属 | 依据 |
|---|---|---|---|
| 两引擎实质差异（汉字 / 标点） | 有（`marks`） | **审校** | 中文书队列 1623 = 899 + 724（PM 审计 2026-10-28，产品口径） |
| 标点按模式批量裁决 | 有（`punct_groups`） | **审校** | 724 条 / 73 组；批量是判，不是自动 |
| 乱码行 / 漏行 | 有（`review/garbled-lines`） | **审校** | 需要页图与重认入口 |
| 页面类型 / 版心 / 页码 | 有（阶段 1–4 的确认与建议） | **审校** | 是审校的前置，不是成品问题 |
| 两路一致但都错 | **无** | **预览导出** | 约 2.5%；队列永远看不到 |
| 段落该并不并 / 不该并 | 无（规则"看起来对"） | **预览导出** | 只有成品能看出来 |
| 标点统一误伤 | 无（规则层） | **预览导出** | 归一是**改数据**，不是导出时替换（见 3.4） |
| 断词还原错 | 无 | **预览导出** | 只有成品里那一个词是错的 |
| 组装、导出范围 / 页眉脚注开关 / 预检 / 写盘 | — | **预览导出** | 阶段 10–11 |

### 1.4 唯一的能力重叠：改一行文本

两页都能改一行文本。这不是"边界没想清"，因为**对象、写路径、裁决语义三者完全相同**：

| | 审校页改一行 | 预览导出页改一行 |
|---|---|---|
| 从哪进来 | 队列里的一处差异 | 成品里读到的一个错 |
| 提交方式 | 先草稿、确认后写库（§2.5） | **同左**（2026-11-05 用户改：所有编辑必须确认提交） |
| 写什么 | `block.text`（以整块为底替换该行）+ `block_line.text` 同步 | 同左 |
| 未决差异 | 写 `diff_ack='edited'` + `diff_ack_text=新行文本` | **同左** |
| 事件 / 撤销 | 同一 batch、同一条事件、一次可退 | 同左 |
| 队列 | 该条 -1 | 该行有未决差异时 -1，否则不变 |

只有一处不同：**你当时在看什么**。所以重叠不产生第二份真相。
两页现在都走"草稿 → 确认 → 写库"同一套动作（预览导出页不再即写即存，理由见 §3.5）。

两条配套规则，缺一不可：

- **编辑一行 = 确认这一行。** 有 `aux_text` 的行，手改后必须写 `diff_ack='edited'` +
  `diff_ack_text=新行文本`。不写的话 `blocks.py:767` 会让旧 ack 立刻失效
  （`(diff_ack_text or "") == current` 不成立），这条又回到队列；
  而如果这行原本没有差异，改完 `text` 与 `aux_text` 反而**凭空多出一条新差异**——
  "改对了却多一条要判"，是荒谬的。
- **`edited` 是第三个 ack 值，不拿 `adopted` 冒充。** 手打的文本不是"第二引擎的候选"，
  记成 `adopted` 会让"采纳候选 N 条"这个质量数字虚高（用户可能据此决定要不要继续跑第二引擎）。
  `diff_ack` 列没有 CHECK（migration 0018），加值**不需要迁移**；但 `DIFF_ACKS`
  （`editing.py:732`）、事件 action、统计卡（`review_status.py:459-480`）、界面标签都要跟着改。
  导出 manifest 不加键——`diff_kept` / `diff_adopted` 的语义保持"保留 / 采纳候选"。
- **批量采纳候选只在审校页。** 预览导出页不提供"换成第二路"（那需要 A/B 对照，属于审校页）。

### 1.5 拆页后审校页能退掉的东西

- 不再渲染全书正文 → v3 里的 394 / 662 页**平铺页码树**换成差异目录（章 → 页 → 条），
  跟随滚动、marks 窗口补位、`branch:none` 竞态全部不再需要。
- "成稿 / 待审红字"这个显示开关退役——成稿只在预览导出页。
- **`renderReading` 一族整块退役，不是留着不用**（用户 2026-11-05 定）：审校页不再渲染整本书流，
  连"以后可能用得上"的入口也不留；留着它，下一个改的人就会以为还能用。
- 页图可以变大：右栏只显示一处差异 ±6 字（v3 F2），不再需要给 614px 正文让位。

## 2. 数据流

### 2.1 只有一层可写：源

```
源（可写，落库）  block / block_line / page        ← 两页的所有修改都写这里
成品（只读，派生） segments + line_spans / 导出文本  ← 每次从源现算，带缓存
```

`block.text` 是当前采用文本（导出、差异现算、两页显示都用它）；
`block_line.text` 是逐行记录，**可能落后于 `block.text`**（采纳候选只改 `block.text`，
`editing.py:833`；`jev_priority.py:155-159` 的注释记录过这个坑）。
所以任何"改一行"都必须**以 `block.text` 切行、只替换该行**，不能拿 `block_line.text` 拼块。

### 2.2 数据 → 谁写 → 谁读 → 什么时候失效

| 数据 | 谁写 | 谁读 | 什么时候失效 |
|---|---|---|---|
| `block.text` | 识别落库 / 采纳候选 / 两页手改 / 合并拆分 / 字符规范化 / 撤销 | 差异现算、组装、导出、两页 | 不缓存；任何写都让 db 内容签名变，下游缓存全体失效 |
| `block_line.text` | 识别落库 / 手改同步（`sync_line_text`）/ 字符规范化 `lines_plan` | 审计与事件、逐行证据 | 同上；**不等于**成品文本 |
| `block_line.aux_text` | 第二引擎运行 | 差异现算、标点分组、Jev 选行 | 重识别新行 → `NULL`；重跑 aux → 覆盖 |
| `block_line.diff_ack` / `diff_ack_text` | 两页的裁决 | 队列、marks、收尾面板 | 当前行文本 ≠ `diff_ack_text` 时**自动失效**（`blocks.py:767`） |
| `block_line.jev_score` | Jev 后台任务 | 审校页排序 | 只能手动清（`jev_priority.py:455`）；**文本变了不会自动清**（见 5.3） |
| `block_line.bbox` | 识别 / 版面 | 审校页 PDF 高亮、版心判定 | 重识别换行 |
| `block.block_type` / `include` / `deleted_at` / `continues_to_next` | 识别 / 两页结构编辑 | 队列过滤、组装、导出、PDF | 立即可见 |
| `page.margin_box` / `include` / `page_type` | 版面 / 确认 | 队列 `inside()`、组装过滤 | 重拟合 |
| `marks`（派生） | 现算（`block_divergence`，`blocks.py:741`） | **只有审校页** | 无缓存；`block.text` / `aux_text` 任一变即变 |
| `segments` + `line_spans`（派生，缓存） | `preview_segments_json` | **只有预览导出页**与导出（审校页 2026-11-05 起不读） | db 签名 + options 签名（`export/project.py:699`）；`PREVIEW_CACHE_VERSION` |
| 收尾面板（派生，缓存） | `review_status` | 审校页进度 | `FINISH_CACHE_VERSION` + db 签名 |
| 导出选项 | 预览导出页 UI | segments 生成、预检、导出 | options 签名（`_options_signature`） |

### 2.3 两页各读什么、写什么

| | 审校页 | 预览导出页 |
|---|---|---|
| 读 | `marks`（未决差异）、`queue_items`（分母）、`jev_score`（排序）、页图；**不读 `segments`**（2026-11-05 定，成品只归预览导出页） | `segments` + `line_spans`（成品）、`review/tree` 的 `chapters`（书籍目录）、页图、块行框 |
| 写 | `diff_ack`（保留 `kept` / 采纳 `adopted` / 自己改 `edited`）、批量标点裁决、乱码与漏行处理、页面 / 版面确认 | 行文本（有 `aux_text` 时同时写 `edited`）、块合并 / 拆分、块类型 / 排除、导出选项、导出 |
| 草稿 | 未提交的改动（localStorage，按项目） | 同左；**有未提交时导出置灰** |
| 不写 | 成品（没有这个东西） | 候选采纳（那是审校页） |

### 2.4 三个数字必须同源

1. 审校页顶栏的"待判 N" = `queue_items().totals.unacked` = 左栏目录逐页相加；
2. 审校页"这一批判了几条"来自事件表，`diff_ack_*` 事件条数必须等于队列的减少量；
3. 预览与导出必须是**同一份 segments**（同 options，`segment_id` / `text` 逐条一致）。

第 1 条现在有个已知分叉：`next-lines` 会把流外的 5 条丢掉（`routes_review.py:452-461`），
而顶栏分母不丢。拆页后审校页不再依赖流内，直接以 `queue_items` 为准，分叉消失。

### 2.5 左目录口径（与 Designer 的"当前页"不冲突）

| 区域 | 数据 | 作用域 | 说明 |
|---|---|---|---|
| 左：差异目录 | `/review/next-lines` | **全书**（带 Jev 开关） | 汉字级逐条（899），游标在全书里走 |
| 左：标点入口 | `queue_items` 的 `punct_*` | 全书汇总 | 724 条 / 73 组；点进批量面板，不逐条占目录行 |
| 中 + 右 | `/review/marks?page=N` | **当前页** | 该页全部差异（含标点、含已判），当前条高亮 |

- **游标全局、面板当前页**：目录负责"下一处在哪"，中右负责"这一页还有几条、长什么样"，所以
  Designer 的"当前页"和"全局队列"是同一件事的两面。
- 顶栏 `total` 必须由 `queue_items()` 给（1623），**不能把左目录的行数加起来**——标点 724 不占行。
- `next-lines` 现在有两个筛子要拆：只收汉字级（标点另设轨道，保留）、只收流内（拆页后没有理由，
  5 条要补回来）。补回时给它们一个页面顺序位置即可，不需要流内坐标。
- **审校页不读 `segments`**：中右的上下文用 `block.text` 的行（±1 / ±2），不需要成品流。
  这样 `/export/preview` 只剩预览导出页一个消费者（Architect 的 R14 棘轮）。

## 3. 两种编辑语义（这次的核心）

### 3.1 审校页的"判"

单位 = 一处差异（mark）。三种结果：保留原文 / 采纳候选 / 两路都不对（自己改）。
写库一次一个 batch，文本与裁决同批（`editing.py:833-940`），撤销一次全退。
**判完这条，队列少一条**，这是审校页唯一的产出。

### 3.2 预览导出页的"改"

单位 = **一行**（不是段、不是整章）。所见是组装后的段落，落笔落在行上：

- 点击成品里的任意字符 → 用 `line_spans` 反查 `(block_id, line_index)`；
- 编辑该行的文本 → 以 `block.text` 为底替换该行 → 写回；
- 成品由同一份 `preview_segments_json` 立刻重算，你看回自己的修改。

**不回写"段"**，因为段不存在持久层。

对用户就一句话说清：

> 「成品里点哪个字，改的就是它所在的那一行。要并段 / 拆段，用行首的「并入上一段」和光标处的
> 「拆成两段」。合并段落时自动补的空格、英文断词还原时去掉的连字符是规则拼出来的、
> 不属于任何一行，这里只读。」

配套：不支持整段重打；跨行编辑一律走结构操作。

**编辑必须先提交（2026-11-05 用户定）**：点进一行改字 → 行首进「待提交」状态（不写库、不进导出）；
`Enter` 或点「提交这一处」才写库。可以攒多处一起提交，一个 batch、一次撤销全退（§3.5）。

### 3.3 为什么不能给预览导出页建"成品版本表"

1. **没有稳定主键。** `segment_id = 首块 block_id`（`segments.py:138`），块一合并 / 一拆分就变；
   段的边界还会随导出选项（页类型、脚注、图注）变化。拿它当覆盖表的主键，迟早对不上。
2. **一存就分叉。** 导出走 `_prepare`（源），预览走覆盖表，两套文本必然有一天不一致，
   而且不一致的时候没人能说清哪份是对的——这正是"界面数字与点下去发生的事对不上"的同族问题。
3. **合并 / 拆分已经能做。** 段边界错了，改的是块（`merge-prev` / `split`，`routes_review.py:879/908`），
   不是改一段字符串。改字符串只会让"下一版组装"再算一遍、把你的修改冲掉。

### 3.4 预览导出页的编辑词汇表（全部是现成接口）

| 用户想做的 | 落在哪 | 现成接口 |
|---|---|---|
| 改一行文本 | `block.text` + `block_line.text` | 行：`POST /review/submit-drafts`（`new_line_text` + `ack='edited'`）。**不要用 `PATCH /blocks/{id}` 改字**——它只写块文本、不写行记录 |
| 这两段该合并 | 块结构 | `POST /blocks/{id}/merge-prev` |
| 这里该拆段 | 块结构 | `POST /blocks/{id}/split` |
| 这段不是正文（书眉 / 图注 / 脚注） | `block_type` / `include` | `PATCH /blocks/{id}` |
| 这页不该导出 | `page.include` | 页面确认接口 |
| 标点统一误伤 | **改数据**（字符规范化，整批可撤销） | `orthography` 的 `lines_plan` |

`submit-drafts` 是唯一同时写块文本与行记录的地方（`routes_review.py:656-666` 调 `sync_line_text`）。
拿 `PATCH /blocks` 改字会留下"块文本变了、行记录没变"的旧文本，而 Jev 选行与行证据读的正是行记录
（`jev_priority.py:155-159` 记录过这个坑）。

最后一行要写死：说明书 9.3 **禁止**在导出时做"统一全角半角 / 全局替换引号"
（`export/cleanup.py` 的 `FORBIDDEN_RULES`）。现有的"标点归一"是**改 `block.text` 的批量数据修复**
（`orthography.py:20`），不是导出变换。这条决定了预览导出页"所见即所得"：只要所有修正都写进源，
就不存在"预览里改了、导出又变回去"。

### 3.5 草稿 + 提交（2026-11-05 用户改：不再是即写即存）

用户明确要求「**所有编辑必须确认提交**」（防误操作）。上一版"预览导出页即写即存"**作废**，
两页统一成「草稿 → 确认 → 写库」。

规则：

- 编辑 → 行首进「待提交」（圆点 / 底色）：**不写库、不进进度、不进导出**；
- `Enter` 或点「提交这一处」→ 写库（一个 batch），状态变「已确认」；
- 可攒多处一起提交：一个 batch、一次 `/undo` 全退；
- **待提交是页面内存态**（不进 localStorage）：刷新 / 关窗口会丢，靠 `beforeunload` + 三键离开提示拦一次；
  页头常驻「N 处未提交」；
- **有未提交时导出按钮置灰**，写明「先提交 N 处」——这是"导出的版本 = 预览的版本"的硬保证；
- 提交前比对草稿的 base：当前行文本变过 → **拒写**并提示「这一行在别处改过了」（上游冲突，见 4.2）；
- 结构操作（合并 / 拆分 / 类型 / 页排除）不走草稿：点一次 → 原位确认 → 写库一次，可撤销。
  （给结构做影子模型不值当。）

**多选提交（用户 2026-11-05 定）**：行首复选框；**勾选 ≠ 提交**。点「提交选中的 N 处」时，
只提交**选中且待提交**的行，没改过的跳过；按钮文案写实际数（选中 5 行 · 3 处待提交 → 「提交选中的 3 处」）。
一次提交 **≤500 条**（`routes_review.py:610` 的批量上限，超了 422），超过时提示分批（分批 = 多次撤销）。

**离开提示**：三键——「提交并离开 / 放弃修改 / 留在这里」。文案先写后果：
「有 3 处未提交，离开会丢失这些修改」。提交失败就不离开，错误可读。

**三态视觉与痕迹**：未编辑 = 正常；待提交 = 行首圆点 + 左缘竖线，文字已是改后的；
已确认 = 标记消失，保留一个**会话内**的「刚才改过」淡痕（行号旁小点）。淡痕不持久——
刷新后只能靠 `diff_ack ∈ {adopted, edited}` 知道"这行判过 / 改过"，那不等于"我刚才改的"。
永久痕迹要加"行级改动时间"列（迁移），v1 不做。

为什么改：

- 防误操作是用户原话；一条 1747 行的队列，误触一次就改一个字的成本太高；
- "导出的版本 = 预览的版本"要求**页面上看到的就是库里的**；有待提交就不能导出，这条让它成立；
- 两页统一后不再有"审校要确认、预览不用"的两套语义。

代价与补偿：每条多一步确认；候选点选仍可 1 步（采用并确认），手改 `Enter` 确认；批量提交摊平。

## 4. 持久化与"上游变了"

### 4.1 一次编辑写什么

```
一个 batch：
  event(block.text before/after)         ← 文本变了才有
  event(block_line.diff_ack before/after) ← 该行有 aux_text 才有，记 edited
  UPDATE block.text / block_line.text / diff_ack / diff_ack_text
撤销：/undo 回放这一批；不需要"预览层"参与。
```

三条规则，缺一条就会"改完又回来"：

1. 有 `aux_text` 的行，手改后写 `diff_ack='edited'` + `diff_ack_text=新行文本`；
2. **`kept` 不携带文本**：`ack_diff_line` 的 kept 分支只写 ack，传入的 `text` 被忽略
   （`editing.py:877/904`）。所以"保留原文但顺手改个字"必须发 `edited`；
   接口应直接拒绝 `kept` + `new_line_text` 的组合（现在是静默丢弃，属于会咬人的静默行为）；
3. 现状 `ack=null` 的手改不写裁决（审校页 `reading-view.js:2784` 的"两路都不对"发的是 `ack=null`），
   改完下一轮**还会回到队列**——这是两页数字对不齐的根源，拆页前必须修掉（改成 `edited`）。

### 4.2 没有"合并顺序"问题，但有三个真实冲突

成品是纯函数，**不存在"用户的成品版本"需要和上游合并**。真正会撞的只有三处：

| 冲突 | 现状 | 规则 |
|---|---|---|
| **重识别页**（新行、新 line_id，aux 与 ack 清空） | 已定：默认跳过有人工改动的页；强制覆盖前自动整库备份 | 预览导出页复用**同一条判据**，不许自己再写一套；覆盖后预览自动重算 |
| **忙时缓存**（有任务在跑时，写库后最多 10 秒内可能拿到旧 segments） | `cache_policy.py:29` `MAX_AGE_SECONDS=10.0`，而注释写的是 3 秒 | 任何写操作后**清掉该项目的 preview 缓存**；否则用户会看到"改了没生效" |
| **草稿基线**（草稿基于旧块文本） | 现有草稿存了 `base` 只用于画修订，**不校验** | 两页的草稿都存 `base`；提交前必须比对，不一致就拒写并提示「这一行在别处改过了」 |

### 4.3 预览与导出必须同 options

`preview_segments_json` 的签名包含导出选项（`export/project.py:699`）。预览导出页必须把当前选项
传进去，并在页面上写明"这份成品是按这些选项生成的"；否则会出现"预览里没有脚注、导出里有"。
选项一变，缓存签名变、成品重算——这是想要的行为，不该被缓存挡掉。

## 5. 排序与 Jev 可疑度

### 5.1 现状（都是实测数字）

- 只给**分歧行**打分，写 `block_line.jev_score`（`jev_priority.py:5/423`），默认关、手动触发；
- 40 页 / 250 行实测（`docs/qa/2026-11-05-jev-acceptance.md`）：队列基线精确率 **25.2%**（250 行里 63 条真错）；
- 排序方式决定收益：**档位排序**（可疑档优先、档内按文流）前 50 精确率 **68.0%**；
  **纯分数排序**前 50 是 **76.0%**（+8 个百分点）；
- 耗时 **0.77 秒/行**，250 行 192 秒；整本 899 行约 11–12 分钟；
- 阈值 0.05 处的一次配方实测：标 86 行、真错 39 条，精确率 **45.3%**（`jev_priority.py:53` 注）。

### 5.2 建议（改文案，不改排序）

1. **默认仍是文流顺序。**
2. **"可疑度优先"只做"档"，不做全排序。** 代码是 `_tier` 返回 `(tier, item["order"])`
   （`routes_review.py:461-474`），即**档内按文流**。我上一稿写的"档内按分数升序"是建议、
   不是现状；现在也不再建议改：那 +8 个点（前 50 68%→76%）只在"判前 N 条就停"时才兑现，
   而产品还没有把"提前停止"定成动作。为它改变一个 opt-in 功能的排序、让同档条目跨页跳，不值。
3. **文案必须跟代码走**：开关叫「可疑优先（同档按阅读顺序）」，副文案写
   「40 页实测：前 50 条命中率 68%，原顺序 25%」。**不许写"按可疑度排序"**——
   点下去发生的是分档，不是排序。
   数字口径锁死：**68% / 25%**（25.2 四舍五入），同一份 40 页 / 250 行样本，
   `docs/qa/2026-11-05-jev-acceptance.md` §③。**76% 不写进界面**——那是"改成纯分数排序"的
   反事实，本轮不做。
4. **不显示原始分数**（0.03 这种），只显示"可疑 / 未打分"两态，详情里才给分数与阈值。
   理由：45.3% 的精确率撑不起一个看起来精确的数字。

### 5.3 一个已知的失效坑

`jev_score` 只在手动"清除"时归零（`jev_priority.py:455`）。字符规范化会改 `block.text`
（`orthography.py` 的 `lines_plan`），改完那行的分数就对应一个不存在的文本了，但排序仍按旧分走。
判据：**行的 `text` 或 `aux_text` 变了，`jev_score` 必须置空（或重算）**。
影响面目前未知，先按 P2 修，修完补一条验收。

## 8. 步骤条与完成态（2026-11-05 用户定：预览并入导出）

**6 步，不收成 5 步。** 要收只能把「目录确认」或「版心确认」并掉，那两个跟"预览"无关，动它们会把
完成度口径和页面状态一起改；用户自己的流程也还是 6 步。**预览只属于第 6 步、不属第 5 步**——这是这次要守的线。

- 第 5 步「正文审校」→ `#view-reading`：只判差异，不渲染成品、不渲染整本书流；`renderReading` 整块退役。
- 第 6 步从「文件导出」改名「**预览导出**」→ `#view-preview`：组装、通读、改、提交、预检、导出全在这一页；
  老的导出面板（`#export-panel` 的 compare）退役。
- **不设"预览完成"**（D-090 继续）：第 6 步用普通态（`plain`，无 ✓），计数可写「已导出 N 次」；
  有没有通读过不进完成度。
- **不造第二个"完成"定义**：导出的把关只有两条事实现状——预检 warnings 如实显示 + **有未提交时导出置灰**
  （§3.5）。两条都不是"完成态"。
- 页内给一个对账：「上次导出：HH:MM；那之后又改了 N 行」（导出记录时间 + 事件表），让用户知道手上
  这份导出是不是最新的。这一步叫对账，不叫完成。
- **导出仍然没有"审校未完成就不许导出"的闸**（代码现状：`routes_exports.py:146` 直接 `run_export`）；
  未审状态由预检提示与 manifest 如实记录。要不要加这道闸是另一个决定。

## 10. 明确不做

- **不做候选表 / 成品版本表**：段 ID 不稳定，存了就会与导出发叉（理由见 3.3）。
- **不在导出时统一标点**：说明书 9.3 禁止；归一是改数据。
- **不让预览导出页做批量采纳候选**：那是审校页的 A/B 对照。
- **不做即写即存**：用户要求编辑必须确认提交；两页都是「草稿 → 提交」（§3.5）。
- **不把预览留在审校页**：审校页不渲染整本书流、不组装、不导出；成品只归预览导出页。
- **本轮不改 "可疑优先" 的排序**：只改文案；档内按分数排是 P2，前提是产品先决定"允许判前 N 条就停"。
- **不因为拆页就放宽重识别**：默认跳过人工改动页、强制覆盖前整库备份，两条都继续有效。

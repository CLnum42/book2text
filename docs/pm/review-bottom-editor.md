## 1. 现状核对（决定方案边界的三个代码事实）

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| 面板**已经不在正文流里**，挂在 `#reading-panel-host`，跨重绘存活 | `index.html:780`、`app.js:19183`；CSS `.reading-panel-host{flex:none;max-height:38vh}` | "被重绘吞掉"这个坑已经填过；下区只是把它从"列间窄条"改成"底部通栏"，不是重写状态机 |
| 但它是**插在 PDF 列与正文列之间的一个列**，`max-height:38vh`，每条**开→判→关** | 同上 + `draftReading()` 只做 close + rerender | 现在每条要一次"关 + 下一次远距离点击 + 重新定位"；这是 567 条量级的主要机械成本 |
| 正文行可**就地编辑**（`contenteditable=plaintext-only`），草稿两套（`readingDrafts` / `readingInlineEdits`） | `app.js:18826`、`18038`、`19283`；提交走 `submit-drafts` | 下区编辑必须接**同一套草稿**；且不能让上区、下区同时处于编辑态 |

补充（审计已记录、需回归确认）：阅读视图里 `Enter` 走 `gotoNextUnreviewed()`，面板开着时会把当前这条**跳过**而不记录。下区常驻后这个缺陷会更致命（用户会一直按 Enter）。

## 2. Q1：下区 vs 浮动面板

### 2.1 结论与理由

**选固定下区，并让它取代浮动面板**（不做两套并存的界面）。

| 维度 | 浮动面板（现状） | 固定下区（提案） |
|---|---|---|
| 每条动作数 | 点差异 → 判 → **关** → 找下一处 → 重新打开 = 3–4 个动作 | 点差异 → 判 → **换内容** = 1 个动作 |
| 567 条的总代价 | 审计口径：约 **29–58 分钟**纯机械前进 + 每条约 1 次长距离指针移动 | 趋近 **0**（键盘闭环，指针不动） |
| 空间 | 不占高度，但挤占横向（列间窄条），且**遮挡/挤压正文列** | 占 276px 高度（900 高的 31%），但正文列宽度不变 |
| 上下文 | 判完即关，上下文要重新找 | 上区常驻可读；下区只压下方 |
| 稳定性 | 每行插入/移除，滚动与重绘都要重挂 | 单一常驻节点，重绘只更新内容 |
| 与"一眼看明白" | 只有整行文本，没有原图局部 | 原图局部 + 对应文本并排，两列对齐 |

**关键取舍：** 下区赢在"**每条 2.1 秒**"这个量级上——567 条 / 20 分钟意味着每条只有约 2 秒，
2 秒里做不了一次"关掉再找回来"。这是它压过浮动面板的唯一硬理由。
**它的代价是固定的 276px 高度**，在 628 高屏幕上要占 46%（第 3 节有数字与缓解）。

### 2.2 为什么不"两者并存"

并存 = 两套打开/关闭状态、两处编辑框、两处高亮，用户要判断"现在该点哪一个"。
**同一屏只允许一个判决面。** 旧面板的位置（列间）归还给正文流。

## 3. Q2：高度怎么分（约束值，Designer 定稿）

### 3.1 预算推导

| 项 | 值 | 来源 |
|---|---|---|
| 顶栏 | 48 | `--topbar-h: 48px` |
| 工具条 | 44（≤700 高时 40） | `.reading-toolbar` |
| 正文行高 | 30.75px（15px × 2.05） | `.reading-stream` |
| 1423×900 可用高 | 900 − 48 − 44 = **808** | — |
| 628 高可用高 | 628 − 48 − 40 = **540** | — |
| 下区内部 | 标题栏 34 + 内容 + 底栏 44 + 上下留白 16 = **内容 + 94** | 与工具栏同密度 |

### 3.2 推荐数值

| 视口 | 下区 默认 / 最小 / 最大 | 上区剩 | 上区行数 |
|---|---|---|---|
| 1423×900 | **276** / 248 / 420 | 526 / 554 / 382 | **≈17.1** / 18.0 / 12.4 |
| 1423×628 | **240** / 220 / 340 | 294 / 314 / 194 | **≈9.6** / 10.2 / 6.3 |
| 1120 宽（窄） | 同高，左树 200，PDF 340 | — | 行数与高度无关，只影响行宽 |

- **上区最小 246px（8 行）**：分割线拖到低于此值 → 停住并提示"下区已到最小"，不允许上区被压到 8 行以下。
- 上区行数口径：`(上区高 − 18px padding-top) ÷ 30.75`。526px → **16.5 行**（不是 17.1）；文案写"约 17 行"，验收按 16.5 算。
- **分割线 6px**，拖动实时改上区/下区比例；**双击复位**为默认 276；**高度按项目记**（localStorage，键名带 project_id）。
- 下区"内容 + 94"里，内容区在 900 高默认 = 182px：裁切图 5 行 × 34px = 170 + 留白 12；
  右侧文本 5 行 × 30.75 = 154（有余量）。
- **628 高时默认 252（建议）**：内容 158px → 裁切行高 28px（240 时是 26px，正好卡在下限；真书行距更大时 240 会挤不下）。上区剩 282px ≈ 9.2 行。

### 3.3 增益/代价

- 下区展开 = 上区从 26 行（808/30.75）降到 17 行，**丢 9 行上下文**（900 高）。
  这是"看得清这一处"必须付的价：**276px 换 2.2–3.0× 的原图放大**。
- 缓解：① 下区可收起（0 高度，正文回到 26 行）；② 判决即前进，用户不需要反复上下看；
  ③ 上区"钉住当前行"，换条时视野不跳。

## 4. Q3：5 行裁切的规则

### 4.1 窗口算法（建议）

1. **纵向**：以审校行的 bbox 为中心，向上取「距中心 2 个行距」内的行、向下同理，合计 **≤5 行**；
   行距 = **该块**相邻行中心距的中位数（不用全书固定值；本书实测行高 0.0187 页高、行距同量级）。
2. **窗口滑动，不缩窗**：审校行在第 1 行时，窗口整体上移贴块首、向下补足 5 行；
   该块不足 5 行就显示实际行数（用同底色铺满剩余空间，不放空白噪声）。
3. **横向：窗口是高度的因变量，不是常数。** 以审校 span 的 bbox 中心为锚，按
   `s = (内容高 − 16) ÷ (5 × 行距)ᵃ`、`窗口(源像素) = 404 ÷ s` 反推：
   - 1423×900（下区 276，内容 182）：s = 0.949 → 显示行高 **33px**、窗口 **426 源像素**；
   - 628 高（下区 252，内容 158）：s = 0.811 → 行高 **28px**、窗口 **498 源像素**。
   ᵃ 行距取**该书该块**的中位行距（本书 1244px 宽、行距约 35px 源像素），**不能写死 35**。
   **窗口占页宽的比例随书变**：426px 在 1244px 宽的页上是 34%，在 A4（约 1654px）上是 26%
   → 界面上不许写"±15%"这种固定比例。
3b. **窗口上限与降级**：窗口 > 页宽 45%，或显示行高 > 40px 时，**减到 4 行、再不行减到 3 行**
   （用户原话是"最多 5 行"，不是"必须 5 行"）；3 行仍不满足 → 保行高上限、允许窗口到 50%。
4. **跨页段落**：块已经按跨页合并（连续流），但**裁切图不跨页**——只取审校行所在那一页，
   上下补不足时按第 2 条处理。**理由**：拼两页会让高亮位置与页边界错位，而用户核对的是"这一页印的是什么"。
5. **放大上限**：显示行高 **≤40px**。页面图按 200 DPI 渲染，源行高 ≈35px（0.0187×1875）→ 40px 约等于 1:1；
   再往上只是插值变糊。若要更清晰，需要后端按 dpr 出裁切图（**另开一刀，不在本版**）。
6. **对齐容差 = 0**：裁切图与高亮必须来自**同一个 bbox 源**（`block_line.bbox` / span bbox），
   画框用的坐标与裁切用的坐标是同一组；**不允许**在裁切图上按字符宽度估算位置（上区那套估算只能留在上区）。
   若必须估算（竖排无 bbox 的行），容差 ≤2px 且与上区共用同一个函数，不许各算一套。

### 4.2 颜色与语义

三层高亮（行/字/框）语义**不改**：行 = 段落底色、字 = 差异片段、框 = 当前行/块。
下区复用同一组 CSS 变量与同一渲染函数，**不新增第四种颜色**。

## 5. Q4：弹出自适应（状态机）

### 5.1 结论

**点差异才弹；弹了就常驻；判完不关；只有明确动作才收。**
不要"每条重弹"，也不要"滚动到差异就自动弹"（后者会打断上面读上下文）。

### 5.2 状态机

| 状态 | 进入方式 | 界面 | 离开 |
|---|---|---|---|
| **收起**（0 高度） | 初始；`Esc`（判决态）；点 × | 上区占满；正文里的红字仍可按 | 点任意差异 → 打开 |
| **判决态** | 点差异 / 键盘 `Enter`/`Space` 后自动 | 下区：左裁切图 + 右文本 + 三个按钮 | 判 → 换下一条（停留判决态）；`Esc` → 收起；点 × → 收起 |
| **编辑态** | 点"手动编辑" / 直接点下区文本 | 编辑框聚焦，**光标落在审校片段最后一个字之后** | `Enter`/⌘Enter → 落草稿并进下一条；`Esc` → 回判决态；点别处 → 落草稿并回判决态 |
| **换条中** | 判决后 | 内容替换（同一位置），不闪白、不改变下区高度 | 完成 |

### 5.3 换条时的具体规则

| 项 | 规则 | 理由 |
|---|---|---|
| 下区自身滚动 | **归零**（不保留） | 每条窗口固定 5 行，没有"共同滚动位置"可保留 |
| 上区滚动 | **钉住当前行在同一屏幕高度**（现有 pin 逻辑） | 换条时视野不跳，20 分钟内眼睛不用重新定位 |
| 上区跟随滚动 → 下区 | **不跟** | 下区由"操作"驱动；滚动只是阅读 |
| 下区高度 | 换条不改 | 高度跳变本身是打断 |
| 当前条未保存的编辑 | 自动落草稿（不弹确认） | 草稿层本来就是这个设计；弹确认会打断 2 秒节奏 |

### 5.4 为什么不是"每条重弹"

567 条 × 1 次重开（点差异 + 重新定位 ≈1.0–1.5s）= **9.5–14 分钟**，占 20 分钟预算的 47–70%。
"弹一次就别再收"不是偏好，是这个量级下唯一可行的节奏。

## 6. Q5：上区与下区的一致性

### 6.1 真源

- **唯一真源**：`block_line.text`（服务端）+ `readingDrafts`（未提交草稿）+ `readingInlineEdits`（就地编辑缓冲）。
- 上区、下区**都是渲染**，谁都不许自己缓存文本副本。
- 下区编辑 → 写 `readingDrafts`（同一个 key）→ 上区同一行立刻重绘；提交仍走 `submit-drafts`，**不新增写库路径**。

### 6.2 单编辑面规则（关键）

- **同一时刻只允许一个编辑面**：进入下区编辑态时，若上区正在就地编辑 → 先落草稿、退出上区编辑；
  反过来，点开上区某行编辑时，下区退出编辑态（但**保持打开**，切到该行为当前条）。
- 这样既满足"上区逻辑不改"（单击即改、光标行为保持），又不会出现两个光标两套草稿。

### 6.3 谁跟谁

| 动作 | 上区 | 下区 |
|---|---|---|
| 点差异 / 键盘换条 | 滚到该行并钉住 | 换内容 |
| 上区手动滚动 | 滚 | **不动** |
| 下区编辑 | 同一行实时重绘（不滚动、不抢焦点） | 保持 |
| 左树点页 | 跳到该页 | 不动（当前条还在，可继续判） |
| 提交 | 清草稿、重绘 | 关闭（没有待改的了） |

## 7. Q6：折叠左树

| 项 | 结论 | 理由 |
|---|---|---|
| 宽度给谁 | **正文流**（+232px：764→996，46→60 字/行） | 判断发生在正文；PDF 保持 420 不缩，图已经不清晰（420 宽时字高约 12px） |
| 记住 | **按项目**（`localStorage`，键含 project_id） | 不同书/不同任务习惯不同；全局改会让另一个项目突然变宽 |
| 折叠后 | 留 **44px 窄条**：竖排显示「回 · 待审 N」，点击展开 | 完全消失后用户找不回来；现有 <1120 的 44px 窄条**没有页码**（已知问题），折叠态必须复用同一个窄条并补上章名 |
| 展开入口 | 窄条点击 + 快捷键 `[` | 键盘用户不用去找 |

## 8. 键盘（进这一版）

| 键 | 作用 | 前提 |
|---|---|---|
| `Enter` | **保留原文**并下一处 | 焦点不在输入框；下区打开 |
| `Space` | **采用候选**并下一处 | 同上（且不在编辑态，避免空格输入） |
| `E` | 进入下区编辑态（光标在片段末） | 下区打开 |
| `Esc` | 编辑态 → 判决态；判决态 → 收起 | — |
| `[` / `]` | 收起 / 展开左树 | 新增，可选 |

**必须同一刀修掉**：现在 `Enter` 在面板开着时走 `gotoNextUnreviewed()`，会跳过当前条且不记录。
下区常驻后用户会一直按 Enter——这个缺陷不修，键盘就是在批量制造"漏审"。

## 10. 不做

| 不做 | 为什么 |
|---|---|
| 下区与浮动面板并存 | 两套判决面 = 两套状态、两处编辑框，用户要判断"该点哪个" |
| 滚动到差异就自动弹 | 会打断上面读上下文；弹出发起者只能是用户动作 |
| 每条重弹 | 567 条 × 1.0–1.5s = 9.5–14 分钟，直接吃掉 20 分钟预算的一半以上 |
| 两个可同时编辑的面 | 双光标 + 双草稿 = 数据分叉 |
| 裁切图跨页拼接 | 高亮与页边界错位，用户核对的是"这一页" |
| 在裁切图上按字符宽度估算画高亮 | 与裁切源不同坐标，必然漂；容差 0 只能靠同一 bbox |
| 把下区做成可自由改多高的"全屏编辑" | 那不是审校，是全屏改写；本版只要 5 行窗口 |
| 用大模型判断"该不该弹" | 未测、成本与隐私未解决（`pipeline-decision.md` 结论） |

## 1. 数据核查（先看事实，再谈 IA）

### 1.1 书眉里到底有没有章节号？**没有。**

真项目 394 页里，含「红楼梦」的行共 **352 行 / 351 页**，bbox 在 `x≈0.01–0.06`（左边距，竖排），`y≈0.56–0.69`。内容是：

| 形态 | 行数 | 例子 |
|---|---|---|
| 只有「红楼梦」 | **256** | `红楼梦` |
| 红楼梦 + 乱码 ASCII | 96 | `红楼梦6EOEO` / `红楼梦/8OO` / `红楼梦印四0` / `红楼梦/0000` |

- **一个可读的章号都没有**：数字串统计里，`()`（无数字）256 次，`('0',)` 18 次，`('6',)` 15 次，
  其余是 `0800` / `0000` 这类。这是扫描件左侧竖排书眉被 OCR 读崩的产物。
- 换句话说：用户设想的"从版心外的书眉定章节"**在这本书上无数据可用**。

### 1.2 页码：不是"模板覆盖 42/267 页"，而是**可以整本线性推导**

- 真项目 `printed_page` **394 页全为 NULL**，`page_number_template` = None，`page_number_ranges` = None
  → 页码定位**还没做**。
- 但页脚数字本身在：**398 条纯数字行覆盖 367/394 页**，位置 `y≈0.97–0.99`（左下页脚）。
- 序列规律：`(2→4) (3→6) (4→8) … (109→218) … (394→788)`，
  **印刷页码 = 2 × PDF 页序**，相邻对里 **325/366 符合 +2**，其余是 OCR 误读（如第 20 页读成 `1`）。
- **产品含义：** 用"中位数拟合偏移 + 残差自检"就能给 367/394 页定页码，剩下 27 页留空或人工补 3–5 处。
  不需要逐页模板，也不需要"覆盖 42/267 页"那种口径。

### 1.3 章首行极干净：27 章 / 394 页

| 项 | 实测 |

## 2. Q1：目录确认值不值得单独成步？

### 2.1 结论

**目录要，但"确认"不要。** 保留为七步里的第 4 步，行为是
**自动生成 + 默认通过 + 只在章号序列不连续时要求人工**——与用户给"版心确认"
设计的规则（"不调就默认确认"）完全同构。

### 2.2 依据

- **章号来源不需要书眉**（1.1：书眉无章号），也不需要页码：章首行自己就是权威来源，
  本书 **27/27 正确、连续、无歧义**。
- **页码不是章号的来源，但可以自动推**（1.2：页码 = 2 × 页序，367/394 有观测）。
- 所以这一步**没有需要人判断的东西**。给它一个"确认"按钮，用户每次点都是空点——
  这正是他抱怨的"要判断的东西太多"里最不该有的一种。

### 2.3 准确率能到多少？失败了怎么办？

| 场景 | 准确率 | 回退 |
|---|---|---|
| 本书（单卷、章号连续） | 章号 **27/27**；页码 367/394 自动 + 残差自检 | 不需要人 |
| 章号缺号 / 重号（换书、跨卷合订） | 未知（本书没有这种情况） | 标"序列异常" + 定位到具体页，人工补 1–2 处 |
| 章首行被 OCR 读错（如「第五十四回」→「第五十四四」） | 未测 | 用"上一章号 +1"补齐；连续两次异常才要求人 |
| 竖排回目两行提取 | **未验证**（27 页没逐页核） | 提取不到就只显示章号，不影响目录可用 |

**失败不会导致"手动建目录"**：最坏情况是补几个章号，成本是分钟级。

### 2.4 "供审校调用"真的有用吗？

**对审校跳转：用处小。** 审校的主循环是"下一页待处理"（1733 条 / 390 页 / 平均 4.44 条/页），
用户很少需要"跳到第 63 回"，他需要的是"下一处"。

**对用户的终点（双语语料库）：用处大。** 章是中文书与英文书**唯一可靠的跨书对齐锚点**
（两本书不共享页码）。目录在导出里是 `meta.json` 的章节结构，这比审校导航重要一个数量级。

**所以目录的定位应该是"导出与对齐用的元数据"，顺带做审校侧栏的导航。**

## 3. Q2：正文审校内嵌到页面视图，会不会更慢？

### 3.1 结论

**会慢。不建议把审校编辑区搬进页面视图。**
七步里的"正文审校"应该是一个**入口 + 进度**，点进去还是现在的独立视图（左图 + 右队列）。

### 3.2 依据（几何与实测）

| 项 | 数值 | 含义 |
|---|---|---|
| 每页正文 | 26.8 行 / 559 字 | 单列在 1440×758 视口里约放 25 行（28px/行）→ **整页文本 + 页图放不下一屏** |
| 每页差异 | 平均 4.44 条 / 最多 13 条 | 一页最多要在一屏内处理 13 处 |
| 现状 | **13 键/页、0 滚动** | 独立视图已经把"条数"压到极限，问题不在条数 |
| 设计稿自诊断 | 一页 15 处 = **至少 30 次跨栏扫视** | 真正的成本是"图↔候选↔编辑框"的视线往返，已用"图上画差异线"缓解 |

内嵌后必须同时可见四样：**① 页图的那一行 ② 两路候选文本 ③ 可编辑正文 ④ 采纳/保留按钮**。
独立视图用"左图约 730px + 右栏 628px"正好放下（L-78 实测：五区展开都是 628/628、零滚动）。
单列放不下 → 必然出现"图上点一下 → 下面滚一段 → 再滚回来"，把 30 次扫视变成 30 次滚动。

### 3.3 真正能降低 1733 条成本的三件事（都不改 IA）

1. **键盘"上一处 / 下一处"**——`L-77` 明确写着**没做**（`Alt+[ / ]` 未做冲突测试，
   现有快捷键只有 ⌘Enter / ⌘Z / ⇧⌘Z / Alt+↑↓）。1733 次操作里每次省一次鼠标定位，是最大单笔收益。
2. **页级分组 + 页内"标点级优先"**：标点级真错率 23.1% vs 汉字级 13.2%（40 页实测）。
3. **一页做完自动翻下一待处理页**（现在是手动）。

### 3.4 什么数据能推翻我的判断

- **单条审校耗时（E0，缺）**：没有它，"哪个更快"只能靠几何推断。
- **内嵌原型的同任务 A/B 耗时**：拿同一页 13 条差异做对照，才有资格说"内嵌更快"。
- 这两条都没有 → 现在做内嵌 = 用猜测替换一个已有实测（13 键/页、0 滚动）的方案。

## 4. Q3：七个步骤的完成判定，逐条交代

| # | 步骤 | 判定条件 | 数据来源 | 结论 |
|---|---|---|---|---|
| 1 | 页面确认 | `page.page_confirmed=1` 且 `page_type` 已定 | 有（394/394） | **能算** |
| 2 | 版心确认 | 每页 `margin_box_method ∈ {fit, bbox}`，或 `mode ∈ {custom, none}` | 有（fit 355 / bbox 37 / custom 2） | **能算，且 394/394 已完成**：`method` 为 NULL 的 2 页是 `custom`（人工设过），不是未定。判定要用 `mode` 兜住 custom，否则会误报 2 页未完成 |
| 3 | 文字识别 | 每页有 `primary` **且** `auxiliary` run | 有（394/394 两路） | **能算**。完成 = **两路都跑完**，不是"差异处理完"（那是第 5 步） |
| 4 | 目录确认 | 章号序列连续（+1、无重号） | **要新表**（现在无 TOC 实体） | 数据能自动算，但**存储与人工修正要新接口**；默认自动通过 |
| 5 | 正文审校 | 版心内 `diff_status='differs'` 的行全部有 `diff_ack` | 有（现全部 NULL） | **能算**。无差异的页自动完成（390/394 页有实质分歧，**4 页没有**） |
| 6 | 结果预览 | 组装成功 | **没有持久化状态**：组装是导出时现算 | **只能人工标记**，而"看过"是伪状态（违反 AGENTS 1.6）。**建议不设完成态**，只做可达入口 |
| 7 | 文件导出 | `export_record` 有记录 | 有（现 0 条） | **能算** |

### 4.1 三个容易做错的地方

1. **"文字识别"完成 ≠ "差异处理完"。** 前者自动（两路跑完），后者是第 5 步。
   如果把差异也算进第 3 步，第 3 步和第 5 步会长期同时显示"未完成"，用户不知道先做哪个。
2. **空文本分歧不能计入第 5 步的待处理。** `differs` 2191 里有 **458 条第二路读空**
   （其中 302 条含「红楼梦」= 竖排书眉）。任务 34 起审校只算**版心内**的块，
   这些书眉在版心外 → 已被排除；但导出页、`bbox` 兜底页（37 页）版心包含书眉时，
   **必须保证它们不进队列**，否则这些页永远不绿。
3. **"自动通过"不等于"步骤完成"。** 自动通过的条件（无分歧 + 无漏行 + 版心已确认 + 双引擎已复核）
   本书 **0 页满足**；但第 5 步"完成"只需要 ack 完。两者不能混成一个绿色。

## 5. Q4：什么时候做——**先跑，再改**

### 5.1 结论

**本轮《红楼梦》第三卷（3–5 小时）在现有 IA 上跑完，再动结构。**
跑之前最多允许一刀**零行为变化**的预置（见 5.4 刀 1）。

### 5.2 理由

1. **这次跑本身就是缺的那份数据。** 单条耗时、卡点在哪、目录跳转是否真的用得上、
   预览要不要有完成态——现在全是推测。先改 = 用推测改，然后在一本真书上验证推测。
2. **重构会让"现在能用的"暂时不可用。** 七步 IA 动的是导航与审校入口，
   而这两个正是跑书时每 30 秒就要碰一次的东西。中途出问题，停下来修的成本高于收益。
3. **IA 不减少任何一个条目。** 1733 条审校、390 页、4.44 条/页——这些是数据决定的，不是界面决定的。
   改 IA 的收益是"顺手"，不是"省时"；而"顺手"可以在跑的过程中被真实观测。
4. **风险对比：** 先改再跑 → 跑在一个没有真实验证过的入口上，出问题就停；
   先跑再改 → 多一次入口搬迁（本来就得分刀，成本不变），但拿到真实数据。

### 5.3 跑的时候要顺手采集什么（不写代码）

- 每 50 页记一次：**当前时间**（算出真实单条耗时）。
- 记卡点：哪一步需要翻回去、哪一页的差异难判、有没有"想跳章"的冲动。
- 这三条就能回答 Q2 和"目录有没有用"，比任何设计稿都硬。

### 5.4 分刀顺序（每刀能独立验收）

| 刀 | 内容 | 独立验收 | 风险 |
|---|---|---|---|
| **1** | **只读**七步状态条 + 完成判定接口（不改任何入口、不改审校视图） | 每步状态与本节第 4 张表一致；改名/改数据后状态跟着变；本书显示「版心 394/394」（custom 2 页算完成）、「审校 0/N」 | 低（纯展示） |
| **2** | 版心：默认全自拟合、拖动即改、不调默认确认 | 新项目零操作即 392/394 绿；拖一页变 custom；**custom 永不被批量覆盖** | 中（碰写路径） |
| **3** | 目录：自动生成 + 默认通过 + 异常才确认 | 第三卷生成 27 条、章号连续、章首页正确；给一本缺号书能标出异常页 | 中（新表） |
| **4** | 审校效率包：上一处/下一处快捷键、页级分组、标点级优先、完成后自动翻页 | 同一页 13 条差异的**键次数与耗时下降**；`diff_ack` 语义不变 | 中（碰审校核心） |
| **5** | 结果预览：左 PDF 右组装文本 | 预览文本与导出 `body.txt` **逐字节一致**（同一组装口径） | 低 |
| **6** | 七步 IA 收口：把审校/预览/导出入口挂到步骤上 | 每个入口都能进、都能回；不新增状态 | 低（只搬入口） |

**内嵌审校（把编辑区搬进页面视图）不进这一轮。** 只有刀 4 做完、且跑完一本书拿到
"单条耗时 + 滚动次数"之后，才有资格讨论。

## 6. 明确不做

| 不做 | 为什么 |
|---|---|
| **把"目录确认"做成需要人工点一下的步骤** | 章号 27/27 自动正确、页码可线性推导 → 确认 = 空点，正是用户抱怨的负担 |
| **从书眉取章节号** | 352 行书眉里 256 行只有「红楼梦」，其余是 `6EOEO` / `0000` 这类乱码，**没有章号可用** |
| **为"页码模板覆盖 42/267 页"去补模板** | 页脚数字与页序是确定性的 `2×页序`，367/394 页有观测，拟合即可；模板是更差的路 |
| **把审校编辑区搬进页面视图（本轮）** | 一页 26.8 行 + 图 + 两路候选 + 编辑框，单列放不下 → 滚动替代扫视；且现状已 13 键/页 0 滚动 |
| **给"结果预览"设完成态** | 没有真实状态；"看过"是伪状态（AGENTS 1.6 真实状态优先） |
| **重写审校视图以适配七步** | 七步是导航层，审校视图是工作层；1733 条的成本在工作层，改导航不动成本 |
| **在跑书之前改导航与审校入口** | 把 3–5 小时的真实跑放在未验证入口上，出问题就停 |

## 8. 一句话总结

**七步 IA 该做，但它不是效率手段。** 该做的是：步骤条 + 目录（自动生成、零确认）+
版心默认自拟合——这三样都降低"判断次数"；**不该做的是**把审校搬进页面视图、
把目录变成空点确认、给预览设伪状态。**时机上先跑这本书**：它产出的真实耗时与卡点，
才是下一刀的依据。

## 0. 结论先行

1. 这一屏的时间**不在点击上，在"心里做 diff"上**。每条差异要求用户读两段 20 字左右的文本、
   自己在脑子里比出不同；而 80.9% 的条目最后什么都不用改。这是 2–3 小时的真正去处。
2. 第二个可归零的成本是**前进**：现在判完一条不会自动到下一处，面板关闭、位置丢失，
   1623 次要重新找。更糟的是：面板开着时按 `Enter`（唯一的键盘前进键）会**跳过当前这条而不记录任何判断**。
3. 只改三件：**一条 = 一处差异**、**判决即前进（键盘闭环）**、**进度说人话（剩几处 + 剩几分钟）**。
   三件都不动数据模型；第 3 件里"按章折叠左树"需要后端补一个字段（一个切片）。
4. 我们**没有一条自洽的单条耗时**：中文书 2–3 小时 / **899 条逐条** ≈ 8–12 秒，
   英文书 20 分钟 / **573 条** ≈ 2.1 秒，差 4–6 倍（工时本身都是估计，不是实测）。
   第 3 件里的"你自己的速度"就是用来把这个数测出来的，不是装饰。

## 1. 问题一：用户坐在这屏前，真正在做什么

计量单位先统一：**一条 = 一处差异（mark）**。产品队列口径（`queue_items()` 实算）：
中文书 **1623 条 = 汉字级 899（逐条判）+ 标点级 724（73 组批量）**；
英文书 **866 条 = 573 + 293 行（28 组批量）**。
**逐条要人看的是 899 / 573**，标点是"批"不是"条"——工时要用前者做分母。

| # | 真在做的事 | 每次的机械成本（看代码数出来的） | 条目数 | 时间（假设 5 秒/条，待实测） |
|---|---|---|---|---|
| 1 | **判一条**：读第一路 + 读第二路候选 → 决定 | 点红字 1 次，读 2×20 字，心里 diff；点一个按钮 | 899（中文） | **1.2–3.0h** |
| 2 | **前进/重新定位** | 关面板 → 点工具条"下一处未审"（或 Enter）→ 视野跳 → 左图重对齐 | 1623 | **29–58min** |
| 3 | **手改**（两路都错的 C1，约 11%） | 点开 → 点"自己改" → 输入框预填整行 → 全选 → 敲 → 点存 | ~100 | 25–40min |
| 4 | **核对左图**（乱码、竖排、跨页） | 眼睛从右跳到左，找行框 | ~190 | 16–32min |
| 5 | 标点批量 / 提交 / 预检 | 一次性，分钟级 | — | 5–10min |

**关键判断：第 1 项的成本结构是错的。** 队列本来就以"一处差异"为单位（`mark` 的粒度是差异片段），
但界面让用户看"整行 + 整行候选"（`openReadingPanel` 把 `entry.candidate` 整行平铺在面板里，
`buildReadingLine` 只给第一路标红）。**判断粒度是片段，显示粒度是行**——每条的阅读量被放大了一个数量级，
而放大出来的部分 80.9% 是噪声。

## 2. 问题二：哪一步最疼（排序，不平均用力）

1. **判一条**（占时 60–70%，且 80.9% 无产出）。→ 必须压缩"看什么"，不是压缩"点几下"。
2. **前进**（纯机械，29–58 分钟，可归零）。→ 收益确定、风险最低，先做。
3. **不知道还剩多久**（心理成本，不是时间成本）。394/662 页、1623 条、进度条还只覆盖一半队列，
   用户无法判断"再坐 20 分钟够不够"，于是要么放弃，要么开第二个会话。
4. **手改**（11% 的条目，但单条最贵，且"改整行"而不是"改那个字"）。
5. 提交（有 `window.confirm`，一次一句，可接受）。

## 3. 问题三：屏幕上"技术需要、用户不需要"的东西

| 屏上的东西 | 它其实是 | 用户需要的是 |
|---|---|---|
| `已审 812 / 899 字` | 差异**条数**（`chars_total` 数的是 mark，不是字） | 还剩几处 |
| `汉字剩 201` | 写死的标签，英文项目上也这么写 | 剩几处（不分语种） |
| 进度条 100% | 只覆盖汉字级 899/1623（标点 724 条在 73 组里） | 一个不会说谎的完成度 |
| `跟随：开` | 滚动同步的实现开关 | 两边永远在同一处（不需要开关） |
| `显示 ▾`（修订标记三档 / 清晰度三档） | 渲染参数 | 只在"看不清"时给一个"高清" |
| `提交 N 处` + 确认框 | 草稿层是写入策略 | 「已保存 / 未保存」，不要"提交"这个动作 |
| `第 N 页 · 第 N 行第二路` | 引擎的内部坐标 | 这一处 |
| `版心外 N 处 · 其他 N` | 队列边界 | （可在"还有多少没进队列"里说一句） |
| `草稿` chip | 状态机 | 这行改过 / 没改过 |
| `收尾 0/6` | 内部六个检查项 | 能不能导出 |
| `可疑行（两路一致但可能都错）` 藏在 ⋯ 里 | **该露的反而藏了** | 这是质量信息，见 5.4 |

## 4. 问题四：只改三件事

### 4.1 P0：一条 = 一处差异（把判断单位还给用户）

- **问题**：每条要读两整行（约 40 字），而差异通常 1–2 字；80.9% 读完结论是"没变"。
- **证据**：`openReadingPanel` 整行平铺候选；`computeCharSpans(base, candidate)` 已经能算出差异片段
  （`buildReadingLine` 用它标红第一路），同一份数据完全够画"候选的第二路对应片段"。
- **方案**：面板改成**就地两行对照**，只显示差异片段 ± 6 字上下文：
  `第一路：…玉忙笑让："姐姐请坐。"` / `第二路：…玉忙笑**嚷**：「姐姐请坐。」`
  点"看整行"才展开。左图只高亮这一行（已有 `drawReadingPdfBox`）。
- **代价/风险**：片段化可能让用户忽略"这一行别处还有错"——但那些别处本来就没有第二路候选，
  现有队列也从来没让用户看过它们（两路一致但都错的 2.5% 由抽检兜，见 5.4）。风险可控。
- **验证**：40 条（20 条 A 类噪声 + 20 条真错），两种呈现各半，计时。
  通过线：中位耗时 **↓≥30%**，且真错漏判 ≤1/40、误改 ≤1/40。
- **优先级**：**P0**（这一条直接决定 2–3 小时能不能变成 1 小时）。

### 4.2 P0：判决即前进（键盘闭环）

- **问题**：判完一条，面板关闭、不前进，用户要再点一次远处工具条；`Enter` 在面板打开时
  会跳过当前条且不记录（`gotoNextUnreviewed` 从游标之后找，当前条被排除）。
  即每条约 3 个动作、1 次长距离指针移动。
- **证据**：`draftReading()` 只做 close + rerender + 刷进度，不推进游标；
  `app.js:20220` 的 keydown 只有 `Enter → gotoNextUnreviewed` / `Esc`，阅读视图里
  **采纳/保留没有键位**（`Enter/⌫` 那套只存在于 `review` 视图的 `diff-queue`）。
- **方案**：判完就地推进——面板不关、内容换成下一条、位置只挪一行；键位：
  `Enter` = 保留并下一处，`Space` = 采纳并下一处，`E` = 改，`Esc` = 停手。
  误按可由现有 undo 撤销；"已判"必须是一眼能看见的状态变化。
- **代价/风险**：`Enter` 从"不记录地跳过"变成"记录一次保留"——这是**语义变严**，
  误按会把一条记成已审。可撤销 + 进度条可回退，接受。
- **验证**：同 40 条计时；指标：每条指针动作 ≤1 次、工具条往返 0 次、误记率 ≤1/40。
- **优先级**：**P0**（预期把 29–58 分钟的前进成本归零——**假设 5 秒/条，待实测**；
  并修掉一个静默跳过。这项的收益不依赖那个假设：动作数从 3 降到 1 是结构事实）。

### 4.3 P1：进度说人话 + 按章折叠

- **问题**：单位混用（字/处/组），主进度条只覆盖 55% 的队列（899/1623），能到 100% 却没完成；
  左树是 394（英文 662）行平铺的页码列表，没有任何"我在书的哪里"。
- **证据**：`renderReadingProgress()` 用 `chars_total`；tree 的 `rows = pages.filter(... || true)`
  把每一页都列出来；章节数据已在导出元数据里（27 回连续无缺，见 `ia-restructure.md`）。
- **方案**：主数字 = **剩 N 处**（单位统一"处"）；副数字 = **按你最近 20 条的实测速度，约剩 M 分钟**；
  标点单列，不混进同一个百分比；进度条不满 100% 除非队列全判（含标点）。
  左树由 394 行改成 **27 回折叠**，展开才出页。前 20 条不显示时间（样本不足）。
- **代价/风险**：计时器是本地节奏，不是承诺；章分组要后端补 `chapter`（一个切片）。
- **验证**：① 进度数字与后端 `complete` 一致率 100%（现在做不到）；
  ② M 分钟与实际用时误差 ≤30%（≥10 次会话）；
  ③ 用户主观"知道还剩多久"≥4/5。
- **优先级**：**P1**（第 2 条做完，这条是把"中途放弃"变成"再坐十分钟"）。

### 4.4 不做（有实测依据）

- 不做页级/章级"一键通过"：不看的页等于没审。
- 不按分歧等级筛噪声（D-042：标点级真错率 23.1% > 汉字级 13.2%）。
- 不把"两路一致"当已核对（2.5% 一致但都错）。
- 不把"可疑行"藏进 ⋯ —— 它是唯一能看见"两路都错"的入口，应该常驻在进度旁边。

不用另开实验。

## 6. 给 Designer 的接口（她出稿需要的四个事实）

1. 一次判断的对象是**一处差异**，不是一行；面板里必须能一眼看出"哪几个字不同"。
2. 判完的下一帧，**下一条已经在眼睛的位置**——这是最强的"判完了"反馈，比任何对勾都强。
3. `628` 高度下，面板展开后正文至少保留 6 行上下文；`<1120` 宽时正文不得窄于 560px
   （现 CSS：树 200 + PDF 340 + 抓手，正文约 570px，已接近下限）。
4. 左图不是每条都要看，但**必须永远在同一处**；"跟随"不该是一个需要用户理解的开关。

## 7. 附录：380–422 宽度下"页图模糊"的三个候选原因（2026-10-28 核实）

用户已两次说页图模糊。Chief 的假设是"canvas 按 CSS 像素渲染、没乘 dpr"。**阅读页列不是这个原因**：

| 事实 | 证据 |
|---|---|
| 阅读页列是 `<img>`，不是 canvas | `app.js` 的 `readingTiles` / `showReadingPlaceholder` |
| 档位按 **CSS 宽 × dpr** 选，已乘 dpr | `detailImageProfile()`（`app.js:4813-4822`）：`need = cssWidth * devicePixelRatio` |
| 380 CSS × dpr 2 = 760 设备像素 → 取 `view` | `view` = 150 DPI，612pt 页面 = **1275px**，是 1.7 倍超采样（`render.py` RENDER_PROFILES） |

所以 dpr 是对的。按可能性排序，真正的来源是：

1. **占位图先上、大图串行解**（最像"糊"，且与"滚动/同步"的抱怨同时出现）：
   `thumb` = 40 DPI（612pt ≈ 340px 宽），显示在 760 设备像素里 = **放大 2.2 倍**；
   `pumpReadingImages()` 一张一张串行解 `view`（0.42 MB/页），快速滚动时窗口内多数页仍在 thumb 上。
2. **显示尺寸**：380–422 CSS px 放一整页，一行字约 15px 高。DPI 再高也不会让 15px 的字变清楚——
   这是浮层（点击放大）要解决的，不是分辨率。
3. **JPEG q=82**：`view` / `zoom` 走 JPEG（`render.py` `ENCODE_FORMAT`），扫描页纸纹被压成振铃，
   小字边缘发毛。同页 PNG 与 JPEG 的截图对比即可定性。

**建议的顺序**：先量三条观感证据（① 用户看到的那一帧是不是 thumb；② 同页 PNG vs JPEG q82；
③ 放大 2× 后字高是否解决），再决定改哪一层。若第 1 条成立，修法是"占位图也用 view"
或"窗口内优先解当前页 ±2"，**不是改 dpr**；若第 3 条成立，先提 q 到 90 再看体积账
（view 0.42 MB → 可能 0.6 MB，394 页有磁盘缓存，可接受）。

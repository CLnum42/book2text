# 准确率报告：合成金标准语料

**语料：** `fixtures/gold/synthetic-corpus.json`（82 行 / 2737 字，3 页）
**PDF：** `fixtures/pdf/synthetic-corpus.pdf`（无文本层，300 DPI 灰度）
**原始数据：** `docs/accuracy-raw.json`（逐页、逐行、含完整识别文本，可事后审计而不必重跑 OCR）
**生成脚本：** `scripts/make_gold_corpus.py`　**测量脚本：** `scripts/measure_accuracy.py`
**比对模块：** `core/ocr/compare.py`（说明书 8.7 规定的归一化步骤）
**引擎：** RapidOCR 3.10.0（ONNX）· macOS arm64 · 300 DPI · 2026-10-14

---

## 0. 这份结果能证明什么、不能证明什么

| | |
|---|---|
| ✅ **验证了比对工具链** | 归一化、编辑距离、CER/WER 现在有了已知答案可校准。做真实样本前必须先有这一步，否则测出来的数字连对不对都不知道。 |
| ✅ **给出了上限基线** | "完美输入"下的表现：这就是这套引擎在理想条件下的天花板。 |
| ✅ **定位了具体失败模式** | 哪些字符类别容易错，见第 3 节——这些对真实样本同样参考价值。 |
| ❌ **不能代表真实扫描书** | 合成语料是完美字体、无倾斜、无噪点、无透印、无对比度不均。真实旧书的准确率会明显更低。 |
| ❌ **不能替代人工校对金标准** | Phase 0 的引擎选型（RapidOCR vs PaddleOCR）仍需要真实扫描件上的 CER，**这份报告不解除那个阻塞**。 |

## 2. ⚠ 发现：说明书 8.7 的归一化规则有一处空白

**这是本次测量最重要的产出。**

说明书 8.7 第 3 步规定"删除**中日韩字符之间**的空格"（为抵消 Windows OCR 在汉字间插空格）。
实测发现，在中英混排文本里，**占主导的是"中日韩与拉丁/数字的边界"上的空格**，
而该规则覆盖不到：

| 金标准（页面上印的） | 识别结果 | 差异 |
|---|---|---|
| 这份文档的格式是 PDF，编码是 UTF-8 | 这份文档的格式是PDF，编码是UTF-8 | 汉字↔拉丁边界空格 |
| 论文引用了 Kuhn (1962) 与 Baker (1993) | 论文引用了Kuhn (1962) 与Baker(1993) | 同上 |
| 在 macOS 与 Windows 上 | 在 macOS 与Windows上 | 同上 |
| 校对时要注意 b 与 6 | 校对时要注意b与6 | 同上 |

（差异是排版约定：中文里拉丁词两侧是否留空隙。页面上确实留了空隙，OCR 没留。）

**影响量化：** 去掉全部空白后，编辑距离从 **149 降到 46**（-69%）。
也就是说**原始 CER 里约三分之二是空白相关差异，不是内容错误**。

**建议（需开发者决定）：** 把 8.7 第 3 步从"中日韩字符之间"扩展为
"中日韩与拉丁/数字的边界也一并处理"。理由是说明书 8.5 自己规定
"格式差异不作为分歧"，而边界空格正属于格式。

**我没有擅自改规则。** `core/ocr/compare.py` 里 `normalize_whitespace_insensitive()`
是一个**额外的测量口径**，函数 docstring 写明"这不是说明书 8.7 的一部分"，
本报告同时给出两种口径的数字（5.291% 与 1.634%），不藏任何一个。

## 3. 具体失败模式（对真实样本同样有参考价值）

### 3.1 生僻字——最集中

| 金标准 | 识别 |
|---|---|
| 靰鞡、靛蓝、黢黑 | 靳鞡、靛蓝、黔黑 |

"靰→靳"、"黢→黔" 这类形近僻字是主要错误来源。**这直接影响真实书的可用性**：
旧书里的异体字、人名地名用字大量属于这一类。

### 3.2 形近字符——连"讲形近字符的那一行"都错

| 金标准 | 识别 |
|---|---|
| 校对时要注意 b 与 6、l 与 1、O 与 0 这三组形近字符。 | 校对时要注意b与6、**1**与1、**0**与0这三组形近字符。 |
| 逗号和句点都是 ASCII 的 | 逗号和句点都是**ASCⅡ**的 |

l 被认成 1、O 被认成 0，连英文字母串 ASCII 都被拆成 ASC + 罗马数字 Ⅱ。
**英文专名与编号要重点核对**（说明书 13.1 本来就把"英文专名 / 数字"列为必测项）。

### 3.3 一处灾难性失败

```
金标准：书名号《红楼梦》、篇名〈葬花吟〉、引号“双”与‘单’。
识  别：°，《》
```

整行 25 个字，只留下了 4 个字符。**这是单行级别的完全崩溃**，不是渐变误差。
一行里同时出现 `《》〈〉“”‘’` 多种标号时风险最高——正好是中文书籍的常见形态。

### 3.4 其他

| 现象 | 例子 |
|---|---|
| 破折号变体误识 | `—` → `一`；`——` → `一` |
| 漏掉成对引号的后半 | `“那才是真正的春天。”` → `……春天。`（丢掉右引号） |
| **页脚整行漏检** | 第 3 页页脚 `— 3 —` 未被识别（该页只有 25 行，金标准 26 行） |

页脚漏检值得注意：说明书 6.5 要求批量标注页眉页脚页码，而**如果页脚根本检不出来，
用户就没法在界面上选中它**。这类"整行漏检"与"识别错字"是两种不同的失败，
前者更隐蔽。

## 4. 结论

1. **比对工具链可用**，且已被已知答案验证。
2. **在完美输入上，中文内容准确率 1.63%，英文 0%**——这是上限。
3. **原始 CER 的 5.29% 里，约三分之二是排版空格差异**，不是识别错误；
   这暴露了说明书 8.7 的一处规则空白（第 2 节），需要开发者决定是否收窄。
4. **失败是集中而非均匀的**：生僻字、形近字符、多标号混排行是重灾区；
   存在单行完全崩溃与整行漏检两种形态。
5. **这份语料不能解除 Phase 0 的阻塞。** 引擎选型需要真实扫描件上的 CER——
   合成语料上两个引擎可能都是 1% 上下，分不出高下，而真正的差别出现在
   倾斜、噪点、低对比度的真实旧书上。

# 已知限制与未验证事项

本文件只记录**当前真实存在**的限制。未实现的功能不写在这里，写在说明书的阶段路线里。
每条限制注明发现日期；一旦解除，移到条目末尾的"已解除"区并注明解除日期。

## 1. 应用能力（截至 2026-10-14）

### L-10 识别有任务执行器了，但还不能挑选页面

识别现在跑在**子进程**里（说明书 Phase 2 的执行器）：批量建任务、进度轮询、
暂停 / 继续 / 取消 / 重试失败页、中断恢复、应用被强杀不留孤儿进程——都可用，
验收标准（中断测试、重试不产生重复块、失败原因可见）都有真子进程的测试覆盖。
**仍未做：**

- **样本试识别没有独立形态**：说明书 6.3 的"识别样本"目前是同一个"识别所选"按钮——
  选 3–10 页时会给提示（"样本结果不代表整本书"），但还没有"样本模式"那种
  两引擎对照与设置微调的流程（那要等第二引擎）。
- **并发固定为 1 个识别子进程**：说明书 6.3 说"默认 1 个，设置中可调整"，设置项未做。
- **暂停的粒度是一页**：说明书也是这么规定的（"当前页完成后停止"），
  但一页可能要几秒到几十秒，因此界面上的"暂停"不是瞬时的（见 D-026）。
- **第二引擎已接入，但结论是"不互补"**：macOS 上接了 Apple Vision（说明书 8.5 / R1b，
  按行图复核、写 `aux_text` / `diff_status`、不生成块）；实测它比第一引擎弱
  （捕获率 17%，自己的错是第一引擎的 4 倍多）——功能保留、界面如实标注，见 L-30。
- **审校还没成套**：块能编辑、能改结构、能确认、能撤销，新识别结果能对比后采用或保留，
  页眉页脚能按位置批量标注，改动都有事件可追溯。**还缺**：逐块采用、
  在图上框选位置新增块、页眉页脚预览的图上高亮（见 L-22、L-29）。
- **"有待选新结果"只能看到、不能采用**：重新识别时若页面已有人工成果，系统按 R2
  只把它保存为待选结果（不覆盖，有测试保证）；采用 / 保留的对比界面在 Phase 3。
- **Windows 未验证**：子进程、终止、看门狗都没在 Windows 上跑过（L-13 / 平台章节）。

### L-27 识别的版面判断（疑似多栏 / 阅读顺序待确认）只写在原始输出文件里

分段模块会给出"检测到疑似 N 栏，阅读顺序仍需人工确认"这类提示（说明书 8.1 明确
"不假装已正确排序"）。项目流程里块本身入了库，但这个**判断依据**没有对应的存储字段，
目前写在 `ocr_runs/<run_id>.json` 的 `layout` 段里——界面上看不到，
也不在块或页面的接口载荷里。

临时上传流程（Phase 0 遗留）反而会显示它。审校视图（Phase 3）需要它，
届时决定是加字段还是从原始输出文件读。

### L-29 审校还缺页眉页脚工具与更细的对比

已做：块文本编辑 + 自动保存、确认 / 不确定 / 排除 / 类型 / 延续、恢复 OCR 原文、
结构编辑（合并 / 拆分 / 上移下移 / 新增 / 软删除）、"确认本页并跳到下一处未完成"、
撤销 / 重做（会话内）、**采用 / 保留新识别结果（整页对比）**、
疑难筛选（还没审完 / 有不确定块 / 识别失败 / 有待选新结果 / **有分歧**）、
按类型与识别状态筛选、**第二引擎分歧的逐行标记与一键换候选**。

**还没做：**

| 项 | 说明 |
|---|---|
| 页眉页脚工具 | ✅ 已做（2026-10-14 任务 20）：位置规则 + 文本条件 → 预览 → 批量应用、整批可撤销、不覆盖人工成果。**未做**：抽样页的原图高亮预览（现在是候选列表） |

| 逐块采用新结果 | ✅ 已做（2026-10-14 任务 26）：对比面板里逐块「换这一块」——按块框位置配对（并列出示重合度），只换那一块、其余不动、可撤销。说明书 R2 只要求整页二选一，这一条是超出 R2 的增强 |

| 键盘操作 | 只做了 4 个（⌘Enter / ⌘Z / ⇧⌘Z / Alt+↑↓）；说明书 7.5 的其余快捷键**未实现，也未在 Chrome / Edge / Safari 里验证过冲突**（说明书要求实现前必须检查） |
| 视图形态 | 审校在页面视图的下半部分，没有独立的"审校"标签页；左右分栏比例拖动、折叠页眉页脚、类型角标开关都未做 |

### L-30 第二引擎（Apple Vision）弱于第一引擎，分歧标记只能当"看哪里"的线索

40 页真书实测（1064 行）：两路分歧 28.9%，但分歧的归属是
**第一引擎对、第二引擎错 187 行** vs **第一引擎错、第二引擎对 8 行**（捕获率 17%）。
逐维度看它都更弱：汉字级错 132 行 vs 第一引擎 29 行，标点级 81 行 vs 32 行；
整页识别的正文 CER 是 2.16%（第一引擎 1.08%）。详见 `docs/ocr-evaluation.md` 第 8 节。

**已按实测做了分级、筛选与批量复核**（2026-10-14 任务 22 / 23）：分歧分
**汉字级 / 标点级**（`compare.grade_line`）；审校视图里逐行标出另一路候选、点一下换过去
（进撤销历史）；疑难筛选有两条；复核可以批量跑。

**2026-10-14 任务 25 用产品口径在同样 40 页上复算后，修正了一条结论**
（`docs/ocr-evaluation.md` 第 9 节）：**"按汉字级筛"没有得到数据支持**——
标点级分歧的信噪比反而更高（可定位行里含第一引擎错 23.7% vs 汉字级 13.3%；
基准 7.1%），因为第二引擎自己的错以**汉字**错误为主（127 行 vs 105 行）。
界面上不再把汉字级说成"值得看"、标点级说成"噪声"，**两类都看**（D-042）。

**由此产生的限制（仍然成立）：**

1. **它给出的候选大多不对**：界面如实写明"被标出的分歧里约八成是它自己的错"，
   所以"换成这一路"是给人判断用的，不是自动采纳（实测改对率约 1/4）；
   说明书 8.5 也明确"不自动采纳任何一方"。
2. **Windows 侧没有第二引擎**：系统 OCR 未实现（L-13）；接口与存储已就位，换引擎只需换适配器。
3. **首次调用有 5–6 秒框架预热**：单页复核的第一次会慢（批量跑时被摊平）。
4. **分歧率现在有汇总的地方了，但捕获率没有**：产品内的质量统计（项目视图的「质量统计」卡片）
   给出"复核了多少行、一致 / 仅格式 / 汉字级 / 标点级各多少、分歧率多少"；
   但**捕获率与"一致但都错"需要人工金标准**，只能离线测量
   （`docs/ocr-evaluation.md` 第 8–9 节：捕获率 64.6%、改对率 24.6%、一致但都错 2.5%）。
   卡片底部如实列出这一条与另外三项没采集的指标（每页审校时间、恢复成功率等），
   见 `docs/decisions.md` D-041。
5. **只有一本书的实测**：9 节的判断依据来自 1 本中文排印本 / 40 页；
   英文、竖排、扫描退化、其他书的数字**都未测**，换书要复核（说明书 1.7）。
5. **块的行结构改过之后标记不可用**：人工在块里增删过换行，行号与复核时的行就对不上了，
   这时界面**不标**（`divergence.stale`）并说明"重新识别这一页可恢复"——
   按序号硬标会指错地方。
6. **"两路都错"的 39 行反而最值得看**：它们集中在引号、破折号、校勘符号这类**排版符号**上
   ——两个引擎在这类符号上都不行，这是下一步最有价值的改进方向。

**已知的一个行为：** 服务被强制结束（不是正常关闭）时，`.lock` 会留在项目文件夹里。
下次打开时会被识别为**失效锁**（本机 + 进程已不存在）并自动覆盖，
因此不会挡住使用——但文件夹里会短暂留有这个文件。
服务目前不跟踪"哪些项目正开着"，因此没有在退出时统一释放锁。

### L-21 分段是启发式的，有三类已知失效场景

`core/structure/grouping.py` 按行距、缩进、对齐（说明书 8.1）把行组合成块。
规则本身有 21 项测试覆盖，但**启发式在以下场景会失效**，都已实测确认：

| 场景 | 现象 | 原因 |
|---|---|---|
| **右不齐（ragged-right）的英文** | 多行被并成一块 | "末行短"规则依赖版心右边界稳定；右不齐时行尾参差，右边界估不准。实测旋转页夹具（3 行英文）被并成 1 块 |
| **多行居中标题** | 可能被拆成多块 | 居中行左边界随行长变化，可能触发"缩进"规则 |
| **每页都有的竖排装饰边栏** | 被识别成"第 2 栏"，页面被标记"阅读顺序待检查" | 边栏的横向区间与正文不重叠，按说明书 8.1 就该标记待检查——但**会导致大量页面都带这个标记**，可能形成噪音 |

**没有加人工兜底：** 用户目前**不能**手动合并 / 拆分块、也不能改块类型。
说明书 6.4 / 7.4 要求的结构编辑（合并、拆分、移动）属于 Phase 3，尚未实现。
因此现在分段错了只能重跑识别，改不了。

### L-22 块类型有批量工具了，但没有版面组件的建议

分段模块（`core/structure/grouping.py`）一律产出 `paragraph`——说明书也说块类型来自
**版面组件的建议或人工标注**，它不越权猜测页眉页脚。

现在有了两条人工路径：审校视图里逐个改类型，以及**页眉 / 页脚 / 页码批量标注**
（说明书 6.5，2026-10-14 任务 20）：位置规则 + 文本条件 → 预览 → 一次批量应用、
整批可撤销、不覆盖人工改过的类型。**仍未做：**

- **版面组件的建议**（说明书 8.4 的路线 B / C 未选定，Phase 0 的版面组件评估还没做），
  说明书允许它作为"预填候选"，但必须先预览、绝不静默生效；
- **预览只有列表形态**：说明书 6.5 第 3 条想要"抽样展示若干页（原图 + 将被标注的块高亮）"，
  现在是候选列表（可逐个取消），图上高亮那一步还没做；
- **侧栏 / 竖排文字**：批量工具已支持**左右区域**（2026-10-14），
  本书左栏的竖排书眉 + 页码因此能被一次标掉（实测 37 块）；
  真正麻烦的是"整块横跨页面高度、又不在任何边缘条里"的装饰物——
  那类只能人工处理，或等版面组件（路线未选定）。

### L-18 OCR 峰值内存约 2.7 GB（只记录，未评级）

实测 RapidOCR 3.10.0（ONNX）处理 300 DPI 页面时**峰值内存 2686.6 MB**。
速度不是问题（中位 2.04 秒/页），**内存才是需要留意的**。

尚未验证：整书批量（400 页）时的内存行为、连续处理是否会持续增长、
在 8 GB 内存机器上是否可行。说明书 4.4/Phase 2 要求 OCR 跑在**子进程**里，
正是为了隔离这类问题，但子进程本身的内存上限还需要实测。

### L-11 识别 DPI 有了实测依据，界面还不能调

原问题：300 DPI 是初值，说明书 8.2 要求"DPI 默认值由样本测试决定"。

**2026-10-14：** 40 页真书实测后默认改为 **200 DPI**（正文 CER 1.08% vs 300 DPI 的 1.31%；
产品级导出正文 0.71% vs 0.94%；漏识少三成）。机理是检测模型对输入尺寸敏感
（同一行在 150/200/400 检出、在 250/300/500 漏掉）。见 D-037 与 `docs/ocr-evaluation.md` 第 7 节。

**仍未解决：**

1. **单本书的结论**：只在这一本干净栅格化的书上测过，换书 / 换扫描质量要复核；
   脚注与小字在低 DPI 下是否吃亏未测。
2. **界面不能调 DPI**：接口的 `POST /jobs/ocr` 支持 `dpi` 参数，但界面用默认值——
   说明书 6.3 的"识别样本 → 调整设置（语言、DPI）后重试"没有入口。
3. **缓解漏行的其它手段都没试**：页内切块（tiling）、多尺度兜底、检测阈值调整。
4. **界面渲染档位（`RENDER_PROFILES`）与识别 DPI 是两回事**，前者仍是初值。

### L-12 前端没有框架，也没有构建步骤

`backend/book2text/static/` 是手写的单页 HTML + 原生 JS。正式前端是
Vue 3 + TS + Vite（说明书 4.2），属于 Phase 1 及以后。当前页面只覆盖
Phase 0 第 4 项要求的"上传 PDF + 显示首页图像"，**不是**审校界面。

### L-13 API 不是最终设计

`/api/scratch/*` 是 Phase 0 临时接口。说明书第 11 节的正式接口以
`/projects/{id}/...` 为中心，要等 Phase 1 引入项目后才有。

## 2. 仓库与账号（2026-10-14）

### L-03 许可证未定，仓库不可公开

仓库已推送至 `git@github.com:CLnum42/book2text.git`，仓库为**私有**，未添加 `LICENSE`。
在许可证确定之前，**不得转为公开、不得对外分发**（见 `docs/decisions.md` D-006、D-008）。
依赖许可证也牵连其中：`pypdfium2` 较宽松，但 `PyMuPDF` 是 AGPL（说明书 4.2）。

### L-07 GitHub PAT 无法访问本仓库（gh 命令会失败）

`gh` CLI 使用的细粒度 PAT 范围为**"仅选定仓库"**，`book2text` 不在其中
（实测 `gh api repos/CLnum42/book2text` 返回 404）。因此针对本仓库的
`gh repo view`、`gh issue`、`gh pr` 等命令**都会失败**，这是权限问题不是仓库问题。

## 4. 测试与质量保证（2026-10-14）

### L-05 有了真实书的金标准，但还不是"真实扫描件"的

原问题：没有人工校对的金标准，因此算不出 CER / 分歧率 / 捕获率。

**2026-10-14 进展：** 开发者提供了 40 页真实书页（无文本层）+ 对应文本
（`gold_standard/`，受版权保护、已 gitignore），并据此完成**第一次真实书的准确率实测**：
正文 CER **1.24%**（20 060 字，40 页），过程与三处口径差异写在
`docs/ocr-evaluation.md` 第 6 节。

**仍未解决的部分：**

1. **它仍不是"真实扫描件"**：与 `sample-20p-300dpi.pdf` 同源，是原生数字排版的
   **干净栅格化**，不含歪斜、噪点、透印、对比度不均——因此 1.24% **偏乐观**，
   不能用来预期旧书扫描件。
2. **口径已定（2026-10-14）**：开发者明确**只要正文**，页眉 / 页脚 / 页码按位置规则排除
   （结构工具已支持左侧 / 右侧区域——本书的竖排书眉贴在左栏，靠上下区域捞不到）。
   实测：41 块一次标掉、零误伤正文，导出里不再出现书眉与页码。
   **章首回目已补进金标准**（对照页图逐字核对后写入，原文件另存备份）；
   口径现在是"正文（含章回标题）对正文"。
3. **页边界是自动推导的草稿**：`金标准文本_分页草稿.txt` 里的 39 个〔PDF 第 N 页〕
   标记需要逐页人工核准（每页首句与末字），核准前不能用来算"按页 CER"。
4. **没有段落标记**：文本按回为一行，因此**分段准确率无法评估**（判别段落切分对不对）。

### L-20 合成语料的准确率只在"完美输入"下成立

`docs/accuracy-report.md` 里的数字（内容 CER 1.63%、英文 0%）来自合成语料，
**代表上限，不代表真实扫描书**。真实旧书的倾斜、噪点、透印、对比度不均
都会显著抬高错误率。此外该语料刻意集中了难例（生僻字、形近字符、多标号混排行），
因此行级一致率（忽略空白 55%）偏低不完全是引擎的问题，也是语料选择的结果。

**未验证：** 同一批页面上的 PaddleOCR 表现；真实扫描件上的任何准确率数字。

### L-17 样本集有两处覆盖缺口，且不是真实扫描件

`fixtures/pdf/sample-20p-300dpi.pdf` 由 `scripts/make_scan_samples.py` 生成，
有以下已确认的局限（详见 `docs/scan-sample-set.md`）：

**覆盖缺口（说明书 13.1 要求但这两本书给不出）：**

- **中文与中英混排**：安乐哲一书是纯英文（0 页含汉字），红楼梦该文件是纯中文
  （0 页含拉丁字母），两本都不含中英混排页。
- **低清晰度或倾斜页面**：源书是原生数字排版，不存在这类页面；人工合成不能代表真实退化。

**性质局限：**

- 源书是**原生数字排版 PDF**，本样本是它的干净栅格化结果，**不含**真实扫描件的
  倾斜、噪点、透印、对比度不均、半色调网点等特征。
  **OCR 在本样本上的表现会好于真实扫描老书，用它预期真实效果会偏乐观。**
- 源 PDF 的文本层**不可靠**：红楼梦文本层有错字（"薛蘅芜"→"薛祷芜"、"三宣"→"三宜"），
  渲染出的图像却正确。故该文本层既不能当金标准，也印证了"已有文本层未必可信"。

### L-16 仓库里没有真实书籍（`test_books/` 被忽略）

`test_books/` 由开发者放入，含两本受版权保护的整本扫描/电子书（≥13MB）。
它被 `.gitignore` 排除，因此**克隆仓库后拿不到这两本书**，相关渲染测量无法直接复现

**理由：** 版权（同 D-005）与体积；一旦进入 git 历史很难彻底清除。
**如需入库**，请先确认版权与必要性，并同步更新 `docs/decisions.md` D-005。

### L-14 没有 CI

`tests/` 已有 57 个测试（单元 + 集成），但全部靠本机手动运行 `uv run pytest`。
没有 GitHub Actions，推送不会触发任何自动检查。

### L-15 Starlette TestClient 的弃用警告

运行测试时会打印一条第三方警告：`Using httpx with starlette.testclient is deprecated;
install httpx2 instead`（来自 starlette 1.8，经 FastAPI 的 TestClient 转出）。

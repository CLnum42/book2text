## 1. 应用能力（截至 2026-10-14）

### L-10 识别有任务执行器了，但还不能挑选页面

识别现在跑在**子进程**里（说明书 Phase 2 的执行器）：批量建任务、进度轮询、
暂停 / 继续 / 取消 / 重试失败页、中断恢复、应用被强杀不留孤儿进程——都可用，
验收标准（中断测试、重试不产生重复块、失败原因可见）都有真子进程的测试覆盖。
**仍未做：**

- **样本试识别没有独立形态**：说明书 6.3 的"识别样本"目前是同一个"识别所选"按钮——
  选 3–10 页时会给提示（"样本结果不代表整本书"），但还没有"样本模式"那种
  两引擎对照与设置微调的流程（那要等第二引擎）。
- **并发固定为 1 个识别子进程**：说明书 6.3 说"默认 1 个，设置中可调整"，设置项未做。
- **暂停的粒度是一页**：说明书也是这么规定的（"当前页完成后停止"），
  但一页可能要几秒到几十秒，因此界面上的"暂停"不是瞬时的（见 D-026）。
- **第二引擎已接入，但结论是"不互补"**：macOS 上接了 Apple Vision（说明书 8.5 / R1b，
  按行图复核、写 `aux_text` / `diff_status`、不生成块）；实测它比第一引擎弱
  （捕获率 17%，自己的错是第一引擎的 4 倍多）——功能保留、界面如实标注，见 L-30。
- **审校还没成套**：块能编辑、能改结构、能确认、能撤销，新识别结果能对比后采用或保留，
  页眉页脚能按位置批量标注，改动都有事件可追溯。**还缺**：逐块采用、
  在图上框选位置新增块、页眉页脚预览的图上高亮（见 L-22、L-29）。
- **"有待选新结果"只能看到、不能采用**：重新识别时若页面已有人工成果，系统按 R2
  只把它保存为待选结果（不覆盖，有测试保证）；采用 / 保留的对比界面在 Phase 3。
- **Windows 未验证**：子进程、终止、看门狗都没在 Windows 上跑过（L-13 / 平台章节）。

### L-27 识别的版面判断（疑似多栏 / 阅读顺序待确认）只写在原始输出文件里

分段模块会给出"检测到疑似 N 栏，阅读顺序仍需人工确认"这类提示（说明书 8.1 明确
"不假装已正确排序"）。项目流程里块本身入了库，但这个**判断依据**没有对应的存储字段，
目前写在 `ocr_runs/<run_id>.json` 的 `layout` 段里——界面上看不到，
也不在块或页面的接口载荷里。

临时上传流程（Phase 0 遗留）反而会显示它。审校视图（Phase 3）需要它，
届时决定是加字段还是从原始输出文件读。

### L-30 第二引擎（Apple Vision）弱于第一引擎，分歧标记只能当"看哪里"的线索

40 页真书实测（1064 行）：两路分歧 28.9%，但分歧的归属是
**第一引擎对、第二引擎错 187 行** vs **第一引擎错、第二引擎对 8 行**（捕获率 17%）。
逐维度看它都更弱：汉字级错 132 行 vs 第一引擎 29 行，标点级 81 行 vs 32 行；
整页识别的正文 CER 是 2.16%（第一引擎 1.08%）。详见 `docs/ocr-evaluation.md` 第 8 节。

**已按实测做了分级、筛选与批量复核**（2026-10-14 任务 22 / 23）：分歧分
**汉字级 / 标点级**（`compare.grade_line`）；审校视图里逐行标出另一路候选、点一下换过去
（进撤销历史）；疑难筛选有两条；复核可以批量跑。

**2026-10-14 任务 25 用产品口径在同样 40 页上复算后，修正了一条结论**
（`docs/ocr-evaluation.md` 第 9 节）：**"按汉字级筛"没有得到数据支持**——
标点级分歧的信噪比反而更高（可定位行里含第一引擎错 23.7% vs 汉字级 13.3%；
基准 7.1%），因为第二引擎自己的错以**汉字**错误为主（127 行 vs 105 行）。
界面上不再把汉字级说成"值得看"、标点级说成"噪声"，**两类都看**（D-042）。

**由此产生的限制（仍然成立）：**

1. **它给出的候选大多不对**：界面如实写明"被标出的分歧里约八成是它自己的错"，
   所以"换成这一路"是给人判断用的，不是自动采纳（实测改对率约 1/4）；
   说明书 8.5 也明确"不自动采纳任何一方"。
2. **Windows 侧没有第二引擎**：系统 OCR 未实现（L-13）；接口与存储已就位，换引擎只需换适配器。
3. **首次调用有 5–6 秒框架预热**：单页复核的第一次会慢（批量跑时被摊平）。
4. **分歧率现在有汇总的地方了，但捕获率没有**：产品内的质量统计（项目视图的「质量统计」卡片）
   给出"复核了多少行、一致 / 仅格式 / 汉字级 / 标点级各多少、分歧率多少"；
   但**捕获率与"一致但都错"需要人工金标准**，只能离线测量
   （`docs/ocr-evaluation.md` 第 8–9 节：捕获率 64.6%、改对率 24.6%、一致但都错 2.5%）。
   卡片底部如实列出这一条与另外三项没采集的指标（每页审校时间、恢复成功率等），
   见 `docs/decisions.md` D-041。
5. **只有一本书的实测**：9 节的判断依据来自 1 本中文排印本 / 40 页；
   英文、竖排、扫描退化、其他书的数字**都未测**，换书要复核（说明书 1.7）。
5. **块的行结构改过之后标记不可用**：人工在块里增删过换行，行号与复核时的行就对不上了，
   这时界面**不标**（`divergence.stale`）并说明"重新识别这一页可恢复"——
   按序号硬标会指错地方。
6. **"两路都错"的 39 行反而最值得看**：它们集中在引号、破折号、校勘符号这类**排版符号**上
   ——两个引擎在这类符号上都不行，这是下一步最有价值的改进方向。

### L-21 分段是启发式的，有三类已知失效场景

`core/structure/grouping.py` 按行距、缩进、对齐（说明书 8.1）把行组合成块。
规则本身有 21 项测试覆盖，但**启发式在以下场景会失效**，都已实测确认：

| 场景 | 现象 | 原因 |
|---|---|---|
| **右不齐（ragged-right）的英文** | 多行被并成一块 | "末行短"规则依赖版心右边界稳定；右不齐时行尾参差，右边界估不准。实测旋转页夹具（3 行英文）被并成 1 块 |
| **多行居中标题** | 可能被拆成多块 | 居中行左边界随行长变化，可能触发"缩进"规则 |
| **每页都有的竖排装饰边栏** | 被识别成"第 2 栏"，页面被标记"阅读顺序待检查" | 边栏的横向区间与正文不重叠，按说明书 8.1 就该标记待检查——但**会导致大量页面都带这个标记**，可能形成噪音 |

**已经有人工兜底：** 审校视图里可以合并 / 拆分 / 上移下移 / 新增 / 软删除块，
也能逐个改块类型（说明书 6.4 / 7.4 的结构编辑，2026-10-14 起可用）。
所有结构编辑都记事件、可撤销；分段错了不用重跑识别。

### L-22 块类型有批量工具和只读规则建议，界面已接；标题只能给 review

分段模块（`core/structure/grouping.py`）一律产出 `paragraph`——说明书也说块类型来自
**版面组件的建议或人工标注**，它不越权猜测页眉页脚。

现在有了两条人工路径：审校视图里逐个改类型，以及**页眉 / 页脚 / 页码批量标注**
（说明书 6.5，2026-10-14 任务 20）：位置规则 + 文本条件 → 预览 → 一次批量应用、
整批可撤销、不覆盖人工改过的类型。

**2026-10-22（任务 40）新增只读建议接口**：`GET /projects/{id}/pages/{page_no}/block-suggestions`，
与批量工具同一套块级规则（位置条带 + 字数 + 跨页重复 + 数字形态），只返回
"建议类型 ≠ 当前类型"的块，**不写库、不改类型**。第二本书 119 块实测：
页眉 9/9、页码 5/5、正文误标 0/98；书眉里夹着的页码会作为候选返回
（`2谁是巴赫金?11` → 候选 2 / 11，提示 11）。

**2026-10-22（任务 41）界面已接**：审校视图块头显示只读徽章
「页眉 · 把握较大 [采用]」/「标题 · 需确认」，点「采用」才走 `PATCH block_type`
（可撤销）；只有 high 能「采用全部建议」，review 必须逐条点；书眉里的页码只显示
「含页码 11（候选 2 / 11）」，**不自动拆块、不改文本**。建议不算"未审"待办；
页面视图缩略图右上角「建议 N」只数 high，且只为算过的可见页显示。**仍未做 / 未验证：**

- **标题建议仍是弱项**：只认 `第X回 / 第X章 / 目录 / 前言` 这类显式标记，
  实测 1/7，且**永远只给 review**；没有编号的加粗小节标题要字号 / 字重，规则看不见；
- **全书识别后的耗时未测**：每页建议接口都会读全书块做跨页重复统计，
  任务 40 的实测只在 119 块上做过；界面已限制"只为可见页请求、并发 2、缓存 200 页"，
  但没有在 7000 块的书上压测；
- **版面组件的建议**（说明书 8.4 的路线 B / C 未选定；结论见
  `docs/region-classification-eval.md` 第 6 / 8 节：页眉 / 页码不需要为它上模型，
  标题若要提升再说），说明书允许它作为"预填候选"，但必须先预览、绝不静默生效；
- **预览只有列表形态**：说明书 6.5 第 3 条想要"抽样展示若干页（原图 + 将被标注的块高亮）"，
  现在是候选列表（可逐个取消），图上高亮那一步还没做；
- **侧栏 / 竖排文字**：批量工具已支持**左右区域**（2026-10-14），
  本书左栏的竖排书眉 + 页码因此能被一次标掉（实测 37 块）；
  真正麻烦的是"整块横跨页面高度、又不在任何边缘条里"的装饰物——
  那类只能人工处理，或等版面组件（路线未选定）。

### L-18 OCR 峰值内存约 2.7 GB（只记录，未评级）

实测 RapidOCR 3.10.0（ONNX）处理 300 DPI 页面时**峰值内存 2686.6 MB**。
速度不是问题（中位 2.04 秒/页），**内存才是需要留意的**。

尚未验证：整书批量（400 页）时的内存行为、连续处理是否会持续增长、
在 8 GB 内存机器上是否可行。说明书 4.4/Phase 2 要求 OCR 跑在**子进程**里，
正是为了隔离这类问题，但子进程本身的内存上限还需要实测。

### L-11 识别 DPI 有了实测依据，界面还不能调

原问题：300 DPI 是初值，说明书 8.2 要求"DPI 默认值由样本测试决定"。

**2026-10-14：** 40 页真书实测后默认改为 **200 DPI**（正文 CER 1.08% vs 300 DPI 的 1.31%；
产品级导出正文 0.71% vs 0.94%；漏识少三成）。机理是检测模型对输入尺寸敏感
（同一行在 150/200/400 检出、在 250/300/500 漏掉）。见 D-037 与 `docs/ocr-evaluation.md` 第 7 节。

**仍未解决：**

1. **单本书的结论**：只在这一本干净栅格化的书上测过，换书 / 换扫描质量要复核；
   脚注与小字在低 DPI 下是否吃亏未测。
2. **界面不能调 DPI**：接口的 `POST /jobs/ocr` 支持 `dpi` 参数，但界面用默认值——
   说明书 6.3 的"识别样本 → 调整设置（语言、DPI）后重试"没有入口。
3. **缓解漏行的其它手段都没试**：页内切块（tiling）、多尺度兜底、检测阈值调整。
4. **界面渲染档位（`RENDER_PROFILES`）与识别 DPI 是两回事**，前者仍是初值。

### L-12 前端没有框架，也没有构建步骤

`backend/book2text/static/` 是手写的单页 HTML + 原生 JS。正式前端是
Vue 3 + TS + Vite（说明书 4.2），属于 Phase 1 及以后。当前页面只覆盖
Phase 0 第 4 项要求的"上传 PDF + 显示首页图像"，**不是**审校界面。

### L-13 API 不是最终设计

`/api/scratch/*` 是 Phase 0 临时接口。说明书第 11 节的正式接口以
`/projects/{id}/...` 为中心，要等 Phase 1 引入项目后才有。

## 4. 测试与质量保证（2026-10-14）

### L-05 有了真实书的金标准，但还不是"真实扫描件"的

原问题：没有人工校对的金标准，因此算不出 CER / 分歧率 / 捕获率。

**2026-10-14 进展：** 开发者提供了 40 页真实书页（无文本层）+ 对应文本
（`gold_standard/`，受版权保护、已 gitignore），并据此完成**第一次真实书的准确率实测**：
正文 CER **1.24%**（20 060 字，40 页），过程与三处口径差异写在
`docs/ocr-evaluation.md` 第 6 节。

**仍未解决的部分：**

1. **它仍不是"真实扫描件"**：与 `sample-20p-300dpi.pdf` 同源，是原生数字排版的
   **干净栅格化**，不含歪斜、噪点、透印、对比度不均——因此 1.24% **偏乐观**，
   不能用来预期旧书扫描件。
2. **口径已定（2026-10-14）**：开发者明确**只要正文**，页眉 / 页脚 / 页码按位置规则排除
   （结构工具已支持左侧 / 右侧区域——本书的竖排书眉贴在左栏，靠上下区域捞不到）。
   实测：41 块一次标掉、零误伤正文，导出里不再出现书眉与页码。
   **章首回目已补进金标准**（对照页图逐字核对后写入，原文件另存备份）；
   口径现在是"正文（含章回标题）对正文"。
3. **页边界是自动推导的草稿**：`金标准文本_分页草稿.txt` 里的 39 个〔PDF 第 N 页〕
   标记需要逐页人工核准（每页首句与末字），核准前不能用来算"按页 CER"。
4. **没有段落标记**：文本按回为一行，因此**分段准确率无法评估**（判别段落切分对不对）。

### L-20 合成语料的准确率只在"完美输入"下成立

`docs/accuracy-report.md` 里的数字（内容 CER 1.63%、英文 0%）来自合成语料，
**代表上限，不代表真实扫描书**。真实旧书的倾斜、噪点、透印、对比度不均
都会显著抬高错误率。此外该语料刻意集中了难例（生僻字、形近字符、多标号混排行），
因此行级一致率（忽略空白 55%）偏低不完全是引擎的问题，也是语料选择的结果。

**未验证：** 同一批页面上的 PaddleOCR 表现；真实扫描件上的任何准确率数字。

### L-17 样本集有两处覆盖缺口，且不是真实扫描件

`fixtures/pdf/sample-20p-300dpi.pdf` 由 `scripts/make_scan_samples.py` 生成，
有以下已确认的局限（详见 `docs/scan-sample-set.md`）：

**覆盖缺口（说明书 13.1 要求但这两本书给不出）：**

- **中文与中英混排**：安乐哲一书是纯英文（0 页含汉字），红楼梦该文件是纯中文
  （0 页含拉丁字母），两本都不含中英混排页。
- **低清晰度或倾斜页面**：源书是原生数字排版，不存在这类页面；人工合成不能代表真实退化。

**性质局限：**

- 源书是**原生数字排版 PDF**，本样本是它的干净栅格化结果，**不含**真实扫描件的
  倾斜、噪点、透印、对比度不均、半色调网点等特征。
  **OCR 在本样本上的表现会好于真实扫描老书，用它预期真实效果会偏乐观。**
- 源 PDF 的文本层**不可靠**：红楼梦文本层有错字（"薛蘅芜"→"薛祷芜"、"三宣"→"三宜"），
  渲染出的图像却正确。故该文本层既不能当金标准，也印证了"已有文本层未必可信"。

### L-16 仓库里没有真实书籍（`test_books/` 被忽略）

`test_books/` 由开发者放入，含两本受版权保护的整本扫描/电子书（≥13MB）。
它被 `.gitignore` 排除，因此**克隆仓库后拿不到这两本书**，相关渲染测量无法直接复现
（测量数据与文件名记录在 `docs/technical-feasibility.md`）。

**理由：** 版权（同 D-005）与体积；一旦进入 git 历史很难彻底清除。
**如需入库**，请先确认版权与必要性，并同步更新 `docs/decisions.md` D-005。

### L-15 Starlette TestClient 的弃用警告

运行测试时会打印一条第三方警告：`Using httpx with starlette.testclient is deprecated;
install httpx2 instead`（来自 starlette 1.8，经 FastAPI 的 TestClient 转出）。
测试全部通过，功能不受影响，属上游演进带来的噪音。等 FastAPI 跟进后再处理。

### L-35 合并审阅的冲突与结构变化两栏未在新界面实测

新界面的合并视图只在**块级修改**这一种分类上真机跑过（左页列表 / 中原图高亮 /
右逐条卡片 / 接受并提交）。**冲突**（负责人与助手改同一块）与**结构变化**（助手增删块）
的三栏对照只有后端测试覆盖（`tests/integration/test_collab_round_trip.py`），

### L-36 缓存里已有的旧界面不会自动失效，需要强制刷新一次

2026-10-15 起界面资源带 `Cache-Control: no-cache`（D-049），**之后**不会再出现"新页面配旧脚本"。
但在这次改动之前已经缓存过 `app.js` / `app.css` 的浏览器不会自动更新——那些缓存副本没有
任何缓存指令，浏览器可以继续按启发式规则复用。

**做法：** 升级后强制刷新一次（macOS `⌘⇧R`、Windows `Ctrl⇧R`）。若刷新后仍有"说不清哪来的
报错"，先按这个思路核对：页面、样式、脚本三者是不是同一个版本（本次的新头能保证以后一致）。

### L-37 块框的"实时"上限由 0.9 秒轮询决定

识别任务的每一页状态靠轮询（900ms 一次）得知，不是服务端推送。所以"这一页认完"
到"界面知道"最多要等 0.9 秒，再加上取块与渲染（实测 61–220ms）：
单页从识别完成到块框出现，最坏约 1.1 秒。**不会更慢，也不会更快**——
要更快只能换成 SSE / WebSocket 推送，本轮没做（本地单机继续用轮询，实现简单、可恢复）。

### L-38 网格滚动的帧率数字只能在同机对比，本机窗口上限约 30fps

同一个 ego 窗口里实测：空闲 rAF 间隔 p50 约 16.7–19ms，但一进入整本滚动就变成
p50 33.4ms；把块框关掉、甚至把 `updatePageVisibility` 换成空函数，p50 仍是 33.4ms。
也就是说**这台机器 / 这个窗口的合成刷新率只有约 30fps**，帧率数字不能和任务 44
记录的"约 60fps"直接比（那是在另一次窗口状态下量的）。
本轮只能确认"块框开 / 关两档相同（21.6 vs 21.7fps、32.9 vs 21.3fps，落在噪声里）"，
即**没有因为块框让滚动更卡**。

### L-39 预取的收益没有单独量化；整本全识别后的滚动未测

- 测试项目只有 49 页已识别（共 267 页），"每页都有几十个块"的极限情况没压过。
- 滚动预取的 A/B（运行时把 `pumpPageBlockPrefetch` 换空函数）落在噪声里：
  同一位置的"停下到出框"两次分别 51/101ms（开）与 11/44ms（关），方向不稳定；
  只确认了请求数受控（进入页面视图 21 个块请求、改前是整本排队）。
- 滚动中"已识别但暂时没框"的页最多同帧 11 个，每页空白持续多久没有逐页计时。

### L-40 页面视图的瓷砖位置缓存在隐藏视图里量不出来

`capturePageTileMetrics()` 现在拒绝记录高度为 0 的结果（否则 267 页全被判成可见，
D-062）。代价：如果页面视图在**隐藏状态下**滚动过，切回来时要等下一次可见性计算
（一帧）才恢复块框——肉眼不可见，但"刚切回来那一帧没有框"是预期行为。

### L-41 多行块在行中间拆开时，被切开的那一行只能整行归一边

一个轴对齐矩形表达不了"上面的行归前块、下面的行归后块"。所以多行块又切在一行中间时，
被切开的那一行**整行归文字多的那一边**（比例 > 0.5 归前块），另一边的框从相邻行边界
开始：两个框不重叠，但有一边少包了那一行（或被切开那行的另一半没有框覆盖）。
单行块（书眉 + 页码那种）不受影响：严格按字符比例横向切开，两块只在边界相接（D-063）。

### L-42 批量拆页码用"带 + 短块"收紧条件，版心内的页码不会自动命中

批量只收：已经是页眉 / 页脚 / 页码的块，或落在**页面上下 12% 带**里、整块 ≤ 40 字、
去掉页码后 ≤ 30 字且不含句子标点、页码数值 ≤ 全书页数的块。这样正文段落里的数字
（"1917 年 11 月"、参考文献里的年份）不会被整本拆坏；代价是**页码排在版心以内**、
或者书眉很长（> 40 字）的版式不会进批量，需要逐块用菜单里的「把页码 N 拆出去」。

### L-43 拆页码只处理"贴着块首 / 块尾"的数字

`page_number_candidates` 会列出块里所有像页码的数字，但只有一边是空白的候选才会被拆
（书眉 `11 导读巴赫金` / `2谁是巴赫金?11`）。夹在中间的数字一律不动——包括确实想拆的
那种（例如 `书名 11 章名`）。理由见 D-063：误拆正文的代价比漏拆高。

### L-44 全库扫描的耗时只在两个口径下量过

- 真项目《导读巴赫金》**已识别 49 页 / 328 块**：预览扫描 **27ms**，应用 **47ms**（65 块）。
- 合成满规模（直接写库的 267 页 × 30 块 = 8010 块，1 个书眉 + 1 个页码 + 28 段）：
  扫描 **450ms**，应用 **74ms**（534 块，一个事务）。
- **没有**在"267 页全部真实 OCR 后"的项目上量过（要识别十几分钟）；合成的块文本与坐标是
  规则的，但块数 / 页数量级与真书一致。

### L-45 自动应用只覆盖本任务的页；撤销要求"之后没有别的修改"

- 自动应用只改**这个任务里成功的页**。跨页重复统计用的是全书，所以一次只识别 2 页时，
  前两页可能因为"重复次数还没到 3"而拿不到 high——它们不会被补应用，需要手动
  「全库采用高把握建议」。
- 撤销自动应用要求这一批**之后没有别的批次写过事件**（用 `event.rowid` 判断）。
  用户在自动应用之后手改过任何东西，就只能先撤销那些修改；否则整批撤销会覆盖它们。

### L-46 自动应用不会拆"书眉 + 页码"粘在一起的块

自动应用只改块类型（`header` / `page_number` / …），不拆块。像 `2谁是巴赫金?11` 这种
一个块里既有书眉又有页码的，采用建议后整块变成 `header`，页码不会自动分出来——
`printed_page` 也为空（导出只从 `page_number` 块或纯数字的页眉页脚里取）。
要拿到印刷页码，用审校块菜单里的「把页码 11 拆出去」或页面视图的「批量拆分书眉页码…」。

### L-47 漏行检测只在两本书的排版上校准过

阈值是拿《导读巴赫金》的扫描件调的（第 3 页 24 个密集块、第 30 页正文页零误报）。
**没有**在以下版式上验证过：表格多（边框是墨迹但不是文字）、整页图（图注之外还有图内文字）、
竖排、双栏、页眉页脚带装饰线。已知的处理：宽高比 < 3 的条带不报（挡表格/竖排）、
插图装饰块盖住的区域不报、没有行记录的块盖住的区域不报（人工补过的块）。
误报仍可能有——它是**提示**，不自动改任何东西。

### L-48 "整页的字都没被认出来"这种情况检测不到

检测的前提是"这一页已经有行记录"：一行都没有时直接返回空（还没识别 / 整页无文本）。
所以如果一整页都识别失败了，不会有提示；它的补救是重新识别整页，不是漏行检测。

### L-49 框选识别每次都要渲染整页 300 DPI

实测 0.9–1.3 秒/块（含渲染与识别）。没有做"只渲染裁切区域"的优化（pypdfium2 的
render 接口按整页出图），也没有缓存渲染结果；连点多次会重复渲染。
框选时外扩 2% 是为了保留笔画，所以返回的行框可能比用户拖的框略大。

### L-50 拆分切行依赖"块文本与行记录对得上"

拆分时如果块文本被人工改过、和 `block_line.text` 对不上（前者不是以后者为前缀），
就不切那一行的文字与坐标，退回 R4 的旧做法（清空坐标与分歧信息）。
这时会多出一条"没有坐标的行"。理由是：把行记录按改过的文本去切会把它改坏。

  打架；收紧后不再参与。这个例子说明规则仍依赖"页码在上下边带"这个版式假设。

**缓解：** 预检显示"页码 K 页 / 已找到 42 / 未找到"；`printed_page_candidates` 列出候选，
冲突就是 null，不猜。用户可以逐页看 `meta.json` 核对。

### L-58 按版心判定时 `headers` / `edge_texts` 整个字段不写，`footers` 保留

**现状：** 用户明确要求"书眉直接丢：不单独保存、不进元数据"。实现是：开关打开时
`meta.json` 不写 `headers`，也不写 `edge_texts`（后者会把未标类型的书眉碎片漏回来）。
`footers` / `captions` / `figures` / `decorations` 仍保留——用户只点名丢书眉，没有说丢页脚；
如果某本书的页脚是重复性文字，它仍会出现在 `meta.json` 的 `footers` 里（但不进正文）。
`page_numbers` 只列**显式 `page_number` 块**的原文；混合书眉只把取到的值写进 `printed_page`，
不把整段书眉存下来。

**如果用户希望页脚也丢：** 改一个条件即可（`page_metadata` 的 margin 分支），但这是数据取舍，
需要先确认。

### L-59 "同时导出注释"默认关闭，旧工作流要重新勾选

**现状：** 任务 51 之前每次导出都会写 `notes.txt` / `notes.jsonl`；现在默认不写。
这是用户明确要求的"注释流改成可选、默认不勾"，但它确实改变了默认产物：
依赖 `notes.*` 的脚本 / 习惯需要勾上「同时导出注释」。
`manifest.stats.notes_count` 只统计本次实际导出的注释；预检仍显示可用条数（标注"未导出"）。
"开关关掉时行为完全一致"的逐字节验证是在**同样勾选注释**下做的，不包含这一项默认变化。

**缓解：** 导出面板的复选框在每次打开项目时回到未勾选（默认），但本次会话内保持用户的选择；
手动勾一次即可恢复旧产物。

### L-60 版心判定的 Windows / Safari 与触屏未验证

### L-61 行框高度当字号代理有反例

**现状：** 脚注的"字号较小"信号用块内 `block_line.bbox` 的平均高度与全书正文行框中位数比
（< 0.85 ×）。行框高度覆盖字形主体，通常能反映字号差，但**不是精确字号**：

- 《导读巴赫金》的脚注与正文几乎同字号：16 条真注释里只有 1 条命中"行高较小"（0.84×），
  其余 0.85–1.0×。这本书的脚注识别主要靠"位置 + 注释符号 / 间距"，不是靠字号。
- 只有标点、上标、孤字的行，bbox 高度会明显小于实际字号；竖排 / 旋转页的行框高度
  表达的是另一条边，不能当字号。
- 刻意用大字的脚注、或正文里的小字引文，会反向失准。
- 没有 `block_line` 的块（人工新增 / 老数据）直接放弃字号信号。

**缓解：** 字号只是四条信号之一；必须再有锚点（注释符号 / 行高较小）才给建议，
且永远 review。竖排书 / 双栏书不要指望字号信号（L-62）。

### L-62 脚注建议的漏报边界

**现状：** 为了不把正文误报成脚注，规则比任务书的"任意两条信号"更保守：

- 位置 + 间距两条**不够**，必须再有注释符号或小字号（真书第 5/6 页的"豆瓣id"就是
  位置 + 间距的误报，见 D-068）；
- 字数超过 120 的块按正文处理（第 30 页末段 170+ 字）；
- 没有注释符号、字号与正文相同、与上一块间距也不大的注文，四条信号只剩"位置"一条，
  会漏报；
- 中文数字页码 / 注释符号（"一、"）不在标记列表；只有 `1 ` / `①` 这类阿拉伯 / 圈号。
- 真书《导读巴赫金》在 56 个已识别页里人工核对的 16 条注文全部命中；没有发现
  带符号 / 小字号而漏报的块。但这个"16 条"是**已识别页**里的地面真值，未识别的 211 页
  没有核对。

**缓解：** 预检 / 审校视图里仍然是"需确认"，用户可以手动把漏掉的块标成 footnote；
下一步可以把"底部短行 + 与上一块间距大"做成一个提示列表，而不是直接建议类型。

### L-63 旁批建议依赖版心 / 页面左右两侧，且不覆盖 high 页眉

**现状：** 旁批 = 版心外左右两侧、≤40 字、不是纯数字。没有版心时退回页面左右 10%。
限制：

- 竖排书的左侧短行通常是**书眉**（"红楼梦\n6"），不是旁批；规则让 high 页眉优先，
  所以这类块不会给旁批建议（真书《红楼梦》40 页里 37 个左侧短行全部保持 header high）。
- 真正的旁批如果跨页重复 ≥3 次，会被判成 high 页眉，旁批建议不覆盖它；
  这是有意的安全取舍（high 页眉是更强的跨页证据）。高把握页脚则会被旁批 review 覆盖，
  避免 high 页脚把侧边短文本从正文里拿走。
- 超过 40 字的侧栏 / 边注不会给建议（避免把整段侧栏文本当旁批）。
- 双栏书的左栏正文在版心外（如果版心只框住右栏）会被误当旁批；这类书应先设对版心。

**缓解：** 旁批只给 review；用户可以在审校里手动改类型。竖排 / 双栏的版心需要先确认。

### L-64 自动推算的版心只用于显示 / 审校，不参与导出；页少时可能不准

**现状：** 识别收尾会自动算一次版心并写进项目（来源 `auto`）。限制：

- **导出不认自动版心**：页级「沿用全局」+ 来源 `auto` 时，导出退回块类型判定，
  直到用户点「采用为全局版心」。这是有意的安全取舍（D-069），但也会让人疑惑
  "版心视图里明明有框，预检却说未确认版心 N 页"——预检的说明文字会解释这一点。
- **页少时框可能只框住半页**：刚识别 2–3 页时，如果这几页是扉页 / 版权页 / 短页，
  自动框可能明显偏小（3 页合成样本实测下沿 49.9%）。审校默认会显示全部块、并提示
  "只用了 N 页"；用户点「版心内」才按框过滤。识别页数攒到 10 页以上、且建议可靠后，
  默认才回到"只列版心内"。
- **会移动**：识别页增加后自动框会小幅更新（≥30 页后通常 < 0.15 百分点/页，
  见 D-069 实测）；早期页少时会移动较大。手动采用后（`manual`）不再被自动覆盖，
  但"建议"仍会更新。
- **不适用于双栏 / 竖排 / 旁批多的版式**：推算算法本身仍是任务 50 的那一套（单栏横排校准），
  双栏取到整页外缘、竖排的边缘语义不同。这类书需要人工调框或标「不适用」。
- **清空后会重新自动填**：用户把全局版心清空后，下一次识别收尾仍会按"没有版心"自动写入。
  如果不想再自动，请把某一页/全局设成手动值，而不是清空。

**缓解：** 自动框只做显示；导出始终可按块类型（默认）。采用 / 手动拖框后行为与任务 50 一致。

### L-65 审校的「版心内 / 版心外」按几何判定，脚注在版心内时仍会出现

**现状：** 审校默认只列中心点落在版心内的块。判定**只看几何**（块中心点），不看块类型：

- 《导读巴赫金》的脚注印在版心内（第 28 页两条注文的 y 约 0.872–0.911，版心下沿 0.932），
  所以它们在「版心内」里，而不是「版心外」。这是"审校内容 = 版心内部"的字面结果；
  导出仍由类型层排除脚注（任务 51）。
- 页眉 / 页脚 / 页码在版心外，切到「版心外」就能看到并编辑。`版心内 N · 版心外 M`
  里的数字是**块数**，包含所有类型；不是"正文块数"。
- 页级「不适用」或项目没有版心时，过滤条收起、列表显示全部块（不隐藏）。
- 如果自动版心偏小、"暂时不准"，默认会显示全部块（见 L-64）；用户手动点「版心内」后
  可能看不到部分正文——列表顶部会写明"只用了 N 页"，切「全部」即可恢复。

**缓解：** 过滤条始终显示三个数量；原图上版心外的块是虚线 / 变淡，点它或框选新增时
会自动切到「全部」。后续可以考虑把"版心外的注文"按类型单独列一组，但那需要先确认
是否要隐藏注文，属于产品口径问题。

### L-66 识别设置的边界：RapidOCR 不换语言模型、双引擎不自动采用

**现状：** 识别设置（引擎 / DPI / 语言 / 双引擎策略）是项目级默认值，建任务时读入并写进
`job.params_json`；不是只写设置文件。限制：

- **RapidOCR 的语言**：包内只有中英混排模型（离线内置），`ch` / `en` / `mixed` 三档
  当前识别结果相同；没有实现按语言换模型（需要额外模型文件，且会破坏离线安装）。
  Apple Vision 会真正按语言切换（`en` 只开英文；`ch` / `mixed` 开中英两档）。
- **Apple Vision 作为第一引擎**：macOS 可用。它比 RapidOCR 弱（整页 CER 2.16% vs 1.08%），
  选它意味着用更弱的引擎做正文；界面没有拦，但报告与评测文档都写明。
- **双引擎比对**：第一路 RapidOCR + 第二路 Apple Vision，耗时约为单引擎的两倍；
  **不自动采用任何一方**。第二引擎的文本只作行级候选（`aux_text`），策略
  `只标分歧` 下连候选都不显示。
- **平台限制**：非 macOS 上 Apple Vision / 双引擎在界面置灰（由 `/api/app/info` 的自检
  结果驱动）；如果项目是在 Mac 上设好、拿到 Windows 打开，设置的仍是 Apple Vision，
  建识别任务会返回 503（明确说引擎不可用），不会静默改成别的引擎。**Windows 的置灰与 503
  只在代码逻辑与模拟中验证过，没有在真 Windows 上跑过。**
- **设置只影响下一次任务**：任务参数在创建时固定；识别中途改设置不会改变已经在跑的这次。
- **DPI 的耗时 / 内存提示来自单本书**：150 / 300 的实测耗时依书而异（`docs/ocr-evaluation.md`
  里 40 页真书：150 1.34s/页、200 2.13s/页、300 1.94s/页）；"200 DPI 单页峰值约 2.7 GB"
  是同一台机器上的量级，不是所有书 / 所有内存配置都成立。

**缓解：** 设置都能随时改回默认；引擎选择记录在任务参数与 `ocr_run.engine_id`，可追溯。

### L-67 四分区右栏在 14 寸屏需要滚动

**现状：** 页面视图右栏固定四个分区（页面设置 / 版心设置 / 页码设置 / 识别设置），
默认只展开前两块，页码与识别折叠。

- 本次实测窗口 1470×758：右栏可视高度 628px、内容 1630px，**需要滚动**。

- 折叠状态按项目存在浏览器 `localStorage`（`b2t.panels.v1.<项目 id>`），换浏览器 /
  清缓存后回到默认；这是界面偏好，不写项目数据库，也不随项目文件夹迁移。
- 页码设置这一刀只有说明文字，没有按钮（下一刀实现页码坐标与 PDF 页 ↔ 印刷页映射）。
- 页面设置的五个类型按钮顺序是固定的（前置 → 目录 → 正文 → 正文排除 → 后置），
  不受筛选或当前页类型影响。

**缓解：** 用户可以把不用的分区折叠起来，状态会记住；14 寸屏上首屏仍能看到页面设置

### L-68 页码模板依赖"位置稳定"，章首页 / 双页扫描 / 无 page_label 会受限

**现状：** 页码候选只收版心外 / 页边的短行，聚成最多 4 个位置模板。限制：

- **章首页的书眉位置会飘**：真书第 62 页的 `43` 比常规书眉更靠右（x 0.845 vs 0.771），
  超出模板容差（0.06），会被归为 `no_candidate`；这一刀不能给同一本书加第二套模板，
  所以这些页只能先留空。它们都在异常列表里，不会悄悄填错。
- **双页扫描 / 每页跳号**：红楼梦的页码是 4、6、8…80，位置模板能聚出来，但数值不是
  "每页 +1"，会被判为不可靠（`offset_break`），界面提示不建议采用；没有自动纠正。
- **没有版心时用页面四周 8% 边带**（任务书写"上下"；左右也收，否则竖排书的左侧页码
  会被漏掉）。页码如果落在更靠内的地方（例如 x=0.12 的竖排栏边），不会被收。
- **书眉里的页码需要 `page_label` 对号**：`2 谁是巴赫金? 11` 这类混合行，只有行内
  恰好有一个数字等于 `page_label` 才收；PDF 没有页标签 / 页标签不是印刷页码时，
  这类书可能一个模板都聚不出来（界面如实说"还没有可用的页码模板"，不乱填）。
- **同一页有多个数字**（边栏原书页码引用 + 书眉页码）：只按模板位置取一个；
  位置重合的多个不同值判 `ambiguous` 并留空。
- 这一刀没有"逐页手动改映射"，异常页只能先看，不能在这版里修。

**缓解：** 所有填充都经过"位置 + 数值"两道；异常页在列表里逐页列出。下一刀做逐页手动映射
与第二套页码范围。

### L-69 页码数值校验抓不到"全书整体偏移"这类错误

**现状：** 校验规则是"相邻页页码差 = PDF 页差"与"`printed_page - pdf_page` 偏移基本恒定"。
它能抓住单页断点（人为把第 60 页改成 99 → `jump` + `offset_break` 各 1），但抓不到：

- **全书整体偏移**：所有页都 +1 / -1 时，差值与偏移都自洽，校验通过。校验没有外部真值，
  只能用"这本书自己的页码序列"判断；模板取到的值本身是页面上印的数字，整体偏移通常意味着
  这本书的印刷页码本来就和 PDF 页号差这么多，不算错。
- **缺候选的页不参与连续性**：跨过缺页的两端只按 PDF 页差推算，所以缺失页本身不会制造
  `jump`；它们单独列在 `no_candidate`。
- **罗马 → 阿拉伯切换**：前后半本用两种数字体系时，按数值比较会被标成偏移突变；
  这是"如实报警"，不是自动识别章节编号体系。
- **同一个错误值重复出现**：两页都印同一个数字时，只按偏移可能只标其中一页；
  异常列表是提示，不是逐字校对。
- **直接改数据库**：这一刀没有手动映射入口；测试里把 `printed_page` 直接改成 99 能触发校验，
  但不会把 `printed_page_source` 标成 `manual`（下一刀才有这个入口）。

**缓解：** 校验只用于"把可疑页推给人"，不自动改任何值；模板不可靠时界面默认不建议采用。

### L-70 页码审校与第二套模板的边界

**现状：** 页码映射支持"默认模板 + 若干互不重叠的页码范围 + 逐页手动值"。限制：

- **页码范围只有一层**：范围不能嵌套、不能重叠；完全相同的范围重设会替换模板。
  要改边界只能先移除再重建。范围以外一律用默认模板；没有默认模板时，
  范围以外的页不会被自动填充。
- **范围页也要先识别**：模板按候选位置取页码，未识别的页即使落在范围里也没有值；
  它们会出现在 `not_recognized`，可以逐页手动填。
- **手动值限制**：只接受规范阿拉伯（≤4 位）或罗马数字（≤100）；不能填"见原书"这类文本。
  逐页保存（无批量粘贴），267 页逐页改会很慢——这是下一刀可以考虑的。
- **重复页码只警告**：`duplicate` 不自动改、不阻止导出；两页映射到同一个值仍然会原样写进
  `meta.json`。
- **导出 source 变化**：没有新映射的页从块类型 source 改成 `legacy`，老项目的
  `meta.json` 字节会变（`printed_page` 值不变）。这是任务书要求的来源区分。
- **导出不校验连续 / 偏移**：导出只写映射，不判断页码是否合理；异常只在页码审校界面提示。

**缓解：** 手动值优先且不被重算覆盖；范围重叠在接口层直接拒绝；重复页码在审校左栏有筛选。

### L-71 版面检测这一刀只有"文字行框"

**现状：** 阶段 2 只实现文字行检测，**没有**区域（图 / 表 / 装饰）、没有可靠的阅读顺序、
没有行类型。`LayoutLine` 只有 bbox / 置信度 / 阅读顺序（当前按从上到下、从左到右排）。

- **阅读顺序对双栏 / 竖排不可靠**：现在按 y 中心分档再按 x 排，双栏书会左右交错。
  后续要么做栏检测，要么沿用现有 `structure.grouping` 的栏判断。
- **多检一条**：真书第 30 页检测到一条无文字横线（y≈0.32，跨度很宽），整页 OCR
  在"识别结果为空"时把它过滤掉了。按检测行裁图识别时，这类行会得到空文本，
  必须记为 `empty` 进人工，不能静默丢。
- **检测成本不是零**：200 DPI 单页约 1.5 秒（整页识别约 4.8 秒）；整本 267 页
  预计 6–7 分钟，尚未做整本实测。
- **只验证了同模型同 DPI**：335 条 OCR 行与检测行 100% 匹配、偏差 0.0000，
  是因为两边都是同一个 RapidOCR det 模型；换检测模型 / 换 DPI 后是否仍然对齐未验证。
- **Windows / Safari 未验证**；Windows CI 只跑非 OCR 用例，不加载 RapidOCR。

**缓解：** 界面上明确写"只检测行框、不识别文字"；检测结果不参与识别与导出；
下一步按检测行裁图识别前，先在双栏 / 竖排书上单独验收对齐。

### L-72 页面工作流这一刀只记录，不驱动流程

**现状：** `page_workflow` 只写 `detected` / `ocr1_done`（以及回填的 `confirmed` /
`page_unconfirmed` / `excluded`），其余阶段留空。

- **不会自动推进**：没有自动通过、没有"继续未完成页"、没有导出预检的工作流计数、
  没有 manifest 状态快照；这些等后续切片。
- **页面类型改动不同步**：在页面视图把正文改成前置，工作流行不会立刻变成 `excluded`；
  下次打开项目回填不会覆盖已有行，所以可能一直显示旧状态。当前以页面类型筛选为准。
- **老项目的旧 OCR 不算"已识别①"**：回填时只到 `confirmed` / `page_unconfirmed`；
  只有新识别任务成功、或检测补上后连续判定到 `ocr1_done`，才会显示已识别①。
- **状态只前进**：`record_stage` 取最靠后的阶段；后续若需要"上游变了回退下游"，
  要按文档 2.4 的回退矩阵实现，不能只靠现在的 max。
- **界面筛选是只读角标**：工作流筛选不影响识别 / 审校 / 导出；"未走完"当前指
  `page_unconfirmed` / `confirmed` / `detected` 三类。

**缓解：** 状态表坏了可以从产物重建（`rebuild_page_stage`）；界面明确说明"只读索引"；
导出完全不读它，所以状态漂移不会污染语料。

### L-73 版心改读检测行后的边界

**现状：** 版心推算优先用 `page_layout_line`，没有检测行的页回退 `block_line`；界面与导出安全阀不变。

- **检测行没有块类型**：显式标注的 `header / footer / page_number` 在 OCR 路径会被整块跳过，
  检测路径只能靠"短行 + 页面上下 4% 带"过滤。宽书眉若落在 4% 带以内，理论上会参与推算。
  真书 14 页对比没有发生（检测行与 OCR 行四边只差六位小数舍入），但双栏 / 竖排 / 旁批书未验证。
- **混合数据源**：一本书里有的页有检测行、有的页只有 OCR 行时，按页各用各的（同页不混）；
  因此"全书版心"可能同时包含两种几何来源。建议先对全书做检测再定版心。
- **5 页时把握只有「中」**：参与页数 ≥5 才可靠，但 5–9 页仍会提示"参与页数较少"；
  真书 5 页检测的例子是把握中、可靠，不是高。
- **页码仍读 OCR 行**：页码需要文字，检测行没有文字；这一刀没动 `page_numbers.py`。
- **检测失败 / 取消的页**：没有检测行，回退 OCR 行；如果连 OCR 也没有，就不参与。
- **自动框仍不参与导出**：规则与任务 53 相同；采用为手动版心后导出才按它判定。

**缓解：** 先检测全书再定版心；宽书眉 / 双栏书用「推算版心」后手动微调；界面明确显示参与页数与把握。

- 没有真正的"区域级 + 生成式"第二意见；跨引擎第三方判断只剩在线仲裁（默认关、未实现）。
- 第一路与 Apple Vision 都错的行，差异分析抓不到；这是当前工作流的固有缺口，不是 bug。
- 保留的 `RegionOcrEngine` / `align_regions_to_lines` 只是接口位，没有实现、没有测试。
- GLM-OCR 的 200 DPI 22.7–27.3 秒/页、无坐标、噪声与忠实性结论见 D-075 / workflow 1.7；

**缓解：** 审校时把 Apple Vision 的分歧当"线索"而不是"答案"；导出前人工确认；在线仲裁实现后再补第三方意见。

### L-75 自动通过是"当时快照"，页面待处理依赖版面确认

**现状：** 自动通过只写 `page_workflow.confirm_mode=auto`；它不会因为之后的编辑自动撤销。
待处理页面筛选包含「版面未确认」，所以一本还没确认版面的书会显示几乎所有页都待处理。

- **后续编辑不自动撤销自动通过**：自动通过后如果又改块文本 / 类型 / 框，状态仍留着；
  需要用户手动「撤销自动通过」或重新人工确认。当前没有做"编辑即失效"的全局钩子，
  因为块编辑路径很多（PATCH / 拆分 / 合并 / 新建 / 删除 / 批量建议），
  只挂一两条会制造"有的编辑失效、有的不失效"的假象。
- **待处理页数可能很大**：版面未确认的页全部算待处理；确认版面后才会减少。
  这是有意的（不能把未确认版面的页当作审校完成），但对新书会显得很多。
- **漏行检测有成本**：页面视图「待处理」对"其他条件都干净"的页才跑漏行检测；
  全书已确认版面且无建议 / 分歧时，第一次筛选会逐页做图像分析，可能较慢。
- **单引擎页永远不自动通过**：即使文本看起来没问题，也必须先跑第二引擎复核；
  这是安全阀，不是 bug。
- **导出五项计数可能重叠**：人工 / 自动是确认状态，单引擎 / 版面 / 识别失败是独立条件；
  它们不相加，界面按"分别报数"显示，不伪造总数。
- **自动通过不参与导出正文**：导出仍按块类型 / 版心设置，状态只写 manifest 快照。

**缓解：** 审校时先按「待处理」处理块级问题，再逐页确认版面 / 版心；自动通过后若要改内容，
先撤销自动通过或重新人工确认；导出预检与 manifest 保留当时状态，事后可追溯。

### L-76 每页自动拟合的边界：5% 尾部、行不足与导出仍按旧口径

**现状：** 版心默认改为页级 `auto`（任务 62）：只用该页检测行里的正文长行拟合，
全局版心降为页内行不足时的兜底。它显著减少了"正文被全局框排除"，但不是万能的。

- **仍有约 0.28% 的正文长行边缘越界。** 真书 `b2t_YV1P2Y` 改后按中心点 **0 / 7888**，
  按行框任一边越出 **22 / 7888 = 0.28%（19 页）**（改前 51.27%、199 页）。
  实现里有两步补收：按相邻行距的安全扩张（`AUTO_SAFETY_GAP=0.034`，最多 3 轮，
  实测调出来的值）与"中心仍在框外的首尾正文长行"尾部回收（高度 ≤0.06 才收）。
  这两步参数在别的书上是否最优**未验证**；界面仍有单页审计提示。
- **37 / 394 页有效长行 <3，回退默认版心。** 这些页没有拟合框；若默认版心不是人工设置，
  自动通过时不算「版心已定」。界面显示「沿用默认版心（行不足）」，不是错误。
- **两个统计口径不能混读。** 改后"全部检测行中心在外"是 1325/10876 = 12.18%，
  比改前 1233 略高；但按行框四边，正文长行越界从 4044/7888（51.27%）降到 22/7888（0.28%）。
  改前那 1233 条基本都是短行（页码 / 边号 / 装饰），它们本来就被拟合过滤掉、**有意**留在框外；
  评估"正文被排除"必须用长行口径，而且最好看边缘越界，不只看中心。
- **`custom` / `none` 永远不覆盖。** 「全部改为每页自动拟合」只动 `auto` / `inherit`；
  想让某页回到自动拟合，需要先手动切回「自动拟合」或「沿用默认」。
- **每页拟合不参与导出。** `export_margin_box()` 没改：导出仍按全局 / custom 口径，
  `auto` 和旧 `inherit` 一样回退全局。所以逐页拟合不会改善"按版心判定正文"的导出结果；
  想把逐页框带进导出需要单独决策。
- **重检测会改框。** 检测行变化后 auto 框跟着变，这是预期行为；它不改文字、不重置审校，
  但用户如果已经按旧框看过，需要重看审计提示。
- **「页面准备」只有一条进度。** 检测 + 拟合合成一个 `layout` 任务，进度按页
  （`N / 总页数`）；已有检测行的页只拟合（很快），没有的页要先检测（较慢），
  用户从同一条进度里看不出当前页在跑哪一步。
- **未验证：** Windows / Safari；倾斜扫描、多栏、竖排页的拟合；只有少量行或大面积插图的页。

**缓解：** 看「页面准备」右栏的汇总（拟合 N 页 / 行不足 N 页 / 自定义 N 页）与单页审计提示；
对提示页拖动版心或切「本页自定义」；导出前若要按版心判定，先确认全局 / custom 口径符合预期。

### L-77 差异线位置是估算的；缺字 / 多字暂不画

**现状：** 审校左图的差异线按"字符推进宽度"估算，不是字符级 bbox（后端没有这个数据）。

- **没有页头「≠ N 行 · 从第一处」按钮。** 页头横幅仍有计数；页面级跳转下一刀再补。

- **没有键盘上一处 / 下一处。** `Alt + [ / ]` 需要先在 Chrome / Edge / Safari 做冲突测试，

- **267 页连续翻页抽验只检查了标题与标记层存在，不逐页截图核对位置**；逐字命中率目标

- **未验证：** Windows / Safari；触屏与 <1180px 上下布局；缩放 <40% 的行级降级
  （设计稿要求行高 <9px 退成整行下划线，本刀还没有专门分支）。

**缓解：** 左图标记只回答"看哪里"，等级文字永远在右侧差异行；当前行有端须；
发现位置偏时以右侧 `A→B` 与 textarea 选区为准，不要只信线的左右位置。

### L-78 页面右栏 628px 预算是按真机尺寸算的，长文案 / 窄屏仍可能破

**现状：** 任务 64 把右栏重排成"摘要 + 手风琴 + 底条"，在 1440×758 的

- **长文案可能把分区头 / 摘要撑成两行。** 书名、模板 label、异常描述很长时，

- **页码异常分析有一次较重请求。** 右栏会调 `/page-numbers` 取模板与异常计数；

- **手风琴默认只在首次打开项目时选。** 之后以用户手动展开 / localStorage 记录为准；

- **未验证：** Windows / Safari、触屏、1180px 以下上下布局、系统 200% 缩放。

**缓解：** 在 14 寸真机上按 628px 复核一次；发现某分区超了，优先把说明再收进 ⓘ，
不要把底条改成随内容滚动。

### L-80 收尾面板的 K、停止续跑与真实书数据边界

**现状：** 任务 66 的六状态面板与两个批量动作都按真实数据工作，但仍有几处边界。

- **真实书可能 0 页可自动通过。** `b2t_YV1P2Y` 有 1733 行第二引擎分歧 + 页眉建议，
  覆盖全部正文页，所以面板显示"0 页可直接通过、394 页要人看"，按钮隐藏；
  这不是 bug，是第二引擎质量 + 建议的结果。干净样书可验证批量动作。
- **停止状态只在当前会话。** `finishLayoutRemaining` / `finishAutoRemaining` 存在
  前端内存，刷新页面或关项目就丢；已经写入后端的确认不会回退，但"续跑"要重新点。
- **K 不是导出预检。** K 只数六个收尾状态；页码"可跳过"未定位时 K 会是 5/6，
  即使导出不被拦。页码的"显式跳过"动作还没做。
- **批量版面按 25 页/批、自动通过按 10 页/批。** 停止时当前批会跑完，剩余页从下一批继续；
  不是逐页取消。某批失败时该批及之后仍未确认，需要重试。

### L-81 已 ack 的差异默认折叠，自动通过仍受其它条件约束

### L-99 踩过的坑：`OcrParams(dpi=0)` 让第二引擎拿不到语言（任务 64 修正）

**现象：** 英文页第二引擎（Apple Vision）的 F1 只有 **0.47**；只开 `en-US` 时是 **0.90**。
它不报错、不告警，只是**静默降质**——审校队列里因此多出大量假差异
（双语书 2,351 条标点差异里，`[英] 引号→无` 728 行几乎都是它造成的）。

**根因：** `recognition._read_one_line()` 给行图传的是 `OcrParams(dpi=0)`，**没带 language**。
Vision 默认中英两个模型都开，中文模型在英文行上把撇号读成空格或直接丢掉
（`She'll` → `She ll`；页 36 实图可核对）。项目级语言设置根本没传到适配器。

**修法：** 按页判定语言（`core/ocr/language.py`，结果落 `page.ocr_language`），
行图识别带上 `OcrParams(dpi=0, language=<页语言>)`。

**修正后的实测（双语书副本，20 个英文页）：**

| 指标 | 文字层 aux | Vision（按页 en-US） |
|---|---:|---:|
| 差异行 | 409 | **162** |
| 撇号 `'` | 549 | **756** |
| 孤立 `1`（把 I 认成 1） | 7 | **1** |

**教训：** 凡是"引擎参数从上层传下去"的地方，都要有一条断言把**参数真的到了适配器**钉住；
没有它，这类 bug 只会以"质量差"的形式出现，永远不会抛异常。

## L-100 · 印刷空页会让"第二引擎复核"任务以 failed 收尾（已修，2026-10-28）

## L-101 · 版心置信度规则默认"两端对齐"，会把左对齐（ragged-right）的英文书判成低可信（已修，2026-10-28）

**现象**：《安乐哲 译本处理》全书 638 页 / 11,917 行，版心建议报 `low`：
左右边缘覆盖率 74.6% / **11.7%**，理由是"左右边缘只覆盖 12% 的正文行，
各页的缩进 / 分栏可能不一致"。但这本书是**左对齐（ragged-right）**排版——
行右端天然参差，右边缘覆盖率低是正常的，不是双栏。**大多数英文书都是这样。**

**根因**：`suggest_from_page_boxes` 用 `coverage = min(left, right)` 判可靠，
等于假设"两端对齐"。另外 `worst = max(四边 spread)` 把"章末页只排半页"造成的
下边缘离散（3.5%）也当成不稳定。

**修复**（三条一起）：

1. **左右与上下的离散分开看**：左右 ≤3% 才可靠，上下放宽到 ≤7%
   （章末页最后一行常常只到半页，这是排版事实，不是识别抖动）；
2. **只要求"有一侧贴整齐"**：左对齐的书左侧覆盖率 75%、右侧 12%，这一侧就是对齐边；
3. **但参差那一侧的"外边界"必须稳**：看每页最左/最右端的中段离散（≤2%）。
   只靠覆盖率会放过"整个版心在逐页漂移"的书（单元测试里那种左右各页相差 40% 页宽），
   加上这一条才安全。

改完后这本书：`medium` / reliable=True；参差排版会附一句
「这本书是「左对齐」排版：左侧有 75% 的行贴边，右侧参差（12%）是正常的，不是双栏。」

## L-102 · 页码可能在文字层里、而且不是"纯数字行"（2026-10-28）

**现象**：同一本书的页码定位只找到 1 个候选模板、覆盖 5 页、`reliable=false`，
等于没有页码。真正原因有两条，缺一不可：

1. 页眉印的是 **`Page 31`**（带词的数字），而候选收集只认 `canonical_page_value`
   （纯数字 / 罗马数字）；
2. 那行页眉的位置**在版心框内**，而 `_position_ok` 只收"版心外"的行。

**修复**：数字原生 PDF（≥80% 正文页有文字层）额外从**文字层**的页眉 / 页脚取候选：
`^Page N$`（以及贴边的裸数字）。页码是**结构化信息**，文字层里就是准确的那几个字，
用它不违反"不拿文字层当第二引擎"（那条要的是"对同一行给出另一个读数"）。

**这本书仍然没有得到可用的页码模板**：270 页取到了 `Page N`，但
`Page 28` 在 PDF 93、`Page 65` 在 PDF 172、`Page 108` 在 PDF 263 ——
印刷页码每页只涨约 0.53，偏移从 65 一路涨到 192。
也就是说 **`Page N` 不是本书的连续页码**（PDF 页数是它的约 2.25 倍），
拿它当锚点会把目录确认指到错页。所以保持 `located: false` + `skippable: true`，
界面上明确告诉用户"这本书没有可用页码，目录确认只有 PDF 页序"。

## L-103 · 页图"清晰度"只量分辨率会漏掉模糊（已修，2026-10-28）

**现象**：用户连续四次报"审校页图糊"，而每一轮量出来的比例都很好：

```
size=view  naturalWidth=1275  页块 384 CSS px  dpr=2  →  比例 1.66
```

**根因**：`.is-placeholder` 带着 `filter: blur(1.5px)`（dpr 2 = 3 个设备像素），
加载完成后代码只 `delete image.dataset.placeholder`，**类没摘**，
高清图一直盖着一层永久模糊。比例与模糊是两件独立的事，比例永远量不出模糊。

## L-106 · 「错误不以红的形式出现」——今晚四起事故的同一形态（2026-10-28）

> **代码 bug 修一次就没了，判据 bug 会一直生 bug。**

**这一条不是某个 bug，是一类 bug 的识别方法。** 四起互不相关的事故，失败方式完全同构：**错误不以 FAIL 出现，而以"看起来像别的东西"出现。**

| 事故 | 报出来的样子 | 真正的原因 |
|---|---|---|
| 页图"糊"（连报四次） | 比例 1.66，看着像分辨率不足 | `filter: blur(1.5px)` 的类没摘，高清图盖着永久模糊 |
| "下一处未审"卡住不动 | 看起来像队列跑完 / 筛选逻辑错 | 数据口径：面板页 356 vs 正文流页 618 |
| `readingTreeOpen` 误删 | 看起来像环境问题（BLOCK + 120 秒超时，报告只写"左树页列表就绪超时"） | 控制台 8 条 `ReferenceError`，断言里一条都没有 |
| 三方页码不一致 | 看起来像"面板和顶部对不上" | 第三个量：左栏自己的滚动位置 |

**共同点**：**判据指向的是替代指标，不是根因。** 于是正确的东西被判成错的，错误的东西被判成环境问题。

**识别方法（可直接用）**：

1. **问一句"这个数字如果错了，它还能不能看起来对？"** —— 比例能看着对而图是糊的，通过率能看着高而页面是炸的。
2. **每个"通过"都要有一个能指向根因的证据**，而不是一个比它更容易测的代用品。
3. **修复类提交必须附「带 bug SHA vs 修复 SHA」对照**，同环境同输入、两次只差那个改动。**没有对照的"修好了"，只能算"现在不红了"。**
4. **控制台错误单列一行，不许藏进 BLOCK 原因里**——藏起来就等于没有。
5. **已知噪声（K1/K2）单列，不混进分子**——否则 42 和 43 的差别会一直被当成噪声解释。

**它的反面教训**：今晚判据本身错了四次（±30 行数守恒、668 行缺口、`grep punctLeft` 缺作用域、`grep buildReadingTree` 缺词边界/锚点）。**每一次都不是数据错，是判据错**——而判据错会让人去删活代码、判错正确的搬运、把 6 层合计当成 12 层。

### L-106 的递归版（Chief 补，2026-10-28）

**判据错，也不以"错"的形式出现。** 今晚四次判据错，每一次看上去都像一条正经的验收标准：

| 判据 | 它看起来像 | 实际 |
|---|---|---|
| 行数守恒 ±30 | 一条保守、讲纪律的验收线 | 没算骨架代码，把正确搬运判成 FAIL |
| 668 行缺口 | 一个精确的算术发现 | 读了 6 层合计当 12 层 |
| `grep punctLeft = 0` | 一条严谨的全仓库检查 | 缺作用域，会删活代码 |
| `grep buildReadingTree = 0` | 一条精确的名字匹配 | 缺词界，短名字吞长名字 |

**没有一条看起来是错的。** 这就是它们能通过自己那一关、被发现得那么晚的原因。

所以识别方法要用在判据自己身上：

> **这条判据如果错了，它会看起来像什么？**
> 如果答案是"看起来像一条更严格的判据"——那它最危险，因为它会被当成好习惯保留下来。

`±30` 那条就是这么活下来的：它看起来很讲纪律，所以没人怀疑它——**直到它把一个正确的搬运判成了 FAIL。**

**判据 bug 的寿命比代码 bug 长**：它还会被写成模板、派给别人、变成下一轮的标准。今晚 `±30` 就派给过 Builder，`grep punctLeft` 也派给过它——**没被拦住，是因为它看起来对。**

| 闸 | 漏法 | 实测 |

> 每个闸都要有一条"扫描器自检"：喂合成样例必须红（A5 已按此形态实现）。缺自检的闸，绿是默认值，不是结论。

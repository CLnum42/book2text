## 1. 应用能力（Phase 0 骨架，2026-10-14）

### L-09 没有项目与数据库

上传的 PDF 只落在应用数据目录的 `scratch/` 下，**不是正式项目**：没有项目库、没有
`project.db`、没有缩略图缓存、没有项目锁、没有自动备份。这些属于 Phase 1。
`core/storage/scratch.py` 是临时实现，Phase 1 应取代它。

### L-10 应用内的 OCR 只能识别单页，还没有"任务"

现在可以在界面上对**当前这一页**点"识别本页"，看到**块**（分段结果）与带坐标的行，
块框叠加在原图上。但离说明书 Phase 2 要求还差很远：

- **没有 Job / JobItem 执行器**：不能批量识别、不能暂停 / 继续 / 取消 / 重试失败页、
  不能中断恢复。每页都是同步识别、点一次跑一次。
- **没有 OCRRun 持久化**：识别与分段结果不落库，只在浏览器内存里缓存（刷新即丢）；
  结果不写 `ocr_runs/<run_id>.json`。
- **没有第二引擎 / 分歧检测**：说明书 8.5 的按行比对尚未开始。
- **不能保存 / 不能编辑**：识别结果与块的文本都不能改，退出即弃（见 L-21）。

### L-23 TXT 能导出了，但 JSONL 与 manifest 还没有

说明书第 9 节的实现进度：

| 小节 | 状态 |
|---|---|
| 9.1 段生成（含跨页拼接、标题单独成段） | ✅ 已实现 |
| 9.2 行合并规则（含断词还原） | ✅ 已实现 |
| 9.3 清理规则 | 🔶 五项中"排除页眉页脚页码"因块类型全是 `paragraph`（L-22）**当前无效**；其余四项已生效 |
| 9.4 TXT | ✅ 已实现 |
| 9.5 JSONL 与 manifest.json | ⬜ **未实现** |

**manifest.json 还没生成**：说明书 9.2 要求把"被断词还原处理过的位置"记入 manifest
便于抽查。记录**已经产出**（`HyphenationRestore`，预检里也显示处数），但写入 manifest
属于 9.5，待做。

**导出文件不落盘**：说明书 4.5 要求导出写入项目的 `exports/` 目录并配
"在文件夹中显示"。当前由浏览器直接下载，服务端不写文件——因为没有项目目录（L-09）。

**没有"仅已确认"之外的导出范围**：预检里的未审校 / 不确定段数已经统计出来，
但审校状态本身还不存在（Phase 3）。

**断词还原可能误处理**：说明书自己也提示 `self-` + `evident` 这类真实连字符
可能被误删。目前只记录，界面上无法人工校正。

### L-24 导出是"本次会话"的范围，且接口是无状态的

导出接口 `POST /api/export/txt` **不读数据库**——它接收客户端提交的块（含原始行与标记），
跑完 9.1 / 9.3 / 9.4 后返回文本。原因是没有持久化（Phase 1/2 未做），
服务端看不到客户端手上的识别结果。**规则实现只有服务端这一份**，客户端不懂拼接与分段。

由此产生三条限制：

1. **导出范围 = 本次会话中已识别过的页面。** 没有批量识别（L-10），
   所以要先逐页点"识别本页"，没识别过的页不会出现在导出里。刷新页面即全部丢失。
2. **块级标记也只存在于当前会话。** "纳入导出"与"延续到下一页"是说明书 5.3 的
   `include` 与 `continues_to_next`，是真实的块操作；但没有持久化，刷新即丢。
3. **预检与导出合并成了一个接口**。说明书 11 分成 `/export/preflight` 与 `/export` 两个；
   这里一个响应同时返回 `preflight` 与 `text`。属临时形态。

### L-21 分段是启发式的，有三类已知失效场景

`core/structure/grouping.py` 按行距、缩进、对齐（说明书 8.1）把行组合成块。
规则本身有 21 项测试覆盖，但**启发式在以下场景会失效**，都已实测确认：

| 场景 | 现象 | 原因 |
|---|---|---|
| **右不齐（ragged-right）的英文** | 多行被并成一块 | "末行短"规则依赖版心右边界稳定；右不齐时行尾参差，右边界估不准。实测旋转页夹具（3 行英文）被并成 1 块 |
| **多行居中标题** | 可能被拆成多块 | 居中行左边界随行长变化，可能触发"缩进"规则 |
| **每页都有的竖排装饰边栏** | 被识别成"第 2 栏"，页面被标记"阅读顺序待检查" | 边栏的横向区间与正文不重叠，按说明书 8.1 就该标记待检查——但**会导致大量页面都带这个标记**，可能形成噪音 |

**没有加人工兜底：** 用户目前**不能**手动合并 / 拆分块、也不能改块类型。
说明书 6.4 / 7.4 要求的结构编辑（合并、拆分、移动）属于 Phase 3，尚未实现。
因此现在分段错了只能重跑识别，改不了。

### L-22 块类型一律是 paragraph

说明书 5.3 的 `block_type` 有 heading / paragraph / header / footer / page_number /
footnote / caption / other 八种取值，但来源是**版面组件的建议（需预览确认）或人工标注**。
本模块不越权猜测，因此**现阶段所有块都是 `paragraph`**。

后果：说明书 6.5 的"批量标注页眉 / 页脚 / 页码"、9.3 的"按块类型排除页眉页脚"
都还没有数据基础。页脚页码目前会被当成普通段落参与后续处理。

### L-18 OCR 峰值内存约 2.7 GB（只记录，未评级）

实测 RapidOCR 3.10.0（ONNX）处理 300 DPI 页面时**峰值内存 2686.6 MB**。
速度不是问题（中位 2.04 秒/页），**内存才是需要留意的**。

尚未验证：整书批量（400 页）时的内存行为、连续处理是否会持续增长、
在 8 GB 内存机器上是否可行。说明书 4.4/Phase 2 要求 OCR 跑在**子进程**里，
正是为了隔离这类问题，但子进程本身的内存上限还需要实测。

### L-11 渲染 DPI 是初值，不是结论

`core/pdf/render.py` 里的档位（thumb 40 / view 150 / zoom 300 DPI）是**待验证的初值**。
说明书 8.2 明确要求默认值由 Phase 0 样本测试决定。目前没有真实扫描样本，
无法评估"150 DPI 够不够看清小字"或"300 DPI 的每页耗时可接受吗"。

### L-12 前端没有框架，也没有构建步骤

`backend/book2text/static/` 是手写的单页 HTML + 原生 JS。正式前端是
Vue 3 + TS + Vite（说明书 4.2），属于 Phase 1 及以后。当前页面只覆盖
Phase 0 第 4 项要求的"上传 PDF + 显示首页图像"，**不是**审校界面。

### L-13 API 不是最终设计

`/api/scratch/*` 是 Phase 0 临时接口。说明书第 11 节的正式接口以
`/projects/{id}/...` 为中心，要等 Phase 1 引入项目后才有。

## 2. 仓库与账号（2026-10-14）

### L-03 许可证未定，仓库不可公开

仓库已推送至 `git@github.com:CLnum42/book2text.git`，仓库为**私有**，未添加 `LICENSE`。
在许可证确定之前，**不得转为公开、不得对外分发**（见 `docs/decisions.md` D-006、D-008）。

### L-07 GitHub PAT 无法访问本仓库（gh 命令会失败）

`gh` CLI 使用的细粒度 PAT 范围为**"仅选定仓库"**，`book2text` 不在其中
（实测 `gh api repos/CLnum42/book2text` 返回 404）。因此针对本仓库的
`gh repo view`、`gh issue`、`gh pr` 等命令**都会失败**，这是权限问题不是仓库问题。

**绕过方式：** 日常用 `git` 命令即可（走 SSH，不受 token 范围限制）。
**状态：** 待处理（不影响 git 推送与拉取）。

### L-08 SSH 密钥无口令

`~/.ssh/id_ed25519` 未设置口令（为支持免交互推送）。任何能读取该文件的进程或人都可以使用
你的 GitHub 写权限。私钥权限为 `600`。如需更高安全性，为密钥加口令并配合 `ssh-agent`。

## 4. 测试与质量保证（2026-10-14）

### L-05 真实扫描件的金标准仍未制作（Phase 0 的阻塞项）

**样本已部分就位（2026-10-14）**：`fixtures/pdf/sample-20p-300dpi.pdf`，20 页，
无文本层（实测字符数 0），逐页来源见 `docs/scan-sample-set.md`。

**合成金标准也已就位（2026-10-14）**：`fixtures/gold/synthetic-corpus.json`，
82 行 / 2737 字，比对工具链已在其上验证（`docs/accuracy-report.md`）。

**但真实扫描件的金标准仍然不存在**，而它才是 Phase 0 判断引擎能否用于真实旧书的依据。
合成语料是完美字体、无扫描退化，在其上测得的准确率（中文内容 1.63%、英文 0%）
**不能外推**。金标准必须由开发者对照页面图像逐字抄录（人工工作）。

### L-20 合成语料的准确率只在"完美输入"下成立

`docs/accuracy-report.md` 里的数字（内容 CER 1.63%、英文 0%）来自合成语料，
**代表上限，不代表真实扫描书**。真实旧书的倾斜、噪点、透印、对比度不均
都会显著抬高错误率。此外该语料刻意集中了难例（生僻字、形近字符、多标号混排行），
因此行级一致率（忽略空白 55%）偏低不完全是引擎的问题，也是语料选择的结果。

**未验证：** 同一批页面上的 PaddleOCR 表现；真实扫描件上的任何准确率数字。

### L-17 样本集有两处覆盖缺口，且不是真实扫描件

`fixtures/pdf/sample-20p-300dpi.pdf` 由 `scripts/make_scan_samples.py` 生成，
有以下已确认的局限（详见 `docs/scan-sample-set.md`）：

**覆盖缺口（说明书 13.1 要求但这两本书给不出）：**

- **中文与中英混排**：安乐哲一书是纯英文（0 页含汉字），红楼梦该文件是纯中文
  （0 页含拉丁字母），两本都不含中英混排页。
- **低清晰度或倾斜页面**：源书是原生数字排版，不存在这类页面；人工合成不能代表真实退化。

**性质局限：**

- 源书是**原生数字排版 PDF**，本样本是它的干净栅格化结果，**不含**真实扫描件的
  倾斜、噪点、透印、对比度不均、半色调网点等特征。
  **OCR 在本样本上的表现会好于真实扫描老书，用它预期真实效果会偏乐观。**
- 源 PDF 的文本层**不可靠**：红楼梦文本层有错字（"薛蘅芜"→"薛祷芜"、"三宣"→"三宜"），
  渲染出的图像却正确。故该文本层既不能当金标准，也印证了"已有文本层未必可信"。

### L-16 仓库里没有真实书籍（`test_books/` 被忽略）

`test_books/` 由开发者放入，含两本受版权保护的整本扫描/电子书（≥13MB）。
它被 `.gitignore` 排除，因此**克隆仓库后拿不到这两本书**，相关渲染测量无法直接复现
（测量数据与文件名记录在 `docs/technical-feasibility.md`）。

**理由：** 版权（同 D-005）与体积；一旦进入 git 历史很难彻底清除。
**如需入库**，请先确认版权与必要性，并同步更新 `docs/decisions.md` D-005。

### L-14 没有 CI

`tests/` 已有 57 个测试（单元 + 集成），但全部靠本机手动运行 `uv run pytest`。
没有 GitHub Actions，推送不会触发任何自动检查。

### L-15 Starlette TestClient 的弃用警告

运行测试时会打印一条第三方警告：`Using httpx with starlette.testclient is deprecated;
install httpx2 instead`（来自 starlette 1.8，经 FastAPI 的 TestClient 转出）。
测试全部通过，功能不受影响，属上游演进带来的噪音。等 FastAPI 跟进后再处理。

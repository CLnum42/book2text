# 目录页图 / 当前项高亮 / 标点差异按模式批量（任务 61）

> 2026-10-28。用户真机三条反馈，全部在**项目副本**上验收（真书库没碰）。
> ③ 的数字与 Chief 的口径一致（本机副本多出 14 行、9 种模式，见文末对账）。

## ① 目录确认页图不显示 —— 根因是图 "永远到不了"，不是渲染失败

### 实测：接口没问题

```
GET /api/projects/b2t_GYM9VE/pages/1/image?size=view
→ 200, image/png, 1,773,131 字节（932 × 1405）
GET …/pages/35/image?size=view → 200, 1,002,442 字节
不带 token → 401（说明不是"没权限还静默成功"）
```

`render.render_page_png` 单页 0.14–0.30 s。所以不是"渲染失败被吞掉"，也不是"返回空图"。

### 真正的根因（已在浏览器里稳定复现）

目录确认的页图是一张一张排队加载的（`pumpIndexImages`）。原来的代码：

```js
const ok = await new Promise((resolve) => {
  image.onload = () => resolve(true);
  image.onerror = () => resolve(false);
  image.src = url;
});
```

而滚动 / 跳页时 `releaseIndexImage()` 会把**还在加载**的图的 `src` 摘掉：

```js
if (!image || !image.dataset.src) return;
image.removeAttribute("src");   // ← 摘 src 既不会触发 onload，也不会触发 onerror
```

摘掉 src 之后那个 `Promise` **永远不 resolve** → `pumpIndexImages()` 的 while 循环卡死 →
`indexImagePumping` 一直是 `true` → **这一次会话里后面每一页都不会再去拿图**。
所以页面区域只剩页纸底色（`--page-paper` 的灰）+ 块框，用户看到的就是"一整片灰、块框还在"。

复现（headless Chrome，真书副本，脚本见 `docs/development-log.md` 任务 61）：

```
queue 150 → 0.05 s 后 releaseIndexImage(150)（模拟滚动离开）
→ pump: true（卡住）  +2s/+4s/…/+12s 一直是 true，queue 0
→ 第 150 页 img.dataset.pending 永远停在 "1"
```

第二个问题：唯一的提示 `#index-image-status`（"正在渲染…"）挂在 490 个页块**之后**
——大约 80 万像素下方，用户永远看不见。所以"为什么没图"没有任何解释。

### 修法

- `waitForImageLoad()`：每次加载都带 **10 s 超时**，`onload` / `onerror` / 超时三选一，
  **一定会 settle**；失败自动重试 1 次；
- `releaseIndexImage()` 遇到正在加载的图**只做 `cancelled` 标记**，等它自己结束再清理，
  绝不摘 src；
- 连续两次失败 → 页块里出现「这一页的图像读不出来 · 点这里重试」（可点，实测重试 1 s 出图）；
- 状态条挪到页列**前面**并吸顶，写清在等哪一页：「正在渲染第 30 页…（第一次打开需要几秒）」。

验收（副本 `b2t_GYM9VE`，490 页）：

| 项 | 结果 |
|---|---|
| 进目录确认，页图 | 页 30 图 1 s 出来（932 px 宽，正常显示） |
| 触发旧 bug 的条件（加载中释放） | `pump` 不再卡死（`indexImagePumping: false`），后续页继续加载 |
| 人为让一页失败 | 出现「图像读不出来 · 点这里重试」；点重试 1 s 成功；状态条同时写明原因 |
| 状态条位置 | 页列上方吸顶，进视图就能看到 |

截图：`docs/screenshots/index-toc-page-labels.png`（页图 + 目录页标签）、
`docs/screenshots/index-image-failed.png`（失败态 + 重试）。

### 顺带：那句「4 页未识别页码」

不是页码丢了，是**分类没认"目录页"**。用户把这本书的 4 页前置页改成了 `toc`
（新项目 `b2t_GYM9VE`：front 30 / toc 4 / back 20），而缺页码的分类只认
`front` / `back` / 回目页，`toc` 落进了"未识别页码"。

现在多一类：`toc` → **「目录页 · 不印页码」**，摘要也单列
`490 页 · 418 页有印刷页码 · 18 章 · 50 页前置/后置 · 4 页目录页 · 18 页回目页`，
`missing_unknown` 归 0（原来那 4 页确实是第 30–33 页的 Contents）。

## ③ 标点 / 空格差异：按模式批量

数字（真书副本 `b2t_YV1P2Y`，394 页）：

| 项 | 值 |
|---|---|
| 差异行合计 | 1629（含汉字 902 / 纯标点 727） |
| 纯标点分组 | **73 种模式**（Chief 在真库上是 64 种） |
| 前 50 种覆盖 | 701 / 724 行（96.8%） |
| 耗时（分组） | 0.35 s |

前几种模式：`；→，` 303 行、`∅→‘` 124 行、`∅→”` 50 行、`∅→—` 44 行、`∅→——` 19 行、
`—→∅` 17 行、`”→∅` 13 行、`∅→␣` 12 行、`∅→，` 10 行……与 Chief 的表逐条对得上。

**做法：**

- 模式按**差异片段**分组（`difflib.SequenceMatcher` 的 replace/insert/delete 段），
  不是整行文本——否则 710 行会变成 710 种"模式"。同一行里同样的片段只算一次。
- 主队列（左树 / 进度 / 下一处未审）只放**含汉字差异**的行；纯标点行交给
  「标点差异 · 按模式批量」面板（`review/marks` 给标点行带 `pattern_key`）。
- 面板每组：模式、行数、**5 条带页码的样例**、三个动作
  **全部采用候选 / 全部保留原文 / 逐条看**。
  「逐条看」把这一组放回主队列（存 localStorage，不改库）。
- 裁决落到**行级** `diff_ack`（和逐条审同一份数据）：队列、进度、导出、撤销全同步，
  不引入第二套"模式级状态"。
  - 采用 = 把那一行换成第二引擎的文本（真的改文本）；保留 = 只写 ack；
  - 一组一个 batch → **撤销一次全退**。

验收（HTTP，副本）：

```
批量采用 ；→，  → applied 303, skipped 0, 1.06 s, history.undo = 1
面板数字         → 724 行 / 73 组 → 421 行 / 72 组
撤销            → changed_blocks 606，数字回到 724 行 / 73 组
```

界面实测（headless Chrome）：

| 项 | 结果 |
|---|---|
| 面板 | 73 组；首组 `；→，` 303 行、5 条样例、三个按钮 |
| 判 `∅→，`（10 行）采用 | 徽标 724 行·73 组 → **714 行·72 组**；底部「最近一次：∅→， 全部采用 10 行」 |
| 撤销最近一次 | 回到 724 行·73 组 |
| 逐条看 | 该组行回到主队列（徽标显示"已转为逐条"） |

截图：`docs/screenshots/punct-groups-panel.png`、`punct-groups-after-decide.png`。

**完成判定**：标点行也是行级 ack，所以"所有模式都判过"就等于"这些行都有裁决"，
收尾面板的待办自然归零，不需要另加一套判定。

## 没验的 / 要你知道的

1. **首图仍可能慢**：应用刚打开、后台还在拉 490 页的树 / 摘要时，第一张 `size=view`
   实测 6.4 s（空载 0.14–0.30 s）。现在**会说明在等什么**、失败会重试，但没有做磁盘缓存
   （`cache/view` 仍是空的；一页 150 DPI 的 PNG 约 1.7 MB，490 页约 830 MB，需要另定上限策略）。
2. **主队列与收尾面板的数字口径不同**：阅读流"已处理 X / 902"只算汉字差异；
   顶栏与收尾面板仍是行级全量（1629，含标点）。两处都真实，但用户会看到两个数——
   进度条后已加「（另有标点 724 行）」，要不要统一成一个数需要产品拍板。
3. **撤销只退最近一次**：面板上的「撤销最近一次」调的是同一个撤销栈；
   判了 A 组再判 B 组后想撤 A，只能先撤 B（界面上按钮的 tooltip 写明了）。
4. 与 Chief 的数字差异（724 / 73 vs 710 / 64）：本机副本比真库多 14 行、9 种模式，
   前 9 种模式逐条一致；差异来自副本与真库的编辑历史不同（真库跑过字框回填），
   不是口径问题。

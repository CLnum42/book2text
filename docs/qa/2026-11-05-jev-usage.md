# Jev 审校队列排序 · 施工配方（交给 Builder）

> 用途：只对**两引擎分歧的行**打分，按分数升序排进审校队列。**不替代第二引擎。**
> 全部数字来自 2026-11-05 在 `b2t_H6GXVG`（40 页 / 1054 行）上的实测。

## ① 模型与体积

| 文件 | 字节数 | sha256 |
|---|---:|---|
| `MiniCPM-OCR-Jev-Q8_0.gguf` | **2,012,021,120** | `7e5227dd810ab20c56076750cb8eeb9bbe3ea52d1b84263975ba64566e30a746` |
| `mmproj-model-f16.gguf` | **671,372,416** | `cad9364b900f79a90c12e371aa07a7cb901966c9f673262379c31b051eeb313a` |

- 来源：ModelScope `OpenBMB/MiniCPM-OCR-Jev-gguf`（HF 被墙时用这个域名即可）。
- 落盘：任意固定目录，建议跟项目数据放一起（不进安装包，2.7 GB 太大）。
- 校验（下载后第一条命令）：
  ```bash
  shasum -a 256 MiniCPM-OCR-Jev-Q8_0.gguf mmproj-model-f16.gguf   # 必须与上表一致
  ```

## ② 引擎（llama.cpp）

- 版本：**llama.cpp 0.8.0**（brew 装，`/opt/homebrew/bin/llama-server`）。
- 启动（Metal，实测加载 ~2.1 s，常驻 **2056 MB**）：
  ```bash
  llama-server -m MiniCPM-OCR-Jev-Q8_0.gguf --mmproj mmproj-model-f16.gguf \
               -ngl 99 -c 32768 --port 18499
  ```
  `-ngl 99` = 全部层上 Metal；纯 CPU 用 `-ngl 0`（慢 4.4 倍）。
  **`--mmproj` 必给**，否则只有文本通路，两张图进不去。

## ③ 打分服务（官方 SDK）

```bash
git clone --depth 1 https://github.com/OpenBMB/MiniCPM-OCR.git
python3 -m venv <独立 venv>            # 必须 Python ≥3.10；不要用项目 .venv
<venv>/bin/pip install -r MiniCPM-OCR/scripts/minicpm-ocr-jev/sdk/requirements-score.txt

cd MiniCPM-OCR/scripts/minicpm-ocr-jev
JEV_BACKEND_CONFIG=sdk/backends/llamacpp.yaml PATH=<venv>/bin:$PATH \
  bash sdk/start_score.sh 18501 http://127.0.0.1:18499
```

- `GET /healthz` → `{"status":"ok","served_model":...}` 才算起来了。
- `POST /v1/score`，一次**批量**（上限 64 条/item，`JEV_MAX_ITEMS` 可调）：
  ```json
  {"items":[{"original_image":"<b64 png>","render_image":"<b64 png>","ocr_text":"<该行 OCR 文本>"}]}
  ```
  返回 `{"results":[{"prob_1":0.00227,"error":null}]}`；base64 **不带** `data:` 前缀。

## ④ 吞吐（实测，含裁剪以外的端到端开销）

| 路径 | 单行 | 25 行/页 | **261 行分歧** |
|---|---:|---:|---:|
| Metal（`-ngl 99`） | 0.629 s（单发）/ **0.674 s**（批量） | 16.5 s | **≈ 176 s（3 分钟）** |
| CPU（`-ngl 0`） | **2.78 s** | 69.5 s | ≈ 726 s（12 分钟） |

0.674 s 是端到端（渲染候选图 + HTTP + 前向），1054 行共 710 s。

## ⑤ 分数语义

`prob_1` = **候选文本与区域原图一致的概率**，0–1，**越低越可疑**。

本库 1054 行实测：

| 行 | 中位 | p10 |
|---|---:|---:|
| 对（859 行） | 0.9960 | 0.9781 |
| 错（99 行） | 0.9345 | **0.0007** |

- **排序用法：按分数升序排，不用阈值。** 阈值只是可选的前置过滤。
- 阈值 0.05 的依据：标出 86 行（占 8.2%），其中真错 39 条，精确率 **45.3%**；
  对照"两引擎分歧"这条现成信号——261 行、精确率 **28.0%**。

## ⑥ 失败模式与应当报的错

| 现象 | 怎么发现 | 应报 |
|---|---|---|
| 模型没下/下坏 | sha256 或字节数不符 | 明确说"模型文件校验失败"，**不要静默降级** |
| 引擎没起 | `curl :18499/v1/models` 连接被拒 | "Jev 引擎未启动"，降级为"不排序" |
| 打分服务没起 | `/healthz` 不通 | 同上 |
| 单批超时 | 服务端 `timeout_sec: 120`；**CPU 下 64 条 = 178 s 会超** | CPU 模式批量 ≤32（89 s） |
| 内存不足 | llama-server 起不来/被 SIGKILL | 常驻 2056 MB；低于 4 GB 可用内存直接不启用 |
| 渲染图与区域图尺寸差太多 | 分数异常低（<0.01）但文本明显正确 | 渲染必须与裁剪图**同宽高** |

## ⑦ 行图怎么裁（Builder 必须用这一份，否则分数不可比）

**40 页那轮用的坐标：`b2t_H6GXVG` 的 `block_line.bbox`（归一化 0–1，页面坐标）。**

```python
# 200 DPI 渲染整页
img = render(page, dpi=200)          # 与产品 DEFAULT_DPI 一致
W, H = img.size
x0, y0, x1, y1 = line.bbox           # 已归一化，直接用
crop = img.crop((int(x0*W), int(y0*H), int(x1*W), int(y1*H)))   # 不扩边
```

**候选文本渲染成图（口径必须一致）**：白底、与 `crop` **同宽高**、宋体 `/System/Library/Fonts/Supplemental/Songti.ttc`、
字号 `int(h*0.72)`、起点 `(6, (h-size)//2)`、PNG。

> 注意：2026-10-28 那轮实验用的是 **RapidOCR 行框 + 外扩 2%**，与本配方**不是同一口径**，
> 两批分数不能混用。Builder 一律按上面这份（`block_line.bbox`、200 DPI、不扩边）。
> 官方说明：渲染环境不同，分数**绝对值会漂、排序稳定**——所以渲染参数也要锁死。

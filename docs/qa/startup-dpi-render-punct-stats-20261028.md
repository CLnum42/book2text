# 启动速度 / 页图清晰度 / 渲染成本 / 标点分组统计（任务 62）

> 2026-10-28。副本：《红楼梦》双语对照 4_可搜索_精简（490 页：front 30 / toc 4 / back 20，
> 正文 436）。真书库没碰。所有数字来自本机（MacBook-Air-3，Apple Silicon）。

## ① 启动：步骤条等的是"重活"，不是"计数"

### 打开一个已处理项目时并行发了什么（浏览器实测，cold）

| 请求 | 耗时 |
|---|---:|
| `/review/finish-summary` | **7,451 ms**（与预览抢 CPU 时） |
| `/export/preview?segments_only=1` | **7,020 ms** |
| `/review/finish-summary`（第二次） | 3,907 ms |
| `/export/preflight` | 3,687 ms |
| `/pages` | 3,311 ms |
| `/page-numbers` | 3,183 ms |
| `/projects/{id}` | 822 ms |

汇总：**点击「打开」→ 步骤条全部出现真实数字 = 11,521 ms**。
原因不是"数字算不出来"，而是：步骤条只要 `finish-summary`，但它和
"整本导出预览 / 页面载荷 / 页码索引"挤在一起抢同一个 Python 进程，被排在后面。

### 改了什么

1. **块级分歧只算一次**：新增 `blocks.divergence_index()`，一次读出块 / 行 / 复核记录 /
   页 / 项目，`block_divergence` 每块只算一次；收尾面板、队列统计、标点分组共用它
   （以前一次 `finish_summary` 里要算三遍）。
2. **比较加快路径**：`compare_line` 原样相同直接返回；`unify_whitespace` 没有"怪空白 /
   连续空格 / 首尾空格"时直接返回。全书比对里 95% 以上的行走快路径。
3. **两处结果缓存，签名 = 数据库文件 mtime（WAL 看 `-wal`）**：
   - `divergence_index`：490 页 **750 ms → 0.1 ms**
   - `structure.suggestions_by_page`（整本 + 默认规则）：**1.8 s → ~0 ms**
   - `finish_summary`：**2.90 s → 0.004 s**
   任何写入提交都会改 mtime，所以不需要给每个写入方加版本号；同一秒内的写入也不会
   拿到旧结果（一开始试过 `updated_at`，同秒的复核重跑就踩坑了）。
4. **前端排序**：`finish-summary` 与项目载荷**并行**取，但"上次的视图"（审校要组装
   整本导出预览，7 s）**等步骤条点亮之后**再进。

### 结果

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 点击打开 → 步骤条真实数字（UI） | 11,521 ms | **4,344 ms** |
| `finish-summary`（进程内第二次） | 2,900 ms | **3.6 ms** |
| `/projects/{id}`（warm） | 822 ms | **44 ms** |

**还没到 ≤1 s，说清剩余瓶颈**：`refreshProject` 里还会同时发 `/pages`（3.3 s）、
`/page-numbers`（3.2 s）、`/review/pending`（1.5 s），步骤条点亮的 4.3 s 里有 4 s 是
在等它们。下一步应该把这些"只属于某个视图"的请求**挪到那个视图真正打开时**再发
（页面确认的 `/pages`、目录确认的 `/page-numbers`、审校的 `/export/preview`），
预期能进 1 s 以内——这属于下一步，不在本次改动里硬塞。

## ② 页图清晰度：150 DPI 在 Retina 上等于放大 2 倍

- 页面宽 447 pt；`view` = 150 DPI → 932 px；Retina 屏上这一页显示约 880 CSS px =
  **1,760 设备像素**，所以糊。
- 现在按设备像素比选档：`devicePixelRatio >= 2 && innerWidth >= 1000` → `zoom`（300 DPI，
  实测 1,864 px 宽），否则仍是 `view`。
- 编码从 PNG 换成 **JPEG q=82**（`thumb` 仍 PNG）：

| 档位 | 改前（PNG） | 改后（JPEG q82） |
|---|---|---|
| `view` 150 DPI | 1.77 MB / 256 ms | **232 KB / 142 ms** |
| `zoom` 300 DPI | 约 7 MB / — | **650 KB / 366 ms** |
| `thumb` 40 DPI | 90 KB / 47 ms | 90 KB / 47 ms（不变） |

肉眼对比（同一页同一区域；左边是 150 DPI 放大到 Retina 设备像素、右边是 300 DPI 原生）：
`docs/screenshots/page-image-150-vs-300.png`。

## ④ 双语书的标点分组：514 组，长尾确实在英文页

《红楼梦》双语（490 页）：纯标点差异 **2,351 行 / 514 组**。

| 覆盖 | 组数 | 行数 | 占比 |
|---|---:|---:|---:|
| 前 20 组 | 20 | 1,393 | **59.3%** |
| 前 50 组 | 50 | 1,699 | **72.3%** |
| 前 100 组 | 100 | 1,882 | 80.1% |
| 前 200 组 | 200 | 2,037 | 86.6% |

按文字分：**英文 1,508 行 / 223 组；中文 843 行 / 291 组**。英文类前 20 组就覆盖
73.9%，但组数仍然多——因为同一行常有 2–3 个标点片段（`'→∅ .→∅`、`'→" ,→;`），
模式就被拆碎。

**建议的归并（不改语义）**：

1. 中文：保持"精确片段"分组（`；→，` 这种能一眼判断）；
2. 英文：按**标点类别**分组（引号 / 句点 / 逗号 / 分号 / 冒号 / 破折号 / 空格 / 无），
   例如 `'→∅`、`'→"`、`'→␣`、`'→:` 都归成「英文引号被改动」；
3. 每行只按"最主要的那一个片段"归组（同一行还有别的标点差异时，跟着这一组一起
   采用/保留——因为裁决本来就是整行）。

按这套规则在副本上试算：**514 组 → 155 组**，前 20 组覆盖 **82.9%**、前 50 组 **93.5%**
（最热的一组是「英文引号 → 消失」728 行，与 OCR 吞引号的判断一致）。
这套改动需要动分组口径，**等确认后再落**，本轮只报数。

## 追加（任务 63）：视图懒加载 + 英文标点归并 + 「谁在吞引号」

### ① 视图懒加载

- 打开项目时只发：`/open` → `finish-summary`（与项目载荷并行）→ 当前视图。
- **页面工作流 / 待处理页 / 页码索引 / 导出预检 / 质量统计**改成 `hydrateView()`：
  只在真的切到那个视图时发，而且**排到 `finish-summary` 到达之后**（`queueAfterSteps()`），
  免得和步骤条抢 CPU。
- 打开项目不再先切到页面视图（那样会立刻拉起三个重请求，然后又被"上次的视图"切走）。
- 收尾面板加**磁盘缓存** `<项目>/cache/finish-summary.json`（签名 = `updated_at` + db mtime）：
  新进程第一次读 **51 ms**（原来是 2.7 s 现算）。
- `project_pending` 里 `suggestions_by_page` 改成不带 `page_numbers` 调用，命中整本缓存：
  `/review/pending` **1.45 s → 0.08 s**。

实测（490 页双语）：
| 项 | 改前 | 改后 |
|---|---:|---:|
| `finish-summary`（新进程，有磁盘缓存） | 2,700 ms | **51 ms** |
| `finish-summary`（同进程第二次） | 2,900 ms | **3.6 ms** |
| `/review/pending` | 1,450 ms | **82 ms** |
| 切到「页面确认」数据就绪 | — | 约 6.3 s（页面图在抢 CPU） |
| 切到「目录确认」页码就绪 | — | 约 1.6 s |

**没做到 ≤1 s，说清原因**：这个项目的"上次视图"是**页面确认**，490 个页块会立刻开始
拉页图（每张 `thumb` 约 47 ms 服务端 CPU），把单进程占满，`finish-summary` 排在后面
仍要 5–7 s。下一步必须给页面网格的取图**限流/暂停**（开机期只给视口首屏取图，
其余等步骤条点亮后再排队），否则任何"先算计数"的优化都会被页图吃掉。

### ② 英文标点按类别归并（中文不动）

- 英文按**主片段的标点类别**归组（引号 / 句点 / 逗号 / 分号 / 冒号 / 破折号 / 空格 / 无），
  中文保持精确片段。
- 双语书：**514 组 → 331 组**（英文 223 → 约 40 组，中文 291 组不动）；
  前 20 组覆盖 **59.3% → 75.5%**、前 50 组 **72.3% → 85.0%**。

### ③ 谁在吞引号：**候选（PDF 文字层）** 吞的，不是原文

页 36 实图（300 DPI）上有 `She'll`、`we'll`、`it's`、`Grannie's`、`Don't`、`Can't`；
而候选（文字层）读成 `She ll`、`we ll`、`it s`。也就是说：

- **原文（主引擎 RapidOCR）是对的，候选（用户的 OCRmyPDF + Vision 文字层）丢了撇号**；
- 逐行统计：撇号在**词内**（`She'll` 这种）**164 行**——这批"全部采用候选"会把正确的
  撇号删掉；其余约 1,200 行撇号在行尾 / 词首（对话引号），方向一致（候选缺）。
- 结论：**这一类不能"全部采用候选"**，默认应该是「全部保留原文」。面板里已给这类组
  加提示：`候选少了引号 / 撇号（多半是文字层的问题）· 建议保留原文`；
  `无→引号` 那一类反过来提示「建议采用候选」。

**完整性检查（建议下一步做）**：判据 = 候选比原文少一个引号/撇号、且该位置在**词内**
（左右都是字母）→ 标「疑似候选漏字」，在队列里排前、并默认归到"保留原文"。
本轮的提示已经把这个方向表达出来，但还没做进识别后的自动标记。

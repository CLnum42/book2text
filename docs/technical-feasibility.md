### 1.2 PDF 渲染（pypdfium2 5.14.0）

在**合成测试文件**（`fixtures/pdf/synthetic-smoke-3pages.pdf`，A4，矢量文字）上的实测：

| 档位 | DPI | 输出像素 | PNG 体积 | 中位耗时 |
|---|---|---|---|---|
| `thumb` | 40 | 331 × 468 | 10.0 KB | 3.2 ms |
| `view` | 150 | 1241 × 1754 | 189.7 KB | 25.6 ms |
| `zoom` | 300 | 2481 × 3508 | 406.0 KB | 86.5 ms |
| `info()`（页数 + 尺寸） | — | — | — | 0.11 ms |

**⚠ 这些数字不能外推到真实书籍。** 该文件是矢量文字，几乎没有位图内容。

### 1.3 真实书籍上的渲染实测

开发者在 2026-10-14 放入 `test_books/` 两本真实书籍用于测试（该目录**不入库**，理由见 `.gitignore`）：

| 文件 | 页数 | 首页尺寸 |
|---|---|---|
| `《红楼梦》双语对照 2_正文_中文部分.pdf` | 369 | 447.3 × 674.3 pt |
| `安乐哲 译本处理.PDF` | 662 | 612.0 × 792.0 pt |

中间页（各取第 93 页 / 第 166 页）渲染实测，3 次取中位：

| 文件 | 档位 | 输出像素 | PNG 体积 | 中位耗时 |
|---|---|---|---|---|
| 红楼梦 | `view` 150 DPI | 932 × 1405 | 414.6 KB | 44.6 ms |
| 红楼梦 | `zoom` 300 DPI | 1864 × 2810 | 830.6 KB | 138.0 ms |
| 安乐哲 | `view` 150 DPI | 1275 × 1651 | 250.7 KB | 30.2 ms |
| 安乐哲 | `zoom` 300 DPI | 2550 × 3301 | 569.1 KB | 116.0 ms |

与合成文件相比，真实页面在 `view` 档慢约 1.2–1.7 倍、PNG 大 1.3–2.2 倍。
按此推算，600 页的书渲染一遍 `view` 档约需 20–30 秒，一次性生成缩略图是可接受的。

**但这两本书都不是扫描版**（数据见本节末尾），所以这些数字**只代表"有文本层、以矢量文字为主"的 PDF**，
真正的扫描页（整页大位图）仍然没有测过，那才是本项目的主场景。

**⚠ 发现：这两本书不满足 Phase 0 的样本要求。** 采样 6 页的文本层字符数：

| 文件 | 采样页的文本层字符数 |
|---|---|
| 红楼梦 | 462、564、711、736、606、533 |
| 安乐哲 | 549、145、743、1174、1157、407 |

两本书**都有大量可提取的文字**。而 Book2Text 针对的是"没有可用文本层的扫描版 PDF"
（说明书 2.1）。因此：

- 它们**不能**用于 Phase 0 第 1–2 项（OCR 引擎实测——有文本层就不需要 OCR，也测不出 CER）；
- 它们**可以**用于验证渲染链路、页面尺寸处理、大页面与多页性能；
- 顺带说明：`《红楼梦》双语对照`是中文原文 + 英文译文对照，与说明书提到的
  "后续双语平行语料建设"方向相关，但**目前不在 MVP 范围内**。

### 1.4 已确认可用的能力

- 页数读取、页面尺寸读取（A4 实测 595.28 × 841.89 pt，正确）
- **页码标签读取**（`get_page_label`）——说明书 Phase 0 第 3 项要求的对比维度之一，接口可用
- **文本层检测**（`get_textpage().count_chars()`）——同为第 3 项要求；在合成文件上返回 845 字符，
  在真实书籍上返回 145–1174 字符（见上表）。**尚未在真实扫描件上验证过"接近 0"的情形**
- PNG 编码经由 Pillow 完成（pypdfium2 的 `to_pil()` 依赖 Pillow）

### 1.5 本地服务与安全（说明书 4.4）

逐条实测，全部通过：

| 要求 | 实测结果 |
|---|---|
| 只监听 127.0.0.1 | 是；未监听 0.0.0.0 |
| 端口可配置 | `--port` 参数生效 |
| 端口被占用时自动向后尝试 | 实测：请求 8903（已占用）→ 自动使用 8904 |
| 每次启动生成随机会话令牌 | `secrets.token_urlsafe(32)` |
| URL 携带令牌，前端放请求头 | `?token=…` → `X-B2T-Token` |
| 令牌校验 | 无令牌 401、错误令牌 401（`hmac.compare_digest`） |
| Origin 校验 | 伪造 Origin 403、正确 Origin 200 |
| 错误格式统一 | 符合说明书第 11 节的 `{error:{code,message,detail,correlation_id}}` |
| 路径穿越防护 | 上传 ID 必须匹配 `^[0-9a-f]{32}$`；`../`、`%2f` 均被拒 |

### 1.6 文件进出（说明书 4.5）

- **流式上传已验证**：边接收边写盘、边算 SHA-256，未把整个文件读进内存。
  实测 3 字节分块切分与整块上传的 SHA-256 一致；magic bytes 跨分块也能正确识别。
- **magic bytes 校验已验证**：非 PDF 内容被拒（400 `invalid_upload`）。
- **"在文件夹中显示"已实现**（`core/platform.py`，macOS 用 `open -R`），
  但**只有 macOS 分支实际跑过**；Windows 的 `explorer /select,` 分支从未执行。

### 1.7 引擎自检接口

已实现说明书 Phase 0 第 4 项要求的自检：列出第一引擎（RapidOCR / PaddleOCR 两种部署形态）、
版面组件（RapidLayout / PP-DocLayout）、第二引擎（Apple Vision / Windows OCR / Tesseract）
各自是否可用、版本、以及**不可用的原因**。

当前实测结果：**0/7 可用**——因为 Phase 0 尚未选定引擎，未安装任何 OCR 依赖。
这是如实报告，不是缺陷。

Windows 侧的语言包检测逻辑（`OcrEngine.get_available_recognizer_languages()`）
**已写出但从未在 Windows 上执行过**，代码中已就地标注 `UNVERIFIED_ON_WINDOWS`。

## 2. 未验证（被前置输入卡住的第 1–3 项）

### 2.1 两个门槛项——**已实测，均已达标**（2026-10-14）

详细数据见 `docs/ocr-evaluation.md`。在 RapidOCR 3.10.0（ONNX）+ macOS arm64 上：

| 门槛项 | 判据 | 实测 | 结论 |
|---|---|---|---|
| 第一引擎能否返回**行级坐标** | 每个文本行有自己的坐标 | **20/20 页**返回行级四点框 | ✅ 达标 |
| 每页识别耗时 | ≤ 18 秒/页 | 中位 2.04 秒，最大 3.67 秒 | ✅ 达标 |

**这意味着"按行比对"的架构基础成立**（说明书 8.5、9.2 都依赖行级坐标）。
但注意两点：① 这是**干净栅格化样本**上的数字，真实扫描页会更慢；
② 只测了 RapidOCR，**PaddleOCR 与版面组件尚未对比**，选型未定。

### 2.2 PDF 库对比（第 3 项）未完成

当前**暂用 pypdfium2**，理由是许可证较宽松（`PyMuPDF` 为 AGPL，说明书 4.2）。
但说明书要求的对比维度**只在 pypdfium2 上取了数据**，`PyMuPDF` 一侧完全没有安装与实测：

- [x] pypdfium2：渲染可用、页码标签可读、文本层可检测、arm64 wheel 可用
- [ ] PyMuPDF：未安装，未测
- [ ] 两者在**真实扫描件**上的渲染质量对比：未做
- [ ] 许可证最终结论：未定（牵连 D-006）

**已获得的一条对比数据（2026-10-14）：`/Rotate` 的处理。**

带 `/Rotate` 的页（扫描时把横放的书页存成竖向页面 + 旋转标记）在真实书籍里很常见。
实测：

| 渲染器 | `/Rotate=90` 的输出 |
|---|---|
| pypdfium2（PDFium） | 横向 842×595 pt，内容方向正确 |
| macOS PDFKit | 横向 842×595 pt，同一方向 |

**两者一致**，说明 pypdfium2 在这项上不需要额外补偿——PDFium 已按 `/Rotate`
返回显示尺寸并渲染出显示方向。这条对 PDF 库选型是加分项。

**顺带记录一个陷阱：** 用 `reportlab` 的 `setPageRotation()` 生成的 PDF，
在 PDFium 与 PDFKit 里**都渲染不出内容**。做测试夹具时不要用它，
正确做法见 `scripts/make_test_fixtures.py`。这个陷阱一度让我误判了 pypdfium2 的行为
（见 `docs/decisions.md` D-014）。

## 5. 当前最大的缺口：Phase 0 的前置输入仍不满足

说明书 13.1 规定：**测试样本制作与金标准校对由开发者在 Phase 0 开始前完成，
是 Phase 0 的前置输入。**

### 5.1 已有的材料，以及各自能做什么

| 材料 | 能做什么 | 局限 |
|---|---|---|
| `fixtures/pdf/synthetic-smoke-3pages.pdf`（reportlab 合成，3 页） | 验证"能上传、能渲染" | 合成矢量文件，与真实书籍无关 |
| `test_books/` 两本真实书籍（369 + 662 页） | 渲染性能、大文件与多页处理 | **有文本层**，不是扫描版 |
| **`fixtures/pdf/sample-20p-300dpi.pdf`**（20 页，无文本层） | **可以开始 Phase 0 第 1–2 项的引擎实测** | 见下方缺口 |

样本集的选页依据、覆盖度对照与全部局限写在 `docs/scan-sample-set.md`。

### 5.2 样本集的两个覆盖缺口（无法从这两本书取得）

| 说明书 13.1 要求的类别 | 状态 | 原因 |
|---|---|---|
| 中文与中英混排 | ❌ 未覆盖 | 两本书都不含中英混排页（安乐哲 0 页含汉字，红楼梦 0 页含拉丁字母） |
| 低清晰度或倾斜页面 | ❌ 未覆盖 | 源书是原生数字排版，无此类页面；未做人工合成 |

### 5.3 样本集的性质局限（影响结论外推）

样本是**原生数字 PDF 的干净栅格化结果**，不含真实扫描件的倾斜、噪点、透印、
对比度不均、半色调网点等退化。**在它上面测得的 CER 会偏乐观**，不能直接用来预期
真实旧书上的识别率。若要对真实扫描条件有把握，仍需真正的扫描样本。

### 5.4 仍然缺失：真实扫描件的人工校对金标准

说明书 13.1 要求 5–10 页人工校对金标准，且明确"未经人工校对的 OCR 输出不能作为金标准"。

**比对工具链已经就绪并验证过**（2026-10-14）：`core/ocr/compare.py` 实现了说明书 8.7
的归一化与比对，`scripts/measure_accuracy.py` 可对照任意金标准测量 CER/WER。
已用**合成语料**校准（`fixtures/gold/synthetic-corpus.json`，82 行 / 2737 字），
结果与全部局限见 [`docs/accuracy-report.md`](accuracy-report.md)。

**但合成语料不能替代真实样本**：在完美输入上中文内容 CER 1.63%、英文 0%，
这只是上限。真实旧书的退化会显著抬高错误率，而**引擎选型恰恰要看这个差别**——
合成语料上两个引擎可能都在 1% 上下分不出高下。

需要补的量化门槛（说明书 Phase 0 第 1 项要求先定门槛再实测）：

- [ ] 每页识别耗时上限（由可接受的全书批量时间反推，如 400 页 ≤ 2 小时 → 每页 ≤ 18 秒）
- [ ] 可接受的 CER 区间
- [ ] 可接受的分歧率 / 捕获率区间
- [ ] 以上写入 `docs/ocr-evaluation.md` 开头

**金标准必须对照页面图像逐字抄录。** 注意：源 PDF 的文本层**不能**用来生成金标准
——已实测确认它带错字（"薛蘅芜"被写成"薛祷芜"），拿它当基准会把 OCR 的正确输出判成错误。

## 6. 风险清单（本阶段实测新增）

| 风险 | 说明 | 当前状态 |
|---|---|---|
| 门槛项可能不达标 | 若第一引擎不返回行级坐标，或每页耗时过长，按行比对方案要改 | 无数据，**Phase 0 必须给出结论** |

| Windows 完全空白 | 骨架、启动脚本、系统 OCR、控制台编码均未在 Windows 上跑过 | 需一台 Windows 机器验收 |
| 性能预期被误读 | 现有测量来自合成文件、有文本层的真实书籍，以及**干净栅格化**的样本集；三者都不代表真实扫描页 | 1.3 节与 5.3 节已标注；真扫描件的耗时与缓存占用仍待测 |
| 单机单用户假设 | 端口探测与 uvicorn 绑定之间存在竞态；未做并发写入保护 | Phase 1 引入项目锁时处理 |

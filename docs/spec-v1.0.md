# Book2Text：本地网页应用开发说明书

**版本：** 1.0
**状态：** 待 Phase 0 验证
**项目名称：** Book2Text
**产品形态：** 跨平台本地网页应用（Python 本地服务 + 浏览器界面），macOS（Apple Silicon）与 Windows（x64）共用一套代码，不支持 Intel Mac
**文档用途：** 作为开发 Agent（DSH 或其他编码助手）的长期开发依据，指导架构、功能、UX、分阶段实现与测试
**核心目标：** 将没有可用文本层的扫描版 PDF 图书，转换为经过人工审校、可追溯、保留结构信息的文本资产，并为后续双语平行语料建设预留基础

## 1. 给开发 Agent 的工作规则

> 本节应同步复制为仓库根目录的 `AGENTS.md`，作为每次开发任务的固定规则。

### 1.1 工作原则

1. **先检查，再写代码。** 开始任务前检查当前目录、Git 状态、已有代码和本文档相关章节。不凭记忆假设第三方库的 API，以已安装版本为准。
2. **小步开发，垂直切片。** 每次只完成一个可运行、可验证的功能切片。开始前说明：目标、修改文件、验收方法、不在范围内的内容。
3. **双平台意识。** 每个涉及文件、路径、进程、编码、依赖的改动，都要考虑 Windows 与 macOS 的差异（见第 10 节）。
4. **不破坏用户数据。** 不修改原始 PDF；不硬删除文本块和识别结果；批量操作显示作用范围并要求确认；重要操作可撤销。
5. **AI 输出不是原文事实。** OCR 和模型输出只是候选。不得润色、补全、翻译、纠正原文。
6. **真实状态优先。** 进度、保存状态、任务状态必须来自真实数据。不显示未实现的按钮，不用模拟进度。
7. **不做无证据的假设。** 未验证的能力（OCR 质量、性能、平台兼容）标注"未验证"。
8. **测试真实运行。** 不得把未运行的测试说成通过；注明是否在 Windows 上验证过。
9. **维护文档。** 每次修改后更新 `docs/development-log.md`、README、已知限制和决策记录。
10. **默认中文沟通。** 开发者没有正式软件开发经验，解释应简洁、可执行。

### 1.2 每次任务的报告模板

- **任务目标：** 本次只解决什么问题。
- **当前状态：** 相关代码、已有实现、测试状态。
- **实施计划：** 3–6 个步骤，列出修改文件和不在范围内的事项。
- **实现与验证：** 实际执行的命令、真实结果、失败项、未验证项（含平台）。
- **用户操作说明：** 如何启动、如何验证、如何回退。
- **下一步建议：** 只给一个最合理的下一步。

### 1.3 代码规则

- 修改前先阅读相关文件；不整文件覆盖已有修改。
- 不把 API Key、令牌、个人绝对路径写入源码、日志或项目数据。
- 不为通过测试而删除或弱化测试；不吞掉异常或用空结果伪装成功。
- 不引入未解释的大型依赖；新增依赖需说明用途、许可证、跨平台可用性。
- 数据库结构变化必须有迁移脚本和迁移测试。
- 失败时先定位原因，不连续做无依据的修改。

### 1.4 决策优先级

功能、速度、准确性、复杂度冲突时，按以下顺序取舍：

1. 不丢失用户数据；
2. 原文忠实与来源可追溯；
3. 用户理解当前状态并能恢复工作；
4. 降低审校操作成本；
5. 导出结果可验证；
6. 控制实现复杂度与依赖数量；
7. 高级自动化与视觉效果。

## 2. 产品定位

### 2.1 产品定义

Book2Text 是一个以"书籍项目"为中心的本地文本生产工具：导入扫描版 PDF → 识别 → 对照原图审校 → 导出可追溯的结构化文本。它不是 OCR 包装器，核心价值在于**高效、可靠的人工审校**和**可追溯的数据**。

### 2.2 用户与场景

- 研究者、译者、语料建设者；团队成员分别使用 macOS 或 Windows。
- 典型任务：处理一本 200–600 页的中文、英文或中英混排扫描书，持续数天到数周，多次中断和恢复。
- **团队角色：**
  - **负责人**：持有主项目，负责导入、识别、结构准备、分派审校任务、审阅合并成果、最终导出。
  - **审校助手**：收到"审校任务包"，只审校分派的页面，回传"审校结果包"。助手不需要原始 PDF 全书、不运行 OCR。
- **协作方式：** 离线任务包（单文件，经微信 / 邮件 / 网盘传递），不做实时同步。主项目只存在于负责人电脑上，是唯一权威数据。流程详见 6.7。
- 主项目文件夹可整体拷贝到另一台电脑，但同一时间只应在一台电脑上编辑（见 7.6 项目锁）。

### 2.3 核心原则

- **原文优先：** 不允许系统或模型改写源文本。
- **可追溯：** 每段导出文本可追溯到 PDF 页、页面区域、文本块和识别来源。
- **可逆：** 排除、清理通过状态和导出规则实现，不破坏源数据。
- **结构优先：** TXT 是输出形式，结构化数据（块、段、类型、来源）才是资产。
- **本地优先：** 默认全部在本机处理；任何在线调用必须事先说明发送范围（MVP 不含在线调用）。
- **诚实反馈：** 未实现、未验证、失败的情况明确呈现。

### 2.4 成功标准

**MVP：**

1. 在 Mac 或 Windows 上启动应用，在浏览器中使用。
2. 创建项目、导入 PDF、查看缩略图，批量标注页面类型和纳入 / 排除。
3. 先试识别样本页，再决定批量识别；看到真实进度与错误；中断后可继续。
4. **按页**对照原图审校，修改文本、调整结构，确认整页后自动进入下一页。
5. 批量标注页眉、页脚、页码，使其不进入正文导出。
6. 关闭、重启后恢复全部成果和上次位置。
7. 导出前看到预检摘要和预览，生成 TXT 与 JSONL；跨页段落被正确拼接。
8. 把项目文件夹从 Mac 拷贝到 Windows（或反向）后可以正常打开和继续工作。

**协作阶段（Phase 5）：**

9. 负责人选择页面范围，生成审校任务包发给助手；主项目中可看到每段页面分派给了谁、处于什么状态。
10. 助手用同一个 Book2Text 打开任务包，只审校分派的页面，导出结果包回传。
11. 负责人导入结果包，逐页查看助手的修改（字符级差异），整体或逐项接受 / 拒绝；冲突被明确标出，不会被静默覆盖。
12. 合并后的每处修改都能追溯是哪位助手、在哪个任务包中完成的，并可整体撤销。

**双路 OCR 阶段（Phase 8）：**

13. 第二路 OCR 能标出分歧行；审校时可一键换用另一路候选；一致处的分歧标记可信，不会被假分歧淹没。

## 3. 范围

### 3.1 MVP 必须实现

1. 跨平台启动方式（启动脚本；打包版在 Phase 6）。
2. 项目库：新建、打开、最近项目、打开已有项目文件夹、从列表移除。
3. PDF 导入：复制到项目内，读取页数、尺寸、页码标签，检测已有文本层。
4. 页面视图：缩略图网格、批量选择、页面类型、纳入 / 排除、状态筛选。
5. 单 OCR 引擎（适配器封装），支持样本页、选中页、全部页识别；按页拆分任务，可恢复、可重试。
6. 审校视图（页面模式）：原图 + 块列表编辑器、bbox 双向联动、确认整页、标记不确定、排除块。
7. 结构编辑：修改块类型、合并、拆分、上移 / 下移、标记"段落延续到下一页"、手动新增块。
8. 页眉 / 页脚 / 页码批量标注工具（基于位置规则，预览后应用）。
9. 自动保存、编辑历史、撤销 / 重做。
10. 疑难筛选：只在含"不确定"块、识别失败或有待选新结果的页面之间跳转。
11. 导出对话框：预检、预览、TXT / JSONL、清理规则开关、导出记录。
12. 项目数据库自动备份、项目锁、错误日志。

### 3.2 MVP 不做

多路 OCR 的自动投票与自动仲裁（本版只把分歧作为人工线索）、视觉模型复核、自动翻译或润色、复杂多栏的自动阅读顺序恢复、审校视图中的字符级差异高亮（合并审阅视图除外）、多人实时同时编辑与云同步、服务器与账号系统、双语对齐、OCR 模型训练、表格 / 公式 / 竖排 / 手写的可靠识别、DSH 集成、在线模型调用。

### 3.3 后续扩展

按优先级：**双路 OCR 与分歧检测**（Phase 8，第 8.4–8.7 节）→ **审校任务包**（Phase 5）→ 打包安装版（Phase 6）→ 块级疑难队列 → 章节导航 → 直接提取已有文本层 → 本地视觉模型盲读复核 → DSH MCP 集成 → 双语对齐与 TMX / XLIFF。

## 4. 总体架构

### 4.1 架构图

```text
┌──────────────── 用户电脑（macOS / Windows）────────────────┐
│                                                            │
│  浏览器（Chrome / Edge / Safari）                           │
│  ┌──────────────────────────────┐                          │
│  │ 前端单页应用（Vue 3 + TS）     │                          │
│  │ 项目库 / 页面视图 / 审校视图   │                          │
│  └──────────────┬───────────────┘                          │
│                 │ HTTP JSON API + 图片（仅 127.0.0.1）       │
│                 ▼                                          │
│  Book2Text 本地服务（Python，单进程，唯一的数据写入方）       │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ API 层（FastAPI）：参数校验、会话令牌、统一错误格式      │  │
│  │ 核心层 core/：project / pdf / ocr / jobs / review /    │  │
│  │              structure / export / storage              │  │
│  │ 任务执行器：后台调度 + 子进程运行 OCR（崩溃隔离）        │  │
│  │ 存储层：每个项目一个 SQLite（WAL）+ 文件目录            │  │
│  └──────────────────────────────────────────────────────┘  │
│                 │                                          │
│                 ▼                                          │
│  项目库目录 / <项目文件夹> / project.db, source/, cache/,    │
│                           exports/, backups/               │
└────────────────────────────────────────────────────────────┘

（后期）DSH Agent ──MCP 工具──► 核心层 / 本地 API（只能读取与提交"候选"）
```

### 4.2 关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 后端语言 | Python 3.11+ | OCR / PDF 生态最完整；Mac 与 Windows 均可用 |
| Web 框架 | FastAPI + Uvicorn | 简单、自带类型校验、自动生成 API 文档 |
| 数据库 | SQLite，每个项目一个 `project.db`，开启 WAL | 零部署；项目文件夹自包含、可拷贝、跨平台 |
| 应用配置 | `config.json`（项目库路径、最近项目、偏好），存于系统用户配置目录（用 `platformdirs` 获取） | 与应用分离，重装不丢 |
| PDF 渲染 | 候选：`pypdfium2`（Apache / BSD）或 `PyMuPDF`（AGPL） | Phase 0 决定；如需对外分发，优先许可证宽松的 `pypdfium2` |
| 第一 OCR 引擎（文本主识别） | PP-OCR 系列；PaddleOCR 或 RapidOCR（ONNX）部署形态由 Phase 0 对比决定（适配器封装） | 负责文本检测与识别、文本行与**行级坐标**；是整个方案的前提，Phase 0 必须确认其返回行级坐标与每页耗时 |
| 版面与块类型（可选增强组件） | 只接**版面检测模型**：PP-DocLayout（PaddleOCR 生态）或 RapidLayout（RapidAI 生态）；**不使用 PP-StructureV3 端到端解析作为主路径**，见第 8.4 节 | 提供版面区域与块类型建议（页眉 / 页脚 / 页码等），为 6.5 批量工具预填候选；未启用时由 grouping.py 组合行、块类型人工设置 |
| 第二 OCR 引擎 | 按平台选：Apple Vision（macOS）/ Windows 自带 OCR / Tesseract（兜底） | 只需要独立血统与**低假分歧**，不要求跨平台一致；各平台细节见 8.4、8.6 |
| 前端 | Vue 3 + TypeScript + Vite，构建产物由后端静态托管 | 审校界面交互复杂，需要组件化；最终用户不需要安装 Node.js |
| 实时状态 | 前端轮询（有运行中任务时每 1 秒，空闲时停止） | 比 WebSocket / SSE 简单可靠，MVP 足够 |
| 环境管理 | `uv`（Python 环境与依赖锁定） | 一条命令安装，Mac / Windows 行为一致 |
| 分发 | MVP：启动脚本；Phase 6（协作阶段之后）：PyInstaller 在两个平台分别打包 | 同一套代码，两次打包 |

### 4.3 分层职责

- **前端：** 只负责展示与交互；所有数据读写通过 API；不持有唯一状态（编辑内容即时提交保存）。
- **API 层：** 薄层；校验输入、调用核心层、统一错误格式；不写业务逻辑。
- **核心层：** 全部业务逻辑，**不依赖 FastAPI**，可被单元测试、命令行脚本和后期 MCP 工具直接调用。
- **任务执行器：** 管理长任务；OCR 在子进程中运行，单页崩溃不拖垮服务。
- **存储层：** 数据库访问、迁移、备份；所有路径为项目内相对路径。

### 4.4 本地服务安全

- 只监听 `127.0.0.1`，不监听 `0.0.0.0`。
- 默认端口可配置；被占用时自动尝试下一个端口，并在启动日志与自动打开的浏览器地址中体现。
- 每次启动生成随机会话令牌，启动时打开的 URL 携带令牌，前端在请求头中发送；后端同时校验 `Origin`，防止其他网页向本地服务发起请求。
- 所有文件访问限制在项目库目录与项目目录内；路径规范化，防止路径穿越。

### 4.5 文件的进出方式（适应浏览器限制）

浏览器无法获取用户本机文件的真实路径，因此：

- **导入 PDF：** 通过浏览器上传（拖拽或选择文件），后端**流式写入**项目的 `source/original.pdf`，边传边算 SHA-256，并显示上传进度；校验文件确为 PDF（magic bytes）。用户原始文件不受影响。
- **导出：** 文件写入项目的 `exports/` 目录；界面提供"下载"链接和"在文件夹中显示"按钮（后端调用 macOS `open -R` / Windows `explorer /select,`，这是少数按平台分支的代码，集中放在 `core/platform.py`）。
- **打开已有项目：** 应用扫描项目库目录中的项目文件夹；也可在设置中输入其他项目文件夹路径（由后端校验）。

## 5. 数据模型

### 5.1 数据原则

- 原始 PDF 只读；所有实体有稳定 ID（ULID 字符串，可排序、跨平台）。
- 识别结果（OCRRun）、块的 OCR 原文、最终文本、导出文本相互分离。
- 删除一律为软删除（`deleted_at`），并记录事件。
- 所有修改写入事件表，支持撤销与追溯。
- 数据库有 `schema_version`，结构变化必须有迁移。
- 同一事实只存一份：能推导的状态不重复存储。

### 5.2 坐标规范

- bbox 使用**归一化坐标** `[x0, y0, x1, y1]`，取值 0–1，相对于**应用 PDF `/Rotate` 之后的页面显示方向**，原点在左上角。
- 与渲染 DPI 无关；渲染任意尺寸的图像时，乘以图像宽高即得像素坐标。
- OCR 适配器负责把引擎返回的像素坐标转换为归一化坐标，并有单元测试覆盖（含旋转页）。

### 5.3 实体

#### Project（`project.db` 中的 `project` 表，仅一行）
`project_id`, `name`, `source_file_name`, `source_sha256`, `page_count`, `created_at`, `updated_at`, `schema_version`, `settings_json`（OCR 引擎、语言、DPI、清理规则默认值等）, `last_view`, `last_page_id`, `last_block_id`

#### Page
`page_id`, `page_no`（PDF 物理页序号，从 1 开始）, `page_label`（印刷页码标签，可空）, `width_pt`, `height_pt`, `rotation`, `page_type`（cover / toc / front / body / appendix / index / blank / other，默认 body）, `include`（是否纳入处理与导出，默认 true）, `has_text_layer`, `active_run_id`（可空）, `note`

页面的识别状态与审校状态**不单独存储**，由 OCRRun 和 Block 推导：
- 识别状态：未识别 / 排队中 / 识别中 / 已识别 / 失败 / 有待选新结果
- 审校状态：未开始 / 进行中 / 已完成（所有纳入的块均已确认）/ 有疑问（存在不确定块）

#### OCRRun
`run_id`, `page_id`, `engine_id`, `engine_version`, `params_json`（语言、DPI、预处理）, `status`（queued / running / succeeded / failed）, `error_code`, `error_message`, `raw_result_path`（`ocr_runs/<run_id>.json`，保存引擎原始输出）, `created_at`, `finished_at`

一个页面可以有多个 Run；`Page.active_run_id` 指向当前采用的 Run。

用 `run_type` 区分主识别与辅助识别：
- `primary`（第一引擎，生成 Block）/ `auxiliary`（第二引擎，只做按行分歧检测，**不生成 Block**）。
- 辅助 Run 也保存在 `ocr_runs/` 下，但记录 `line_results`：每条为 `{block_id, line_index, text, raw}`，只作为行级候选。

#### BlockLine（块内的行）
`line_id`, `block_id`, `line_index`（块内顺序）, `bbox`（行级归一化坐标）, `text`（该行最终文本，缺省时由 `Block.text` 按 `\n` 推导）, `aux_text`（可空，第二引擎的该行候选）, `diff_status`（identical / format_only_differs / differs，可空）

行为说明：
- 第一引擎必须在 Phase 0 确认能返回行级坐标；不能返回时，`BlockLine` 只用 `text` 的换行推导，`bbox` 为空，分歧检测退化为"块级比对"，并在界面中说明精度下降。
- 用户编辑 `Block.text` 时，行级划分按换行重新计算；因此分歧标记在人工编辑后视为参考信息，可清除或重跑。
- 合并块时，行记录随文本拼接保留原 bbox；拆分块时，光标前的行归前块、光标后的行归后块，被从中间切开的行清空 bbox 与分歧信息。

#### Block
`block_id`, `page_id`, `origin_run_id`（手动新增时为空）, `origin`（ocr / manual / split / merge）, `order_index`（页内阅读顺序）, `bbox`（可空）, `block_type`（heading / paragraph / header / footer / page_number / footnote / caption / other）, `ocr_text`（创建时来自 OCR，之后不变）, `text`（最终文本，保留行内换行 `\n`）, `review_status`（unreviewed / confirmed / uncertain）, `include`（默认 true）, `continues_to_next`（本段延续到下一个纳入的正文块，通常用于跨页）, `confidence`（可空）, `revision`（整数，每次修改加 1，用于协作冲突检测）, `reviewed_by`（最后一次确认或标记的人，可空）, `comment`（审校备注，可空，用于助手向负责人提问）, `created_at`, `updated_at`, `deleted_at`

推导规则：
- **已修改** = `text != ocr_text`，界面显示"已修改"标记，不需要用户设置。
- **识别失败** 属于页面 / Run，不属于块。
- **跳过** 是导航动作，不是状态。
- 页眉、页脚、页码类型的块在导出时由清理规则排除，不需要改 `include`。

#### Segment（导出时推导，不单独存储）
按全书阅读顺序（`page_no`, `order_index`）遍历纳入的块，`continues_to_next = true` 的块与下一个块合并为同一段。
**段 ID = 首块的 `block_id`**。只要首块不被删除或拆分，段 ID 就保持稳定，可供后续双语对齐引用。

#### Event（编辑历史）
`event_id`, `batch_id`（同一次批量操作共享，用于整体撤销）, `entity_type`, `entity_id`, `action`（edit_text / set_status / set_type / set_include / merge / split / reorder / create / delete / apply_run / merge_review_result / …）, `before_json`, `after_json`, `actor`（user / system / agent / reviewer）, `actor_name`（如"张三"）, `package_id`（来自审校结果合并时填写）, `created_at`

撤销 / 重做基于 Event、按 batch 进行，**撤销栈仅限本次会话**，应用重启后不可撤销历史操作（已保存的成果本身不受影响）。

#### Job 与 JobItem
- `Job`：`job_id`, `job_type`（ocr / render_thumbnails / export）, `status`（queued / running / paused / succeeded / failed / cancelled / interrupted）, `total`, `done`, `failed`, `params_json`, `created_at`, `started_at`, `finished_at`
- `JobItem`：`item_id`, `job_id`, `page_id`, `status`, `run_id`, `error_message`, `attempts`

任务按页拆分为 JobItem，以支持断点续跑与幂等重试：服务启动时，把状态仍为 `running` 的 Job 改为 `interrupted`；用户点击"继续"后，只处理未成功的 Item。

#### Assignment（审校任务分派）
`package_id`, `assignee_name`, `page_ids`（分派页面）, `context_page_ids`（随包附带的只读上下文页）, `instructions`, `base_snapshot_path`（`assignments/<package_id>/base.json`，分派时这些页面所有块的快照与 revision）, `status`（issued / returned / partially_merged / merged / cancelled）, `created_at`, `due_date`（可空）, `last_result_seq`, `merged_at`

#### 应用级身份
`config.json` 中保存"我的名字"（首次使用时填写），用于事件记录、任务包和结果包中的署名。这只是署名，不是账号或权限系统。

#### ExportRecord
`export_id`, `format`, `scope_json`, `rules_json`, `file_paths`, `segment_count`, `char_count`, `unreviewed_count`, `uncertain_count`, `created_at`, `status`

### 5.4 关键业务规则

**R1 首次识别：** 页面没有 active run 时，Run 成功后自动设为 active，并从中生成 Block。

**R1b 辅助识别（第二引擎）：** 页面已有 active run 时，可单独启动辅助识别。它按行识别第一引擎切出的行图，结果记录为 `run_type = auxiliary` 的 OCRRun，并写入 `BlockLine.aux_text` 与 `diff_status`。辅助识别可以随时单独重跑，**不影响** `Block`、`Block.text` 与审校状态。

**R2 重新识别：**
- 页面上没有任何块被确认、修改或结构调整过 → 新 Run 成功后直接替换（旧块软删除，可撤销）。
- 页面已有人工成果 → 新 Run 只保存为"待选结果"，页面标记"有新识别结果"。用户在审校视图中左右对比，选择"采用新结果"（旧块软删除，可撤销）或"保留现有"。**系统绝不自动覆盖人工成果。**

**R3 确认整页：** 将本页所有纳入且状态为 unreviewed 的块设为 confirmed；状态为 uncertain 的块保持不变，并提示"本页仍有 N 个不确定项"。

**R4 合并 / 拆分：** 合并时文本以 `\n` 连接，bbox 取并集，`ocr_text` 同样合并，来源块记录在事件中；拆分在光标位置切开，两块暂沿用原 bbox，并标记为"位置近似"。

**R5 文本隔离：** 修改 `text` 不改变 `ocr_text`；清理规则只作用于导出结果，不回写 `text`。

**R6 协作冲突：** 合并审校结果时，以分派时的 `revision` 为基准。主项目中某块（或某页的块结构）在分派后被改动过，即视为冲突，必须由负责人逐项处理，不自动覆盖任何一方（详见 6.7.5）。

**R7 数据库设计前置：** `revision`、`reviewed_by`、`comment`、`actor_name` 等协作字段，以及 `run_type`、`BlockLine`（含 `aux_text`、`diff_status`）等双路 OCR 所需结构，从 Phase 1 / Phase 2 起就建立，避免后续迁移。

## 6. 功能设计

### 6.1 项目管理

- **新建项目：** 输入名称 → 上传 PDF → 后端复制文件、计算 SHA-256、读取元数据、检测文本层 → 后台生成缩略图（作为 Job）→ 进入页面视图。
- **已有文本层提示：** 若检测到大部分页面已有文本层，提示"这本 PDF 可能已包含文本"（MVP 只提示；"直接提取文本层"为后续功能）。
- **打开项目：** 获取项目锁 → 自动备份数据库 → 进入上次的视图与位置。
- **从列表移除：** 只从最近项目列表中移除，不删除任何文件。
- **删除项目：** MVP 不在界面中提供；用户可手动删除项目文件夹（只是项目内的副本，用户原始 PDF 不受影响）。

### 6.2 页面准备

- 缩略图网格采用虚拟滚动（只渲染可见区域），支持 1000 页以上。
- 选择方式：单击、Shift 范围选择、Mod + 单击多选、输入页码范围（如 `1-12, 300-310`）。
- 批量操作：设置页面类型、纳入 / 排除、识别、重新识别。
- **最低限度准备：** 所有页面默认纳入、类型为正文；不要求识别前逐页分类。界面建议在识别前排除封面、版权页、空白页，以节省时间。

### 6.3 识别

- **样本试识别：** 用户选择 3–10 页 → "识别样本" → 完成后在审校视图中查看 → 决定批量识别、调整设置（语言、DPI）后重试，或更换引擎。界面提示：样本结果不代表整本书。
- **批量识别：** 选中页或全部纳入页；已有识别结果的页面默认跳过（可勾选"包括已识别页面"，此时适用规则 R2）。
- **任务控制：** 暂停（当前页完成后停止）、继续、取消；失败页可单独重试。只显示技术上真实支持的操作。
- **并发：** 默认 1 个 OCR 子进程；设置中可调整（默认值依 Phase 0 测得的 CPU / 内存占用确定）。
- **第二引擎（第二阶段）：** 在样本页试识别时同时运行第二引擎，并显示"分歧行 / 总行数""预计需要重点看的行数"，用于判断是否值得继续。
- **错误：** 每个失败页记录错误码与可读信息；缩略图显示失败标记。

### 6.4 审校（核心）

**页面模式（默认）**：逐页审校，是主要工作流程。
**疑难筛选**：在页面模式中开启筛选，只在"含不确定块 / 识别失败 / 有待选新结果 / 未完成 / **有分歧（第二阶段）**"的页面之间跳转。（块级专用队列模式在 Phase 7 根据使用反馈再加入。）

审校功能：
- 编辑块文本（自动保存）。
- 原图与块双向联动：点击块 → 原图高亮对应区域并在需要时滚动；点击原图区域 → 选中对应块。无 bbox 的块明确显示"无位置信息"，不绘制虚假高亮。
- 查看 OCR 原文：已修改的块可展开查看 `ocr_text`，并可"恢复为 OCR 原文"。
- **（第二阶段）分歧处理：** 有分歧的行以高亮标出，旁边显示另一路的候选文本，点一下即可将该行替换为另一路候选（作为一次普通编辑，进入撤销历史）。"格式差异"的行以淡色显示，默认不提示。**系统不自动采纳任何一路的结果。** 快捷键：跳到下一处分歧 `Mod + Alt + ↓`。
- 块操作：标记 / 取消不确定、排除 / 纳入、修改类型、与上一块合并、在光标处拆分、上移 / 下移、标记"延续到下一页"、新增块、删除（软删除）。新增块时可选择在原图上**框选位置**以补全 bbox（用于 OCR 漏检区域的补救，如未被检出的页眉）；不框选则按"无位置信息"处理。不做已有块 bbox 的几何拖拽调整（bbox 不参与导出，只影响联动高亮与行图裁剪，行框以引擎产出为准）。
- 确认整页并进入下一页（规则 R3）。
- 撤销 / 重做（基于 Event，按 batch 撤销）。
- 跳页：按 PDF 页序号跳转；有页码标签时同时显示。

### 6.5 页眉 / 页脚 / 页码批量标注

扫描书的页眉页脚每页都有，逐页处理不可行。工具流程：

1. 在页面视图或审校视图中打开"结构工具 → 标注页眉页脚"。
2. 设置规则：页面顶部区域高度（如 8%）、底部区域高度（如 8%）、可选文本条件（纯数字或罗马数字 → 页码；字数少于 N）、作用范围（默认全部纳入的正文页）。
3. **预览：** 显示将被标注的块数量，并抽样展示若干页（原图 + 将被标注的块高亮），可逐个取消。
4. 应用：作为一个 batch 写入 Event，可整体撤销。
5. 已被人工修改过类型的块不会被覆盖。

规则来源有两种：**位置规则**（默认，如上）；启用版面组件（8.4）时，模型给出的页眉 / 页脚 / 页码类别建议作为**预填候选**。两种来源都必须经过预览与人工确认后才应用，模型建议绝不静默生效。位置规则的区域高度等参数可随时调整并重新预览，确认效果后再应用。

### 6.6 导出

导出是一个对话框（或右侧抽屉），流程如下（格式规范见第 9 节）：

1. 选择格式：TXT / JSONL / 两者。
2. 选择范围：全部纳入内容 / 仅已确认内容；页面范围（默认全书）。
3. 选择内容类型：正文与标题（默认）、脚注（默认不含）、图注、附录页、索引页等；"其他"（other）类型默认不导出，可勾选（侧栏文本等未映射类别归入 other）。
4. 清理规则开关（第 9.3 节），每条附简短说明。
5. **预检摘要**（实时计算）：预计段数与字数；已确认 / 未审 / 不确定块数；排除的页面与块数；未识别或识别失败的纳入页数；启用的规则。
6. 存在未审或不确定内容时给出明确提示，用户可以继续导出（未审内容不会因此被标为已审）。
7. **预览：** 显示开头若干段以及用户指定页附近的输出，用于检查段落拼接、跨页合并、页眉页脚是否被去除。
8. 执行导出 → 写入 `exports/<时间>_<格式>/` 与 `manifest.json` → 显示"下载"与"在文件夹中显示"。
9. 导出记录列表：时间、格式、范围、数量。

### 6.7 团队协作：审校任务包

#### 6.7.1 流程总览

```text
负责人（主项目）                                   审校助手
────────────────                                   ────────────
导入、识别、标注页眉页脚
   │
   ├─ 分派：选择页面范围 + 助手名字 + 说明
   │      → 生成 任务包 .b2tpkg ──（微信 / 邮件 / 网盘）──►  打开任务包
   │        页面标记"已分派给 张三"                         审校分派的页面
   │                                                       （可分多次完成）
   │                                                          │
   │  ◄──（微信 / 邮件 / 网盘）── 结果包 .b2tres ◄── 导出审校结果
   │
   ├─ 导入结果包 → 合并审阅视图
   │      逐页查看差异：接受 / 拒绝 / 处理冲突
   │
   └─ 合并完成 → 页面标记"已合并（张三）" → 继续审阅或导出
```

- 一个主项目可以同时有多个任务包，分派给不同助手的不同页面。
- 同一页面同一时间只能处于一个未完成的任务包中，避免两位助手改同一页。
- 助手可以多次导出结果包（例如每天发一次进度）；负责人每次导入时只处理尚未合并的变化。

#### 6.7.2 任务包（.b2tpkg）

一个 ZIP 文件，文件名示例：`书名缩写_p87-136_张三_20250301.b2tpkg`。内容：

```text
package.json        # 格式版本、package_id、project_id、书名、source_sha256、
                    # 分派页面与上下文页面列表（page_id、page_no、page_label）、
                    # 助手名字、负责人名字、说明、截止日期、允许的操作、应用版本
source/subset.pdf   # 仅包含分派页面及前后各 1 页上下文页的 PDF 子集（不含全书）
data.json           # 这些页面的页面信息与全部块的快照（含 revision）
```

- **前后上下文页**：分派范围首页的前一页和末页的后一页以只读方式附带，方便助手判断跨页段落。上下文页不能编辑。
- 包内不含 OCR 原始输出和其他页面，体积约为原书对应页数的比例。
- 生成任务包时，主项目创建 Assignment 记录并保存基准快照。

#### 6.7.3 助手端：审校包模式

助手使用同一个 Book2Text 应用，通过"打开任务包"导入。应用为其创建一个**审校包项目**，在项目库中显示"审校任务"标记、负责人名字、页数、截止日期和说明。

| 操作 | 助手是否可用 |
|---|---|
| 编辑文本、确认、标记不确定、排除 / 纳入块 | 可以 |
| 修改块类型、合并、拆分、移动、新增、删除块、标记跨页延续 | 可以（合并时按整页处理，见 6.7.5） |
| 块备注（向负责人提问或说明） | 可以 |
| 撤销 / 重做 | 可以 |
| 运行 OCR、重新识别 | 不可以（按钮不显示） |
| 修改页面类型、页面纳入 / 排除、页眉页脚批量工具 | 不可以 |
| 导出 TXT / JSONL | 不可以；只能导出审校结果包 |
| 编辑上下文页 | 不可以（只读显示） |

助手使用与负责人相同的审校视图（第 7.4 节），只是隐藏了不可用的功能，顶部显示"审校任务：第 87–136 页 · 来自 李四"。

#### 6.7.4 结果包（.b2tres）

一个 ZIP 文件（通常只有几十 KB，适合用聊天工具发送），文件名示例：`书名缩写_p87-136_张三_结果2.b2tres`。内容：

```text
result.json   # package_id、project_id、source_sha256、助手名字、导出时间、
              # 序号 seq（同一任务包的第几次导出）、
              # 每页：基准 revision、当前全部块的最终状态（含备注）、是否有结构变化
events.json   # 助手的编辑事件记录（用于追溯）
summary.json  # 统计：已确认、不确定、修改块数、备注数、未处理页数
```

导出前显示摘要：已完成 N 页、未完成 M 页、不确定 K 块、备注 J 条。允许导出部分完成的结果。

#### 6.7.5 合并规则

**导入校验：**
- `project_id` 与 `source_sha256` 必须与主项目一致，否则拒绝并说明原因。
- `package_id` 必须对应主项目中的 Assignment；对应的 Assignment 已作废时，提示并要求负责人明确确认后才能继续。
- 序号 `seq` 不大于已合并的序号时，提示"这是较早的结果"，默认不处理。

**逐页分类（以分派时的基准快照为参照）：**

| 分类 | 判定 | 处理 |
|---|---|---|
| 无变化 | 助手未修改该页 | 不显示 |
| 块级变化 | 只有文本、状态、类型、纳入、备注、延续标记变化，没有块的增删、合并、拆分、重排 | 逐块审阅；可以逐块接受或拒绝 |
| 结构变化 | 有块的增删、合并、拆分或重排 | **按整页**接受或拒绝（块之间相互依赖，不能只接受一部分） |
| 冲突 | 分派后，负责人在主项目中也修改了同一块（块级）或同一页的任何块（结构变化时） | 必须单独处理：保留我的 / 采用助手的 / 手动编辑后确认 |

**接受后的写入：**
- 每次导入产生一个 batch，所有接受的变化写入 Event，`actor = reviewer`、`actor_name = 助手名字`、`package_id` 已填写；整个 batch 可以撤销。
- 助手确认过的块，合并后状态为"已确认"，`reviewed_by = 助手名字`。负责人在审校视图中可以按审校人筛选，进行抽查。
- 被拒绝的变化不写入主项目，但保留在 `assignments/<package_id>/` 的结果记录中，可以随时查看。
- 全部处理后，Assignment 状态变为"已合并"；有被拒绝或未完成页面时为"部分合并"，这些页面可以重新分派。

#### 6.7.6 分派期间的主项目

- 分派中的页面在页面视图显示"张三 · 审校中"。
- 负责人仍可以编辑这些页面，但审校视图顶部提示"本页已分派给张三，现在修改将在合并时产生冲突"。
- 负责人可以**作废**任务包（例如助手无法继续），页面恢复为未分派；之后收到的该包结果需明确确认才能导入。
- 不允许对分派中的页面重新识别（避免块全部被替换后无法合并），按钮显示原因。

### 7.6 保存、并发与恢复

- **自动保存：** 输入停止 500ms 或编辑框失去焦点时提交；切换块无需等待（每个块的保存请求独立排队，按顺序发送）。
- **保存状态指示**（顶部栏）：`保存中…` / `已保存 ✓ 14:32` / `保存失败 ⚠ 重试`。保存失败时编辑内容保留在编辑框，同时暂存到浏览器 `localStorage`，服务恢复后提示用户恢复。
- **离开保护：** 有未完成的保存请求时关闭标签页，浏览器弹出提示。
- **服务断开：** 前端检测到本地服务不可达时，显示提示"本地服务已停止，请重新启动 Book2Text"，编辑内容不丢失。
- **项目锁：** 打开项目时在项目文件夹中写入 `.lock`（主机名、进程号、时间）。若锁已存在且属于其他电脑或仍在运行的进程，提示"该项目可能正被其他人或另一个窗口使用"，提供"只读打开"或"强制打开（附风险说明）"。用于防止网盘同步的文件夹被两台电脑同时编辑。
- **多标签页：** 同一项目只允许一个标签页处于编辑状态，其他标签页提示切换或以只读方式查看。
- **自动备份：** 每次打开项目时将 `project.db` 备份到 `backups/`，保留最近 10 份；每次导出前也备份一次。备份使用 SQLite 在线备份 API 或 `VACUUM INTO`（WAL 模式下不直接复制数据库文件，避免得到不一致的副本）。

### 7.7 反馈与错误

- 错误信息回答三件事：发生了什么；哪些数据已经保存；接下来可以做什么。技术细节可展开查看，附关联 ID。
- 普通、低风险的操作不弹窗；批量操作（批量排除、批量标注、采用新识别结果）显示作用范围并要求确认，完成后显示可点击的"撤销"提示条。
- 未实现的功能不显示按钮；暂时不可用的按钮说明原因（如"需先识别本页"）。

### 7.8 无障碍与视觉

- 状态同时用文字或图标表示，不只依赖颜色。
- 控件有可读的名称与清晰的焦点样式；主要流程可完全用键盘完成。
- 界面语言为中文；所有用户可见文案集中管理，便于以后支持多语言。
- 首版追求清晰稳定，不追求视觉效果。

## 8. OCR 与处理策略

### 8.1 OCR 适配器接口

```python
class OcrEngine(Protocol):
    engine_id: str
    def version(self) -> str: ...
    def available(self) -> tuple[bool, str]: ...        # 是否可用，以及不可用的原因
    def supported_languages(self) -> list[str]: ...
    def recognize(self, image_path: Path, params: OcrParams) -> OcrResult: ...

@dataclass
class OcrResult:
    blocks: list[OcrBlock]   # 文本、归一化 bbox、可选行列表、可选置信度、可选类型建议
    raw: dict                # 引擎原始输出，原样保存
```

- PP-OCR 核心流程只返回行、不返回块（见 8.4）：块由 `core/structure/grouping.py` 按行距、缩进、对齐把行组合而成；启用版面组件时，先按组件给出的区域划分、再在区域内分组。规则必须有测试。
- 版面组件返回区域类别（标题、页眉等）时，作为 `block_type` 的初始建议，不静默应用（见 8.4）。
- 结果按阅读顺序排序：单栏书按从上到下；检测到疑似多栏（块的横向范围明显分为两组）时，页面标记"阅读顺序待检查"，不假装已正确排序。

### 8.2 页面渲染

- 识别用图像按需渲染到 `cache/ocr/`，DPI 可配置（默认值由 Phase 0 样本测试决定，预计为 300）。
- 审校显示用图像渲染到 `cache/view/`（中等分辨率；放大时按需渲染更清晰的版本）。
- 缩略图渲染到 `cache/thumbs/`。
- 缓存可以随时删除并重建，不影响项目数据；设置页提供"清理缓存"入口，Phase 0 需实测并记录每页缓存占用（供评估整书磁盘占用）。
- MVP 不做去噪、二值化、裁切；旋转只按 PDF `/Rotate` 处理。

### 8.3 文本的三个版本

1. `ocr_text`：OCR 原文，创建后不变；
2. `text`：用户审校后的最终文本，保留行内换行；
3. 导出文本：由 `text` 经清理规则生成，不回写数据库。

### 8.4 引擎选型

**第一引擎（文本主识别）：** PP-OCR 系列，部署形态在 PaddleOCR（官方）与 RapidOCR（ONNX）之间由 Phase 0 对比选定；若目标平台不可用，回退到上一代同系列模型。它负责文本检测与识别，给出文本行与**行级坐标**。**整个按行比对的方案都依赖它返回行级坐标，这一点必须在 Phase 0 实测确认。** **模型文件随安装包内置**（安装包约增大 100–300MB），安装后完全离线，不做首次联网下载——与产品的完全本地定位一致。

注意：PP-OCR 核心流程（文本检测 → 方向分类 → 文本识别）只产出"一行文字 + 行的框"，**不做版面分析**。版面能力在 PaddleOCR 生态中由 PP-Structure 流程（另一组独立模型，需单独调用）提供，在 RapidAI 生态中由 RapidLayout / RapidDoc 提供——两边都有版面能力，但都不是第一引擎自带，需要额外接入。

**版面与块类型（可选增强组件，独立于第一引擎，是否启用由 Phase 0 实测决定）：** 只接入**版面检测模型**——PP-DocLayout（PaddleOCR 生态）或 RapidLayout（RapidAI 生态），由它提供区域、类别与区域阅读顺序建议；文字识别仍由第一引擎完成。版面检测类别与 `block_type` 的对应关系：

| 版面检测类别 | block_type |
|---|---|
| 段落标题 / 文档标题 | heading |
| 文本 | paragraph |
| 页眉 | header |
| 页脚 | footer |
| 页码 | page_number |
| 脚注 | footnote |
| 图表标题 | caption |
| 侧栏文本等未映射类别 | other |

使用原则与边界：

- 版面模型的输出**只是建议，绝不静默应用**：可作为 `block_type` 的初始值，并为 6.5 的页眉 / 页脚 / 页码批量标注预填候选，但都必须经过预览与人工确认，整批可撤销。
- 它给出的是**区域**，不是自然段：一个"文本"区域通常包含多个自然段，区域内的行仍由 `grouping.py` 按行距、缩进分组成块。版面组件是补充，不是替代。
- 版面模型的训练数据偏论文、杂志、研报类版面；扫描老书的噪声、倾斜、老式排版下的类别准确率（尤其页眉 / 页脚 / 页码）必须用自己的样本实测，不能默认可用。
- 额外开销：模型体积几十至一百多 MB，CPU 上每页推理在数百毫秒量级（取决于机器，需实测），与 OCR 耗时叠加，可能出现"精度高的模型组合在一起很慢"的情况，Phase 0 一并记录。
- 未启用版面组件时：块由 `grouping.py` 按行距、缩进规则组合，块类型由人工标注或 6.5 的批量工具设置。

#### 8.4.1 三条主路径与选型

PP-StructureV3 不是单纯的"排版分析器"，而是一条**完整的解析流程**（版面检测 → 各区域分别识别 → 表格 / 公式处理 → 阅读顺序恢复 → 输出 Markdown / JSON），内部**自带识别模型**。因此"先用 StructureV3 分析排版、再用第一引擎识别文字"并不是它的用法，可选的路径实际有三条：

| 路线 | 组合方式 | 定位 |
|---|---|---|
| **C 基线** | 第一引擎全页识别 → `grouping.py` 按行距、缩进组合成块 | **先做通**；单栏中文书可能已经够用 |
| **B 增强** | 版面检测模型（PP-DocLayout 或 RapidLayout）→ 第一引擎识别 → 块类型继承区域类别 | **首选增强方向**；控制力最强 |
| A 对照 | PP-StructureV3 端到端解析 | **仅作 Phase 0 对照**，不作为主路径 |

**不把 PP-StructureV3 端到端解析作为主路径**的原因：

1. 其内置的识别模型由流程决定，不一定是我们选定的第一引擎版本；能否替换为指定模型需实测，不能假设。
2. 它面向论文、报告、杂志类文档设计，扫描书（噪声、倾斜、老式排版）的表现需单独验证。
3. 它会做排版决策（合并段落、生成 Markdown 结构、处理表格和公式），与"原文优先、结构由我们控制"的原则存在冲突；文本结构和块类型应由 Book2Text 自己的数据模型决定，并全部可审、可撤销。

**版面模型的价值主要在块类型，而不是分段：** 它给出的是区域而非自然段，段内分组仍靠 `grouping.py`；它真正省人力的地方是直接给出页眉、页脚、页码、脚注、标题等类别候选（见上表）。

#### 8.4.2 单页处理流水线（路线 B；路线 C 跳过第 1 遍）

```text
第 1 遍  版面检测（可选，小模型，全页）
          → 区域：类别 + 框 + 区域阅读顺序
          → 页眉 / 页脚 / 页码区域 → 对应 block_type 的候选（经 6.5 预览确认后生效）
          → 疑似多栏时，按区域顺序排序，而不是简单从上到下

第 2 遍  第一引擎识别
          → 得到每行文字与行级坐标
          → 行归入所在区域；区域内按行距、缩进组合成块（grouping.py）
          → 块类型的初始建议继承所在区域的类别

第 3 遍  第二引擎（Apple Vision / Windows 自带 OCR / Tesseract）
          → 只读取第 2 遍切出的行图，逐行识别
          → 逐行比对，标出分歧（见 8.5）

输出：块（类型建议 + 行 + 坐标）+ 每行的第二路候选 + 分歧标记
```

要点：

- **两级阅读顺序：** 区域顺序（第 1 遍）× 区域内行顺序（第 2 遍）= 全书阅读顺序，不需要额外的全局排序。
- **第 2 遍的两种接法，Phase 0 二选一实测：** ① 先按区域裁图再分别识别；② 全页识别后，再按行坐标把行归入区域。②少一次裁图，通常更简单；若区域内识别更准则选①。
- **第 3 遍完全独立于前两遍：** 第二引擎只认行图，版面层是否启用、用哪个版面模型，都不改变第二引擎的接法。
- **开销估计：** 第二引擎的开销取决于行数而非页数，本来就接近一遍整页识别；真正新增的是第 1 遍的版面检测，小模型每页约数十至一两百毫秒（需实测）。主要成本在于多一套依赖，而不是 CPU 时间。
- 版面模型给出的所有类别都只是**建议**，不静默应用（见上文使用原则）。

#### 8.4.3 第二引擎

**第二引擎（分歧检测）：** 独立于第一引擎的另一条技术路线，按行识别（见 8.5）。第二引擎**不需要版面能力**：行图由第一引擎切出，它只负责逐行读取。

| 平台 | 第二引擎 | 说明 |
|---|---|---|
| macOS（Apple Silicon） | Apple Vision（系统框架） | 免费、离线、速度快，支持简体中文与英文 |
| Windows x64 | Windows 系统自带 OCR（`Windows.Media.Ocr`） | 微软自家模型，与 PP-OCR 血统独立；印刷体中文尚可，速度快 |
| 兜底 | Tesseract | 两平台都可安装；中文较弱，仅作兜底 |

选择依据：第二引擎的唯一职责是**可靠地发现分歧**。它自身质量不足会产生大量假分歧，使分歧标记失去可信度。因此在第二引擎上，**质量比跨平台一致性更重要**。各平台的具体差异与已知坑见 8.6。

### 8.5 按行比对（分歧检测方式）

按行比对，不采用"两个引擎各自识别整页再对齐版面"的做法。

1. **第一引擎切行：** 对每一页，取 8.4.2 流水线第 2 遍的结果（路线 B 经版面区域分块，路线 C 由 grouping.py 分块），得到每个文本块及其所有行的文本框（归一化 bbox）。
2. **裁行图：** 按行 bbox（外扩约 2% 以保留笔画）从页图裁出单行小图，写入 `cache/lines/<page>/<line>.png`。
3. **第二引擎逐行识别：** 对这些小图识别，得到该行的第二个文本。
4. **逐行比对：** 比较两个文本，判定是否一致；不一致的行标记为"有分歧"。

这样做的原因：两个引擎的版面切分规则不同，整页结果无法可靠对齐；按行比对把问题降为"一行对一行"，无需处理版面对齐，而且分歧可以精确定位到具体行乃至具体字符。

**存储与重跑：**

- 第二引擎识别的是**行**，不是块，因此**不生成 Block**，只作为行级候选保存。
- 第二引擎的识别作为 `run_type = auxiliary` 的 OCRRun 记录（见 5.3），其行级结果写入对应 `BlockLine.aux_text` 与 `diff_status`。
- 行信息（行文本、行 bbox）保存在 `BlockLine` 表中，`line_index` 即块内阅读顺序。
- 第二引擎的参与方式与第一引擎无关，可以随时对已识别的页面**单独补跑或重跑**，不需要重跑第一引擎。

**一致性判定：** 先归一化，再比较。归一化规则见 8.7，对所有引擎共用。

- **实质差异：** 归一化后字符不同 → 标记"有分歧"，进入疑难队列。
- **格式差异：** 归一化前不同、归一化后相同（全角/半角标点、空白、连字符写法等）→ 不作为分歧，但在界面上可选显示。

不得把格式差异计入分歧统计，否则中文行会因为空格差异全部被标为分歧（见 8.6）。

**分歧标记的用处（MVP 的落点）：**

- 审校视图中，有分歧的行高亮，并显示另一路候选，点一下即可替换为另一路文本（作为对 `text` 的编辑，进入撤销历史）。
- 疑难筛选增加"有分歧"条件（第 6.4 节）。
- **不自动采纳任何一方的结果。** 分歧只影响"看哪里"和"从哪个候选开始改"，不改变原文事实。
- 分歧率与捕获率写入项目的质量统计（第 13.4 节）。

### 8.6 平台已知问题与处理

**Apple Vision（macOS）**

- 需要 `pyobjc`，只在 macOS 上可安装（依赖用环境标记管理：`sys_platform == 'darwin'`）；Windows 上该适配器不可用（`available()` 返回 false 及原因）。
- 支持的语言需在系统中已安装；启动时检测简体中文是否可用。
- 对倾斜、竖排、装饰体的古籍版面识别明显变差（属于已知限制）。
- 不提供逐词置信度。

**Windows 系统自带 OCR**

- **依赖系统语言包中的"光学字符识别"组件。** 缺少中文组件时，**引擎不会报错，而是返回空结果**。因此必须在启动时主动检测（尝试创建中文识别器），不可用时要明确提示"需要安装中文 OCR 语言包"，并给出安装路径说明（设置 → 时间和语言 → 语言 → 中文 → 语言选项 → 可选功能）。
- **识别中文时会自动在字与字之间插入空格**（例如"探索" → "探 索"）。这必须在比对前作为格式差异归一化掉，否则中文行的假分歧率会接近 100%。用户的最终文本以第一引擎的结果为起点，不受此影响。
- 单次识别的图像有边长上限（约 2600 像素）。按行裁出的小图远低于该上限，不受影响。
- 不返回逐词置信度。

**Tesseract（兜底）**

- 中文识别质量明显弱于上述两者，会产生大量假分歧，默认不作为首选；仅在系统引擎不可用时启用，并在界面中说明"当前第二引擎质量有限，分歧标记可能偏多"。
- 需要单独安装语言数据（`chi_sim`、`eng`）并确认版本兼容。

**通用要求：**

- 设置页必须明确显示**当前实际使用的第二引擎**，以及在某个平台上为什么没有使用首选引擎。
- 如果所有第二引擎都不可用，应明确显示"第二意见不可用"，**不显示分歧标记，也不假装仍在比对**。

### 8.7 归一化与比对模块（`core/ocr/compare.py`）

该模块不属于任何引擎，所有引擎共用，必须有完整单元测试。

归一化步骤（顺序固定）：

1. 统一换行与空白字符；去除行首尾空白。
2. 全角 ↔ 半角标点映射（仅在比对时使用，不修改原文本）。
3. **删除中日韩字符之间的空格**（用于抵消 Windows OCR 的插空格行为）。
4. 常见等价符号归一化（如不同的引号、破折号写法）。
5. 拉丁字母大小写：默认不归一化（大小写属于原文），仅在英文比较的宽松模式下可选。
6. 英文行尾连字符：不在此处处理，交由导出规则的"断词还原"负责。

比对输出：

- `identical`：归一化后相同；
- `format_only_differs`：仅格式差异（可显示，不计入分歧）；
- `differs`：实质差异（计入分歧）。

**核心指标（在人工校对样本上计算）：**

| 指标 | 含义 | 期望方向 |
|---|---|---|
| 分歧率 | 被标记为有分歧的行占全部行的比例 | 越低越好（假分歧少） |
| 捕获率 | 第一引擎的错误行中，被标为分歧的比例 | **越高越好（最关键）** |
| 一致但都错 | 两路一致但都偏离金标准的行比例 | 越低越好（决定一致处能否快扫） |

**必须逐平台实测。** macOS 上的捕获率不能用来推断 Windows，两个平台的第二引擎不同，指标要分别计算并分别记录。

### 8.8 在线视觉模型的使用边界（第二阶段，默认关闭）

- **不允许**用在线大模型直接识别整页或整本书。
- **不允许**让在线模型作为"仲裁者"在多个候选中挑选（它会倾向于选择语言上更通顺的结果，而不是图中实际印刷的内容，在印刷错误、旧拼写、专有名词处尤其容易选错）。
- **允许**的方式：对**有分歧的行**截图，以**盲读**方式提交——不告知模型其他引擎的结果，要求"仅转录图中可见文字，看不清用 `[?]` 标记，不翻译、不补全、不纠正"。其结果作为**第三票**，只用于在界面上提示"2:1 倾向"，最终仍由审校人决定。
- 优先级：**先评估本地视觉模型**（在 Apple Silicon 上可运行的小型视觉 OCR 模型）；本地模型不满足需求时，才考虑在线模型。
- 在线调用必须是项目级开关、默认关闭；每次发送前显示将上传的范围与页数；只上传分歧行的小图，不上传整页（除用户明确选择）。
- 记录每次调用的模型名称、时间、输入范围与结果，并保留可关闭的开关。

## 9. 导出格式规范

### 9.1 段的生成

1. 按 `page_no`、`order_index` 顺序遍历块，条件为：所在页 `include = true` 且页面类型在导出范围内；块未删除、`include = true`、块类型在导出范围内；范围为"仅已确认"时块须为 confirmed。
2. `continues_to_next = true` 的块与下一个符合条件的块组成同一段（中间被排除的页眉、页脚、页码块自动跳过）。
3. 标题块单独成段，不与前后正文合并。
4. 每段记录来源：涉及的页码、块 ID、各块审校状态。

### 9.2 行合并规则（段内拼接）

块内换行和跨块拼接使用同一规则，按换行位置两侧的字符决定：

| 换行前 | 换行后 | 处理 |
|---|---|---|
| 中日韩字符或全角标点 | 中日韩字符或全角标点 | 直接连接，**不加空格** |
| 拉丁字母 + 行尾连字符 `-` | 小写拉丁字母 | "英文断词还原"开启时删除连字符并直接连接；关闭时保留连字符并直接连接 |
| 拉丁字符或半角标点 | 拉丁字符 | 加一个空格 |
| 中日韩字符 | 拉丁字符（或反之） | 直接连接，不额外加空格 |

- 所有被"英文断词还原"处理过的位置都记录在 `manifest.json` 中，便于抽查（例如 `self-` + `evident` 这类真实连字符可能被误处理）。
- 规则实现必须有覆盖上表每一行的单元测试。

### 9.3 清理规则（MVP）

| 规则 | 默认 | 说明 |
|---|---|---|
| 排除页眉 / 页脚 / 页码块 | 开 | 按块类型排除 |
| 段内行合并 | 开 | 按 9.2 规则；关闭时保留原始换行 |
| 英文断词还原 | 开 | 见 9.2 |
| 规范化换行符 | 开 | 统一为 LF |
| 去除行首尾多余空白 | 开 | 不改变行内字符 |

不得提供或默认开启：全局替换引号或破折号、统一全角 / 半角、拼写纠正、删除"疑似重复行"。

**与分歧检测的关系：** 分歧标记只影响审校时"看哪里"，不参与导出；导出只使用 `text` 与清理规则（见 8.7 的归一化只用于比对，不修改原文）。

### 9.4 TXT

- 编码 UTF-8（无 BOM），换行 LF。
- 段与段之间空一行；标题前后各空一行。
- 可选：在页面边界插入页码标记 `〔p.87 / 印71〕`（默认关闭）。
- 可选：脚注以"页末附注"方式输出，放在包含该页结尾的段之后，以 `［注］` 开头（默认不导出脚注）。

### 9.5 JSONL

每行一个段。示例（为便于阅读而换行，实际文件中每条占一行）：

```json
{"schema": "book2text.segment.v1",
 "segment_id": "01J9ZK3M8Q…",
 "seq": 57,
 "type": "paragraph",
 "text": "In the early years of the …",
 "pages": [{"page_no": 87, "page_label": "71"}, {"page_no": 88, "page_label": "72"}],
 "block_ids": ["01J9ZK3M8Q…", "01J9ZK4A2B…"],
 "review": {"all_confirmed": false, "unreviewed": 1, "uncertain": 0, "modified": true},
 "source": {"engine": "rapidocr", "engine_version": "x.y.z"}}
```

同一目录生成 `manifest.json`：项目名、源文件名与 SHA-256、导出时间、应用版本、导出范围、启用的规则、断词还原位置列表、统计数据。

## 10. 跨平台规范

| 主题 | 规则 |
|---|---|
| 路径 | 一律使用 `pathlib`；数据库与 JSON 中只存项目内相对路径，统一用 `/` 分隔 |
| 编码 | 所有文件读写显式指定 `encoding="utf-8"`；日志与控制台输出同样处理 |
| 换行 | 导出统一为 LF；仓库用 `.gitattributes` 统一源码换行 |
| 文件名 | 项目内文件名只用 ASCII（ID、编号）；书名只存数据库，不用作路径 |
| 路径长度 | 项目文件夹名简短（如 `b2t_7KQ2M9`），避免触发 Windows 260 字符限制 |
| 网盘同步 | 不在网盘同步进行中使用项目；文档提示"交接前先关闭应用，等待同步完成" |
| 子进程 | 统一使用 `multiprocessing` 的 `spawn` 方式（Windows 默认如此，Mac 显式设置以保持一致） |
| 平台分支 | 只允许出现在 `core/platform.py`（打开文件夹、默认目录等） |
| 目标平台 | macOS Apple Silicon（arm64）与 Windows x64；不支持 Intel Mac 与 32 位 Windows |
| 依赖 | 新增依赖须确认在 macOS arm64 和 Windows x64 上都有可用的安装包（wheel）；平台专属依赖（如 pyobjc 仅 macOS）用环境标记声明（如 `sys_platform == 'darwin'`），避免在另一平台安装失败 |
| 任务包与结果包 | ZIP 内部路径统一用 `/`、文件名用 UTF-8 编码；在 Mac 生成的包必须能在 Windows 打开，反之亦然 |
| 测试 | 每个阶段验收时，至少在一台 Windows 电脑和一台 Mac 上实际运行 |
| 启动 | `scripts/start.command`（Mac）与 `scripts/start.bat`（Windows），两者只调用同一个 Python 入口 |

## 13. 质量保证

### 13.1 测试样本

从 1–2 本真实书籍中截取 20–40 页制成测试 PDF，覆盖：普通单栏正文、章节标题、页眉页脚页码、脚注、英文专名 / 数字 / 标点、中文与中英混排、跨页段落、低清晰度或倾斜页面，以及一页复杂版面（作为已知限制）。其中 5–10 页人工校对作为金标准。未经人工校对的 OCR 输出不能作为金标准。**样本制作与金标准校对由开发者在 Phase 0 开始前完成，是 Phase 0 的前置输入。**

### 13.2 自动测试重点

- **核心层单元测试：** 坐标转换（含旋转）、行组合、段生成、行合并规则（中英文各种组合）、清理规则、重识别规则 R2、确认整页规则 R3、合并 / 拆分、撤销 / 重做、数据库迁移。
- **第二引擎相关测试：** 归一化与比对模块（中英文、全角半角、**中文中插入空格的场景**）、行裁图边界（首行 / 末行 / 紧邻块的行）、辅助 Run 的清空与重跑（重跑后 `aux_text` 与 `diff_status` 应完全重建）、分歧行定位到正确块与行。
- **集成测试：** 导入 → 识别（可使用假引擎）→ 编辑 → 导出；校验 JSONL 每行都是有效 JSON、预检数量与实际导出一致、排除内容不出现在导出中。
- **中断测试：** 识别过程中结束服务进程，重启后任务为 interrupted，继续后不产生重复块。
- **跨平台测试：** 同一测试集在 Mac 与 Windows 上运行；同一项目文件夹在两个平台间拷贝后，可以打开并导出完全相同的结果。

### 13.3 UX 验收场景

**场景 A：导入与样本识别**
新建项目 → 上传测试 PDF → 看到缩略图 → 排除封面 → 选 5 页识别样本 → 在审校视图检查 → 启动全部识别。
通过标准：无需逐页分类；进度真实；样本结果与页面对应正确。

**场景 B：按页审校**
打开第一个未完成页 → 修改一处文字 → 将一块标记为不确定 → 合并两个被错误拆开的块 → 确认本页 → 自动进入下一页 → 撤销刚才的合并。
通过标准：保存状态清晰；不确定块未被确认；原图联动高亮正确；全程可以只用键盘完成。

**场景 C：页眉页脚批量标注**
用结构工具标注全书页眉页脚 → 预览 → 取消一个误判 → 应用 → 整体撤销 → 再次应用。
通过标准：数量准确；人工设置过类型的块不被覆盖；撤销完整。

**场景 D：中断与恢复**
编辑过程中关闭浏览器并结束服务 → 重新启动 → 在项目库点击"继续"。
通过标准：已编辑内容都在；回到原页；中断的任务可以继续。

**场景 E：导出**
项目中同时存在已确认、未审、不确定和排除的内容 → 打开导出 → 查看预检与预览 → 导出 TXT 与 JSONL → 打开文件检查。
通过标准：数量与预检一致；跨页段落正确拼接；中文之间没有多余空格；英文断词处理位置写入 manifest。

**场景 F：跨平台交接**
在 Mac 上完成部分审校 → 关闭应用 → 将项目文件夹拷贝到 Windows → 打开、继续审校、导出。
通过标准：数据完整；上次位置正确；导出结果与在 Mac 上导出的一致。

**场景 G：审校任务包往返（协作阶段）**
负责人在 Mac 上分派第 10–19 页给助手 → 助手在 Windows 上打开任务包 → 修改文字、确认、拆分一块、添加备注 → 导出结果包 → 同时负责人在主项目中修改了第 12 页的一块 → 负责人导入结果包。
通过标准：第 12 页被标为冲突且未被自动覆盖；其他变化可以一键接受；字符级差异显示正确；备注可见；合并后的修改可追溯到助手和任务包，并可整体撤销；重复导入同一结果包不会重复写入。

### 13.4 质量指标（保留数据，供后续统计）

CER / WER（对照金标准）、分歧率、捕获率、一致但都错的比例、人工修改率（`text != ocr_text` 的块所占比例）、每页平均审校时间、不确定块数量、任务失败率、恢复成功率。

## 14. 分阶段开发路线

### Phase 0：技术可行性验证（不开发业务功能）

1. **第一引擎与版面组件实测（macOS arm64）——分三层评估，不要混在一起：**

   | 层次 | 测什么 | 判据 |
   |---|---|---|
   | 行级 | 第一引擎的中文、英文、中英混排 CER（对照金标准）、**是否返回行级坐标**、每页耗时、内存占用与安装难度 | **门槛项**，不达标方案要改 |
   | 版面 | 分块是否合理、阅读顺序是否正确（尤其多栏） | 相对"只用 grouping 规则"是否有明显提升 |
   | 块类型 | 页眉、页脚、页码、脚注、标题的识别准确率 | 能否把页眉页脚的人工工作量降下来（这层最值得花时间，直接决定人力投入） |

   **先量化门槛再实测：** 以可接受的全书批量时间反推每页耗时上限（例如 400 页的书、可接受 2 小时 → 每页 ≤ 18 秒），连同可接受的分歧率 / 捕获率区间一并写入 `docs/ocr-evaluation.md` 的开头，再开始测试。

   按第 8.4.1 节的三条路线实测并选定方案：
   - **C 基线**：第一引擎全页识别 + `grouping.py`。先跑通，作为所有对比的基准。
   - **B 增强**：版面检测模型（PP-DocLayout 或 RapidLayout）+ 第一引擎识别。重点看：块类型准确率（尤其页眉 / 页脚 / 页码）、多栏页面的阅读顺序、每页额外耗时；并对比"先裁区域再识别"与"全页识别再按坐标归入区域"两种接法。
   - **A 对照**：PP-StructureV3 端到端，只用来对照其输出质量，**不作为主路径候选**（理由见 8.4.1）。

   第一引擎的部署形态（PaddleOCR 或 RapidOCR）在路线 B、C 内一并对比：同一模型在两种运行方式下的 CER、行级坐标与速度，以及 RapidOCR 是否提供所选模型版本。在样本书上块类型识别得准、整体耗时可接受的组合胜出（并准备上一代同系列模型作为回退）。注意：版面模型给出的是区域而非自然段，区域内行仍需 grouping.py 分段；扫描老书与论文 / 杂志类版面差异大，以实测为准；版面组件的体积、每页额外耗时与每页缓存占用一并记录。**每页耗时与行级坐标是门槛，结论必须明确。**
2. **第二引擎实测（逐平台）：** 在 macOS 上验证 Apple Vision 的中文 / 英文识别、可用性与行级裁图输入；写出 Windows 自带 OCR 的验证步骤（含语言包检测）。在样本上分别计算**分歧率、捕获率、一致但都错**三个指标（第 8.7 节），macOS 与 Windows 的数字必须分别记录。
3. **PDF 库选定：** 对比 `pypdfium2` 与 `PyMuPDF` 的渲染效果、页码标签读取、文本层检测与许可证。
4. **最小骨架：** `uv` 环境 + FastAPI 服务 + 一个静态页面，页面可上传 PDF 并显示第一页图像；在 Mac 和 Windows 上通过启动脚本运行成功。骨架中加一个"引擎自检"接口：列出第一 / 第二引擎是否可用、版本、以及不可用的原因（Windows 语言包缺失要能明确报出）。
5. 输出 `docs/technical-feasibility.md`：已验证 / 未验证事项、平台差异、推荐方案、风险。

验收：两个平台都实际跑通骨架；第一引擎的行级坐标与每页耗时、版面组件的分块质量与块类型准确率（含路线 B / C 与部署形态的选定结论，以及路线 A 的对照结果）、第二引擎逐平台的分歧率与捕获率都有实测数据。**完成后暂停，等待开发者确认。**

特别提醒：若第一引擎不返回行级坐标，或每页耗时导致全书识别时间不可接受，必须立即向开发者报告并调整方案（例如改用按块比对、或调整模型档位），不要静默降级。

### Phase 1：项目库与页面视图

### Phase 7：根据真实使用优化

块级疑难队列模式、快捷键调整、章节导航（基于标题块）、直接提取已有文本层、审校时间与修改率统计、**导出对照模式**：导出预览升级为左侧原图、右侧导出形态的连续段文本，点击段跳转来源页并高亮来源块（段 → 块 → 页的溯源数据见 9.1，无需新增存储）。识别完成后的对照检查直接使用审校视图（7.4），不设独立视图。

- 工具示例：`list_projects`、`project_summary`、`list_uncertain_blocks`、`get_page_image`、`submit_candidate`（把视觉模型的转录作为新的候选提交，`actor = agent`）、`quality_report`。

- 调用在线模型前，必须向用户展示将要发送的范围（哪些页面或区域）。
- MCP 服务与 Web 界面同时运行时，必须经由同一个本地服务写入数据，避免两个进程同时写同一个数据库。

## 16. 风险清单

| 风险 | 应对 |
|---|---|
| OCR 效果不佳，或在某个平台上装不上 | Phase 0 双平台实测（PaddleOCR 与 RapidOCR 两种部署形态对比）；适配器封装，可替换引擎 |
| Windows 上的编码、路径、进程问题 | 遵守第 10 节规范；每个阶段在 Windows 上实测 |
| 审校效率低 | 按页审校、整页确认、页眉页脚批量工具、键盘操作 |
| 重新识别覆盖人工成果 | 规则 R2：人工成果只能由用户选择替换 |
| 跨页段落断裂，影响后续对齐 | `continues_to_next` + 稳定的段 ID 规则 |
| 清理规则误改正文 | 规则只作用于导出；可开关；断词处理位置写入 manifest |
| 坐标错位 | 统一归一化坐标；旋转页测试 |
| 第一引擎不返回行级坐标 | Phase 0 优先验证；不能返回时降级为块级比对并向开发者报告 |
| 端到端解析流程的排版决策改写原文结构 | 不把 PP-StructureV3 端到端作为主路径；只接版面检测模型，类别仅作建议，经人工确认生效 |
| 版面组件对扫描老书效果不佳 | Phase 0 第三层实测分块质量与块类型准确率；不达标则不启用版面组件：块由 grouping.py 组合，块类型靠人工标注与 6.5 批量工具 |
| 第二引擎产生大量假分歧 | 逐平台实测分歧率与捕获率；中文空格等格式差异在归一化中处理；指标不合格就不启用该引擎 |
| Windows 缺少中文 OCR 语言包导致静默空结果 | 启动时主动检测；明确提示安装方法；不可用时关闭分歧标记并说明 |
| 两路一致但都错 | 单独统计该比例，作为"一致处可快扫"的可信度依据；必要时抽样人工复核 |
| 在线视觉模型被当成事实来源 | 只做盲读第三票，只上传分歧行，永不自动采纳；界面始终标注候选来源 |
| 任务中断导致数据丢失或重复 | 按页拆分 JobItem、幂等处理、中断测试 |
| 网盘同步导致数据库损坏或冲突 | 项目锁；交接说明；自动备份 |
| 本地服务被其他网页访问 | 只监听 127.0.0.1；会话令牌；Origin 校验 |
| PDF 库或 OCR 许可证限制分发 | Phase 0 评估，优先许可证宽松的库 |
| 大型书籍性能问题 | 虚拟滚动、按需渲染、缓存；设置页提供缓存清理入口 |
| 非专业开发者难以维护前端构建 | 前端构建产物随版本提供；最终用户无需安装 Node.js |
| 协作合并覆盖负责人或助手的成果 | 基于 revision 的冲突检测（R6）；冲突必须人工处理；合并按 batch 可撤销；被拒绝的结果保留存档 |
| 两位助手改到同一页 | 同一页面同一时间只能属于一个未完成的任务包 |
| 任务包和结果包版本不兼容 | 包内记录格式版本与应用版本；不兼容时明确拒绝并说明需要升级哪一方 |
| 任务包外传带来的版权与隐私风险 | 包内只含分派页面及上下文页；在分派对话框和手册中提示仅限团队内部传递 |
| 未签名应用被系统拦截 | 手册中说明打开方法；对外分发时再做签名 |

## 17. 已确认事项与待确认问题

**已确认：**

1. 团队需要协作处理同一本书：负责人做识别与准备，分派页面给助手审校，助手回传结果，负责人审阅后合并。→ 采用离线"审校任务包"方案（第 6.7、7.9 节，Phase 5）。
2. 语言：中文和英文（含中英混排）。→ 第一引擎在 PP-OCR 系列内由 Phase 0 实测选定（PaddleOCR 或 RapidOCR）；版面组件只接版面检测模型（PP-DocLayout / RapidLayout），为可选增强，是否启用由 Phase 0 实测决定；PP-StructureV3 端到端解析只作对照，不作为主路径；第二引擎按平台选用 Apple Vision / Windows 自带 OCR / Tesseract（第 8.4 节）。
3. 平台：Mac 为 Apple Silicon（M 系列），Windows 为 64 位。→ 目标平台为 macOS arm64 与 Windows x64。
4. 助手**允许**做结构调整（合并、拆分、移动、新增块）；含结构变化的页面在合并时按整页接受或拒绝。
5. 负责人**不强制**对助手已确认的内容做二次确认；合并后标记审校人，负责人可按审校人筛选抽查。

**待确认（未确认时按括号中的默认假设执行）：**

6. 典型书籍的页数与数量？（默认：单本 200–600 页，同时处理的项目不多）
7. 是否需要将应用分发给团队以外的人？（影响 PDF 库与 OCR 引擎的许可证选择以及应用签名；默认：仅团队内部使用）

## 附录：核心 UX 验收清单

- [ ] 在 Mac 和 Windows 上都能启动并使用。
- [ ] 项目库能看懂每个项目的识别进度、审校进度和问题数量，并能一键继续。
- [ ] 不必在识别前逐页分类。
- [ ] 能先识别样本页，再决定批量识别。
- [ ] 所有长任务显示真实状态；中断后可以继续，且不产生重复数据。
- [ ] 按页审校：原图与文本块双向联动（有坐标时），确认整页后自动进入下一页。
- [ ] 能修改块类型、合并、拆分、调整顺序、标记跨页延续。
- [ ] 能批量标注页眉页脚，并可整体撤销。
- [ ] 保存状态真实；保存失败时不丢失编辑内容。
- [ ] 重新识别不会自动覆盖人工成果。
- [ ] 导出前能看到未审、不确定、排除和预计导出数量，并能预览。
- [ ] 跨页段落拼接正确；中文之间不插入多余空格。
- [ ] TXT 与 JSONL 的用途与差异清楚。
- [ ] 项目文件夹可以在 Mac 与 Windows 之间交接。
- [ ] 未实现的功能不会以可用按钮或虚假状态出现。
- [ ] （协作）负责人能分派页面生成任务包，并看到每段页面的分派状态。
- [ ] （协作）助手只能审校分派的页面，不能运行 OCR 或导出全文。
- [ ] （协作）合并时能看到字符级差异；冲突不会被自动覆盖；合并可整体撤销并可追溯到助手。
- [ ] （第二阶段）第二引擎可用时显示分歧；不可用时明确说明，不假装在比对。
- [ ] （第二阶段）分歧行可以一键换用另一路候选，并进入撤销历史；系统从不自动采纳。

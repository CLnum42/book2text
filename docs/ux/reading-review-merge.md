# 正文审校 × 结果预览 合并：连续正文流

> 状态：设计稿（未改产品代码）。基线 `main@7c5b92d`（差异队列、`diff_ack`、字符级 spans 都已实现）。
> 依据：用户 2026-10-27 原话（见 §0）、`docs/pm/pipeline-decision.md` 的真实计数、上两单的 `review-workspace-v2.md`。
> 产出：本文 + `reading-review-merge-mockup.html` / `.png`（三档宽度 + 628 高，五个状态）。
> **一个推荐方案，不列 A/B/C。**

## 0. 用户原话（验收标准）

> "正文审校和结果预览有没有必要合并？……如果两个 OCR 版本无差异，即作为正常预览文本；如果有差异，则把推荐的版本放在预览中，并红色高亮，表示需要审校。点击红色高亮文本，即在段落（或行？感觉行级单位更好？）下方展开另一个 OCR 替补版本。展开的替补 OCR 版本内容旁边可以点击应用。如果用户觉得两个版本都不好，那么可以自行在文本框中进行编辑。然后点击提交保存，后台更新到数据库中。"

以及："为什么目录和审校部分，你都设计的单页，而非多页滚动？每审校完一页还要点按钮到下一页，有点麻烦。"

## 1. 结论

1. **合。** 「正文审校」与「结果预览」合成一个**连续正文流**：左 PDF 多页滚动、右正文逐段排开、两路一致就是正常文本，不一致才出现红字。步骤条 **7 → 6**，第 6 步「文件导出」承接预检与落盘。
2. **审校单位是行，排版单位是段，导航单位是页。** 行级展开（用户判断正确）；展开面板作为块级元素插在**两行之间**，段落只在该处自然断行，不拆段。
3. **密度不是问题，单条成本才是问题。** 1733 条 × 平均 1.8 字 ≈ 3120 字 = 全文 **1.4%** 的字符；约 **12.7%** 的行带标记；一屏（约 17.5 行）平均 **2.2 处**。真正贵的是 80.9% 打开后原文是对的——所以设计重心在**一次点击判完一条 + 键盘**，不在减少标记。
4. **草案层**：采用 / 保留 / 手改三种动作都先落草稿（琥珀色），顶部「提交 N 处改动」一次写库；草稿进 localStorage。
5. **单页翻页取消**：连续滚动 + 双向行级同步 + 「下一处未审」跳转。用户问得对——394 页 × 2 次翻页 ≈ 788 次点击本来就是白花的。

## 2. 为什么该合，以及哪些不合

**该合的理由**（都是可量化的）：

- 现状审校在「页面视图的右栏」，看不到组装后的段落与跨页拼接；预览在导出对话框里，两处都不完整。用户要判的是"这段文字最终对不对"，答案只在组装结果里。
- 单页翻页把 394 页变成 788 次点击 + 788 次页面渲染等待，而它只回答"我在第几页"——这件事左树与进度条已经能做。
- 合并后，**审校看到的文字 = 导出的文字**（同源组装），"审的是不是最终交付的东西"这个疑问从根上消失。

**不该合的东西**：

| 保留 | 理由 |
|---|---|
| 左树（目录 + 每页待审数） | 它是全书的地图与进度；正文流再长也替代不了"我在第几章" |
| 左 PDF（多页滚动） | 它是唯一的事实来源；判字必须看图 |
| 导出步骤 | 预检、格式、记录、manifest 不属于"读" |
| 块级结构操作（类型、合并、拆分、排除） | 低频，进正文区的 `⋯` 或块的浮动菜单，不占主界面 |

## 3. 三个单位与 DOM 结构

| 单位 | 职责 | 数据 |
|---|---|---|
| **页** | 同步、跳转、进度（左树 + PDF 滚动 + 行尾页标） | `page_no` |
| **段** | 排版容器；跨页段已合并；连续流的最小视觉单位 | `segments[]`（`pages`、`block_ids`、`text`） |
| **行** | 审校数据单位；一条差异一行；展开面板挂在行下 | `block_line`（`line_index`、A 文本、B 文本、`diff_ack`、行框） |

- 渲染：一个段落 = 一个块容器，里面按行顺序排 **行元素**（`<span class="ln" data-block data-line>`），行与行之间**不加换行**，由字流自然连成一段——这就是"合并段内换行"的显示层实现。
- 差异红字 = 行元素内部的一段 `<mark>`（字符区间），**只包差异字符**，沿用任务 63 的 `computeCharSpans`。
- 展开面板 = 插在两个行元素之间的块级元素（`display:block`），因此该段在面板处断行；关掉即回流。**段仍是同一个段**，DOM 不拆、`block_id` 不变。

### 3.1 行级 vs 段落级（用户问的）

**行级。** 三个理由：

1. 数据本来就是行级（后端一条 `LineDivergence` 一行，候选也只有这一行）；
2. 段落级展开会把整段（8–20 行）挤下去，读到一半的段落被推走，**上下文丢失比多一次点击更贵**；
3. 行级才能做到"一条差异一次判断"的成本模型。

代价与处理：

- 段落被面板暂时撑开：面板左缩进 24px、左侧 2px 彩条、宽度 = 段宽 − 24px，视觉上它是"注"，不是正文；
- 同屏只允许展开一处：点另一处红字，上一处自动收起（否则连续流会被撑成碎片）；
- 面板关闭后段落立即回流，不残留空行。

### 3.2 段内行边界从哪来（这是唯一的架构依赖）

组装文本在导出侧由 `join_pair` 生成（去首尾空白、CJK 不加空格、拉丁加空格、行末连字符还原）。审校视图要"在组装文本里标出某一行的字符"，就需要知道每行在段文本里的**偏移**。

**推荐：后端在段记录里下发 `line_spans`**（组装时本来就知道）：

```jsonc
// GET /export/preview 的 segments[] 增加
{ "seq": 128, "text": "维太平不易之元……", "pages": [87, 88], "block_ids": ["b1","b2"],
  "line_spans": [ { "page_no": 87, "block_id": "b1", "line_index": 0, "start": 0,  "end": 30 },
                  { "page_no": 87, "block_id": "b1", "line_index": 1, "start": 30, "end": 61 } ] }
```

- 前端据此把段文本切成行元素，红字落在行内——**审校看到的字与导出完全一致**，不需要在前端重写 `join_pair`。
- 过渡方案（如果这一刀后端排不上）：前端按同样的 4 条规则拼（`join_pair` 的规则可移植），并用**每页一致性校验**兜底——把前端拼出的段文本与 `/export/preview` 的同段做一次 diff，不一致的段只读不给审（宁可少审一段，不可审错位置）。过渡方案是权宜，`line_spans` 落地后删掉。

## 4. 红点密度与分级

用户担心"1733 处会不会红成一片"。算一下（全书 22.4 万字 / 390 页 / 约 35 行一页）：

| 指标 | 数值 | 说明 |
|---|---|---|
| 差异字符占比 | 1733 × 1.8 字 ≈ 3120 / 224,000 = **1.4%** | 红的是字，不是块 |
| 带标记的行占比 | 1733 / 13,650 ≈ **12.7%** | 平均每 8 行一处 |
| 一屏（628 高、28px 行高、可用 492px ≈ 17.5 行） | ≈ **2.2 处** | 读完一屏遇到两处，节奏正常 |
| 其中第二引擎自己的错 | **80.9%**（约 1418 条） | 打开多半是"原文是对的" |

**结论**：密度不构成阅读障碍，不需要为了"少红"去降级显示。要解决的是**单条成本**。

分级与过滤：

- **同一套红色，两种形状**：汉字级 = 实线下划线，标点级 = 虚线下划线（灰度也分得开）。不引入第二个颜色。
- 默认**全部显示**。
- 过滤三档（工具条下拉）：`全部差异 / 只看汉字级 / 只看未审`（隐藏已审绿）。
- **不提供**"按可信度排序"或"批量静默保留"：没有可靠信号（`pipeline-decision.md` 已证明置信度不可用），批量静默就会丢真错。

## 5. 别让人漏审

四个机制，都常驻：

1. **进度（顶部工具条，44px 内）**：`已处理 300 / 1733` + 细进度条 + `未提交 12` 徽标。
2. **「下一处未审 ⏎」按钮**：在进度右侧，**任何滚动位置都可见**（工具条 sticky）。跳转后自动展开那一处并滚到视口 40%。
3. **方向感**：`↑ 上一处` / `↓ 下一处` 两个小按钮 + 键盘 `[` / `]`；到了文末仍有未审，跳转**回卷到第一处**，并提示 `已回到第一个未审（第 87 页）`。
4. **完成态**：`1733 / 1733 · 全部处理完` + 进度条转绿 + 主按钮变 `提交并前往导出`。

左树（232px）保留每页剩余数：`第 370 页 13 处` 这个数字随处理实时减少，是"粗进度"；顶部是"细进度"。两者同源（草稿 + 已提交）。

## 6. 编辑态与草稿层

### 6.1 三种动作，一个草稿层

| 动作 | 结果 | 落库时 |
|---|---|---|
| 采用候选 | 行文本 = B | `PATCH block.text` + `diff_ack=adopted` |
| 保留原文 | 文本不变 | `diff_ack=kept` |
| 自己改 | 文本 = 用户输入 | `PATCH block.text`（差异随之重算） |

**全部先进草稿**：不写库、不刷新整页——这是把单条成本从 2.5–5 秒压下来的关键。

### 6.2 正文流里的标记色（行内，白纸底）

| 状态 | 填充 | 下划线 | 灰度下靠什么 |
|---|---|---|---|
| 未审 · 汉字级 | `rgba(220,38,38,.12)` | 2px 实线 `#dc2626` | 实线 + 底色 |
| 未审 · 标点级 | `rgba(220,38,38,.10)` | 2px **点线** `#dc2626` | 点线 |
| 已审（保留原文） | `rgba(22,163,74,.12)` | 2px **点线** `#16a34a` | 绿点的疏密与红点不同 + 无实线 |
| 草稿（采用/手改） | `rgba(217,119,6,.14)` + 左侧 3px 竖条 | 2px 实线 `#d97706` | 竖条是形状通道 + `草稿` 文字 chip |

- 文字本身的对比度：白底叠 12–14% 色后墨色对比度仍 >12:1，逐字读音不受影响。
- 已审**不长期留绿**：采用后该行文本已等于候选、差异消失，只闪绿 1.2 秒；绿色只留在"保留原文"的行上（差异仍在）。

### 6.3 视觉

- 草稿行：行底色琥珀 14% + 左侧 3px 琥珀竖条 + 行尾 `草稿` 小 chip（文字，不只靠色）。
- 已提交的采用行：红字消失（文本已等于候选）；已提交的保留行：红转**淡绿**（差异仍在，但已决定）。
- 采纳瞬间给 1.2 秒绿色闪一下再消失——这是"我按对了"的反馈，不长期留绿（否则绿色只增不减，页面越读越花）。

### 6.4 进入与退出编辑

- 入口：展开面板里的 `自己改`，或行尾 hover 出现的 `✎`，或直接双击行。
- 形态：该行变成单行编辑框（等宽行高、无边框、行底色白 + 琥珀左轨），**只覆盖这一行**，上下行不动。
- `Esc` 取消并还原；`⌘/Ctrl + ↵` 收进草稿；失焦也收进草稿（不丢）。
- 与"采用"共存：编辑框开着头部的 `[采用第二路]` 仍可点，点后文本框内容替换为 B 并保持编辑态，光标在行首。

### 6.5 提交

- 顶部右侧 `提交 12 处改动`（有草稿时为主按钮，无草稿时禁用并写 `没有待提交的改动`）。
- 点击 → 确认面板：按页分组列出（`第 87 页 · 采用 2 · 保留 3 · 手改 1`），底部 `提交全部 / 取消`。
- 提交中逐块 PATCH（一页一块，几十次请求），进度条真实推进；失败项**留在草稿**并列出原因，成功的转"已提交"。
- 草稿存 localStorage（键：project + block + line），重新打开提示 `有 12 处未提交（10-27 15:32）[恢复] [丢弃]`。
- 提交后左树计数与顶部进度同步刷新；**进度 = 草稿 + 已提交**，`未提交 N` 单独标。

## 7. 步骤条 7 → 6

| 旧 | 新 |
|---|---|
| ①页面确认 ②版心确认 ③文字识别 ④目录确认 | 不变 |
| ⑤正文审校 + ⑥结果预览 | **⑤正文审校（连续流，含"成稿模式"）** |
| ⑦文件导出 | **⑥文件导出** |

"结果预览"原本要回答三件事，各自的新去处：

1. **组装能不能生成 / 段落拼得对不对** → ⑤ 里的 `成稿模式`（同一界面，隐藏所有红字与面板，显示干净正文 + 段尾页范围 + 预检条），读一遍就是验收；
2. **与 PDF 对照** → 左右同步滚动，审校与成稿模式都有；
3. **导出前摘要** → ⑥ 文件导出（预检 5 项 + workflow 快照），不重复。

所以 7→6 不丢东西。**唯一要注意**：⑥ 的完成判定仍按"有成功导出且快照与现状一致"（见 `review-workspace-v2.md` §2），不受影响。

## 8. 三档宽度与 628 高度

### 8.1 宽度

| 档 | 左树 | PDF | 正文 | 合计 |
|---|---|---|---|---|
| **≥1320** | 232 | 420 | flex（1320 下 ≈ 668 / 1440 下 ≈ 788） | 最少 1320（232+420+668） |

- PDF 420 宽在 200 DPI 页面上约 0.55×，够判断字形与偏旁（判字不需要读整页）。

### 8.2 628 高度预算

| 区块 | 高 | 滚动 |
|---|---|---|
| 顶栏（六步步骤条） | 44 | 固定 |
| 阅读工具条（模式 / 过滤 / 进度 / 上一处·下一处 / 未提交） | 44 | 固定 |
| 三栏内容区 | **492** | 左树、PDF、正文各自内部滚 |
| 提交栏（草稿计数 / 提交 / 撤销） | 48 | 固定 |

- 正文区 492px ≈ 17.5 行；一段 8–20 行，一屏约一到两段，节奏合适。
- PDF 区 492px 显示约 1.3 页 A4（缩到 420 宽时一页约 590 高）——**多页滚动**，上下都能看到半页。
- "零滚动"在这里同样指**整页不滚**：三个栏各自内部滚。

## 9. 双向同步滚动

- **跟随开关**（工具条，默认开）：开时两边联动；用户手动拖动某一侧超过 1.5 秒即视为"我要单独看"，自动关掉跟随并显示 `已停止跟随 [恢复]`。
- **粒度：行**。PDF 侧取视口 35% 高度处最近的一行（用 `page_layout_line` 的 bbox），映射到正文侧同一 `(block_id, line_index)` 的行元素，把它滚到视口 30% 处。
- **回声锁**：程序化滚动后 150ms 内忽略 scroll 事件；反向同理。
- **节流**：rAF 内只做一次；拖动时不做平滑动画，松手后 120ms 对齐一次。
- 跳转（下一处/树/页）时先滚动正文，再让 PDF 跟到该行——**正文是主轴**，避免两次滚动打架。

## 11. 验收（可截图核对）

1. 打开第 87 页：右侧连续正文按段落排开，无差异处是纯文本，差异处只有**那几个字**是红的（汉字级实线、标点级虚线）。
2. 点红字：该行下方就地展开候选面板（左缩进 24px、2px 彩条），段落其余部分在面板后继续，**其他段不动**；点另一处红字，上一处自动收起。
3. 采用后：该行红字消失并闪绿 1.2 秒；文本与候选一致；顶部 `未提交` +1、进度 +1。
4. 保留后：红字转淡绿（虚线），顶部同步。
5. 双击行进入编辑：只有该行变成编辑框，上下行不动；`Esc` 还原；`⌘↵` 收草稿；行尾出现 `草稿` chip。
6. 顶部 `提交 3 处` → 确认面板按页分组 → 提交成功后 chip 消失、进度写库；刷新后不再出现。
7. 草稿层：改 3 处不提交，关闭浏览器再打开 → 提示恢复，3 处仍在（黄色）。
8. 密度：随机一屏截图，红色字符占版面 < 2%；一屏红点数 ≤ 4。
9. 不漏：`下一处未审` 在任意滚动位置都可见可点；到文末跳回第一处并提示；全部处理完进度条转绿。
10. 同步：滚 PDF 到某页中间，正文自动对到同一行（误差 ≤ 1 行）；关掉跟随则互不干扰。
11. 三档宽度：1440/1200/1000 各截一张，无横向滚动，正文列 ≥520，PDF 在 <1120 时可切换浮层。
12. 628 高：body 无滚动条；正文、PDF、左树三处各自内部滚；工具条与提交栏固定。
13. 成稿模式：切换后红字与草稿标记全部隐藏，显示干净正文 + 段尾页范围 + 预检条（段数/跨页/未识别页）。

## 12. 风险与未验证

- **`line_spans` 是本单的架构依赖**：没有它，前端要复刻 `join_pair` 的 4 条规则（去空白、CJK 不加空格、拉丁加空格、连字符还原），一旦与导出侧不一致，就会出现"审的字不是导出的字"。过渡方案必须带一致性校验（§3.2）。
- **草稿层的失败面**：不提交就没有任何落库状态；进程崩溃靠 localStorage，但**多标签页同时编辑会互相覆盖草稿**。建议第一版限制单标签（项目锁已存在），提交时按块 revision 冲突检测。
- **同步滚动的抖动**：行级同步在长段（跨页段）里可能来回跳，需要在真书上量；备选是段落级同步（粗一档），先做行级、不行降段落级。
- **density 数字基于 22.4 万字 / 1733 条**（PM 文档真书统计），但"一屏 17.5 行"取决于字号与段距，需要真机截图复核一次。
- **未验证**：80.9% 噪声下，用户连续点 1733 次的疲劳曲线；可能需要在真书前 50 页做一次计时（目标 ≤ 2 秒/条）。

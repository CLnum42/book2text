## D-003 | 2026-10-14 | 换行策略：源码统一 LF，仅 `*.bat` / `*.cmd` 为 CRLF

**决策：** 见 `.gitattributes`。默认 `* text=auto eol=lf`；`*.bat`、`*.cmd` 强制 CRLF；`*.command`、`*.sh` 强制 LF。

**理由：** 说明书第 10 节要求"仓库用 `.gitattributes` 统一源码换行"。同时有两个必须保留的例外——Windows 批处理在 LF 下可能行为异常，而 macOS 的 `.command` 启动脚本在 CRLF 下会因 shebang 解析失败而无法执行。

**影响：** 两个平台的检出结果一致；改换行策略需要重新规范化整个仓库（`git add --renormalize .`）。

**状态：** 生效。

## D-007 | 2026-10-14 | Git 提交身份与 GitHub 认证方式

**决策：**
- 全局提交身份：`user.name = CLnum42`，`user.email = CLnum42@users.noreply.github.com`。
- GitHub 认证：SSH 密钥 `~/.ssh/id_ed25519`（ed25519，无机密短语），远端 `git@github.com:CLnum42/book2text.git`。
- `~/.ssh/config` 为 `github.com` 指定该密钥，`IdentitiesOnly yes` 避免试探其他密钥。

**理由：**
- **身份与既有历史对齐。** 从 `CLnum42/dsh-DSchat` 的提交记录中查到开发者此前使用的身份正是 `CLnum42 <CLnum42@users.noreply.github.com>`，并验证了该 noreply 邮箱能正确关联到账号（5 条提交全部链接成功）。沿用它可以避免同一人出现两套提交身份，也不泄露真实邮箱。
- **改用 SSH 是权限所迫，不是偏好。** 原计划走 HTTPS + `gh` 凭据助手，但该细粒度 PAT 的仓库范围是"仅选定仓库"：新建仓库被拒（`createRepository` 无权限），对 `book2text` 的 API 请求返回 404。SSH 密钥不受仓库范围限制，且今后新建仓库无需再改配置。
- **修改 PAT 权限有风险。** 编辑细粒度 PAT 的仓库范围可能触发令牌重新生成，进而导致 `gh` 登录失效，需要重新走一次浏览器授权。相比之下新增 SSH 密钥是纯增量的，不会破坏既有凭据。

**影响：**
- 私钥**未设口令**（详见 `docs/known-limitations.md` L-08），文件权限 600。
- `gh` CLI 仍使用原 PAT，因此针对本仓库的 `gh` 命令会 404（详见 L-07）。日常使用 `git` 命令不受影响。
- 仓库创建与密钥添加都必须在浏览器中完成，其中添加 SSH 密钥需要 GitHub 的 sudo 模式验证（重新输入密码），**开发者本人操作，不得代为输入密码**。

**状态：** 生效。

## D-010 | 2026-10-14 | 骨架的三处实现取舍

**决策：**

1. **上传接口用原始请求体，不用 multipart。**
2. **令牌与 Origin 校验用 FastAPI 依赖，不用 `BaseHTTPMiddleware`。**
3. **错误统一由异常处理器转换，各路由不自己拼错误 JSON。**

**理由：**

1. 说明书 4.5 要求"流式写入，边传边算 SHA-256，并显示上传进度"。multipart 解析会先把整个文件缓冲起来，几百页的扫描书会直接吃掉内存。原始字节流可以用 `request.stream()` 直接落盘。代价是前端的进度条必须用 `XMLHttpRequest`（`fetch` 拿不到上传进度）。
2. `BaseHTTPMiddleware` 会**缓冲请求体**，与第 1 条直接冲突——中间件一读，`request.stream()` 就拿不到数据了。依赖注入在路由参数解析前执行，不影响流式读取。
3. 说明书第 11 节规定了固定的错误形状（含 `correlation_id`）。集中转换能保证形状一致，也避免每个路由重复拼装。

**影响：** 这三条是骨架的实现方式，不是产品决策；但第 2 条有后效——**今后新增中间件时都要注意它会不会碰请求体**，与上传相关的路由尤其如此。

**状态：** 生效。

## D-014 | 2026-10-14 | `/Rotate` 交给 PDFium 默认处理，不要手工补旋转

**决策：** 渲染不再传 `rotation` 参数；新增 `page_rotation()` 访问器但**仅供记录**
（对应说明书 5.3 的 `Page.rotation` 字段）。

**理由（实测）：** PDFium **已经正确应用了 `/Rotate`**——`get_size()` 返回的是显示尺寸
（`/Rotate` 为 90/270 时宽高已交换），`render()` 默认参数渲染出的就是显示方向。
另与 macOS PDFKit 对照：同一份 `/Rotate=90` 文件两者都给出横向页面。

**这个决策纠正了我自己的一次误判。** 我最初得出的是相反结论（"PDFium 不应用
`/Rotate`，需要手工补 `rotation=(360-r)%360`"），并据此改过代码。该结论基于一个
**坏夹具**：用 reportlab 的 `setPageRotation()` 生成的 PDF 在 PDFium 与 PDFKit 里
**都渲染不出内容**，看起来像"内容跑到画布外"。换成正确构造的夹具后真相相反。
若沿用那个"修正"，真实书籍里所有带 `/Rotate` 的页都会被**重复旋转**。
经过与教训记在 `scripts/make_test_fixtures.py` 与 `fixtures/README.md`。

**影响：** 所有渲染出口统一走 `render_page_image()`，保证**界面显示与 OCR 用图同源**——
这是归一化坐标能和用户看到的画面对齐的前提（说明书 5.2）。
`tests/unit/test_ocr_coords.py` 里有回归测试锁定"默认渲染必须有内容"。

**状态：** 生效。

## D-015 | 2026-10-14 | 新增「忽略空白」的额外 CER 口径，但不改说明书 8.7 的规则

**决策：** 在 `core/ocr/compare.py` 中新增 `normalize_whitespace_insensitive()`，
作为**测量用**的额外口径。它**不改变**说明书 8.7 定义的归一化与比对结果，
函数 docstring 里明确写了这一点。

**理由（实测发现）：** 在合成语料上测量时发现，说明书 8.7 第 3 步只规定
"删除**中日韩字符之间**的空格"，但中英混排文本里占主导的是
**中日韩与拉丁/数字边界**上的空格：

```
金标准（页面上确实留了空隙）：这份文档的格式是 PDF，编码是 UTF-8
识别结果：                    这份文档的格式是PDF，编码是UTF-8
```

去掉全部空白后，编辑距离从 149 降到 46（-69%）。也就是说**原始 CER 5.291% 里
约三分之二是排版差异，不是识别错误**。若只报 5.291%，会把中文排版的常见约定
算成识别缺陷、高估错误率；若只报 1.634%，则掩盖了说明书规则与实测数据的落差。

**影响：**
- 两个口径**都报**，见 `docs/accuracy-report.md`，不藏任何一个。
- **是否把边界空格并入 8.7 第 3 步，是说明书的修订问题，需要开发者决定**，
  我没有擅自修改规则。建议倾向：并入，因为说明书 8.5 自己规定"格式差异不作为分歧"。
- 该口径只影响测量，不影响界面上的分歧标记（那仍走 8.7）。

**状态：** 生效（附带一条待开发者裁决的说明书修订建议）。

## D-016 | 2026-10-14 | 分段用相对阈值，且不猜块类型

**决策：** `core/structure/grouping.py` 的三条分段规则（行距 / 缩进 / 对齐）阈值
全部以**行高或字宽的倍数**表示，不用绝对坐标；块的 `block_type` 一律给 `paragraph`。

**理由：**
- **相对阈值**：归一化坐标虽然与 DPI 无关，但**版心宽度、字号因书而异**。
  用绝对坐标做阈值，换一本书就要重调参数。以"几个字宽""几倍行高"表达，
  同一套默认值能在不同书上工作。字宽由"行宽 / 字数"的中位数估算，
  因此也随字号自动缩放。
- **不猜块类型**：说明书 5.3 的 `block_type` 来源写明是"版面组件的建议（需预览确认）
  或人工标注 / 6.5 的批量工具"。本模块若凭几何位置猜页眉页脚，就是**把未确认的
  判断当成事实**，与说明书"绝不静默应用"的要求相悖。因此只给中性的 `paragraph`。

**影响：**
- 换用不同字号 / 版心的书时，参数可调但**未做跨书验证**——目前只在样本的两本书上跑过。
- 页眉页脚页码暂无类型标记，说明书 9.3 的"按块类型排除"暂时没有数据基础（L-22）。
- 分段是启发式的，已知三类失效场景记在 L-21。**没有人工兜底**（合并 / 拆分属 Phase 3），
  分错了只能重跑。

## D-017 | 2026-10-14 | 行合并规则对说明书未覆盖情形的解释

**决策：** 实现说明书 9.2 的行合并规则时，对规则表**未列出的组合**作如下解释，
并写进 `core/export/joining.py` 的模块说明（可审计，不是自由发挥）：

1. **规则 3 右侧的"拉丁字符"含数字。** 英文用空格分词，`chapter` + `3 begins`
   需要空格；只认字母会拼成 `chapter3`。
2. **规则 3 右侧只算字母数字，不算标点。** `abc,` + `def` 得 `abc, def`；
   而 `abc` + `, def` 若加空格会变成 `abc , def`，是错的。
3. **说明书未列出的组合一律不加空格。** 在说明书没要求的位置插空格，
   比直接连接更容易破坏原文。
4. **行尾连字符后接大写字母或数字时，保留连字符并直接连接。**
   说明书只规定了小写字母的情形。理由是 `Anglo-` + `Saxon` 应得 `Anglo-Saxon`、
   `1990-` + `1995` 应得 `1990-1995`；若走规则 3 会得到错误的 `Anglo- Saxon`。
5. **弯引号按标点归类**，使 `word,”` + 拉丁字母 能走规则 3 得到空格。

**理由：** 说明书 9.2 的表格只覆盖四种典型组合，实际排版还有若干边界情形。
不写明解释的话，实现者会各自发挥，同一本书在不同版本里会拼出不一致的文本。
写明的解释**可以被推翻**——这比隐式假设好。

**影响：**
- 第 4 条是对规则的**扩展**（说明书没写），第 1、2 条是对"拉丁字符"一词的**收窄解释**，
  都已在文档与代码注释中标注。
- 规则集中在 `join_pair()` 一个函数里，41 项测试覆盖规则表每一行；
  若要改某条，改动是局部的，且会立刻被测试暴露。
- **另记一条约定冲突**：规则 4 规定中日韩↔拉丁**直接连接、不额外加空格**
  （如 `1971 年` + `summer` → `1971 年summer`），这与中文排版里"拉丁词两侧留空隙"的
  习惯相反。而说明书 8.7 的空格归一化**不会**删掉这种边界空格（D-015）。
  两处管的是不同的事（9.2 管行合并、8.7 管比对），但**都与"中日韩/拉丁边界"有关**，
  建议开发者在裁决 D-015 时一并考虑这两条要不要统一口径。

**状态：** 生效（第 1、2、4 条如有异议可直接推翻）。

## D-018 | 2026-10-14 | 导出接口做成无状态的，客户端只提交原始行

**决策：** `POST /api/export/txt` 接收客户端提交的块（**原始文本行** + 块级标记 + 选项），
在服务端跑完 9.2 拼接 → 9.1 段生成 → 9.3 清理 → 9.4 渲染，返回文本与预检摘要。

**为什么客户端提交的是"原始行"而不是"拼好的段落"：**
拼接、分段、清理的规则**只在服务端实现一份**。若让客户端先拼好再提交，
浏览器里就会出现第二份 9.2 的实现，两份必然漂移；而且服务端的单元测试覆盖不到客户端那份。

**为什么要无状态：**
说明书 11 的正式接口是 `POST /projects/{id}/export`，服务端从数据库读块——
但持久化（Phase 1/2）还没做，服务端根本看不到客户端手上的识别结果。
无状态接口是当前唯一可行的形态，且**没有隐藏状态**：请求里有什么，就导出什么。

**影响：**
- 导出范围 = 本次会话已识别的页面（L-24）。要先逐页识别，没识别过的页不会出现。
- 块级标记（`include` / `continues_to_next`）只存在于当前会话，刷新即丢。
- 预检与导出合并成一个响应（说明书 11 分了 `/preflight` 与 `/export` 两个接口）。
- **持久化落地后这个接口应当被替换**，而不是在它上面继续加功能。
  核心逻辑（9.1/9.2/9.3/9.4）与路由层是分开的，替换时只改路由层。

**状态：** 生效（临时，待 Phase 1/2 持久化落地后替换）。

## D-019 | 2026-10-14 | `char_count` 统一指"内容字数"，不指文件长度

**决策：** `preflight.char_count` 与 `manifest.stats.char_count` 都定义为
**各段文本长度之和**，不含 TXT 的段间空行等格式字符。

**理由：** 实现 9.5 时发现同一个字段名在两处含义不同——manifest 算的是内容字数，
preflight 算的是文件长度，两者相差段间空行的数量（实测 17 对 20）。
同一个名字两种含义会让人对不上账，而说明书 13.3 的通过标准要求"数量与预检一致"。

**取舍：** 选"内容字数"而不是"文件长度"，因为对一本书而言有意义的是**导出了多少字**；
文件长度会随格式变化（TXT 的空行、JSONL 的 JSON 包装），不适合作为统计口径。

**影响：** 想知道文件字节数的人需要自己看文件。

**状态：** 生效。

## D-020 | 2026-10-14 | 项目 ID 用短 ID 而不是 ULID

**决策：** 项目的 `project_id` 就是**文件夹名**：``b2t_`` + 6 个 Crockford Base32 字符
（如 ``b2t_7KQ2M9``）。其他实体（page 等）仍按说明书 5.1 用 26 字符的 ULID。

**理由：** 两处说明书要求在这里交汇——说明书 5.1 说"所有实体有稳定 ID（ULID 字符串）"，
而 12.1 把项目文件夹画成 ``b2t_7KQ2M9``，第 10 节又明确"项目文件夹名**简短**，
避免触发 Windows 260 字符限制"。项目 ID 是唯一会出现在**文件路径**里的实体 ID
（一个项目下还有 ``source/original.pdf``、``cache/thumbs/``、
``exports/<时间戳>_<格式>/`` 等），用 26 字符的 ULID 会让路径明显变长。
因此项目用短 ID，其余实体用 ULID。

**短 ID 的碰撞风险：** 6 个 Base32 字符约 30 位，个人项目库规模下可忽略；
且创建时**检查目录是否已存在**，冲突则换一个（最多 20 次）。

**影响：** 项目 ID 大小写敏感（Crockford 字典只有大写），
`is_valid_project_id()` 会拒绝小写与其他前缀——它同时承担**防路径穿越**的职责。

**状态：** 生效。

## D-021 | 2026-10-14 | 图片接口允许用查询参数传令牌

**决策：** `/api/*` 的令牌校验仍以请求头 `X-B2T-Token` 为准，
但**额外接受查询参数 ``?token=``**，用于 ``<img>`` 类的请求。

**理由：** 浏览器的 ``<img src>`` **无法携带自定义请求头**，而项目页面的缩略图网格
正是 ``<img>``。若不接受查询参数，就只能用 fetch + blob URL 逐个取图——
400 页就是 400 次 fetch 加 400 个 blob 的生命周期管理，得不偿失。

**暴露面没有实质变化：** 说明书 4.4 本身就规定"启动时打开的 URL 携带令牌"，
也就是说令牌**本来就在页面 URL 里**（并因此进入浏览器历史）。
多接受一种携带方式不增加新的泄露途径，而服务只监听 127.0.0.1。

**影响：** 校验实现在 `api/security.py` 一处，两条来源合并后仍用
`hmac.compare_digest` 做常量时间比较。

**状态：** 生效。

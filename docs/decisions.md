## D-003 | 2026-10-14 | 换行策略：源码统一 LF，仅 `*.bat` / `*.cmd` 为 CRLF

**决策：** 见 `.gitattributes`。默认 `* text=auto eol=lf`；`*.bat`、`*.cmd` 强制 CRLF；`*.command`、`*.sh` 强制 LF。

**理由：** 说明书第 10 节要求"仓库用 `.gitattributes` 统一源码换行"。同时有两个必须保留的例外——Windows 批处理在 LF 下可能行为异常，而 macOS 的 `.command` 启动脚本在 CRLF 下会因 shebang 解析失败而无法执行。

**影响：** 两个平台的检出结果一致；改换行策略需要重新规范化整个仓库（`git add --renormalize .`）。

**状态：** 生效。

## D-007 | 2026-10-14 | Git 提交身份与 GitHub 认证方式

**决策：**
- 全局提交身份：`user.name = CLnum42`，`user.email = CLnum42@users.noreply.github.com`。
- GitHub 认证：SSH 密钥 `~/.ssh/id_ed25519`（ed25519，无机密短语），远端 `git@github.com:CLnum42/book2text.git`。
- `~/.ssh/config` 为 `github.com` 指定该密钥，`IdentitiesOnly yes` 避免试探其他密钥。

**理由：**
- **身份与既有历史对齐。** 从 `CLnum42/dsh-DSchat` 的提交记录中查到开发者此前使用的身份正是 `CLnum42 <CLnum42@users.noreply.github.com>`，并验证了该 noreply 邮箱能正确关联到账号（5 条提交全部链接成功）。沿用它可以避免同一人出现两套提交身份，也不泄露真实邮箱。
- **改用 SSH 是权限所迫，不是偏好。** 原计划走 HTTPS + `gh` 凭据助手，但该细粒度 PAT 的仓库范围是"仅选定仓库"：新建仓库被拒（`createRepository` 无权限），对 `book2text` 的 API 请求返回 404。SSH 密钥不受仓库范围限制，且今后新建仓库无需再改配置。
- **修改 PAT 权限有风险。** 编辑细粒度 PAT 的仓库范围可能触发令牌重新生成，进而导致 `gh` 登录失效，需要重新走一次浏览器授权。相比之下新增 SSH 密钥是纯增量的，不会破坏既有凭据。

**影响：**
- 私钥**未设口令**（详见 `docs/known-limitations.md` L-08），文件权限 600。
- `gh` CLI 仍使用原 PAT，因此针对本仓库的 `gh` 命令会 404（详见 L-07）。日常使用 `git` 命令不受影响。
- 仓库创建与密钥添加都必须在浏览器中完成，其中添加 SSH 密钥需要 GitHub 的 sudo 模式验证（重新输入密码），**开发者本人操作，不得代为输入密码**。

**状态：** 生效。

## D-010 | 2026-10-14 | 骨架的三处实现取舍

**决策：**

1. **上传接口用原始请求体，不用 multipart。**
2. **令牌与 Origin 校验用 FastAPI 依赖，不用 `BaseHTTPMiddleware`。**
3. **错误统一由异常处理器转换，各路由不自己拼错误 JSON。**

**理由：**

1. 说明书 4.5 要求"流式写入，边传边算 SHA-256，并显示上传进度"。multipart 解析会先把整个文件缓冲起来，几百页的扫描书会直接吃掉内存。原始字节流可以用 `request.stream()` 直接落盘。代价是前端的进度条必须用 `XMLHttpRequest`（`fetch` 拿不到上传进度）。
2. `BaseHTTPMiddleware` 会**缓冲请求体**，与第 1 条直接冲突——中间件一读，`request.stream()` 就拿不到数据了。依赖注入在路由参数解析前执行，不影响流式读取。
3. 说明书第 11 节规定了固定的错误形状（含 `correlation_id`）。集中转换能保证形状一致，也避免每个路由重复拼装。

**影响：** 这三条是骨架的实现方式，不是产品决策；但第 2 条有后效——**今后新增中间件时都要注意它会不会碰请求体**，与上传相关的路由尤其如此。

**状态：** 生效。

## D-012 | 2026-10-14 | OCR 适配器层落地，`OcrResult` 暂以「行」为返回单位

**决策：** 新增 `core/ocr/base.py`（协议与数据类型）与
`core/ocr/adapters/rapidocr.py`（RapidOCR 实现）。渲染出的像素坐标由**适配器**
转成归一化坐标（说明书 5.2 的要求），原语 `normalize_quad()` 独立可测。

**与说明书的偏差：** 说明书 8.1 里 `OcrResult` 的字段是 `blocks`，本层如实只提供
`lines`。

**理由：** 说明书 8.4 自己说明"PP-OCR 核心流程只返回行、不返回块"，块要由
`core/structure/grouping.py` 按行距、缩进、对齐组合而成——而 `grouping.py` **尚未实现**。
此时若按 8.1 的形状返回 `blocks`，只能把每行塞成一个块或空着，两种做法都是
把"未实现"伪装成"已实现"，违反说明书 1.6。

**影响：** 当时说明书 5.3 的 `Block` 实体、审校视图（7.4）、导出（第 9 节）都还不能做。
**这是一次记录在案的偏离，不是静默偏离。**

**2026-10-14 更新（组块与落库完成后）：** `grouping.py` 已实现（任务 7），
识别落库时真的由它组合出块（任务 12），块与行都已按说明书 5.3 存进项目数据库。
**偏离仍在，但性质变了**：不再是"因为没实现而只能给行"，而是**分层的结果**——
引擎只产出**行**（说明书 8.4 自己也这么说），块是 `core/structure/grouping.py`
的产物，所以 `core/ocr/` 这一层给 `lines` 是准确的，`blocks` 由上层组合。
说明书 8.1 的 `OcrResult.blocks` 因此不会被填上——若要严格对齐 8.1 的字面形状，
应在识别流程的出口（`core/project/recognition.py`）而不是适配器出口装配块。

**状态：** 生效（按上述解释继续保留，不再视为"临时"）。

## D-014 | 2026-10-14 | `/Rotate` 交给 PDFium 默认处理，不要手工补旋转

**决策：** 渲染不再传 `rotation` 参数；新增 `page_rotation()` 访问器但**仅供记录**
（对应说明书 5.3 的 `Page.rotation` 字段）。

**理由（实测）：** PDFium **已经正确应用了 `/Rotate`**——`get_size()` 返回的是显示尺寸
（`/Rotate` 为 90/270 时宽高已交换），`render()` 默认参数渲染出的就是显示方向。
另与 macOS PDFKit 对照：同一份 `/Rotate=90` 文件两者都给出横向页面。

**这个决策纠正了我自己的一次误判。** 我最初得出的是相反结论（"PDFium 不应用
`/Rotate`，需要手工补 `rotation=(360-r)%360`"），并据此改过代码。该结论基于一个
**坏夹具**：用 reportlab 的 `setPageRotation()` 生成的 PDF 在 PDFium 与 PDFKit 里
**都渲染不出内容**，看起来像"内容跑到画布外"。换成正确构造的夹具后真相相反。
若沿用那个"修正"，真实书籍里所有带 `/Rotate` 的页都会被**重复旋转**。
经过与教训记在 `scripts/make_test_fixtures.py` 与 `fixtures/README.md`。

**影响：** 所有渲染出口统一走 `render_page_image()`，保证**界面显示与 OCR 用图同源**——
这是归一化坐标能和用户看到的画面对齐的前提（说明书 5.2）。
`tests/unit/test_ocr_coords.py` 里有回归测试锁定"默认渲染必须有内容"。

**状态：** 生效。

## D-015 | 2026-10-14 | 新增「忽略空白」的额外 CER 口径，但不改说明书 8.7 的规则

**决策：** 在 `core/ocr/compare.py` 中新增 `normalize_whitespace_insensitive()`，
作为**测量用**的额外口径。它**不改变**说明书 8.7 定义的归一化与比对结果，
函数 docstring 里明确写了这一点。

**理由（实测发现）：** 在合成语料上测量时发现，说明书 8.7 第 3 步只规定
"删除**中日韩字符之间**的空格"，但中英混排文本里占主导的是
**中日韩与拉丁/数字边界**上的空格：

```
金标准（页面上确实留了空隙）：这份文档的格式是 PDF，编码是 UTF-8
识别结果：                    这份文档的格式是PDF，编码是UTF-8
```

去掉全部空白后，编辑距离从 149 降到 46（-69%）。也就是说**原始 CER 5.291% 里
约三分之二是排版差异，不是识别错误**。若只报 5.291%，会把中文排版的常见约定
算成识别缺陷、高估错误率；若只报 1.634%，则掩盖了说明书规则与实测数据的落差。

**影响：**
- 两个口径**都报**，见 `docs/accuracy-report.md`，不藏任何一个。
- **是否把边界空格并入 8.7 第 3 步，是说明书的修订问题，需要开发者决定**，
  我没有擅自修改规则。建议倾向：并入，因为说明书 8.5 自己规定"格式差异不作为分歧"。
- 该口径只影响测量，不影响界面上的分歧标记（那仍走 8.7）。

**状态：** 生效（附带一条待开发者裁决的说明书修订建议）。

## D-016 | 2026-10-14 | 分段用相对阈值，且不猜块类型

**决策：** `core/structure/grouping.py` 的三条分段规则（行距 / 缩进 / 对齐）阈值
全部以**行高或字宽的倍数**表示，不用绝对坐标；块的 `block_type` 一律给 `paragraph`。

**理由：**
- **相对阈值**：归一化坐标虽然与 DPI 无关，但**版心宽度、字号因书而异**。
  用绝对坐标做阈值，换一本书就要重调参数。以"几个字宽""几倍行高"表达，
  同一套默认值能在不同书上工作。字宽由"行宽 / 字数"的中位数估算，
  因此也随字号自动缩放。

## D-017 | 2026-10-14 | 行合并规则对说明书未覆盖情形的解释

## D-020 | 2026-10-14 | 项目 ID 用短 ID 而不是 ULID

**决策：** 项目的 `project_id` 就是**文件夹名**：``b2t_`` + 6 个 Crockford Base32 字符
（如 ``b2t_7KQ2M9``）。其他实体（page 等）仍按说明书 5.1 用 26 字符的 ULID。

**理由：** 两处说明书要求在这里交汇——说明书 5.1 说"所有实体有稳定 ID（ULID 字符串）"，
而 12.1 把项目文件夹画成 ``b2t_7KQ2M9``，第 10 节又明确"项目文件夹名**简短**，
避免触发 Windows 260 字符限制"。项目 ID 是唯一会出现在**文件路径**里的实体 ID
（一个项目下还有 ``source/original.pdf``、``cache/thumbs/``、
``exports/<时间戳>_<格式>/`` 等），用 26 字符的 ULID 会让路径明显变长。
因此项目用短 ID，其余实体用 ULID。

**短 ID 的碰撞风险：** 6 个 Base32 字符约 30 位，个人项目库规模下可忽略；
且创建时**检查目录是否已存在**，冲突则换一个（最多 20 次）。

**影响：** 项目 ID 大小写敏感（Crockford 字典只有大写），
`is_valid_project_id()` 会拒绝小写与其他前缀——它同时承担**防路径穿越**的职责。

**状态：** 生效。

## D-024 | 2026-10-14 | 中断清理的时机改为"打开项目时"，不是"服务启动时"

**决策：** 说明书 5.3 要求"服务启动时，把状态仍为 `running` 的 Job 改为 `interrupted`"。
本项目把这件事放在**打开项目时**（`library.open_project`，拿到项目锁之后）：
把 `queued` / `running` 的任务改为 `interrupted`，对应的 `ocr_run` 改为
`failed`（`error_code = interrupted`），`job_item` 也标记失败并写明原因。

**理由：** 任务属于**某个项目的数据库**，而服务启动时并不知道用户会打开哪些项目——

识别本身是同步的，一旦返回就已经结算。有测试覆盖（用 `KeyboardInterrupt` 模拟强杀）。

**状态：** 生效。

## D-025 | 2026-10-14 | 识别跑在子进程里，父子只通过数据库与一根管子通信

**决策：** 每个识别任务起一个**子进程**（`python -m book2text.worker --project-dir … --job …`），
父进程（服务）只负责起进程、跟踪存活、终止与对账。

**理由（三条，按重要性）：**

1. **内存**：RapidOCR 认一页的峰值约 2.7 GB（Phase 0 实测）。跑在服务进程里，
   界面会跟着卡；任务结束后内存也不一定归还。
2. **可取消**：取消要立刻停手。杀一个进程最干脆——服务进程没法"停一半"。
3. **崩溃隔离**：ONNX 引擎崩了不该把整个应用带走。

**父子之间只交换两样东西：**

- **数据库**：状态、进度、失败原因全在 `job` / `job_item` / `ocr_run` 里。
  控制信号也走状态字段——暂停就是写 `paused`，取消就是写 `cancelled`，
  子进程在**页与页之间**读一次。因此没有自定义协议，两边谁重启都不丢进度。
- **一根从不写入的 stdin 管子**：父进程用 `stdin=PIPE` 起子进程但永不写入，
  父进程一死（包括 `kill -9`）操作系统就关掉管子，子进程读到 EOF 便知自己成了孤儿，
  于是**做完当前页就收工**并把任务结算成中断。

**为什么需要那根管子：** 没有它，应用被强杀后会留下一个**孤儿识别进程**继续写项目数据库——
而用户很可能马上重新打开项目（锁是失效锁，会被覆盖），于是两个写入者同时改同一个库。
实测验证过：强杀服务后子进程立刻自行退出。

**影响：** 单页识别也要现付一次子进程启动与模型加载（数秒），因此"点一页识别"比之前稍慢；
换来的是同一套代码路径与可取消。PyInstaller 打包（Phase 6）时要改 `worker_command()`：
打包后没有"用源码跑模块"这条路，改成 `[sys.executable, "--b2t-worker", …]` 并用
`sys.frozen` 判别。

**状态：** 生效。

## D-026 | 2026-10-14 | 同一项目同时只允许一个识别任务；暂停在"页与页之间"生效

**决策：**

- 一个项目同时只允许一个**进行中**（`queued` / `running` / `paused`）的识别任务；
  再建就明确拒绝并指出那个任务（说明书 6.3："默认 1 个 OCR 子进程"）。
- 暂停 / 取消都是**协作式**的：写状态，子进程在页与页之间读到才照办。
  因此"暂停"在**当前页做完之后**生效，不是瞬时的。
- **取消不回滚**：已经认完的页保留成果；正在认的那一页记为失败（原因写明"任务已取消"），
  还没轮到的页保持**排队**（不是失败）——"继续"时接着做。
- "对账"（reconcile）发生在**读任务状态时**：任务写着 `running` 但本进程没有对应的活子进程
  （引擎崩了之类），立刻改成 `interrupted` 并结算未完成的记录。读接口做写操作是刻意的——
  状态不真实比"读接口很纯"更糟糕。

**理由：** 两个子进程同时写同一个数据库，除了争锁，还会让 R1 / R2 的判断互相打架
（都认为页面"没有 active run"，于是都去生成块）。协作式暂停则是因为同步地停在任意一点
需要引擎本身支持中断——它不支持，而说明书也只要"当前页完成后停止"。

**影响：** 界面上"暂停"是"正在暂停…（当前页做完停下）"这种语义，
`GET /jobs/{jid}` 的 `alive` 字段让界面能如实区分"正在跑"与"进程没了"。
排队中的页在界面上显示"排队中"，与"失败"分开。

**状态：** 生效。

## D-029 | 2026-10-14 | 撤销栈：服务进程内存 + 复用原批次 + 撤销也记事件

**决策：** 撤销 / 重做的实现在三处定形：

1. **栈放在服务进程内存里**（`app.state.review_history`，按项目分栈，最多 100 批），
   不落库。依据是说明书 5.3 的原话："撤销栈**仅限本次会话**，应用重启后不可撤销历史操作
   （已保存的成果本身不受影响）"。
2. 栈里放的是**原始那一批事件**，不是"撤销产生的新事件"。撤销 = 写回 `before`，
   重做 = 再写 `after`，同一个批次在两个栈之间来回搬。
3. **撤销 / 重做本身也记事件**（复用原批次的 `batch_id`），因此事件表始终是一条线性的、
   可追溯的历史——"谁在什么时候把哪一处改回原文"同样查得到。

**理由：** 落库的撤销栈会与"仅限本次会话"的规格冲突，还要处理"哪次会话的栈"这类问题；
而只把栈放内存又必须让**历史**完整落库，否则破坏 5.1 的"所有修改写入事件表、支持追溯"。
两条合起来：**数据是持久的，撤销能力是会话的**。

**影响：** 事件表的 `before_json` / `after_json` 存的是**这次改动涉及的字段**
（不是整行快照）——撤销就是把这些字段写回去，事件本身也保持可读。
`batch_id` 因此会出现在多条事件里（含撤销 / 重做产生的那些），按 `batch_id` 聚合即可还原
"那一批操作的全过程"。

**状态：** 生效。

## D-031 | 2026-10-14 | 结构编辑的三处实现取舍：行也能被撤销、新块先"软删除"、位置近似用 origin

**决策：** 合并 / 拆分 / 换位 / 新增 / 删除这五个操作落在同一套事件与撤销机制上，
为此做了三处取舍：

1. **事件可以作用在"块内行"上**（`entity_type = block_line`）。合并要把行搬进上一块、
   拆分要按光标分配行、被切开的那一行还要清掉坐标——这些都记成普通事件
   （`before` / `after` 是 `block_id` / `line_index` / `bbox` 这类真实列值），
   于是撤销时同一套逻辑把行也搬回去。**不引入任何特殊载荷格式。**
2. **新增块先以"软删除"状态插入，再把"恢复可见"记成一条事件**。若直接插入一个可见的块，
   事件里就没有 `before` 可写，撤销会"什么都不做"（实测踩到：新块撤不掉）。
   先删后恢复之后，"撤销新增"就是一次普通的 `deleted_at` 写回，
   "重做新增"是把它写回 NULL——撤销机制里不需要为新块开特例。
3. **"位置近似"用 `origin`（split / merge）承担**，不新增字段。说明书 R4 说
   "拆分后两块暂沿用原 bbox，并标记为'位置近似'"——`origin` 本来就是记来源的
   （ocr / manual / split / merge），界面据此显示"位置近似"，
   不需要为一句提示加一列。

**理由：** 这三条都指向同一个目标——**让"能不能撤销"不依赖操作的种类**。
每加一个结构操作，只要它是"改真实列值"，撤销就自动成立；
反过来，任何为新操作开特例的做法都会让撤销逻辑长出一堆分支，迟早漏掉一个。

**影响：** 一次合并会产生多条事件（合并 + 软删除 + 每条行的搬迁），
`batch_id` 把它们串成一批；事件表会因此长得快一些，但它同时就是"这一块是怎么变成现在这样的"
完整记录。

**状态：** 生效。

## D-034 | 2026-10-14 | 页眉页脚工具的四处判定：整块在区域内、数字正则、actor 区分人工与系统

**决策：** 说明书 6.5 只给了规则的方向（位置 + 文本条件 + 预览 + 批量 + 不覆盖人工成果），
落地时四处判定这样定：

1. **"在区域内"= 整块都在区域内**（顶部：`y1 <= top_ratio`）。跨界的块不算——
   一个从 3% 伸到 30% 的大段落不是页眉，把它标成页眉只会让人奇怪。
2. **数字判定用正则**：允许常见的装饰字符包着（`· 62 ·`、`- iv -`、`[12]`），
   只认纯数字与罗马数字（说明书点名的两种）。中文数字（"十二"）不认——
   说明书没提，而它在正文里出现的概率远高于页码。
3. **"已被人工修改过类型的块"看事件的 `actor`**：只有 `actor = 'user'` 的 `set_type`
   事件才算"人工改过"；批量结构工具自己的改动记 `actor = 'system'`，
   撤销也沿用原批次的 actor。因此"标注 → 撤销 → 再预览"能重新标上，
   而人手动改过的块永远不会被覆盖（即使他又改回了段落——那是明确的决定）。
4. **应用由界面显式传回确认过的块**（`items: [{block_id, block_type}]`），
   而不是服务端自己重算一遍：这样"预览里逐个取消"天然生效，
   也避免"预览与实际应用的不是同一批"。

**理由：** 第 1 条与第 2 条都是"宁可少标、不要标错"——批量操作一旦标错，
用户要面对几十上百个错误标注；而漏标的代价只是再调一次规则。
第 3 条是这次真机验证暴露的真问题：撤销也写事件，若把"有事件"当成"人工改过"，
撤销一次之后那些块就永远标不上了。第 4 条把"用户确认了什么"这件事实**唯一化**。

**影响：** `event.actor` 从"记录署名"变成了**判定依据**，因此 `revert_events`
必须沿用原批次 actor，不能一律写 `user`（否则撤销会把系统的改动变成"人工改过"）。
结构工具的候选列表最多返回 50 条跳过记录（含原因），完整数量另给 `skipped_count`。

**状态：** 生效。

第一引擎（RapidOCR @200 DPI）是 1.08%——排除"按行裁图害了它"这个可能。

**保留它的价值：**

- 它**快**（0.29 秒/页，第一引擎 1.94 秒/页）、**零模型下载**、完全离线、随系统提供；
- 对**个别页**做第二意见仍然有用（用户可以在有疑问的页上点一下，逐行看两路候选）；
- 它是 Windows 侧（系统 OCR）与将来换引擎时可复用的**结构**：接口、存储（`run_type=auxiliary`、
  `aux_text`、`diff_status`）、界面都已就位，换引擎只需换适配器。

**实现上的两条硬规则**（都不是可选项）：

1. **固定 `accurate` 级别**：`fast` 级别实测**不支持中文**（只认 6 种拉丁语言）；
2. **关掉 `usesLanguageCorrection`**：开着它会"顺手把文本改通顺"，违反说明书 1.5
   （不得润色、补全、纠正原文）。

**影响：** 分歧率本身**不能直接当"需要人工看的行数"**——28.9% 里七成是第二引擎自己的错；
真正需要人看的是"两路都错"的那一类（占可定位行 14.7%），而它们集中在引号、破折号、
校勘符号这类排版符号上。**"难"不在汉字，在排版符号。**

**状态：** 生效。

## D-039 | 2026-10-14 | 分歧标记不落库：按"块里现在的文本"现算，并分汉字级 / 标点级

**决策：** `block_line.diff_status` 仍按说明书 8.7 存三态（`identical` /
`format_only_differs` / `differs`），**界面上的逐行标记不读它**，而是读取时用
`compare.grade_line(块里现在的那一行, aux_text)` 现算，得到四态：

| 分级 | 含义 | 在哪用 |
|---|---|---|
| `identical` | 归一化前就相同 | 不标 |
| `format_only_differs` | 仅格式差异（说明书 8.5 不计入分歧） | 单独计数，可显示 |
| `differs_punct` | 归一化后只剩标点 / 符号不同 | 标"标点级" |
| `differs_chars` | 归一化后汉字 / 字母 / 数字不同 | 标"汉字级" |
| `no_candidate` | 第二引擎什么也没读出来 | 单独计数，**不算分歧** |

不新增数据库列、不加迁移：分级规则会随实测演进，且它依赖**当前文本**（见下）。

**理由一（说明书 8.5 的原话）：** "有分歧的行高亮，并显示另一路候选，
**点一下即可替换为另一路文本（作为对 `text` 的编辑，进入撤销历史）**"。
替换之后那一行的标记必须消失。若照抄 `diff_status`（它记录的是**识别那一刻**的比较），
替换完标记还挂着，用户会以为没生效。因此标记必须跟着"现在的文本"走。
同理，人工把字改对之后标记也会跟着变或消失——这一条有测试锁定。

**理由二（L-30 的实测）：** 两路分歧 28.9% 里七成是第二引擎自己的标点习惯，
**"分歧行数"不等于"需要人工看的行数"**。所以要有一个更窄的口径：
`differs_chars`（汉字级）才是"第一引擎可能真的认错了"。界面与筛选都以此为准，
"标点级"退到第二档（筛选里单列一条，缩略图上只标汉字级）。

**理由三：** 空候选（第二引擎返回空串）**不是分歧**——它没有提供任何关于原文的信息，
标记它只会制造噪声。它单列 `no_candidate` 并单独计数，界面上写"第二引擎没读出这一行"。
因此三处统计口径固定为：`分歧行 = 汉字级 + 标点级`，`no_candidate` 与 `format_only_differs`
各自另计。

**代价（必须知道）：** 块里的行结构改过之后（人工增删换行），行号与复核时的行对不上，
按序号标就会指错地方。这时**不标**：`divergence.stale = true`，界面写明
"行结构改过，逐行标记暂时收起——重新识别这一页可以恢复"，页面级把它记成
"结构改过的块"数，而不是悄悄算成 0 分歧。有测试锁定。

**顺带修正一处与说明书的出入：** 说明书 R4 规定拆分时"被从中间切开的那一行
清空 bbox 与**分歧信息**"，原实现只清了 `bbox`；本次一并清掉
`aux_text` / `diff_status`（拆分事件里记下清空前的值，撤销能恢复）。

**状态：** 生效。

## D-040 | 2026-10-14 | 第二引擎复核接进任务执行器：同一个执行循环，按 `job_type` 分派

**决策：** 批量复核不再是"新写一套任务机制"，而是在**同一个 `run_job`** 里按
`job.job_type` 分派到两条每页动作：

- `ocr`：第一引擎识别一页 → 生成块（R1 / R2，`_run_item`）；
- `auxiliary`：第二引擎复核一页 → 只写行级候选（8.5 / R1b，`_run_auxiliary_item`）。

两种任务共用：`job` / `job_item` 两张表、逐单元循环（`_run_job_loop`）、
`should_continue` 控制信号（暂停 / 取消 / 父进程死亡）、结算规则、失败原因落库、
以及界面上的任务抽屉与"暂停 / 继续 / 取消 / 重试失败页"四个按钮。

**理由一（说明书 6.3 的控制语义要一模一样）：** "暂停（当前页完成后停止）、继续、取消；
失败页可单独重试"是任务的性质，不是识别的性质。复核一次一页 1–15 秒、一本 400 页的书
跑十几分钟，同样需要这些。分别实现两套，就必然出现"取消对识别有效、对复核不生效"这类
不一致。子进程入口（`book2text.worker`）因此**完全不需要改**：它只管调 `run_job`，
任务类型写在数据库里。

**理由二（为什么要批量）：** 单页复核要人点一次（任务 22 只做了这一条）。
第二引擎是"给页加第二意见"，页数是整本书——逐页点等于没有这个功能。

**范围解析的三条规矩（`resolve_aux_pages`）：**

1. **只有已有第一引擎结果的页能复核**（说明书 8.5：第二引擎读的是第一引擎切出的行图）。
   显式页码里混进未识别的页时**报错说清楚**，而不是静默丢掉或建一个注定失败的任务。
2. **默认跳过已复核的页**（说明书 8.5 的"补跑"语义）：已复核的页不重复跑；
   要去掉勾选（`skip_checked=false`）才是"重跑"。
3. **第二引擎不可用时不建任务**（说明书 8.6："明确显示第二意见不可用，不显示分歧标记，
   也不假装仍在比对"），接口回 503 并把原因原样带出来。

**与单页复核的关系：** 审校视图里的单页按钮保留（改一行、看一行时最方便，秒级返回）。
两条路写的是同一份数据（`aux_text` / `diff_status` / `run_type=auxiliary`），
可以混着用——两者用的还是同一个 `run_auxiliary`。

**状态：** 生效。

## D-041 | 2026-10-14 | 质量统计是**读模型**：分歧率只算能算的，算不出来的如实列出

**决策：** 新增 `core/project/stats.py`，实现说明书第 11 节的 `GET /projects/{id}/summary`。
它是**只读聚合**——不新增表、不新增列、不写任何东西，所有数字实时算。

**说明书 13.4 列了九项指标，本模块按三类处理：**

| 类别 | 指标 | 处理 |
|---|---|---|
| 算得出来 | 分歧率、人工修改率、不确定块数、任务失败率、页面识别概况、审校进度 | 本模块实时算 |
| 需要人工金标准 | CER / WER、捕获率、"一致但都错" | **产品里不算**，指向 `docs/ocr-evaluation.md` 的离线测量 |
| 没有采集 | 每页平均审校时间、恢复成功率 | 列进 `not_measured`，**写明原因**，界面照原样显示 |

**分歧率的口径（写死，有测试锁定）：**

```
分歧率 = （汉字级 + 标点级） ÷ （一致 + 仅格式差异 + 汉字级 + 标点级）
```

- 分母是**两边都有文本、能比的行**；"第二引擎没读出来"的行**不进分母**——
  它没提供任何关于原文的信息，算进去只会把比率冲淡。这些行单独报（`empty`）。
- 行数按**块里现在的文本**逐行现算，与界面上标出来的分歧**同源**
  （都走 `blocks.page_divergences`）——同一本书里不能出现两个不同的分歧数。
- 行结构被人工改过的块（`stale_blocks`）不参与行统计，另行报出。

**界面：** 项目视图里的「质量统计」卡片（识别 / 审校 / 两路复核 / 任务四行 + 未采集说明），
随任务结束自动刷新，也可以手动刷新。放在项目视图而不是导出预检，是因为
说明书 8.5 明确"分歧标记只影响审校时看哪里，**不参与导出**"。

**不做的两件事（有意）：** 不把捕获率用"两路互相印证"之类的办法凑出来
（没有金标准就没有捕获率，凑出来的是假的）；不在摘要里加自动建议动作
（说明书 7.4 说建议"只是入口，不强制"，而现在的疑难筛选已经承担了这件事）。

**状态：** 生效。

## D-042 | 2026-10-14 | 修正一条口径：分级不减少噪声，"两类都看"

**背景：** D-039 定分级时假定了"汉字级是值得看的，标点级多半是第二引擎自己的标点习惯"，
界面与筛选也照这个说法写（"汉字级值得看"）。任务 25 用**产品自己的口径**
（`scripts/measure_divergence.py` + `compare.grade_line`）在同样 40 页真书上复算，
结论与这个假设相反，**以实测为准，修正。**

**实测（40 页 / 1064 行 / 915 行可定位 / 第一引擎错 65 行 = 基准 7.1%）：**

| 标出的分歧 | 可定位行 | 其中含第一引擎的错 | 相对基准 | 改对率 |
|---|---|---|---|---|
| 汉字级 | 113 | 15（13.3%） | 1.9× | 11.5% |
| 标点级 | 114 | 27（23.7%） | **3.3×** | 33.3% |

**原因：** 第二引擎自己的错以**汉字**错误为主（127 行汉字级 vs 105 行标点级），
所以"汉字级分歧"这一桶里塞满了它自己的错；而标点级分歧里第一引擎的标点错占比更高。

**决策：**

1. **界面不再把等级当"值不值得看"的判据**：缩略图芯片、块内提示、复核面板的文案
   一律改成"两类都看"，并把实测数字写进 tooltip（"标出的分歧里约八成是第二引擎自己的错，
   但标记能圈进第一引擎约 2/3 的错行"）。
2. **两条筛选都保留**（"有分歧（汉字级）"/"有分歧（含标点级）"）：它们仍然是
   "差在哪一层"的说明，也仍然能让用户自己决定看哪一类——只是不再规定哪一类"才有意义"。
3. **分级本身保留**（D-039 的技术结论不变）：它让"只差标点"的候选替换风险更低，
   也是质量统计里能分开报数的前提。

**顺带修正一处指标口径：** 第 8 节写的"捕获率 17%"实际是**改对率**
（第二引擎把第一引擎的错改对的比例 = 16/65 = 24.6%；第 8 节当时只在**分歧行**里统计，

**捕获率是 64.6%**——这个数字比 17% 高得多，也决定了"按分歧筛页确实有效"。
两个口径都在 `docs/ocr-evaluation.md` 第 9.1 节列清。

**边界：** 结论来自 **1 本书 / 40 页 / 中文排印本 / 200 DPI**。

**状态：** 生效。

## D-043 | 2026-10-14 | 逐块采用的语义与配对规则；顺手修好"采用之后丢了行记录"

**背景：** 说明书 R2 只要求整页"采用新结果 / 保留现有"（已做）。但真实情形常常是
**取长补短**——这一版这三块更好、那两块更差。任务 26 补上**逐块采用**（说明书 6.4 的
两版对比），并支持**框选新增块**（6.4 的"新增块时可选择在原图上框选位置以补全 bbox"，
此前只能建成"无位置信息"的块）。

**逐块采用的语义（三件事，一次 batch、可撤销）：**

1. **目标块软删除**（不是改它的文本）——这样"采用"与整页采用是同一种动作，
   数据模型一致：块的文本、`ocr_text`、行记录、bbox 全部来自那一版结果；
2. **候选块按原样插回来**，**沿用目标块的 `order_index`**：阅读顺序不变、其余块一个不动；
3. 候选里**多出来的块**（现有块里没有对应）插进阅读顺序的合适位置（按 bbox 的竖直位置）。

保留人工成果的边界不变（说明书 R2："系统绝不自动覆盖人工成果"）：换哪一块**是用户点的**，
而且整件事可以撤销——撤销之后目标块回来、新块消失，连人工改过的文本一起回位。

**配对规则（`blocks.match_candidate_blocks`，纯函数、有测试）：**

1. 先按 **bbox 重叠（IoU ≥ 0.3）** 贪心配对，重叠大的先配，一个现有块最多配一次；
2. 配不上的**按序号**退化配对（两次识别的块顺序通常一致）；
3. 还配不上的就是"这次多出来的块"，界面显示"加进这一页"。
   界面会**并列出示配对依据**（"对应现有 #2（位置重合 100%）"或"按顺序配对"），
   不让人猜它是怎么对上的。

**顺手修好的一个旧缺口（2026-10-14 发现）：** 采用新结果原先**只重建块、不重建行**，
于是采用之后那一页**没有行级坐标**——第二引擎复核会直接拒绝它
（"这一页没有可复核的行"），按行比对与分歧标记也就此断掉。
现在整页采用与逐块采用都会从那次运行的原始输出**重建行记录**
（`line_index` 在块内重新编号），真机上验过：整页采用之后立刻做第二引擎复核，26 行正常。

**框选新增块的插入位置：** 按**框选的竖直位置**决定插在阅读顺序的哪里——
漏检的页眉插到最前面，漏掉的段落插在它该在的位置。
（说明书只说"框选位置以补全 bbox"，插入位置是必须自己定的：补 bbox 的用途正是
"OCR 漏检区域的补救"，所以按位置插才是它要的效果。）

**状态：** 生效。

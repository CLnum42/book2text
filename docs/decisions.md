## D-003 | 2026-10-14 | 换行策略：源码统一 LF，仅 `*.bat` / `*.cmd` 为 CRLF

**决策：** 见 `.gitattributes`。默认 `* text=auto eol=lf`；`*.bat`、`*.cmd` 强制 CRLF；`*.command`、`*.sh` 强制 LF。

**理由：** 说明书第 10 节要求"仓库用 `.gitattributes` 统一源码换行"。同时有两个必须保留的例外——Windows 批处理在 LF 下可能行为异常，而 macOS 的 `.command` 启动脚本在 CRLF 下会因 shebang 解析失败而无法执行。

**影响：** 两个平台的检出结果一致；改换行策略需要重新规范化整个仓库（`git add --renormalize .`）。

**状态：** 生效。

## D-007 | 2026-10-14 | Git 提交身份与 GitHub 认证方式

**决策：**
- 全局提交身份：`user.name = CLnum42`，`user.email = CLnum42@users.noreply.github.com`。
- GitHub 认证：SSH 密钥 `~/.ssh/id_ed25519`（ed25519，无机密短语），远端 `git@github.com:CLnum42/book2text.git`。
- `~/.ssh/config` 为 `github.com` 指定该密钥，`IdentitiesOnly yes` 避免试探其他密钥。

**理由：**
- **身份与既有历史对齐。** 从 `CLnum42/dsh-DSchat` 的提交记录中查到开发者此前使用的身份正是 `CLnum42 <CLnum42@users.noreply.github.com>`，并验证了该 noreply 邮箱能正确关联到账号（5 条提交全部链接成功）。沿用它可以避免同一人出现两套提交身份，也不泄露真实邮箱。
- **改用 SSH 是权限所迫，不是偏好。** 原计划走 HTTPS + `gh` 凭据助手，但该细粒度 PAT 的仓库范围是"仅选定仓库"：新建仓库被拒（`createRepository` 无权限），对 `book2text` 的 API 请求返回 404。SSH 密钥不受仓库范围限制，且今后新建仓库无需再改配置。
- **修改 PAT 权限有风险。** 编辑细粒度 PAT 的仓库范围可能触发令牌重新生成，进而导致 `gh` 登录失效，需要重新走一次浏览器授权。相比之下新增 SSH 密钥是纯增量的，不会破坏既有凭据。

**影响：**
- 私钥**未设口令**（详见 `docs/known-limitations.md` L-08），文件权限 600。
- `gh` CLI 仍使用原 PAT，因此针对本仓库的 `gh` 命令会 404（详见 L-07）。日常使用 `git` 命令不受影响。
- 仓库创建与密钥添加都必须在浏览器中完成，其中添加 SSH 密钥需要 GitHub 的 sudo 模式验证（重新输入密码），**开发者本人操作，不得代为输入密码**。

**状态：** 生效。

## D-010 | 2026-10-14 | 骨架的三处实现取舍

**决策：**

1. **上传接口用原始请求体，不用 multipart。**
2. **令牌与 Origin 校验用 FastAPI 依赖，不用 `BaseHTTPMiddleware`。**
3. **错误统一由异常处理器转换，各路由不自己拼错误 JSON。**

**理由：**

1. 说明书 4.5 要求"流式写入，边传边算 SHA-256，并显示上传进度"。multipart 解析会先把整个文件缓冲起来，几百页的扫描书会直接吃掉内存。原始字节流可以用 `request.stream()` 直接落盘。代价是前端的进度条必须用 `XMLHttpRequest`（`fetch` 拿不到上传进度）。
2. `BaseHTTPMiddleware` 会**缓冲请求体**，与第 1 条直接冲突——中间件一读，`request.stream()` 就拿不到数据了。依赖注入在路由参数解析前执行，不影响流式读取。
3. 说明书第 11 节规定了固定的错误形状（含 `correlation_id`）。集中转换能保证形状一致，也避免每个路由重复拼装。

**影响：** 这三条是骨架的实现方式，不是产品决策；但第 2 条有后效——**今后新增中间件时都要注意它会不会碰请求体**，与上传相关的路由尤其如此。

**状态：** 生效。

## D-012 | 2026-10-14 | OCR 适配器层落地，`OcrResult` 暂以「行」为返回单位

**决策：** 新增 `core/ocr/base.py`（协议与数据类型）与
`core/ocr/adapters/rapidocr.py`（RapidOCR 实现）。渲染出的像素坐标由**适配器**
转成归一化坐标（说明书 5.2 的要求），原语 `normalize_quad()` 独立可测。

**与说明书的偏差：** 说明书 8.1 里 `OcrResult` 的字段是 `blocks`，本层如实只提供
`lines`。

**理由：** 说明书 8.4 自己说明"PP-OCR 核心流程只返回行、不返回块"，块要由
`core/structure/grouping.py` 按行距、缩进、对齐组合而成——而 `grouping.py` **尚未实现**。
此时若按 8.1 的形状返回 `blocks`，只能把每行塞成一个块或空着，两种做法都是
把"未实现"伪装成"已实现"，违反说明书 1.6。

**影响：** 当时说明书 5.3 的 `Block` 实体、审校视图（7.4）、导出（第 9 节）都还不能做。
**这是一次记录在案的偏离，不是静默偏离。**

**2026-10-14 更新（组块与落库完成后）：** `grouping.py` 已实现（任务 7），
识别落库时真的由它组合出块（任务 12），块与行都已按说明书 5.3 存进项目数据库。
**偏离仍在，但性质变了**：不再是"因为没实现而只能给行"，而是**分层的结果**——
引擎只产出**行**（说明书 8.4 自己也这么说），块是 `core/structure/grouping.py`
的产物，所以 `core/ocr/` 这一层给 `lines` 是准确的，`blocks` 由上层组合。
说明书 8.1 的 `OcrResult.blocks` 因此不会被填上——若要严格对齐 8.1 的字面形状，
应在识别流程的出口（`core/project/recognition.py`）而不是适配器出口装配块。

**状态：** 生效（按上述解释继续保留，不再视为"临时"）。

## D-014 | 2026-10-14 | `/Rotate` 交给 PDFium 默认处理，不要手工补旋转

**决策：** 渲染不再传 `rotation` 参数；新增 `page_rotation()` 访问器但**仅供记录**
（对应说明书 5.3 的 `Page.rotation` 字段）。

**理由（实测）：** PDFium **已经正确应用了 `/Rotate`**——`get_size()` 返回的是显示尺寸
（`/Rotate` 为 90/270 时宽高已交换），`render()` 默认参数渲染出的就是显示方向。
另与 macOS PDFKit 对照：同一份 `/Rotate=90` 文件两者都给出横向页面。

**这个决策纠正了我自己的一次误判。** 我最初得出的是相反结论（"PDFium 不应用
`/Rotate`，需要手工补 `rotation=(360-r)%360`"），并据此改过代码。该结论基于一个
**坏夹具**：用 reportlab 的 `setPageRotation()` 生成的 PDF 在 PDFium 与 PDFKit 里
**都渲染不出内容**，看起来像"内容跑到画布外"。换成正确构造的夹具后真相相反。
若沿用那个"修正"，真实书籍里所有带 `/Rotate` 的页都会被**重复旋转**。
经过与教训记在 `scripts/make_test_fixtures.py` 与 `fixtures/README.md`。

**影响：** 所有渲染出口统一走 `render_page_image()`，保证**界面显示与 OCR 用图同源**——
这是归一化坐标能和用户看到的画面对齐的前提（说明书 5.2）。
`tests/unit/test_ocr_coords.py` 里有回归测试锁定"默认渲染必须有内容"。

**状态：** 生效。

## D-015 | 2026-10-14 | 新增「忽略空白」的额外 CER 口径，但不改说明书 8.7 的规则

**决策：** 在 `core/ocr/compare.py` 中新增 `normalize_whitespace_insensitive()`，
作为**测量用**的额外口径。它**不改变**说明书 8.7 定义的归一化与比对结果，
函数 docstring 里明确写了这一点。

**理由（实测发现）：** 在合成语料上测量时发现，说明书 8.7 第 3 步只规定
"删除**中日韩字符之间**的空格"，但中英混排文本里占主导的是
**中日韩与拉丁/数字边界**上的空格：

```
金标准（页面上确实留了空隙）：这份文档的格式是 PDF，编码是 UTF-8
识别结果：                    这份文档的格式是PDF，编码是UTF-8
```

去掉全部空白后，编辑距离从 149 降到 46（-69%）。也就是说**原始 CER 5.291% 里
约三分之二是排版差异，不是识别错误**。若只报 5.291%，会把中文排版的常见约定
算成识别缺陷、高估错误率；若只报 1.634%，则掩盖了说明书规则与实测数据的落差。

**影响：**
- 两个口径**都报**，见 `docs/accuracy-report.md`，不藏任何一个。
- **是否把边界空格并入 8.7 第 3 步，是说明书的修订问题，需要开发者决定**，
  我没有擅自修改规则。建议倾向：并入，因为说明书 8.5 自己规定"格式差异不作为分歧"。
- 该口径只影响测量，不影响界面上的分歧标记（那仍走 8.7）。

**状态：** 生效（附带一条待开发者裁决的说明书修订建议）。

## D-016 | 2026-10-14 | 分段用相对阈值，且不猜块类型

**决策：** `core/structure/grouping.py` 的三条分段规则（行距 / 缩进 / 对齐）阈值
全部以**行高或字宽的倍数**表示，不用绝对坐标；块的 `block_type` 一律给 `paragraph`。

**理由：**
- **相对阈值**：归一化坐标虽然与 DPI 无关，但**版心宽度、字号因书而异**。
  用绝对坐标做阈值，换一本书就要重调参数。以"几个字宽""几倍行高"表达，
  同一套默认值能在不同书上工作。字宽由"行宽 / 字数"的中位数估算，
  因此也随字号自动缩放。

## D-017 | 2026-10-14 | 行合并规则对说明书未覆盖情形的解释

## D-020 | 2026-10-14 | 项目 ID 用短 ID 而不是 ULID

**决策：** 项目的 `project_id` 就是**文件夹名**：``b2t_`` + 6 个 Crockford Base32 字符
（如 ``b2t_7KQ2M9``）。其他实体（page 等）仍按说明书 5.1 用 26 字符的 ULID。

**理由：** 两处说明书要求在这里交汇——说明书 5.1 说"所有实体有稳定 ID（ULID 字符串）"，
而 12.1 把项目文件夹画成 ``b2t_7KQ2M9``，第 10 节又明确"项目文件夹名**简短**，
避免触发 Windows 260 字符限制"。项目 ID 是唯一会出现在**文件路径**里的实体 ID
（一个项目下还有 ``source/original.pdf``、``cache/thumbs/``、
``exports/<时间戳>_<格式>/`` 等），用 26 字符的 ULID 会让路径明显变长。
因此项目用短 ID，其余实体用 ULID。

**短 ID 的碰撞风险：** 6 个 Base32 字符约 30 位，个人项目库规模下可忽略；
且创建时**检查目录是否已存在**，冲突则换一个（最多 20 次）。

**影响：** 项目 ID 大小写敏感（Crockford 字典只有大写），
`is_valid_project_id()` 会拒绝小写与其他前缀——它同时承担**防路径穿越**的职责。

**状态：** 生效。

## D-024 | 2026-10-14 | 中断清理的时机改为"打开项目时"，不是"服务启动时"

**决策：** 说明书 5.3 要求"服务启动时，把状态仍为 `running` 的 Job 改为 `interrupted`"。
本项目把这件事放在**打开项目时**（`library.open_project`，拿到项目锁之后）：
把 `queued` / `running` 的任务改为 `interrupted`，对应的 `ocr_run` 改为
`failed`（`error_code = interrupted`），`job_item` 也标记失败并写明原因。

**理由：** 任务属于**某个项目的数据库**，而服务启动时并不知道用户会打开哪些项目——

识别本身是同步的，一旦返回就已经结算。有测试覆盖（用 `KeyboardInterrupt` 模拟强杀）。

**状态：** 生效。

## D-025 | 2026-10-14 | 识别跑在子进程里，父子只通过数据库与一根管子通信

**决策：** 每个识别任务起一个**子进程**（`python -m book2text.worker --project-dir … --job …`），
父进程（服务）只负责起进程、跟踪存活、终止与对账。

**理由（三条，按重要性）：**

1. **内存**：RapidOCR 认一页的峰值约 2.7 GB（Phase 0 实测）。跑在服务进程里，
   界面会跟着卡；任务结束后内存也不一定归还。
2. **可取消**：取消要立刻停手。杀一个进程最干脆——服务进程没法"停一半"。
3. **崩溃隔离**：ONNX 引擎崩了不该把整个应用带走。

**父子之间只交换两样东西：**

- **数据库**：状态、进度、失败原因全在 `job` / `job_item` / `ocr_run` 里。
  控制信号也走状态字段——暂停就是写 `paused`，取消就是写 `cancelled`，
  子进程在**页与页之间**读一次。因此没有自定义协议，两边谁重启都不丢进度。
- **一根从不写入的 stdin 管子**：父进程用 `stdin=PIPE` 起子进程但永不写入，
  父进程一死（包括 `kill -9`）操作系统就关掉管子，子进程读到 EOF 便知自己成了孤儿，
  于是**做完当前页就收工**并把任务结算成中断。

**为什么需要那根管子：** 没有它，应用被强杀后会留下一个**孤儿识别进程**继续写项目数据库——
而用户很可能马上重新打开项目（锁是失效锁，会被覆盖），于是两个写入者同时改同一个库。
实测验证过：强杀服务后子进程立刻自行退出。

**影响：** 单页识别也要现付一次子进程启动与模型加载（数秒），因此"点一页识别"比之前稍慢；
换来的是同一套代码路径与可取消。PyInstaller 打包（Phase 6）时要改 `worker_command()`：
打包后没有"用源码跑模块"这条路，改成 `[sys.executable, "--b2t-worker", …]` 并用
`sys.frozen` 判别。

**状态：** 生效。

## D-026 | 2026-10-14 | 同一项目同时只允许一个识别任务；暂停在"页与页之间"生效

**决策：**

- 一个项目同时只允许一个**进行中**（`queued` / `running` / `paused`）的识别任务；
  再建就明确拒绝并指出那个任务（说明书 6.3："默认 1 个 OCR 子进程"）。
- 暂停 / 取消都是**协作式**的：写状态，子进程在页与页之间读到才照办。
  因此"暂停"在**当前页做完之后**生效，不是瞬时的。
- **取消不回滚**：已经认完的页保留成果；正在认的那一页记为失败（原因写明"任务已取消"），
  还没轮到的页保持**排队**（不是失败）——"继续"时接着做。
- "对账"（reconcile）发生在**读任务状态时**：任务写着 `running` 但本进程没有对应的活子进程
  （引擎崩了之类），立刻改成 `interrupted` 并结算未完成的记录。读接口做写操作是刻意的——
  状态不真实比"读接口很纯"更糟糕。

**理由：** 两个子进程同时写同一个数据库，除了争锁，还会让 R1 / R2 的判断互相打架
（都认为页面"没有 active run"，于是都去生成块）。协作式暂停则是因为同步地停在任意一点
需要引擎本身支持中断——它不支持，而说明书也只要"当前页完成后停止"。

**影响：** 界面上"暂停"是"正在暂停…（当前页做完停下）"这种语义，
`GET /jobs/{jid}` 的 `alive` 字段让界面能如实区分"正在跑"与"进程没了"。
排队中的页在界面上显示"排队中"，与"失败"分开。

**状态：** 生效。

## D-029 | 2026-10-14 | 撤销栈：服务进程内存 + 复用原批次 + 撤销也记事件

**决策：** 撤销 / 重做的实现在三处定形：

1. **栈放在服务进程内存里**（`app.state.review_history`，按项目分栈，最多 100 批），
   不落库。依据是说明书 5.3 的原话："撤销栈**仅限本次会话**，应用重启后不可撤销历史操作
   （已保存的成果本身不受影响）"。
2. 栈里放的是**原始那一批事件**，不是"撤销产生的新事件"。撤销 = 写回 `before`，
   重做 = 再写 `after`，同一个批次在两个栈之间来回搬。
3. **撤销 / 重做本身也记事件**（复用原批次的 `batch_id`），因此事件表始终是一条线性的、
   可追溯的历史——"谁在什么时候把哪一处改回原文"同样查得到。

**理由：** 落库的撤销栈会与"仅限本次会话"的规格冲突，还要处理"哪次会话的栈"这类问题；
而只把栈放内存又必须让**历史**完整落库，否则破坏 5.1 的"所有修改写入事件表、支持追溯"。
两条合起来：**数据是持久的，撤销能力是会话的**。

**影响：** 事件表的 `before_json` / `after_json` 存的是**这次改动涉及的字段**
（不是整行快照）——撤销就是把这些字段写回去，事件本身也保持可读。
`batch_id` 因此会出现在多条事件里（含撤销 / 重做产生的那些），按 `batch_id` 聚合即可还原
"那一批操作的全过程"。

**状态：** 生效。

## D-031 | 2026-10-14 | 结构编辑的三处实现取舍：行也能被撤销、新块先"软删除"、位置近似用 origin

**决策：** 合并 / 拆分 / 换位 / 新增 / 删除这五个操作落在同一套事件与撤销机制上，
为此做了三处取舍：

1. **事件可以作用在"块内行"上**（`entity_type = block_line`）。合并要把行搬进上一块、
   拆分要按光标分配行、被切开的那一行还要清掉坐标——这些都记成普通事件
   （`before` / `after` 是 `block_id` / `line_index` / `bbox` 这类真实列值），
   于是撤销时同一套逻辑把行也搬回去。**不引入任何特殊载荷格式。**
2. **新增块先以"软删除"状态插入，再把"恢复可见"记成一条事件**。若直接插入一个可见的块，
   事件里就没有 `before` 可写，撤销会"什么都不做"（实测踩到：新块撤不掉）。
   先删后恢复之后，"撤销新增"就是一次普通的 `deleted_at` 写回，
   "重做新增"是把它写回 NULL——撤销机制里不需要为新块开特例。
3. **"位置近似"用 `origin`（split / merge）承担**，不新增字段。说明书 R4 说
   "拆分后两块暂沿用原 bbox，并标记为'位置近似'"——`origin` 本来就是记来源的
   （ocr / manual / split / merge），界面据此显示"位置近似"，
   不需要为一句提示加一列。

**理由：** 这三条都指向同一个目标——**让"能不能撤销"不依赖操作的种类**。
每加一个结构操作，只要它是"改真实列值"，撤销就自动成立；
反过来，任何为新操作开特例的做法都会让撤销逻辑长出一堆分支，迟早漏掉一个。

**影响：** 一次合并会产生多条事件（合并 + 软删除 + 每条行的搬迁），
`batch_id` 把它们串成一批；事件表会因此长得快一些，但它同时就是"这一块是怎么变成现在这样的"
完整记录。

**状态：** 生效。

## D-034 | 2026-10-14 | 页眉页脚工具的四处判定：整块在区域内、数字正则、actor 区分人工与系统

**决策：** 说明书 6.5 只给了规则的方向（位置 + 文本条件 + 预览 + 批量 + 不覆盖人工成果），
落地时四处判定这样定：

1. **"在区域内"= 整块都在区域内**（顶部：`y1 <= top_ratio`）。跨界的块不算——
   一个从 3% 伸到 30% 的大段落不是页眉，把它标成页眉只会让人奇怪。
2. **数字判定用正则**：允许常见的装饰字符包着（`· 62 ·`、`- iv -`、`[12]`），
   只认纯数字与罗马数字（说明书点名的两种）。中文数字（"十二"）不认——
   说明书没提，而它在正文里出现的概率远高于页码。
3. **"已被人工修改过类型的块"看事件的 `actor`**：只有 `actor = 'user'` 的 `set_type`
   事件才算"人工改过"；批量结构工具自己的改动记 `actor = 'system'`，
   撤销也沿用原批次的 actor。因此"标注 → 撤销 → 再预览"能重新标上，
   而人手动改过的块永远不会被覆盖（即使他又改回了段落——那是明确的决定）。
4. **应用由界面显式传回确认过的块**（`items: [{block_id, block_type}]`），
   而不是服务端自己重算一遍：这样"预览里逐个取消"天然生效，
   也避免"预览与实际应用的不是同一批"。

**理由：** 第 1 条与第 2 条都是"宁可少标、不要标错"——批量操作一旦标错，
用户要面对几十上百个错误标注；而漏标的代价只是再调一次规则。
第 3 条是这次真机验证暴露的真问题：撤销也写事件，若把"有事件"当成"人工改过"，
撤销一次之后那些块就永远标不上了。第 4 条把"用户确认了什么"这件事实**唯一化**。

**影响：** `event.actor` 从"记录署名"变成了**判定依据**，因此 `revert_events`
必须沿用原批次 actor，不能一律写 `user`（否则撤销会把系统的改动变成"人工改过"）。
结构工具的候选列表最多返回 50 条跳过记录（含原因），完整数量另给 `skipped_count`。

**状态：** 生效。

- 它**快**（0.29 秒/页，第一引擎 1.94 秒/页）、**零模型下载**、完全离线、随系统提供；

- 它是 Windows 侧（系统 OCR）与将来换引擎时可复用的**结构**：接口、存储（`run_type=auxiliary`、
  `aux_text`、`diff_status`）、界面都已就位，换引擎只需换适配器。

**实现上的两条硬规则**（都不是可选项）：

1. **固定 `accurate` 级别**：`fast` 级别实测**不支持中文**（只认 6 种拉丁语言）；
2. **关掉 `usesLanguageCorrection`**：开着它会"顺手把文本改通顺"，违反说明书 1.5

真正需要人看的是"两路都错"的那一类（占可定位行 14.7%），而它们集中在引号、破折号、
校勘符号这类排版符号上。**"难"不在汉字，在排版符号。**

## D-039 | 2026-10-14 | 分歧标记不落库：按"块里现在的文本"现算，并分汉字级 / 标点级

**决策：** `block_line.diff_status` 仍按说明书 8.7 存三态（`identical` /
`format_only_differs` / `differs`），**界面上的逐行标记不读它**，而是读取时用
`compare.grade_line(块里现在的那一行, aux_text)` 现算，得到四态：

| 分级 | 含义 | 在哪用 |
|---|---|---|
| `identical` | 归一化前就相同 | 不标 |
| `format_only_differs` | 仅格式差异（说明书 8.5 不计入分歧） | 单独计数，可显示 |
| `differs_punct` | 归一化后只剩标点 / 符号不同 | 标"标点级" |
| `differs_chars` | 归一化后汉字 / 字母 / 数字不同 | 标"汉字级" |
| `no_candidate` | 第二引擎什么也没读出来 | 单独计数，**不算分歧** |

不新增数据库列、不加迁移：分级规则会随实测演进，且它依赖**当前文本**（见下）。

**理由一（说明书 8.5 的原话）：** "有分歧的行高亮，并显示另一路候选，
**点一下即可替换为另一路文本（作为对 `text` 的编辑，进入撤销历史）**"。
替换之后那一行的标记必须消失。若照抄 `diff_status`（它记录的是**识别那一刻**的比较），
替换完标记还挂着，用户会以为没生效。因此标记必须跟着"现在的文本"走。
同理，人工把字改对之后标记也会跟着变或消失——这一条有测试锁定。

**理由二（L-30 的实测）：** 两路分歧 28.9% 里七成是第二引擎自己的标点习惯，
**"分歧行数"不等于"需要人工看的行数"**。所以要有一个更窄的口径：
`differs_chars`（汉字级）才是"第一引擎可能真的认错了"。界面与筛选都以此为准，
"标点级"退到第二档（筛选里单列一条，缩略图上只标汉字级）。

**理由三：** 空候选（第二引擎返回空串）**不是分歧**——它没有提供任何关于原文的信息，
标记它只会制造噪声。它单列 `no_candidate` 并单独计数，界面上写"第二引擎没读出这一行"。
因此三处统计口径固定为：`分歧行 = 汉字级 + 标点级`，`no_candidate` 与 `format_only_differs`
各自另计。

**代价（必须知道）：** 块里的行结构改过之后（人工增删换行），行号与复核时的行对不上，
按序号标就会指错地方。这时**不标**：`divergence.stale = true`，界面写明
"行结构改过，逐行标记暂时收起——重新识别这一页可以恢复"，页面级把它记成
"结构改过的块"数，而不是悄悄算成 0 分歧。有测试锁定。

**顺带修正一处与说明书的出入：** 说明书 R4 规定拆分时"被从中间切开的那一行
清空 bbox 与**分歧信息**"，原实现只清了 `bbox`；本次一并清掉
`aux_text` / `diff_status`（拆分事件里记下清空前的值，撤销能恢复）。

**状态：** 生效。

1. **只有已有第一引擎结果的页能复核**（说明书 8.5：第二引擎读的是第一引擎切出的行图）。
   显式页码里混进未识别的页时**报错说清楚**，而不是静默丢掉或建一个注定失败的任务。
2. **默认跳过已复核的页**（说明书 8.5 的"补跑"语义）：已复核的页不重复跑；

3. **第二引擎不可用时不建任务**（说明书 8.6："明确显示第二意见不可用，不显示分歧标记，

**与单页复核的关系：** 审校视图里的单页按钮保留（改一行、看一行时最方便，秒级返回）。
两条路写的是同一份数据（`aux_text` / `diff_status` / `run_type=auxiliary`），
可以混着用——两者用的还是同一个 `run_auxiliary`。

**状态：** 生效。

## D-041 | 2026-10-14 | 质量统计是**读模型**：分歧率只算能算的，算不出来的如实列出

**决策：** 新增 `core/project/stats.py`，实现说明书第 11 节的 `GET /projects/{id}/summary`。
它是**只读聚合**——不新增表、不新增列、不写任何东西，所有数字实时算。

**说明书 13.4 列了九项指标，本模块按三类处理：**

| 类别 | 指标 | 处理 |
|---|---|---|
| 算得出来 | 分歧率、人工修改率、不确定块数、任务失败率、页面识别概况、审校进度 | 本模块实时算 |


- 分母是**两边都有文本、能比的行**；"第二引擎没读出来"的行**不进分母**——

- 行结构被人工改过的块（`stale_blocks`）不参与行统计，另行报出。

**不做的两件事（有意）：** 不把捕获率用"两路互相印证"之类的办法凑出来
（没有金标准就没有捕获率，凑出来的是假的）；不在摘要里加自动建议动作
（说明书 7.4 说建议"只是入口，不强制"，而现在的疑难筛选已经承担了这件事）。

## D-043 | 2026-10-14 | 逐块采用的语义与配对规则；顺手修好"采用之后丢了行记录"

**背景：** 说明书 R2 只要求整页"采用新结果 / 保留现有"（已做）。但真实情形常常是
**取长补短**——这一版这三块更好、那两块更差。任务 26 补上**逐块采用**（说明书 6.4 的
两版对比），并支持**框选新增块**（6.4 的"新增块时可选择在原图上框选位置以补全 bbox"，
此前只能建成"无位置信息"的块）。

**逐块采用的语义（三件事，一次 batch、可撤销）：**

1. **目标块软删除**（不是改它的文本）——这样"采用"与整页采用是同一种动作，
   数据模型一致：块的文本、`ocr_text`、行记录、bbox 全部来自那一版结果；
2. **候选块按原样插回来**，**沿用目标块的 `order_index`**：阅读顺序不变、其余块一个不动；
3. 候选里**多出来的块**（现有块里没有对应）插进阅读顺序的合适位置（按 bbox 的竖直位置）。

保留人工成果的边界不变（说明书 R2："系统绝不自动覆盖人工成果"）：换哪一块**是用户点的**，
而且整件事可以撤销——撤销之后目标块回来、新块消失，连人工改过的文本一起回位。

**配对规则（`blocks.match_candidate_blocks`，纯函数、有测试）：**

1. 先按 **bbox 重叠（IoU ≥ 0.3）** 贪心配对，重叠大的先配，一个现有块最多配一次；
2. 配不上的**按序号**退化配对（两次识别的块顺序通常一致）；
3. 还配不上的就是"这次多出来的块"，界面显示"加进这一页"。
   界面会**并列出示配对依据**（"对应现有 #2（位置重合 100%）"或"按顺序配对"），
   不让人猜它是怎么对上的。

**顺手修好的一个旧缺口（2026-10-14 发现）：** 采用新结果原先**只重建块、不重建行**，
于是采用之后那一页**没有行级坐标**——第二引擎复核会直接拒绝它
（"这一页没有可复核的行"），按行比对与分歧标记也就此断掉。
现在整页采用与逐块采用都会从那次运行的原始输出**重建行记录**
（`line_index` 在块内重新编号），真机上验过：整页采用之后立刻做第二引擎复核，26 行正常。

**框选新增块的插入位置：** 按**框选的竖直位置**决定插在阅读顺序的哪里——
漏检的页眉插到最前面，漏掉的段落插在它该在的位置。
（说明书只说"框选位置以补全 bbox"，插入位置是必须自己定的：补 bbox 的用途正是
"OCR 漏检区域的补救"，所以按位置插才是它要的效果。）

**状态：** 生效。

**背景：** 说明书 Phase 5（6.7 / 7.9）要求"分派 → 助手审校 → 结果包回传 → 合并审阅"。
本机（macOS）跑通了一整轮往返：负责人建项目识别 → 分派并生成 `.b2tpkg` →
另一个应用实例（另一套项目库）打开任务包审校 → 导出 `.b2tres` →
负责人导入、看字符级差异、接受 → 合并完成（可整批撤销）。

**一、合并的判断基准是"分派时的快照"，不是"上一次的结果"。**

`assignments/<id>/snapshot.json` 记下分派那一刻每一页每一块的**全部字段与 revision**。
合并时比两次：结果包 vs 快照（助手改了什么）、主项目当前 vs 快照（负责人改了什么）；
两边都动过的块就是**冲突**（说明书 6.7.5 的定义）。这也让结果包可以很小——
只带每页的最终块状态，不需要带原文。

**顺带定了一条边界：** "已经合并过的变化不再显示"。结果包与主项目当前状态相同的字段
不算变化，否则同一份结果导入两次会一直提示"这一页改过"（说明书 6.7.1 说
"每次导入只处理尚未合并的变化"）。

**二、pdfium 必须串行化（真机上抓到的 bug，与协作无关但必须写下来）。**

`render.py` 里所有碰 pdfium 的公开函数现在都套在 `_PDFIUM_LOCK` 上（`@_serialized`）。
起因：真机分派时 `import_pages` 抛 "Failed to import pages."，同时缩略图接口
抛 "Failed to load page."——pdfium **不是线程安全的**，而接口层用线程池渲染缩略图。
这个 bug 在协作之前就存在（缩略图会偶发失败），只是没人碰到过。
多线程并发渲染有回归测试（`test_concurrent_rendering_is_serialized`）。

**三、权限限制写在服务端，不只藏按钮。**

说明书 6.7.3 的"助手不能做什么"由两道守卫实现：
`require_main_project()`（识别 / 复核任务、页面类型与纳入、页眉页脚工具、导出 TXT/JSONL）
与 `require_editable_page()`（只读上下文页）。界面同时把入口藏起来，
但服务端必须拦——一个手写的请求不该能越过限制。

**四、合并审阅只做"保留我的 / 采用助手的"，没有"编辑后确认"。**

说明书 7.9.3 给冲突列了三条出路：保留我的 / 采用助手的 / **编辑后确认**。
前两条在这一个视图里直接完成；第三条没有单独做——**先"保留我的"，再到审校视图里改**
（改完就是主项目的内容，冲突自然消解）。理由：把"编辑"塞进三栏对比视图要再造一套
带差异的编辑器，而审校视图本来就是改文本最顺手的地方，两处入口重复。
同理，合并视图的快捷键（`Mod + Enter` 等）也未做——审校视图已有 `⌘Enter / ⌘Z`。

**五、助手端的结果包允许"部分完成"。** 说明书 6.7.4 明确允许：导出前给摘要
（已完成 / 未完成页数、不确定块、备注数），负责人每次只处理尚未合并的变化。

**状态：** 生效（macOS 单机两实例跑通；Windows 侧未验证）。

## D-049 | 2026-10-15 | 界面资源一律 `Cache-Control: no-cache`（不用 `no-store`）

**决策：** `/` 与 `/static/*` 的响应都带 `Cache-Control: no-cache`；
`/static` 由 `_RevalidatingStaticFiles` 统一补头（Starlette 的 `StaticFiles` 不给这个头）。

**理由：**

- 这是本地应用，**升级方式就是替换 `static/` 下的文件**（源码运行或打包都一样）。
  界面由 `index.html` / `app.css` / `app.js` 三份文件组成，**只要其中一份来自缓存、
  另一份是新拉取的，页面就会半新半旧**。2026-10-15 真的发生了：用户浏览器缓存着旧
  `app.js`，配上新 `index.html`，项目库照旧渲染、点"新建项目"报
  `Cannot set properties of null (setting 'hidden')`（旧脚本引用的节点在新页面里没了），
  而且这个报错**与当下代码毫无关系**，排查成本极高。
- **不用 `no-store`**：那样每次刷新都要重传三份文件。`no-cache` 的语义是"用之前回源确认"，
  文件没变时服务端回 304（Starlette 的 `FileResponse` 自带 ETag / Last-Modified 判断），
  一致性和开销都照顾到了。
- 顺带把这条约定**钉进测试**（`tests/integration/test_ui_assets.py`）：三份资源都带头、
  没变时走 304，另外还有一条"`app.js` 用到的 id 必须都在页面里"——少一处引用就会在运行时
  报 `Cannot set properties of null`，而那通常只在某个具体操作路径上才暴露。

**影响：** 浏览器会多一次条件请求（304，无正文）。旧的、缓存里既有的 `app.js` 不会自动失效，
**用户需要强制刷新一次**；之后不会再出现半新半旧。项目渲染图（`/pages/{n}/image`）不受影响，
它们仍是 `private, max-age=300`（那是图片，内容随页固定，缓存有益）。

## D-051 | 2026-10-21 | 版面块人工确认：块级状态、`order_index` 是派生字段、改框只重算行归属

**决策一：版面确认做成块级状态（`block.layout_confirmed`），不是页级。**
错误是局部的——一个框拖偏、一个类型标错、两块顺序颠倒——页级开关会逼着用户把
已经正确的块也一起点一遍。下一包的"页面确认"可以直接聚合这个块级状态
（本页所有纳入块都确认 = 本页版面确认），现在不必先造一个页级字段。

确认是**状态标记，不是硬闸门**：导出只在"整本一个版面块都没确认过"时给一条警告，
不阻止导出。依据是 `docs/region-classification-eval.md` 的实测（自动分组正文误标
0/965、导出路径 CER 0.68%），硬闸门只会让人多点几十下。确认的人与时间由 `event`
表记录（`action = set_layout_confirmed`），不另加两列。

**决策二：`order_index` 是派生字段，`block_id` 才是稳定主键。**
上移 / 下移 / 拖动排序都只改 `order_index`，`block_id` 永不因排序而变——段 ID
（= 首块 `block_id`）与协作包里的引用因此不会断。正文按 `(page_no, order_index)`
组装（现有导出逻辑本来就是这样，本次补了"排序后导出顺序跟着变"的测试）。

**决策三：块框可手动拖拽 / 缩放，吸附文字行边界；改框只重算行归属，绝不重跑 OCR。**
说明书 6.4 原文写"不做已有块 bbox 的几何拖拽调整"，理由是 bbox 不参与导出。
本次按新需求改成可编辑，这是一次**记录在案的偏离**：bbox 现在参与行归属与版面确认，
但识别与导出文本仍不依赖它。

行归属的具体规则：

1. 行与块框有**正面积重叠**才算候选（贴边、面积为 0 不算，避免浮点噪声）。
2. 只落在一个块里 → `assigned`。
3. 落在多个块里 → `conflict`，归给**重叠面积最大**的块；面积并列时取**面积更小的块**
   （更具体），再并列取页内顺序靠前的块，保证结果稳定可复现。
4. 哪个块都不沾 → `unassigned`。行**仍留在原来的块下**（`block_id` 不变），
   只改 `layout_status`；界面用灰色虚线画出来并计数。行一条都不会被删除或丢弃。
5. `line_index` 按块内几何顺序（上到下、左到右）重排；没有 bbox 的行排在块尾，
   保持原有相对顺序。所有变化都记 `reassign_line` 事件，与 `set_bbox` 同一个 batch，
   撤销一次整体还原。

**为什么未归属行不换 `block_id`：** `block_line.block_id` 是 NOT NULL 外键，行本来就有
"最后归属"；把状态与归属分开，既不用重建表，也不会让未归属行的文本从页面上消失。
`Block.text` 始终是导出的唯一文本来源，拖框只动行记录、不动任何文本——避免"拖一下框
就把人工改过的字洗掉"。

**决策四：`figure` / `decoration` 是"不输出文本"的版面块。**
插图块可以**没有文本**（本次允许空文本块正常展示）。这两个类型永远不进正文导出，
不受"内容类型"开关影响；它们只能人工标，不做自动判定——同样是
`region-classification-eval.md` 的结论（不引入版面模型）。

**迁移（0006）：** 只 `ALTER TABLE ... ADD COLUMN`，不重建表、不搬数据：
`block.layout_confirmed` 默认 0、`block_line.layout_status` 默认 `assigned`。
老项目打开即升级，所有块默认"未确认"。真实项目副本 `b2t_C0WS5D` 上实测 5 → 6，
128 个块 / 455 行原样保留。

**状态：** 生效（macOS + Chrome 实测；Windows 未验证，见 CI）。

## D-052 | 2026-10-22 | 页面确认：页级状态列、保守的自动建议、确认不拦识别

**决策一：确认状态存在 `page.page_confirmed`（迁移 0007 新列），不是推导字段，也不复用 `note`。**

`region-classification-eval.md`：自动判定已经准，硬闸门只会让人多点几十下。

- 已跑过识别（项目里有块）但本页 0 块、墨迹占比 ≥ 45% → `front`，把握中；

## D-054 | 2026-10-22 | 页面视图缩放：渲染档位跟着缩放走；块框只给可见页渲染

**决策一：四档缩放，显示尺寸与渲染 DPI 一一对应。**

| 档位 | 版式 | 渲染档位 |
|---|---|---|
| 1 / 4 · 网格 | 自动填充（同原网格） | `thumb`（40 DPI） |
| 2 / 4 · 大网格 | 3 列 | `view`（150 DPI） |
| 3 / 4 · 单列 | 1 列，页宽 ≤680px | `view`（150 DPI） |
| 4 / 4 · 单页 | 1 列，页宽 = 容器宽度 | `zoom`（300 DPI） |

单页档在 267 页真书上实测：显示宽 1129px，渲染图 1480×2457，仍是缩小显示，不会把
40 DPI 的缩略图拉糊。**不做缩略图后台 Job**，也不改 `render.py` 的档位定义。

**决策二：只给"离视口不远"的页保留大图，离屏清 `src`。**

  `<img>` 的矩形必须完全一致——第 30 页实测两者都是 1129×1874.95，逐块对齐。

**决策四：块类型标签放进框内左上角、半透明。**
原来 `.box__badge` 浮在框外上方，会压住上一行文字，看起来像"块框错位"。现在统一
`top:2px; left:2px`、`rgba(255,255,255,.78)`、字号 9.5px；审校视图与页面视图共用。

## D-057 | 2026-10-22 | 任务抽屉只由用户操作打开；失败只主动提示一次

**问题与根因：** 用户报"关掉任务抽屉后它自己弹回来"。根因不是启动入口多开，而是

3. 选择这个口径而不是"每次任务都自动弹"：用户明确关掉抽屉就是在说"别挡我"；

## D-059 | 2026-10-22 | 页面类型收成五类，`include` 变成派生值

**决策一：只保留五类：`front / toc / body / body_excluded / back`。**
用户拍板："保留这五类，去掉纳入和排除选项"。以前是"类型 + 纳入"两个概念，
现在**一个概念**：`body` 进 OCR 与语料，其余四类都不进。界面、筛选器、导出页类型
选择器、`PAGE_TYPES` 全部同步；未知值仍然拒绝（400 / ProjectError），不静默接受。

**决策二：`page.include` 保留列，但它是派生值，唯一来源是 `page_type`。**
删列风险大（协作包、导出、识别范围都在用），因此：
- `update_page` / `update_pages` **不再接受 include 参数**；写类型时同一条 SQL 写

- `PATCH /pages/{id}` 与 `PATCH /pages` 保留 `include` 字段**只为明确拒绝**
  （`400 include_is_derived`），不会被 pydantic 静默忽略。
- 其余写 `include` 的路径只剩三处，且都由类型派生：新建项目（默认 body/1）、
  协作任务包导入（类型映射后派生）、迁移 0008（按类型重算）。
  代码里没有"只改 include、不改类型"的入口。

**决策三：迁移 0008 按"行为不变"映射，用户确认过。**

| 旧状态 | 新类型 |
|---|---|
| include = 1（不论旧类型） | body |
| include = 0 且旧类型 body | body_excluded |
| include = 0 且 cover / front / foreword / copyright | front |
| include = 0 且 toc | toc |
| include = 0 且 appendix / index / blank / other | back |

迁移后 `include` 再按新类型重算一次（body → 1，其余 → 0）。不删列、不丢页；
迁移测试逐行覆盖上表 12 个组合。**统计口径变化**写进 CHANGELOG：以前说
"正文 20 页、其中排除 3 页"，现在是"正文 17 页、正文排除 3 页"——总数仍是五类之和。

**决策四：老协作包里的旧值也要映射，不许写进库。**
任务包只记 `page_type`、不记 `include`，所以按类型映射：body → body、toc → toc、
cover/front/foreword/copyright → front、appendix/index/blank/other → back；
未知值抛 `ProjectError`，包打不开（400），而不是把脏值写进去。迁移用"include 优先"
的表，包导入用"类型优先"的表，两边都复用 `library.normalize_page_type`。

**决策五：自动建议只给五类，且仍不自动应用。**
空白 / 整页图像 → `body_excluded`；首页 → `front`；CIP / ISBN / 版权 / 前言 / 序 /
导言 / 译者的话 / 凡例 → `front`；目录关键词 / 点线目录 / 连续页码特征 → `toc`；
索引 / 附录 / 参考文献 / 后记 / 跋 → `back`；其余不给建议（保持正文）。
`include` 不再作为"给不给建议"的过滤条件——五类都允许被建议，才能把误判的页改回来。

**状态：** 生效（macOS + Chrome 实测；Windows 未验证）。

## D-061 | 2026-10-22 | 整页「版面确认」：与页面确认分开，块改动自动重置

**决策一：两个确认是两件事，界面文案必须分开。**
- **页面确认**（`page.page_confirmed`）：这页**算不算正文**，由五类页面类型
  （正文 / 正文排除 / 目录 / 前置 / 后置）决定；在「页面」视图确认。
- **版面确认**（`page.layout_confirmed`，迁移 0009）：这页**里面哪些块是正文**；
  在审校视图右栏顶部「本页版面」面板确认。
  面板常驻一句解释（"页面确认 = 这页算不算正文；版面确认 = 这页里面哪些块是正文"），
  不再用同一个"确认"词指两件事。块级 `block.layout_confirmed`（0006）保留在数据层，
  但界面上不再提供单块"确认版面"按钮，避免出现第三种"版面确认"。

**决策二：确认人 / 时间写事件表，不加新列。**
`POST /pages/{no}/layout/confirm`（可带 `page_numbers` 批量）写
`event(entity_type=page, action=confirm_layout, before/after={"layout_confirmed":0/1})`，
`actor_name` 沿用审校事件的来源；重复确认幂等（已确认的页不再写事件）。
确认不进撤销栈——它是状态标记，不是内容修改。

**决策三：重置用数据库触发器，而不是在每条编辑路径里补代码。**
块的写入路径很多（PATCH、结构编辑、合并审阅、任务包导入、撤销重做）；触发器保证
"类型 / 框 / 顺序（含新增 / 软删除）真的变了 → `page.layout_confirmed = 0`"，
改文本 / 审校状态 / 块级 `include` **不重置**（不是版面变化）。
`AFTER UPDATE OF block_type, bbox, order_index, deleted_at ... WHEN OLD.x IS NOT NEW.x`
+ `AFTER INSERT`。这样以后新增编辑入口也不会漏；代价是"页级状态由数据层维护"，
业务层不能偷偷保留已确认——这正是想要的。

**决策四：`margin_note` 进注释流，不进元数据。**
侧栏 / 旁批和脚注一样是"不属于正文、但文字不能丢"的内容，而且同样可能需要
"它在正文哪一段旁边"的定位；所以进 `notes.txt` / `notes.jsonl`，带
`source_type="margin_note"` 与「旁批」标记，引用位置沿用"最近前一个正文块"。
图注 / 书眉 / 页码 / 插图 / 装饰仍然进 `meta.json`：它们没有"注释引用"语义，
按页保留原文即可。正文流只收 `paragraph` + `heading`；`other` 也不进正文。

**决策五：预检只警告、不阻断。**
预检返回 `layout_pages / layout_confirmed_pages / layout_unconfirmed_pages`
（只统计这次导出范围）；未确认时界面给一条警告"正文可能夹带页眉 / 页码 / 旁批"，
导出照常进行——沿用"确认是状态标记不是硬闸门"的既有口径。

**状态：** 生效（macOS + Chrome 实测；Windows / Safari 未验证）。

## D-062 | 2026-10-22 | 块框实时性：识别完成即刷新；滚动预取；瓷砖位置"量不准就不记"

**背景：** 用户实测两条——"识别到哪里，页面应该实时出现块色块"（任务进行中不出框，要等结束或刷新）、
"网格滚动时块框出现有延时"。排查后发现不是网络慢，而是两个实现问题叠在一起。

**决策一：瓷砖位置在视图隐藏时量不出来，就不记。**
`capturePageTileMetrics()` 原来无条件记录每个瓷砖的 top / height。打开项目时的顺序是
`renderProject()` → `renderPages()`（此时页面视图还是 `hidden`）→ `showView("pages")`，
于是 267 个瓷砖全被量成 `top=0,height=0`；`updatePageVisibility()` 用这份缓存判断
"bottom(0) > scrollTop-60 && top(0) < scrollTop+viewport+60" 对每一页都成立，
**267 页全部被当成"在视口内"**：块请求排队、框画出来又被下一帧当离屏清掉。
真浏览器实测：进入页面视图 10 秒后 `visiblePageNos = 267`、`/blocks` 请求 36 次且仍在
按页序往整本推进、屏幕上 **0 个块框**。
现在：首个瓷砖高度为 0 时不记（`pageTileMetrics = null`），等视图可见后下一次
可见性计算再量；`showView("pages")` 也强制重量。代价是"打开项目后第一帧可能不算可见性"，
可忽略。

**决策二：任务轮询按"页单元状态"做增量，不按进度数字猜。**
轮询载荷里的 `items[].status` 是真实数据：某页从 running 变 succeeded 就是它认完了。
`collectNewlySucceededPages()` 每个任务记一个"已处理过的页"集合，**每页只处理一次**；
处理方式是丢掉该页块缓存（同时把"作废代次" +1，让在途的旧响应作废）、
可见就重画、审校视图正在看这一页就先落库输入再重载块列表。
轮询间隔 1200 → 900ms，且"刷新页面状态"与"补画刚认完的页"并行发。
实测：任务载荷报告成功 → 框出现 61–220ms；加上一轮轮询，单页从完成到出框 ≤ 约 1.1 秒。

**决策三：任务结束不再整格重建，改为就地刷新。**
原来收尾调 `reloadProjectPages()`（重建 267 个瓷砖），最后一个框要多等约 1–2 秒，
而且整格重建会再发一轮可见页的块请求。现在收尾 = 按增量补最后几页 + 就地刷新
页面状态与顶部统计（`renderPageSummary()` 从 `renderPages()` 里拆出来，
`syncPageStates()` 也会更新它），最后才调 `loadTasks()` / `loadSummary()`。
`reloadProjectPages()` 仍是"暂停 / 取消 / 失败重试"等控制操作的刷新入口。

**决策四：滚动预取，但预取不许挤掉视口内的请求。**
`updatePageVisibility()` 在网格档同时收集"视口上下各约 1.5 屏"的候选页，
按离视口由近到远排序，一次最多排 8 页；**只预取已识别的页**（未识别页没有块，
为它们发请求就是给整本书发一串空响应）。在途请求上限 3 → 6，其中预取最多占 4 个，
保证视口内的页始终有位置。块缓存 40 → 80 页。
"先画后补"：可见页若已有缓存，就在这一帧直接画（每帧仍限 3 页），不等下一个 rAF。

**决策五：网格档"滚动停下再扫建议角标"的防抖 140 → 60ms，且用瓷砖位置缓存。**
仍然只在停下后扫一次（不为 267 个瓷砖每帧量矩形），单次扫描从 267 次
`getBoundingClientRect()` 变成读缓存。

**未量化：** 预取对"滚动中空白页时长"的改善，本次 A/B 落在测量噪声里
（本机 ego 窗口的 rAF 上限约 30fps，整本快速滚动时块框开 / 关两档相同），
只确认了"不更差"，没有给出预取的单独收益数字。

**状态：** 生效（macOS + Chrome 实测；Windows / Safari 未验证）。

## D-063 | 2026-10-22 | 拆分：两块各自有自己的框；页码只拆"贴边"的候选；批量条件收紧

**背景：** R4 的规定是"拆分后两块暂沿用原 bbox"。真书上这等于两个**完全重叠**的框
（第 30 页书眉拆开后，用户还得手动拖一次框）。用户要求：拆开后两块各有自己的框，
单行内按字符比例横向切分；另外要能把"书眉 + 页码"粘在一起的块里的页码拆出去，批量做。

**决策一：按行框估 bbox，单行内用同一个切线值给两边。**
- 切在行边界：前块 = 前 N 行框的并集，后块 = 其余行框的并集。两组行互不相交，
  框也就不重叠（第 30 页实测：前块 y 0.3504–0.3681，后块 y 0.3810–0.6203）。
- 切在一行中间（单行块）：`cut = 行框.x0 + 行框宽 × 已切字符数 / 该行字符数`，
  同一个 `cut` 值同时当前块右边界与后块左边界（都先 round 到 6 位），
  所以两块只在边界上相接，**不产生浮点重叠**。
- 多行块又切在一行中间：一个轴对齐矩形表达不了"上面的行归前、下面的行归后"。
  这时被切开的那一行**整行归文字多的那一边**（比例 > 0.5 归前块，否则归后块），
  另一边的框从相邻行边界开始——宁可少包一行，也不要两个框压在一起（L-41）。
- 两个框都裁剪到原块范围内（行框可能因为拖动略超出块框）。
- 代价：R4 的"位置近似"标记（`origin=split`）只加在新块上；原块保持 `origin=ocr`，
  它的框现在是估算出来的，这一点记在 D-063 与 known-limitations 里，不改数据语义。

**决策二：页码只拆"贴着块首或块尾"的候选。**
`page_number_candidates` 会给出块里**所有**可能是页码的数字。夹在中间的（"第 11 章"、
脚注 `1 这里采用的是…`）两边都有正文，拆了就是把正文切坏，所以一律不动。
书眉的两种排法都覆盖：`11 导读巴赫金`（页码在块首）与 `2谁是巴赫金?11`（块尾）。
页码块类型固定为 `page_number`，另一半保持原类型；原块本来就是 `page_number` 时另一半
退回 `other`（避免"页码块里还有一段书眉"这种自相矛盾的状态）。

**决策三：页码提示从"类型建议"里独立出来。**
块类型建议只返回"建议类型 ≠ 当前类型"的块。用户一旦把书眉采用成 header，
建议就消失了，拆分按钮也跟着消失——这是实测发现的死角。现在 `block-suggestions`
额外返回 `page_numbers:[{block_id, candidates, hint}]`（只读），
覆盖"已经是 header/footer/page_number"与"被建议成这三类"的块，只收贴边候选。

**决策四：批量条件比任务描述收紧一档。**
任务写的条件是"块类型是 header/footer/page_number，或文本里含页码候选"。照字面做，
正文段落里的数字（"1917 年 11 月""北京大学出版社,2007"）会被整本拆掉——实测预览
一开始就命中了 42 页 50 块，其中一半是脚注与参考文献。现在的条件是：

- 已经是 header / footer / page_number：贴边候选即可；
- 其余类型：必须同时落在**页面上下 12% 带**、整块 ≤ 40 字、去掉页码后剩下的部分
  ≤ 30 字且**不含句子标点**（，。；：、,;:！？等）、页码数值 ≤ 全书页数。

在测试库上：267 页里命中 29 页 29 块，全部是书眉 / 页脚；脚注、参考文献、
"第 11 章"一个都没进。批量执行整批共享一个 `batch_id`，**一次撤销**回退 29 页 337 条事件。

**状态：** 生效（macOS + Chrome 实测；Windows / Safari 未验证）。

## D-064 | 2026-10-22 | 一次采用全库高把握建议；识别完成后自动应用（项目级开关）

**背景：** 用户问"有没有办法自动识别页眉页脚？而不是我每一页手动改？目前 OCR 结果似乎全是正文"。
事实是建议**已经算出来了**（`suggest_block_types`），但按既定原则不自动应用，所以看起来全是
`paragraph`。用户要的是"别让我一页页点"，不是"偷偷改"。

**决策一：全库扫描一次算完，不逐页调单页接口。**
`scan_high_suggestions` 用与 `suggest_block_types` **同一套规则**（`_region_of` + `_propose` +
`_with_confidence`，跨页重复统计也一样），但只加载一次全书块、算一次候选与重复计数，
再按页分组。逐页调单页接口是 O(页数 × 全书块数)：267 页要几分钟；一次算完实测
49 页 / 328 块 **27ms**，合成满规模 267 页 / 8010 块 **450ms**（L-44 里有口径）。
预览与执行共用这份计划，`dry_run` 不写库、不进撤销栈。

**决策二：只应用 `high`，标题永远不进批量。**
`high` 只有两种来源：页码形态（纯数字 / 罗马数字）、同一区域跨页重复 ≥ 3 次。
标题建议本来就是 `review`（`looks_like_heading` 只给建议），扫描里再显式挡一道，
即使规则以后变了也不会从这条路漏出去。

**决策三：自动应用放在识别**子进程**的任务收尾，不放 API 轮询。**
只有子进程真正知道"这一页做完了"。放 API 轮询里做，用户关掉页面就不会应用，
那不叫"服务端自动应用"。所以 `_run_ocr_job` 在 `_run_job_loop` 之后读项目设置，
打开时对本任务**成功的页**跑一次 `scan_high_suggestions(page_numbers=本任务页)` 并一次应用
（一个 batch），再写一条 `auto_apply_run`。跨页重复统计仍用全书，否则书眉只出现一两次，
会被判成"需确认"。失败只写一行日志（不写路径 / 文本），不影响任务本身的结算。

**决策四：自动应用的"整批撤销"跨进程，用表 + batch_id 而不是撤销栈。**
撤销栈只活在 API 进程内存里（说明书 5.3），子进程写的事件带 `batch_id`。所以：
迁移 0010 建 `auto_apply_run`（`auto_apply_id` 同时就是 `batch_id`），撤销时按 batch_id
从 `event` 表把那一批读回来，交给 `editing.revert_events` 反过来应用，再把记录标 `undone`。
**安全性：** 只允许撤销**最近一次**、且这一批之后没有别的批次写过事件——用 `event.rowid`
判断，不用 `created_at`（它只有秒精度，同一秒里的手工修改会漏掉，测试就是这么抓到的）。
不满足就返回 400「自动应用之后还有别的修改，先撤销那些」。

**决策五：自动应用只覆盖**本任务**的页，不回头补早先的页。**
一次识别 3 页，第 3 页让前两页的书眉变成"跨页重复 ≥ 3"（high）——但前两页不在本任务里，
不会被自动改。理由是"不要因为一次任务去改用户没碰过的页"；要补的话用户可以用
「全库采用高把握建议」，预览里写清楚影响多少页。

**为什么这不算"静默应用"：**
1. 项目级开关，**默认关**；关着时行为与以前完全一样（只建议）；
2. 打开时界面弹确认，说明只动 high、只动之后完成的任务；
3. 每次自动应用记一条 `auto_apply_run`，顶部有提示条（几页几块、按类型分布），
   右栏有"上次自动应用"状态；
4. 一键撤销整批（见决策四）；
5. 每次都有事件可追溯（`actor=system`，与结构工具一致，不覆盖"人工改过"的块）。

**状态：** 生效（macOS + Chrome 实测；Windows / Safari 未验证）。

## D-065 | 2026-10-22 | 漏行检测与局部重识别；拆分把被切开的行切成两条行记录

**背景：** 用户截图指出"页面中部有一整行文字没有被任何块框住"——这是检测阶段（RapidOCR 的 det）
漏了一行，不是分组问题。唯一的补救是「✚ 框选新增块」，但要用户手打文字。
另外，拆分把被切开那一行的 `block_line.bbox` 清空（R4 旧行为），批量拆 29 页就会多出
29 条"没有坐标的行"，行归属统计与导出的行级信息都缺一块。

**决策一：可疑漏行 = "有墨迹、但没有任何行框覆盖"的横条（只读）。**
用 view 档（150 DPI）渲染、Otsu 二值化；把块内行框与"不是文字"的块画成覆盖掩码；
墨迹减覆盖、逐行求未被认领的墨迹占比（`Image.resize((1,h), BOX)` 在 C 里做，PIL 就够，
不引入 numpy）；连续超阈值的行组成条带。**所有阈值都放在一个文件里**：

| 常量 | 值 | 作用 |
|---|---|---|
| `ROW_INK_RATIO` | 1% 页宽 | 一行里未被覆盖的墨迹至少占这么多才算可疑 |
| `MIN_BAND_HEIGHT` / `MAX_BAND_HEIGHT` | 1.2% / 6% 页高 | 太薄是笔画边缘，太高多半是图 |
| `MIN_BAND_ASPECT` | 3.0（宽/高） | 表格边框、竖排侧栏是"高"的，靠这条挡掉 |
| `LINE_OVERLAP_LIMIT` | 40% | 条带与已有行框的竖直重叠超过它 → 这行其实有框（框画得比字紧） |
| `OUTER_MARGIN` | 3% | 扫描仪边缘、裁切黑边不报 |
| `MAX_PAGE_INK` | 45% | 整页偏暗（背景噪声）不做检测 |
| `MAX_CANDIDATES` | 6 | 多了就不是"漏了一行"，而是这页没识别好 |

排除项还有：插图 / 装饰块盖住的区域、**没有行记录的块**（人工新增 / 拆分产物——
人已经给它建了块，再报就是噪声）、没有行记录的页（还没识别）。
误报会变成噪声，比漏报更烦人，所以所有阈值都是按"宁可少报"调的（实测见任务 49 报告）。

**决策二：框选识别用 300 DPI 整页渲染 + 裁切，只返回文字，不落库。**
`POST /pages/{no}/recognize-region` 用 zoom 档（300 DPI）渲染整页，按 bbox 外扩 2%
（与第二引擎行图同一口径）裁切，交第一引擎识别；行框从**裁图坐标**映射回整页：
`page_x = (left + crop_x * crop_w) / page_width`（y 同理），所以返回的框与用户看到的位置一致。
**不落库是结构性保证，不是自律**：`recognition.recognize_region(source, page_index, bbox)`
拿不到项目目录、也从不打开数据库——它只做"渲染 → 裁切 → 识别 → 坐标映射"。
接口层也不写任何表。结果填进「框选新增块」的输入框，用户改完点「创建这一块」才走现有新增块接口。
代价：每次要渲染整页 300 DPI（实测 0.9–1.3 秒），换的是"不建 Run、不建块、不建行、不写事件"。

**决策三：拆分时把被切开的行切成两条 line 记录。**
旧行为（R4）清空坐标，理由是"这行不再精确对应任何一整行"——但代价是行归属统计与导出
的行级信息缺一块。现在：前块那半改这一行的文字与左半坐标，后块那半**新建**一条行记录拿右半，
两边用**同一个 cut 值**（与块框一致）。分歧信息（`aux_text` / `diff_status`）两边都清空：
第二引擎读的是原来那一整行，两个半边都不再对应它。
块文本被人工改过、与行记录对不上时**不切文字**，退回旧做法（只清坐标与分歧），
免得把行记录改坏。

**决策四：新建的行记录在撤销里是"删掉"，不是"改回空值"。**
`block_line` 没有 `deleted_at`（不像块可以软删除），所以 `revert_events` 对
`create_line` / `delete_line` 两个动作单独处理：撤销新建 = 删掉那一行，重做 = 插回去，
两个方向都幂等。这条只影响拆分产生的行——其他行操作仍然走原来的"改字段"路径。

**状态：** 生效（macOS + Chrome 实测；Windows / Safari 未验证）。

**背景：** 用户提出"大多数书的正文都在版心里，页眉 / 页脚 / 页码都在版心外"，与其逐块分类，

迁移 0011 加 `project.margin_box`、`page.margin_box`、`page.margin_box_mode`
（`inherit` / `custom` / `none`，默认 `inherit`）。四边存 JSON `[x0,y0,x1,y1]`，与 `block.bbox`

四边在 0–1、左 < 右、上 < 下、最短边 ≥ 2% 页宽；接口层把错误转 400。
`custom` 必须给四边；切回 `inherit` / `none` 会清掉页级四边，避免留下一个看不见的旧框。
改项目默认只影响 `inherit` 的页，不碰 `custom` / `none`。**不发事件、不进撤销栈**：
它是一个设置项（与页面类型类似），每次打开项目都会自动备份数据库；不做"撤销版心"这类假功能。

**决策二：推算只读，规则可解释、阈值一处可调。**
`GET /margin-box/suggestion` 读已有的 `block_line`，不写库：

1. 只看正文页（`include=1`）；显式 `header / footer / page_number / figure / decoration` 的块整块跳过

2. 每页剔掉短行（宽度 < max(25% 页宽, 该页行宽中位数的一半)）与页面上下 4% 带里的行

贴着实测边缘画框会被 OCR 抖动切到个别页的字（真书第 30 页左边缘比众数偏左约 1.5%）。
安全边距让框"覆盖正文而不切线"；用户拖动时会吸附到真正的行边界，可以再收紧。
这一条写进建议的 notes，界面可见。

**会失准的版式（如实记录）：** 双栏 / 多栏（左右取的是整页外缘，不是单栏）、竖排、
整页居中的版权页 / 扉页、大量旁批、旋转页。真书《导读巴赫金》53 页有行数据的正文页：
左 9.6%、上 8.7%、右 90.2%、下 91.2%，离散 0.2%–0.4%，覆盖率 33% / 36%，把握"高"。
第 3 页那种密集版权页有两条 x0=6.8% 的行会落在建议框外，需要页级自定义或标"不适用"。

**决策四：版心视图默认关，拖动 = 编辑这一页。**
页面视图右上角「版心」按项目记住（localStorage `b2t.pagesMargin.v1.<project_id>`，默认关）。

2. **字号**：块平均行框高度 < 0.85 × 全书正文行框中位数（行框高度是字号的代理，
   不是精确字号；反例见 L-61）；
3. **开头形态**：圈号 `①–⑳`、`*`、`注：`、`［注`、`译者注` / `译注`，以及**行内**
   的 `——译注`；OCR 把 `①` 读成 `1 ` 时按"1–2 位数字 + 空白"算一个标记；
4. **间距**：与**同一页上一块**（且上一块是 paragraph / heading）的垂直间距
   > 1.5 × 全书块内行距中位数。
- **锚点：位置 + 间距两条还不够。** 真书第 5/6 页的「豆瓣id:坏卡超」「豆瓣id:Igitur」
  正好在版心下沿、与上一块间距 3.2–3.6 倍，会组成"位置 + 间距"两条误报；
  它们没有注释符号、字号也不小。因此要求至少再命中"注释符号"或"行高较小"其中一条。
  这比"任意两条"更保守，符合"宁可少报"；只给 review 也不能拿误报当噪声。
- **字数上限 120**：更长的块按正文处理（第 30 页末段 170+ 字，不会因为"在下沿 + 间距大"
  被建议成脚注）。这是保守的漏报边界，见 L-62。
- 显式 `footnote` / `margin_note` 不再给自己建议；纯数字 / 罗马数字交给边缘条带的
  `page_number`，不被脚注抢走。

**决策三：旁批 = 版心外左右两侧 + 短行 + 不是页码；不覆盖 high 页眉。**
- 有版心时：中心在版心的左 / 右外侧，纵向在版心上下沿之间；没有版心时退回页面左右 10%。
- 短行：≤ 40 字；不是纯数字 / 罗马数字（那些是页码）。
- **优先级**：如果同一块已经被边缘条带判成 **high** 页眉（跨页重复），保留 high 页眉，
  不给旁批建议——竖排书左侧的「红楼梦\n6」是书眉，不是旁批。高把握的**页脚**才允许
  旁批 review 优先（误标一个页脚同样会让文字离开正文）。旁批只覆盖 review 级的
  页眉候选或不进边缘条带的块。真书《红楼梦》40 页里 37 个左侧短行因此保持 header high，
  0 个被误建议成 margin_note。

**实测（两本书，真数据）：**

| 书 | 识别页 | 真注释 | 脚注建议 | 误报 | 漏报 | 备注 |
|---|---|---|---|---|---|---|
| 《导读巴赫金》 | 56 页有块 | 16 条（11 页） | 16 条，全 review | 0 | 0（已核对） | 位置 16/16、注释符号 15/16、间距 11/16、行高 1/16 |
| 《红楼梦》前 40 页 | 40 页 | 0 条（金标准无注文） | 0 条 | 0 | 0 | 37 个左侧书眉保持 header high |

- 第 28 页两条注文（原文未标类型时）：`脚注 · 需确认` ×2；采用后导出与任务 51 一致
  （正文不含注文，`notes.txt` 含两条）。
- 第 30 页正文页：0 条脚注 / 旁批建议；第 3 页版权页：0 条建议。
- `suggest_block_types` 单页 26–33ms（56 页 / 370 块 / 1379 行），
  `scan_high_suggestions` 全书 29ms（导读）/ 18ms（红楼梦）。

**状态：** 生效（macOS + Chrome；Windows / Safari 未验证）。

## D-069 | 2026-10-23 | 版心随识别自动推算，并接进审校视图

**决策：** 用户 2026-10-23 早上提出「版心应随 OCR 自动计算并显示，页面视图与审校视图都要显示」
与「审校默认只审校版心内的内容」。实现分三块：

1. **服务端触发自动推算。** 识别任务**收尾**时（子进程里，`recognition._auto_margin_after_job`）
   整本算一次并把结果写进项目；打开项目时给"升级前就识别过、还没有建议"的老项目补一次。
   一次任务只算一次，不按页算。
2. **写入规则（不覆盖手动值）。** 迁移 0012 给 `project` 加 `margin_box_source` /
   `margin_box_set_at` / `margin_box_suggestion`：
   - 没有全局版心，或当前来源就是 `auto` → 自动写入建议，来源标 `auto`（带时间）；
   - 来源是 `manual` → **只更新建议，不动当前值**；
   - 迁移 0012 之前手动设过（`source` 是 NULL + 版心非空）也按手动对待——否则升级后
     第一次识别就会悄悄改掉用户定好的版心；
   - 用户清空版心（PUT null）后允许下一次识别重新自动填。
3. **审校视图。** 原图上画版心框 + 版心外压暗（只读、无把手）；块列表顶部
   `版心内 N · 版心外 M · 全部 T`，**默认「版心内」**；判定用块**中心点**，与导出的
   版心层同口径。版心外的块在原图上变淡 / 虚线，列表里带「版心外」标记。

**为什么用三列而不是 `settings_json`：** 这三项是项目级实体状态（来源、时间、一份带 schema
的结果），识别子进程要写、API 与界面要读；放进设置会被"未知设置键"校验挡住，也不便查询。

**安全阀一：自动版心不参与导出。** 自动推算会随识别页增加而移动（见下表），而版心在导出里是
"正文 = 版心内"的硬判据；一个没人确认过的框不该决定哪些字进正文。`export_margin_box` 在
页级 `inherit` + 全局 `source=auto` 时返回 None，导出退回块类型判定；用户点
「采用为全局版心」（source 变 `manual`）后导出才按它判定。导出预检会写明"自动版心未确认，
不会使用它"。这样"这一刀不改导出"对所有既有项目成立：真书第 3–9 页在开关关掉时导出，
`body.txt` / `meta.json` 仍是任务 50 的
`49ef6fa19d7156ebeb82040712d4550db3ee686786005ba2e4c78373cfeae4e7` /
`64a39c5a6c9229bdf1bb786b1aa98f5c061cbf307a040641436247a3e53c223f`；
打开"按版心判定"后，`source=auto` 与"没有版心"两次导出逐字节相同。

**安全阀二：自动框"暂时不准"时不按它隐藏块。** 刚识别 2–3 页（尤其前几页是扉页 / 版权页）时，
框可能只框住半页（3 页合成样本实测下沿 49.9%）。此时审校默认显示**全部**块，过滤条写明
"只用了 N 页，可能还不准"，用户点「版心内」才按框过滤。判据：`pages < 10` 或 `reliable=false`。
页面稍多后自动回到"默认只列版心内"。

**安全阀三：隐藏不等于不可操作。** 过滤只决定"渲染哪些卡片"；所有块仍在 `reviewBlocks` 里，
原图上的框照画。切到「全部 / 版心外」后文字编辑、类型下拉、建议采用、框选新增都照常；
点原图上被过滤掉的块、框选新增、撤销聚焦都会自动切到「全部」（`ensureBlockListed`）。

**自动推算会不会随识别页增加反复跳动（真书《导读巴赫金》实测）：**

| 参与页 | 四边（左/上/右/下） | 与上一次最大位移 |
|---|---|---|
| 5 | 5.29 / 7.40 / 89.84 / 92.87% | — |
| 15 | 7.32 / 6.99 / 91.97 / 92.99% | 2.0 百分点 |
| 30 | 7.22 / 6.77 / 91.87 / 93.14% | 0.15 百分点 |
| 50 | 7.63 / 6.66 / 92.17 / 93.25% | 0.11 百分点 |
| 53 | 7.63 / 6.66 / 92.17 / 93.23% | 0.02 百分点 |

早期每加一页最多 12.6 百分点（前几页是封面 / 版权页）；参与页 ≥ 30 后，逐页追加位移 < 0.15
百分点。真任务实测：53 → 56 页下沿 -0.009 百分点；56 → 58 页左边 -0.10、下沿 -0.006 百分点。
界面显示的百分比只到 0.1%，所以用户看到的是"基本不动"。

**影响：** 自动版心只用于显示与审校过滤；导出、组装、识别流程、块类型判定都不读它（除非手动采用）。

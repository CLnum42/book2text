# 产品笔与 test-contract 笔的落地顺序（一页规则）

> 2026-10-30 立。背景：`582e8c7` 撞 R12 形态闸（A1 产品/测试不许同笔；A3 动 tests/js 旧断言须 `test-contract:`）。
> pre-commit 验**索引树**，于是「只提产品 → 新代码+旧期望 红」「只提测试 → 新期望+旧代码 红」，单人会卡死。
> 这条不是分析，是**照做就对的顺序**。

## ① 默认顺序：先测试、后产品（成立条件：期望是下界）

```
第 1 笔  test-contract: 落新期望（代码不动）
         判据：索引里「新期望 + 旧代码」必须绿 —— 只在下界/区间断言时成立（>= 、<= 上界、范围）
第 2 笔  docs/refactor 或产品：改代码
         此时「新期望 + 新代码」绿；旧期望已被第 1 笔替掉，不存在中间红
```

**一句话照做**：**先落测试，再落产品；只有当新期望在旧代码上仍成立（下界/区间）时，这个顺序才合法。**
第 1 笔必须是 `test-contract:` 首行 + `Approved-by` + §18.6 登记（A3 要求）。

## ② 等值断言（`==`）：三选一，**推荐 (a)**

等值断言下第 1 笔必红——旧代码不满足新期望。三条路都要显式，不许“看着办”：

| 方案 | 形态 | 代价 | 判据能否查 |
|---|---|---|---|
| **(a) 三笔：放宽 → 产品 → 收紧**（推荐） | ① `test-contract:` 把 `==新` 临时放宽成 `==旧`（绿；注释 `Temp-Relax: <原因>`）② 产品笔改代码（绿）③ `test-contract:` 收紧回 `==新`（绿） | 多一笔；中间两笔期间**断言是弱的**（真值时第 1 笔通过、第 2 笔靠代码追平） | 能：`grep Temp-Relax` 计数，且只降不升；③ 落地后该注释必须消失 |
| (b) 同笔 + trailer `Shape-Mixed: <理由>` | 一笔里产品+测试，pre-commit 见 trailer 放行 | 一次破 A1；**混笔难以单独回滚** | 能：计数、只降不升；但“理由”可被滥用 |
| (c) DevLead 两次落、第一笔红 | 第一笔允许红 → 必须 `--no-verify` | **破“所有提交都绿”**；绕过进账本（BYPASS/STALE） | 能：账本里看得见，但等于制度化绕过 |

**推荐 (a)**：三笔全绿、全程无绕过、不新增 trailer 语义；代价只是多一笔与一个**可查的短暂弱断言窗口**。
**不推荐 (c)**：它把“绕过”变成流程的一部分——而绕过一旦常态化，账本就没人看。

## ③ 可机检判据（规格，先不实现）

**pre-commit 提示行**（不是拦，先给信号）：

```
当 diff 同时满足：
  a) 改了产品文件（backend/book2text/static/*、backend/**/*.py）
  b) tests/ 里对**被改符号**存在 `==` 等值期望
→ 打印一行：`ℹ 本笔改了 <sym>，tests 里有 == 断言（<file>:<line>）；若期望要变，按 §test-contract-order ①/② 走`
```

**能拦的两条**（做成红，成本低）：

```
· test-contract: 首行提交里出现产品文件路径        → 红（A1 已有，保持）
· Temp-Relax: 出现次数 > 1 且未在上两笔内收紧回    → 红（防放宽常驻）
```

## ③b A1 的第一条例外：新**服务**模块的"落文件 + 登记"（2026-11-02 定）

**为什么需要例外**（三条路都撞红，没有一条能走）：

```
只落模块            ⇒ 「登记完整性」闸红（挂了 window.X = api 的文件必须登记）
先加登记            ⇒ 闸的循环会 readFileSync 一个还不存在的文件 ⇒ 抛错红
合成一笔            ⇒ A1 红（普通提交不许同时碰产品与 tests/js）
move: 笔            ⇒ 改动必须落 OWNERS / VIEW_STATE_PREFIXES / VIEW_EXPORTS / KNIVES 四张表，
                        DOMAIN_MODULES 不在这四张里 ⇒ 用不上
```

**规则（按"范围"开口子，不按提交类型）**：

```
当索引里**新增了** `backend/book2text/static/*.js`，且该文件暴露 `window.<X> = api` 时，
允许同一笔修改 tests/js —— 但改动范围**只许落在三张登记表的数组字面量内**：

  DOMAIN_MODULES · NON_DOMAIN_MODULES · ALLOW_QUERY_SELECTOR_WHITELIST

越出这三处任何一行（改断言、改 import、改别的测试、改这三张表以外的常量）⇒ 红。
同一笔里**删除或改写**已有登记行也 ⇒ 红（那是另一件事，走 `test-contract:`）。
```

**为什么按范围而不是按提交类型**：判据盯的是**改了什么**（`git diff --cached` 落在哪个文件、哪一段，纯机械判断），
不是**这笔叫什么**（`-m` 的内容在 pre-commit 里拿得别扭，且可被随意书写）。
新增 `move(module):` 类型是更硬的方案，但它依赖提交信息解析——本仓库已经吃过"提交信息说了、代码没做"的亏。

**机检规格（交 TestDev，4 条）**：

```
① 本笔索引 diff 里有 ≥1 个**新增**（A 状态）的 static/*.js，且其中至少一个含 `window.<X> = api`
② tests/js 侧的改动行，逐行必须落在上述三个数组的**声明区间**内
   （区间 = 数组起止方括号配对算出来的行范围，**不写死行号**；数组改名/挪位置时按名字重新定位）
③ 不满足 ① 或 ② 的任一条 ⇒ 例外不生效，按 A1 普通规则判红
④ 例外只放行**新增行**（`+` 且不以 `-` 配对改写同一行语义）；删除/改写已有行 ⇒ 红
```

**实现口径（TestDev `e8bf700`，main `1cf44d0`；下面两句是可机检的措辞，照抄进实现注释）**：

```
① 登记表块的行范围**从源码派生**；例外只要求「新模块名在这三张表的数组字面量之内」，
   **不校验表里有多少项**——表里多一项少一项是别的闸的事，别让这个例外跟着表长漂。
② 这个口子只放行"**新增** window.X = api 模块"；**放行不了**"改已登记模块的文件名 / 接口名"——
   那种改动仍会红（因为没有新增模块，例外不成立）。
   若将来出现"重命名已登记模块"，**要另开一条规则**，别指望这条能覆盖。
```

**实战限制（首刀就撞到，`a064aee`）：目标数组是单行时必须先落一笔纯格式笔**

```
A1 例外要求"产品笔只含新增行"（④）。但 ALLOW_QUERY_SELECTOR_WHITELIST 原本是一行数组：
  往它上面加第三个模块，必然要"删掉旧的那一行 + 写一行新的" ⇒ 被 ④ 判成改写已有行 ⇒ 红。
解法（已实践）：先单独落一笔 test-contract，只把那一行数组改成多行（一个名字一行，**内容不变**、
  断言不变、逻辑不变），单独过闸；产品笔再"新增一行"，就只含新增行了。
实例：`a064aee`（单行改多行）→ 之后的模块引入笔只加一行。
⇒ **判据**：凡是"要往单行字面量里加一项"的模块引入，先做格式笔；别在同一笔里既改格式又加内容。
```

**本口子明确不管什么（写下来，防止它被当万能钥匙）**：

```
· 重命名已登记模块（无新增文件 ⇒ 例外不成立 ⇒ 红）
· 改已登记模块的导出名 / 接口面（同上）
· 往三张表以外的地方加东西（改断言、改 import、加别的测试文件）⇒ 越界红
· 既有模块的"顺手清理"（删登记行 / 合并两条登记）⇒ 红，走 test-contract:
· 任何"提交信息自称是模块引入"但不满足 ① 的情况 ⇒ 不看信息，只看索引 diff
```

**给施工方的硬规定（写进书，别靠记）**：

> **新模块引入笔 = 产品文件 + 三张表里的新增行，其他一律不许动。**
> 要改断言 / 加测试 / 改别的常量，另开 `test-contract:` 笔。

## ③c A1 的第二条例外：新**视图**模块（2026-11-06 定）

**事实**：新建视图模块（如 `preview-view.js`）时 A1 报 **77 处**「越出登记表块」——③b 只建模了
「新**服务**模块 + 三张服务登记表」，而视图模块要改的是另外几张表。拆笔也关不上：
先登记后产品 ⇒ R8 红；先产品 ⇒ R8 红；合成一笔 ⇒ A1 红。⇒ 只能补例外（bypass 只跳 pre-commit，R12 下次照样红）。

**规则（同样是"按范围"开口子）**：

```
触发  同一笔**新增** `backend/book2text/static/*-view.js`（视图模块）且暴露 `window.<X> = api`
允许  同笔只许改这几处：
        OWNERS · VIEW_STATE_PREFIXES · VIEW_EXPORTS · SECTION_OWNERS（**新增段**）·
        EXPORT_IDS · idRefsIn 的 helper 名
禁止  改断言体 / 改 assert 行 / 放宽 STABLE · TEMPORARY · 白名单 / 动任何 MAX 类旋钮
      删除或改写已有登记行也 ⇒ 红（那是搬家笔，见下面 ①）
自检  绿：新视图模块 + 只改上述表；红：同一笔再改一句 assert
```

**两条边界（写进闸的注释，别只写在这里）**：

```
① 不覆盖「改已有视图模块的登记表」——那是搬家笔，走既有 test-contract 顺序（③ 的三笔或 §① 的下界顺序）。
② 到期检查：某笔自称"新视图模块"但**没有新增 static 文件** ⇒ 红。
   防的是把例外当万能钥匙：自称随文案走，判据只看索引里有没有 A 状态的新文件。
```

**为什么和 ③b 分开写**：两条例外放行的**表不同**（服务模块三张 / 视图模块六处），合并成一条会让人
以为"新模块一律可以改任意登记表"——那正好是这条例外想防的事。

## ④ 边界

- 本规则只管**顺序与形态**，不改任何判据的严格性；
- `test-contract:` 仍然不许削弱断言（A1b 删除行 0 不变）；
- 任何时候都**不许**把 `--no-verify` 当常规路径；唯一例外是 ②(c)，且必须先被批准。

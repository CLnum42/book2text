# 产品笔与 test-contract 笔的落地顺序（一页规则）

> 2026-10-30 立。背景：`582e8c7` 撞 R12 形态闸（A1 产品/测试不许同笔；A3 动 tests/js 旧断言须 `test-contract:`）。
> pre-commit 验**索引树**，于是「只提产品 → 新代码+旧期望 红」「只提测试 → 新期望+旧代码 红」，单人会卡死。
> 这条不是分析，是**照做就对的顺序**。

## ① 默认顺序：先测试、后产品（成立条件：期望是下界）

```
第 1 笔  test-contract: 落新期望（代码不动）
         判据：索引里「新期望 + 旧代码」必须绿 —— 只在下界/区间断言时成立（>= 、<= 上界、范围）
第 2 笔  docs/refactor 或产品：改代码
         此时「新期望 + 新代码」绿；旧期望已被第 1 笔替掉，不存在中间红
```

**一句话照做**：**先落测试，再落产品；只有当新期望在旧代码上仍成立（下界/区间）时，这个顺序才合法。**
第 1 笔必须是 `test-contract:` 首行 + `Approved-by` + §18.6 登记（A3 要求）。

## ② 等值断言（`==`）：三选一，**推荐 (a)**

等值断言下第 1 笔必红——旧代码不满足新期望。三条路都要显式，不许“看着办”：

| 方案 | 形态 | 代价 | 判据能否查 |
|---|---|---|---|
| **(a) 三笔：放宽 → 产品 → 收紧**（推荐） | ① `test-contract:` 把 `==新` 临时放宽成 `==旧`（绿；注释 `Temp-Relax: <原因>`）② 产品笔改代码（绿）③ `test-contract:` 收紧回 `==新`（绿） | 多一笔；中间两笔期间**断言是弱的**（真值时第 1 笔通过、第 2 笔靠代码追平） | 能：`grep Temp-Relax` 计数，且只降不升；③ 落地后该注释必须消失 |
| (b) 同笔 + trailer `Shape-Mixed: <理由>` | 一笔里产品+测试，pre-commit 见 trailer 放行 | 一次破 A1；**混笔难以单独回滚** | 能：计数、只降不升；但“理由”可被滥用 |
| (c) DevLead 两次落、第一笔红 | 第一笔允许红 → 必须 `--no-verify` | **破“所有提交都绿”**；绕过进账本（BYPASS/STALE） | 能：账本里看得见，但等于制度化绕过 |

**推荐 (a)**：三笔全绿、全程无绕过、不新增 trailer 语义；代价只是多一笔与一个**可查的短暂弱断言窗口**。
**不推荐 (c)**：它把“绕过”变成流程的一部分——而绕过一旦常态化，账本就没人看。

## ③ 可机检判据（规格，先不实现）

**pre-commit 提示行**（不是拦，先给信号）：

```
当 diff 同时满足：
  a) 改了产品文件（backend/book2text/static/*、backend/**/*.py）
  b) tests/ 里对**被改符号**存在 `==` 等值期望
→ 打印一行：`ℹ 本笔改了 <sym>，tests 里有 == 断言（<file>:<line>）；若期望要变，按 §test-contract-order ①/② 走`
```

**能拦的两条**（做成红，成本低）：

```
· test-contract: 首行提交里出现产品文件路径        → 红（A1 已有，保持）
· Temp-Relax: 出现次数 > 1 且未在上两笔内收紧回    → 红（防放宽常驻）
```

## ④ 边界

- 本规则只管**顺序与形态**，不改任何判据的严格性；
- `test-contract:` 仍然不许削弱断言（A1b 删除行 0 不变）；
- 任何时候都**不许**把 `--no-verify` 当常规路径；唯一例外是 ②(c)，且必须先被批准。

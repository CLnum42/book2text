# app.js 域划分：排优先级用（不是施工图）

> **状态：意见，等 Chief 批。** 作者 Architect，2026-11-01。量数树 `main@20049f9`（app.js **12,755** 行 / **505** 个顶层函数 / **254** 份顶层 `let`/`var`）。
> **本文只排优先级**，不写每域的施工图——那会在真正开工时全过期（`export-ratchet.md` §五 已经栽过一次）。

## 0. 口径（先写明，免得下一轮又出现三个数）

```
域      = app.js 里 `// ---------------------------------------------------------------- 名字` 分出来的 64 段，
          按语义归成 15 个域（归属关系见 §1 表，脚本可复算：段界 + 函数起止 + 引用三栏）
行数    = 该域各段 span 之和（含注释与空行，因为它决定"app.js 还能剩多少"）
函数    = 段内顶层 function 声明数
对外入口 = 该域的函数里，**被 *-view.js 经 injected.<名> 调用的**条数（按函数名，不按调用点）
外来状态 = 该域函数体内引用、但**声明在域外**的顶层 let/var 个数  ← 这条是"上帝对象"判据的核心
自己状态 = 声明在域内、被域内引用的顶层 let/var 个数
el(     = 域内 document.getElementById 的调用次数（DOM 归属面）
写盘    = apiJson( / fetch( 次数
```

合计校验：12,727 + 28 行尾部 = 12,755；505 个顶层函数；与 `export-ratchet.md` §五 的行数账一致。

## 1. 表（按"拆完还是不是上帝对象"排序，不是按行数）

**判据**（可判定，别改成感觉）：一个域搬成模块后，它要从注入面拿多少个**别人的状态**。

```
外来状态 ≤ 3      → 服务模块（搬完就是窄接口，风险最低）
外来状态 4–10     → 有边界的模块（可搬，但注入表要逐条写清）
外来状态 11–20    → 领域模块（可搬，搬之前先问"它读的那 15 个状态是不是本来就该跟它一起走"）
外来状态 > 20     → **换皮的上帝对象**：整体搬只是把 God object 换个文件名，必须先切碎
（自己状态 > 50 → 内部状态极多，搬的时候状态必须整块跟着走，否则会变成"两个口径"）
```

## 2. 我建议的顺序（只给顺序与理由，不给施工图）

```
第一批（低风险热身，一周内可连做两三个）：结构工具 · 质量统计 · 页面确认 · 目录确认 · 任务抽屉
  理由：外来状态 ≤ 4、自己状态 ≤ 6、写盘 ≤ 2。搬完 app.js 少 ~540 行，
        并且能第一次验证"域模块"的**注入表形态**（每条注入 = 一个访问器 + 一个动作），成本低、纠错便宜。

第二批（有边界、有写盘）：导出 · 协作 · 跨视图服务（全库采用建议）· 第二引擎
  理由：外来状态 1–3，但写盘 6–13 处 ⇒ 接口必须按**动作**命名（不能给 setter），
        这批真正练的是"能力键 vs 状态访问器"的区分，那是后面两批的前提。

第三批（大块）：页面侧剩余（2,214 行）与 审校侧（5,546 行）
  理由：外来状态 13–15 已经进入"领域模块"档，且 45 / 17 个入口。
        这两块**必须按子域切**（页面侧至少三份：网格/选择 · 页码 · 版心；审校侧由 ① 的边界决定）。

不做：外壳基础设施（47 个外来状态）
  它不是一个域，是"所有域的公共依赖 + 所有域的回调"。正确动作是**把它拆成服务**
  （通信 / 确认框 / 应用信息 / 工作流状态各一个），而不是搬走。
```

## 3. 三条先说清的风险（真开工时最贵的三个）

```
① "外来状态 47"这个数不是统计噪声：外壳段的函数在读别人 47 个状态。
   把它整体搬走只会得到 `shell-view.js`——名字变了，耦合一条没少。
   所以第 15 行不能"搬"，只能**切**：每次切出去一个服务（通信 / 确认框 / 应用信息），
   切完再看外来状态降不降；降不下来说明切的不是服务，是"又一个外壳"。

② 写盘 ≠ 难，**写盘之后的读回**才难。
   9.3 的教训（`knife-numbering.md` §七）：调用位不许挂在无关请求之后。
   凡是写盘 6 处以上的域（导出 / 协作 / 项目库 / 页面侧 / 审校侧），接口要按"做完什么"命名，
   让读回与重画在模块内部连起来，外壳不参与"先 fetch 再通知"的顺序编排。

③ 45 个对外入口的域（页面侧）不能按"函数"搬，要按**资源**搬。
   §21 / §23 判据：唯一资源 + 唯一生命周期 + 唯一失效语义。
   页面侧的候选资源只有四个：网格 DOM · 页面选择集 · 页码数据 · 版心数据。
   搬一个资源，它周围的函数跟着走；按函数名切就会得到四个"内容相似的小上帝"。
```

## 4. 这张表不该被当成什么

```
不是施工图：每个域的入口清单、注入表、行数预算，开工那一刀现量（这里写死就会过期）。
不是排期：顺序是我给的**风险顺序**，什么时候做、谁做、做几刀，归 DevLead。
不是判据：它是"先切哪个"的输入；真正的判据是 §1 那个外来状态分档，以及拆完之后的注入表条数。
```

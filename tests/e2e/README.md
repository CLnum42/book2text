# Book2Text 前端↔后端一致性验收（QA 脚手架）

这套东西只解决一件事：**让"我测过了"变成"这条命令跑出来是这样"**。

它来自三次真实误判，每条纪律都对着一次事故：

| 事故 | 当时怎么错的 | 现在怎么防 |
|---|---|---|
| 测到半加载状态 | 页面没加载完就数标记，报"主界面坏了" | 所有等待都是 `waitForFunction` 等**可观测状态**，没有一处 `sleep` |
| 用被自己污染的副本 | 脚本往行尾追加字符，下一轮报"历史数据不一致" | 每次 `up` 都从源项目**重新复制**一份临时库；`prepare` 还会清掉浏览器里的草稿 |
| 测的窗口和用户不一样 | 940px 下说"85% 缩放清楚"，用户 1423px 下是糊的 | 浏览器视口固定 **1423×900 CSS px、dpr 2**，与用户机器一致 |

## 一条命令起 / 一条命令拆

在仓库根目录：

```bash
.venv/bin/python tests/e2e/qa.py up --project b2t_ZAQHGH   # 复制项目库 + 起独立服务（18765 起）
.venv/bin/python tests/e2e/qa.py prepare                   # 开浏览器（1423×900@2）→ 打开项目（此时已可截图）
.venv/bin/python tests/e2e/qa.py smoke                     # 七步冒烟（含两条底线）
.venv/bin/python tests/e2e/qa.py check                     # 三组一致性断言
.venv/bin/python tests/e2e/qa.py images --selftest         # 只量页图清晰度 + 低清负向自检
.venv/bin/python tests/e2e/qa.py down                      # 关服务 + 删临时库
```

`up` 会打印：项目副本路径、服务地址、**带令牌的界面地址**、日志路径。
所有证据落在 `$TMPDIR/b2t-qa/<run>/`：`report-smoke.json` / `report-check.json` /
`server.log` / `screenshots/*.png`。

### 收尾必须关掉 ego-browser 的 space（否则会泄漏）

`down` 会调 `await task.finish({ keep: [] })` 关掉本轮 space，输出里的
`space_finished` 就是结果。**不要跳过 `down`，也不要手工杀进程了事**——
space 不关会一直占着浏览器上下文，累积到上限后以"莫名其妙起不来"的形式爆发。

`up` 之前会先列出属于 agent 的 `b2t-qa-*` space；**发现有遗留就直接报错并打印 id**，
不会静默继续。这时先 `qa.py down`（或按 id 手工关）再 `up`。

手工核查残留（在 tests/e2e 目录下）：

```bash
python -c "import _env, pathlib; print(_env._list_spaces(pathlib.Path('/tmp')))"
```

## 结构

```
tests/e2e/
  qa.py                   # 唯一的 CLI：up/down/prepare/step/reading/smoke/check
  _env.py                 # 复制库（sqlite backup，不 cp 活动库）+ 起停服务
  _api.py                 # HTTP API 客户端 + 只读 Store（核对"库里真的变了"）
  _browser.py             # 把一条命令交给 ego-browser，收回 JSON
  browser/driver.mjs      # 浏览器侧：真实鼠标、视口、等待条件、抽取 DOM
```

依赖：本机装了 **ego-browser**（团队统一的 Chromium 驱动，支持 `page.cdp`）。
它负责真实鼠标事件（CDP `Input.dispatchMouseEvent`）与视口覆盖。

## 七步冒烟（`smoke`）

| 步骤 | 核心断言 |
|---|---|
| 0 打开项目 | 视口 1423×900@2；步骤条 6 步；页数 662（API） |
| 1 页面确认 | 页面摘要里的页数 = API；纳入集合 = 662 |
| 2 文字识别 | 主引擎 662/662 + `active_run` 662 页；步骤条数字 = API |
| 3 版心确认 | 有文字的页都有版心框（`margin_box` = 662 − 无文字页）；步骤条 662/662 |
| 4 目录确认 | 界面"1 页有印刷页码 / 661 页未识别" = finish-summary；无可信页码时步骤条写「可跳过」；**页图三条底线（适合宽度 + 85% 两屏）** |
| 5 正文审校 | 左树头「队列 N 处」= 各行「N 处」之和 = API `total_items`；顶栏分母 = API `chars_total`；阅读流文本自检 0 失败；**页图清晰度 ≥ 1.0（第 1 屏 + 中间一屏）** |
| 6 导出 | 导出覆盖 662 页；预览段数 = 预检段数；点「导出」真的落盘（`body.txt` / `meta.json` / `manifest.json`） |

## 五条不能破的底线

1. **显示 = 导出**：右栏看到的字，必须逐字等于导出器写出的字。
2. **页图分辨率**：`比例 = img.naturalWidth ÷ (img 的 CSS 宽 × devicePixelRatio) ≥ 1.0`。
   小于 1 就是低清图被放大显示。
3. **页图没被模糊**：对每个可见页图，
   - `getComputedStyle(img).filter === "none"` —— 不是 none 就是被 CSS 模糊；
   - `img.classList.contains("is-placeholder") === false` —— 不能还挂着占位类。

4. **左右页同步**：顶部页码必须等于左栏当前可见页（tile 的 `data-page`）。
5. **三方同步**：**当前差异项所在页**（候选面板头 `第 N 页`）== **顶部页码** == **左栏可见页**。
   只看第 4 条会漏掉真正错的那一类：用户报"左右不对应"时，面板是第 13 页、
   顶部和左栏都是第 28 页——两个都对、第三个错，两方断言照样绿。

> **教训：比对了两个数不等于比对了正确的两个数。** 用户报"左右不对应"时，
> 真正错的是第三个量（当前审校项），而我们比的两个量恰好一致——**断言绿着，用户看到的却是错的。**

第 2、3 条必须一起看：**高清图 + 残留 `is-placeholder`（blur 1.5px）时，比例仍是 1.66，
只看分辨率会 PASS**——用户提了四次"页图糊"就是这一类（用户 2026-10-28 定位到的根因）。
页图判据同时记录 `size=`（请求档位）、`naturalWidth`、CSS 宽、dpr、filter、占位类——
失败时一眼能分出是"请求了低档"、"占位图没替换"，还是"分辨率够但被模糊"。

## 三组一致性断言（`check`）

1. **显示 = 导出**：阅读流里每个已渲染段落，逐字对比 `/export/preview` 的段文本
   （用**阅读视图自己发出的选项**取预览，避免把"选项差异"误报成 bug）。
2. **提交 → 库**：UI 上真实鼠标点行、键盘改 2 处 → 点「提交 N 处」→ 查库：
   块文本变了、含新输入的行、`revision` 递增。
3. **撤销 → 字节**：点「撤回上次提交」→ 相关块的内容指纹（id + text + ocr_text +
   review_status + include + continues_to_next，不含时间戳）必须回到提交前。

## 规矩

- **修复类提交必须附「带 bug SHA vs 修复 SHA」对照**。同环境、同输入，两次只差那个改动。
  没有对照的"修好了"只能算"现在不红了"——只有对照才能证明"红的那个东西确实是这个原因"。
  模板：`artifacts/page-gate-check/COMPARE.md` + 两份 `report-smoke.json` / log。
- **smoke 的 PASS/FAIL 里包含「控制台错误 0 条」**，报告里单列一行，不许藏在 BLOCK 原因里。
  "删错声明"这类运行时错误不会红在任何断言上，只会让某一步 BLOCK 成"等待超时"；
  控制台错误（`ReferenceError` 等）是唯一能看出根因的地方（`prepare()` 已挂收集器）。
- **smoke 报数把 K1 / K2 单列**，别混进分子：
  `smoke 42/44（K1 1 条、K2 1 条单列；其余 42 条：42 过 / 0 失败）`。
  否则 42 和 43 的差别会一直被当成噪声解释。K1 = 左栏滚到 120 页（页码语义冲突），
  K2 = 窗口尺寸变化后高亮丢失（已知偶发，同一根因，不按回归处理）。
- **判据要断言行为，不要断言实现形态**：不要用 `typeof someFn === "function"` 去"确认能力还在"——
  函数搬进模块/改了作用域，探测就恒 false，而且有守卫时它连红都不会红。
  要断言"行框取到了"就断言 `plan.bbox` 非空 / DOM 元素真的出现。
- **注释里的意图不算覆盖**：`// 用 X 判断 Y` 而代码里没有实现，比死代码更危险——
  它让人**以为有覆盖**。加判据时要么真写进去，要么把注释一起写清楚是"待办"。
- **"通过"必须附命令和输出**。任何一次改动后的结论，至少要有：
  `qa.py smoke` / `qa.py check` 的完整输出或 `report-*.json` 路径。
- **不许用合成事件当用户操作**：点击一律 `page.click` / `page.mouse.click`。
  块图层 `pointer-events: none` 时合成事件能触发、真鼠标不能，这条已经被骗过一次。
- **不许 `sleep` 当等待**：等的是"marks 加载完 / 元素出现 / 某请求返回 / 进度停止"，
  不是"等 6 秒"。
- **测量的对象必须先确认是那个对象。** 量"中间一屏"之前，先断言页号在中段；
  否则异步重开把你拽回顶部，你会量到第一屏还全绿（2026-10-28 真实发生过一次：
  p1/p2 全 PASS，差点当成"中间也没问题"）。
- **凡是"滚到某处再测"的场景，都带一条位置断言**（第几页 / 第几段），并二次确认位置站住；
  页面是异步重画的，任何测量前都得先确认自己站在哪儿。
- **产品问题不改代码**：失败项写进报告（最小复现、期望 vs 实际、影响范围），交 Chief 派给开发。

## 测试自己造成的假结论（比产品 bug 更值得记）

这套脚手架跑到现在，抓出的"测试假结论"比产品 bug 还多。它们共同的特征是：
**以为在验 X，其实没验到 X。**

| 假结论 | 当时怎么错的 | 现在的默认规则 |
|---|---|---|
| "主界面坏了" | 页面没加载完就数标记（其实等 6 秒有 69 个） | 等一个**可观测状态**（`waitForFunction`），不 sleep、不猜时间 |
| "历史数据不一致" | 上一轮脚本往行尾追加过字符，复用了被污染的副本 | 每次 `up` 从源**重新复制**；`prepare` 清本机草稿；测前先确认队列/数据量 |
| "中间一屏也没问题" | 阅读流异步重开把页列拽回顶部，量到的其实是第一屏（p1/p2 全绿） | **测量的对象必须先确认是那个对象**：滚完二次确认位置，并断言页码落在中段（`min_page`） |
| "左右不同步"的断言一直是绿的 | 只比"顶部 == 左栏"，而真正错的是第三个量（当前差异项） | 三方断言；并且用**覆盖视口面积最大的 tile** 当"可见页"，不用固定 25% 锚点 |
| "候选面板没开 = 队列跑完了" | 开发副本队列快空，20 次里 8 次没面板被归因成"空了" | 测前先量队列长度（`pending_items`）；数据能推翻解释时，以数据为准 |

**给下一个项目的默认规则：**

1. 所有等待都是"等状态"，没有 sleep。
2. 每次从干净源起环境；测前重置客户端状态、确认数据量。
3. 判据用客观量（实际像素、覆盖面积、字节），不用容易失效的固定比例/固定锚点。
4. 凡是"滚到某处再测"，都带位置断言并二次确认位置站住。
5. **"点了之后应该出现某个东西"的操作，等 500ms 再断言一次它还在**——等一次只能证明
   "出现过"，等两次才能证明"没被异步重绘收掉"（这条已经被 `dc02100` 之前的面板竞态验证过）。
6. **看到症状先看数据，别先改逻辑。** 排查"下一处未审返回 none"时，先看
   `__b2tNextLog` 的 `globalUnacked` / `pagesWithCounts` / `sample`：服务端说还有 567、
   本地每页计数也在、样本页 unacked>0，那就不是数据问题，别再去动搜索函数。
7. 报"通过"必须附命令与输出；测试自己的结论也要能被测试推翻。

## 已知边界

- 只在本机 macOS + ego-browser 上跑；Windows/Linux 未验证。
- `up` 复制的是**项目库快照**；源项目在测试期间被别的进程写入时，快照仍是复制那一刻。
- 662 页的项目打开阅读流需要几秒；等待上限按 3 分钟设，不是"卡住"。
- 「中间一屏」会校验实际页码（必须落在中段），防止阅读流异步重开把页列拽回第 1 页
  造成假通过；滚完要再确认一次位置，站不住会重试。

### 抓到的真 bug（已修复）：空区间差异标记被渲染成一个空格

- **样本**：`b2t_ZAQHGH` 第 1 页，块 `01M609YSCTY9T6D986R8XMC3ZS` 第 1 行，
  `current=":pp"`、`candidate="ddc:"`（差异是"插入"，base 侧区间为空）。
- **实际**：右栏显示 `lcc: :pp`；导出段文本是 `lcc::pp`。
  根因在 `static/app.js` 的 `buildReadingLine`：
  `markEl.textContent = baseText.slice(range.start, range.end) || " "` ——
  空区间用一个空格占位，这个空格进了 `textContent`。
- **规模**：全书 866 条差异标记中，有 **1022 个**这样的空区间（`qa.py` 的 `audit` 命令，
  用应用自己的 `computeCharSpans` 算的）——即最多 1022 处会多显示一个空格。
- **影响**：只影响"看"，不影响导出；但它违反"审的字 = 导出的字"，
  用户会以为原文多一个空格，甚至去"修"一个导出里不存在的问题。
- **期望**：占位不进入文本（如空 `<span>` + `aria-hidden`，或伪元素），
  `textContent` 必须与 `segment.text` 逐字相同。
- 打开 `?checktext=1` 时应用自带的 `[文本自检]` 也会报这一处（`__b2tTextCheckFails=1`）。
- **已修复**：`257c5b5`（占位不进 textContent）+ `f57ec23`（行与行连续切片）；
  修复后 `qa.py check` 的 A 项从 FAIL 变 PASS（32 个已渲染段落逐字相同）。

### 必须按「语义序列」跑，不能按固定点击序列

每轮只做一件事：**面板开着就判，没开才点「下一处未审」**，直到队列判满。

理由（有实测）：改前「判完关面板」，改后「判决即前进、面板自动换下一条」。
固定写成"每轮点一次下一处再点一次判决"，两种行为会被刷出不同的假数：

| 跑法 | 墙钟 | 单条 | panel/judge |
|---|---|---|---|
| 旧探针（每轮点下一处 + 8s 超时） | 341s | 2,906ms | 1.32 |
| 旧探针（无 observer） | 285s | 2,633ms | 1.248 |
| 旧探针（无 observer + 预热） | 98s | 928ms | 1.165 |
| **语义序列（改前）** | 215s | 1,997ms | **1.000** |
| **语义序列（改后）** | 114s | 1,068ms | **1.028** |

同一份改前代码，墙钟能差 3.5 倍——**固定点击序列量的是探针自己，不是产品**。
`panel/judge` 也一样：旧探针在"队列空了、面板还开着"时照点，把 panel 埋点刷高，
于是 1.32 那个"每判一条要开 1.32 次面板"其实是空转。**按真实序列，改前就是 1.000。**

### 验收线（Chief 2026-10-29 定）

```
① 每条用户动作数 ≤1.05     （改前 2.0 / 改后 1.0，来源是"每条少一次点击"）
② 单条受控耗时             （改前 1,997ms / 改后 1,068ms）
③ 面板消失次数             （只证明本轮没撞上，不证明 L-107 修好）
```

`panel/judge` 仍会打印，但**只作参考**：改前按真实序列就是 1.000，它不区分改前改后。

### `stalls` 别用（死因留档）

`step-timing` 的 `stalls` **恒等于动作数**：`bump()` 先 `timingProgress()` 更新进度键、
再 `armStall()`，判定基准已经是"动作之后"的键，500ms 后当然没变。
实测 253 次动作 → 252 次 stall（1:1）。

**它不能当"卡住次数"读。** Chief 2026-10-29 批准删除，需要在
`docs/known-limitations.md` 写一行"原 stall 口径恒等于动作数（253 动作→252 stall），
已删，勿复现"——删掉的指标也要留死因，否则半年后有人重新发明它。

## 常规检查项：入口上写的数 == 点下去真正发生的范围（2026-10-30 定）

**任何显示计数的入口，括号里 / 按钮上的数，必须和"点下去真的会处理多少"对上。**
判法不是看文案好不好看，而是取两个数比：

```
1) 读入口文本里的数 N（例：检测版面…（362 页还没有版心））
2) 读真发出去的请求范围（GET 的查询参数 / POST body 的 pages 长度、scope）
3) N 必须等于范围；有选择时 N 是所选范围内的数，没选择时才是全书数
```

已两次踩同一个坑，都不是"文案错字"，而是**两个变量各算各的**：

```
· 393 / 394：底部旧按钮 pendingAll 只数 unrecognized，主按钮把 failed 也算 → 差的是第 102 页
· 检测版面：选中 1 页时入口仍写全书 362 页，对话框才说 1 页（已派 Builder 改成听选择）
```

配套看两处容易漏的：① 数字为 0 附近的**取整**（0.39 秒 → 「约 0 秒」，应说「不到 1 秒」）；
② 同一条动作的**多个入口**（主按钮 / 底部条 / ⋯ 菜单）可能各用一个计数函数，改一处忘一处。

## 报告写法：既有行为 / 本次新风险，分两段写（2026-10-30 定）

同一个现象在两段里含义完全不同，混着写将来分不清「回归」还是「老账」。每次在大改动上读数时按这两段给：

```
① 既有行为（改前就这样，附带能复现它的输入）
② 本次改动引入的新风险（新代码路径上才可能发生的事）
```

实例（zoom2 / 350 DPI 档）：

```
① 既有行为：超大页在 300 dpi 就已超 MAX_RENDER_PIXELS → 400 + 「页面渲染尺寸过大（约 44 百万像素，上限 40 百万）」
   夹具 tests/e2e/fixtures/huge-page-1600pt.pdf（1600×1600 pt = 2.56e6 pt²，300dpi 44.4MP / 350dpi 60.5MP）
② 新风险：这类页能不能走到 350 档、走不到时界面说什么（空白图 / 永久转圈都算没交代）
```

判据里还落了两条通用做法：

```
· 判断内容格式看**字节头**（PNG 魔数 89 50 4E 47），不看 content-type——头写 image/jpeg 内容却是 PNG，
  只有魔数抓得到（ENCODE_FORMAT 缺键时会静默走 PNG）
· 错误路径能用一个更低的档先验，就别等新档：300 dpi 的超大页今天就能验「人话错误」
```

## 读数有效性：比「树 sha」更准的判据（2026-10-30 定）

tip 变了不等于读数作废。**判据是前端产物有没有变**：

```bash
git diff --stat <旧 tip> <新 tip> -- backend/book2text/static   # 空 → 已有读数有效，不用重跑
```

依据：`39edaf2 → b37ee7a` 这次只多了一笔测试提交（树 sha 变了），
但 `backend/book2text/static` 一个字节没变，所以 zoom2 在 `39edaf2` 上的读数直接归到 `b37ee7a`。
比整棵树 sha 准——否则每加一笔测试提交都要判一次「要不要重跑」。

## 测试断言别锁字面量（2026-10-30，一次真被挡住）

`tests/integration/test_ui_assets.py:106` 曾经断言字面量 `'image: "zoom"'`。
